## 0. 阅读说明

| 术语 | 含义 |
|---|---|
| 内核服务 | `finx serve --listen unix://` 进程：常驻，承载全部会话，多个客户端共用（protocol-design §8.2） |
| 内置内核 | 打包在 FinxWork.app 里的 `finx` 二进制，与应用同一次构建、同一个版本 |
| 守护器 | 主进程里负责内核服务的模块（`main/kernel/`）：发现、拉起、握手、重连、升级替换 |
| 控制连接 | 守护器自己与内核服务之间的一条连接，用来握手、观察服务状态、请求退出。它不转发页面的消息 |
| 页面连接 | 每个窗口一条：页面 ⇄ MessagePort ⇄ 主进程 ⇄ socket。主进程只转发字节（DD-03） |
| 服务记录 | 内核服务写在单实例锁文件里的一行 JSON：进程号、版本、协议版本、可执行文件、启动时间（§5.1） |
| 登录环境 | 用户登录 shell 加载配置之后的环境变量（PATH、密钥、语言等）。从访达或程序坞启动的应用拿不到它（§7） |

- 编号：本文的决策接续桌面端文档，为 DD-10 起；待定问题为 DQ-09 起。内核与协议一侧的新决策接续总方案，为 D-37 起，同步登记到 protocol-design.md §14 与 technical-design.md §19。
- 本文给出的数值（超时、退避间隔、空闲时间）都是初始值，实测后可调。

## 1. 目标与约束

### 1.1 目标

| 编号 | 目标 | 含义 |
|---|---|---|
| IG1 | 首装即用 | 双击 FinxWork.app 就能用。不需要终端，不需要预先安装 finx、Rust 或 Homebrew，不需要手写配置文件。没有模型密钥时，应用里就能填 |
| IG2 | 稳定、能自愈 | 应用用到的内核版本一定与它匹配；内核崩溃、被杀、应用升级、系统睡眠之后，应用自己恢复，用户不用重启任何东西 |
| IG3 | 任务独立于窗口 | 关窗口、退出应用、升级应用，都不打断正在运行的任务（DD-02） |
| IG4 | 快 | 内核已在运行时，打开应用到列表可见只多一次本机连接；冷启动只多一次内核启动（毫秒级）。事件路径上主进程不解析、不复制第二次（DD-03） |
| IG5 | 一个内核 | 每个用户只有一个内核服务，桌面端、命令行、以后的编辑器接入都连它；桌面端没有私有通道，也不在自己的进程里跑内核 |
| IG6 | 安全 | 只有同一用户能连内核；密钥放在系统钥匙串里，不进协议消息、不进日志、不进命令行参数 |

### 1.2 初装用户会遇到的问题

逐条列出，后文给出对策：

| 问题 | 不处理会怎样 | 对策 |
|---|---|---|
| 电脑上没有 finx | 应用什么都做不了 | 内置内核（§4） |
| 电脑上有一个版本不同的 finx 服务在跑（例如用户自己用命令行启动的） | 协议版本不同时连不上；版本相同但能力不同时，界面功能缺失 | 握手时核对版本，按 §5.5 的策略处理，空闲时换成内置版本 |
| 从访达启动的应用只有最小的环境：PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`，没有用户在 `.zshrc` 里导出的变量 | 模型要跑的 `cargo`、`npm`、`brew` 装的命令全都找不到；环境变量里的密钥拿不到；中文输出乱码 | 拉起内核前解析登录环境（§7） |
| 用户没有任何模型密钥 | 第一个任务就失败，报"no API key" | 首次使用的引导：在应用里填密钥，存进钥匙串（§8） |
| 内核崩溃或被强制退出 | 界面卡死，或者一直转圈 | 守护器发现断开，自动重新拉起并重连，页面以新快照恢复（§6） |
| 应用升级时有任务在跑 | 强行换内核会打断任务 | 新应用先接上旧内核继续用，等没有任务在跑时再换（§6.4） |
| 两个进程同时拉起内核（应用与命令行） | 两个服务抢同一个 socket | 内核的单实例锁保证只有一个成功，另一个直接连上它（§5.6） |
| `FINX_HOME` 路径很长 | socket 路径超过 104 字节，内核拒绝启动 | 启动前检查，给出明确的说明（§5.7） |
| 应用在下载目录里直接打开（系统会把它放到随机路径下运行） | 内置内核的路径每次不同 | 内核路径只在拉起时使用，不写进任何配置；服务记录里的路径只用于诊断 |

### 1.3 不在本文范围

- 公证、DMG、自动更新、登录自启：三期（desktop-design §11）。本文只说明它们与集成的关系。
- Windows 的命名管道与 Linux 的打包：四期。本文的设计在平台适配里给它们留了位置（§3.3）。
- 远程内核（WebSocket）：protocol-design §8.3。

## 2. 方案选择

### 2.1 内核从哪里来（DD-10）

| 方案 | 优点 | 问题 |
|---|---|---|
| **内置在应用里** | 版本永远匹配；首装即用；升级应用就升级内核 | 应用体积多约 10 MB |
| 用用户 PATH 里的 finx | 体积小 | 初装用户没有；版本不可控 |
| 首次运行时下载 | 体积小 | 需要网络；下载、校验、签名都要处理；离线不可用 |

结论：**内置**。应用只使用自己内置的内核，不去找 PATH 里的 finx。开发时可以用环境变量指定别的二进制（§4.5）。

### 2.2 进程模型（DD-11）

| 方案 | 优点 | 问题 |
|---|---|---|
| 子进程 + stdio（`finx serve --stdio`） | 最简单 | 退出应用就结束任务（违背 IG3）；命令行和编辑器不能共用会话 |
| **常驻服务，按需拉起**（`finx serve --listen unix:// --idle-exit`） | 任务独立于应用；多客户端共用；协议已经实现 | 要处理发现、拉起、版本、重连 |
| 交给 launchd（SMAppService 登记的 LaunchAgent） | 系统管理生命周期，崩溃自动重启；可以由 launchd 持有 socket，按需激活 | 首次登记会弹出"已添加后台项目"的系统通知，初装用户容易困惑；内核要改用 launchd 的 socket 激活接口；环境同样是最小环境 |

结论：**常驻服务，由应用按需拉起，空闲自动退出**。登录自启以后作为可选项，用 SMAppService 实现，届时内核的拉起方式不变（DQ-09）。

### 2.3 共用还是独占内核（DD-12）

- **共用默认端点** `$FINX_HOME/run/finx.sock`。命令行启动的服务和应用拉起的服务是同一个东西，用户的会话只在一个进程里加载，不会出现"这个会话被另一个服务打开了"（`session_busy`）。
- 版本不一致时，应用按 §5.5 的策略接管：协议兼容就先用着，空闲时换成内置版本；协议不兼容就请它退出后再拉起内置版本。
- 独占一个应用专用的 socket 看起来更省事，但会出现两个内核同时管理 `~/.finx/sessions`：在一个里运行的会话，在另一个里只能看到"未加载"，打开就报占用。这比偶尔替换一次服务糟得多。

### 2.4 登录环境由谁解析（DD-13）

- 由**主进程的平台适配**解析，拉起内核时作为它的环境传入（§7）。
- 不放进内核：从终端启动的 finx 本来就有完整环境，只有图形界面拉起时才需要；把"读取用户 shell 配置"做成内核的默认行为，会拖慢命令行的启动（technical-design §1.4 的启动预算是毫秒级）。
- Windows 不需要这一步（图形界面程序本来就有完整的用户环境），平台适配返回当前环境即可。

### 2.5 密钥放在哪里（DD-14，内核一侧为 D-39）

- **由内核负责存取**，桌面端只通过协议提交和删除。命令行以后加 `finx login` 时用同一份存储，用户在应用里填过的密钥，命令行也能用。
- macOS 上存进**登录钥匙串**，经由系统自带的 `/usr/bin/security` 读写：
  - 钥匙串条目的访问控制绑定在 `security` 这个由系统签名的程序上，内核升级（签名变化）后读取不会弹出授权框；
  - 写入时密钥经标准输入传给 `security -i`，不出现在命令行参数里；
  - 不引入新的 Rust 依赖。
- 其他平台暂用 `$FINX_HOME/credentials.toml`（权限 0600），以后换成各自的系统凭据库。

### 2.6 协议类型由谁维护（DD-15）

- `@finx/protocol` 的类型**由内核导出的 JSON Schema 生成**（`crates/finx-protocol/schema.json` → `packages/protocol/src/generated.ts`），不再手写。手写的只剩一层很薄的辅助类型（方法表、`EventMsg` 等）。
- 测试检查生成结果与 schema 一致，与内核一侧检查 schema 与 Rust 类型一致的做法相同。协议有改动时，两边在同一次提交里更新。
- 这就是 desktop-design §7 的 P9。生成器是仓库里一个不依赖第三方包的脚本，只覆盖 schemars 实际产出的那部分 JSON Schema。

## 3. 总体架构

```
┌──────────────────────────────── FinxWork.app ────────────────────────────────┐
│ Contents/MacOS/FinxWork（Electron）          Contents/MacOS/finx（内置内核）   │
│                                                                               │
│  页面（每个窗口一个）                                                          │
│    store ── RpcClient ── MessagePort ──┐                                      │
│                                        │ NDJSON 文本，原样转发                 │
│  主进程                                ▼                                      │
│    守护器 Supervisor ──────── 页面连接（每个窗口一条 socket 连接）               │
│      ├─ 登录环境（平台适配）                                                   │
│      ├─ 拉起：spawn 内置 finx（脱离应用的进程组）                               │
│      └─ 控制连接：握手、版本、空闲判断、请求退出                                 │
└──────────────────────────────────────┬────────────────────────────────────────┘
                                       │ Unix socket $FINX_HOME/run/finx.sock（0600）
                                       ▼
            finx serve --listen unix:// --idle-exit 600   （常驻，同一用户只有一个）
              服务记录：$FINX_HOME/run/finx.lock（独占锁 + 一行 JSON）
              会话：$FINX_HOME/sessions/…    日志：$FINX_HOME/logs/…
              ▲
              └── 同一个服务也接受命令行、以后的编辑器接入的连接
```

### 3.1 组件与职责

| 组件 | 位置 | 职责 | 不做 |
|---|---|---|---|
| 内核服务 | `finx serve` | 会话、任务、审批、权限、密钥、列表推送 | 不关心谁拉起了它 |
| 守护器 | `apps/desktop/src/main/kernel/supervisor.ts` | 保证有一个与应用匹配的内核服务在跑，并告诉页面它的状态 | 不解析、不改写页面连接上的消息 |
| 登录环境 | `main/platform/*`（`loginEnvironment()`） | 解析用户登录 shell 的环境 | 不缓存到磁盘 |
| 页面连接 | `main/kernel/index.ts` | 每个窗口一条 socket，字节双向转发（DD-03） | — |
| 页面 | `renderer/src/store.tsx`、`kernel.ts` | 初始化协议、订阅列表、接入会话；断开后按快照恢复 | 不知道内核在哪里、怎么启动 |

### 3.2 两种连接

- **控制连接**（守护器独有）：在主进程里用 `@finx/client` 的 RpcClient（它不依赖 DOM，可以在 Node 里跑）。握手、订阅会话列表以判断"有没有任务在跑"、需要时发 `server/shutdown`。控制连接上的消息由主进程解析，但这条连接上只有少量控制消息，不影响 DD-03：**转发页面消息的路径上主进程仍然只复制字节**。
- **页面连接**：页面自己做 `initialize`，订阅列表，接入会话。一个窗口一条，窗口关闭即断开。

控制连接同时是守护器的"心跳"：内核服务退出或崩溃时，它第一个知道（socket 关闭），不需要轮询。

### 3.3 平台适配接口的增补

```ts
interface Platform {
  // ……（desktop-design §4.2 已有的部分）
  /** 内核端点：macOS、Linux 为 Unix socket 路径；Windows 为命名管道名（四期） */
  kernelEndpoint(finxHome: string): string;
  /** 内置内核的路径：macOS 为 Contents/MacOS/finx */
  kernelBinary(): string;
  /** 拉起内核时使用的环境：macOS、Linux 解析登录 shell；Windows 直接用当前环境 */

```

## 4. 内置内核与打包

### 4.1 位置

- `FinxWork.app/Contents/MacOS/finx`。Apple 的约定是辅助可执行文件放在 `Contents/MacOS`（或 `Contents/Helpers`），不要放进 `Contents/Resources`：后者里的 Mach-O 文件在签名和公证时会被当作资源，容易出错。desktop-design §3.3 原定的 `Resources/bin/finx` 相应修改。
- 同目录放一份 `Contents/Resources/kernel.json`：`{ "version": "0.1.0", "protocol_version": 2 }`，打包时由 `finx --version` 和 schema 中的协议版本生成。守护器据此判断内核服务是不是"自己的"版本，不需要在运行时调用一次 `finx --version`。

### 4.2 构建

- `pnpm app` 在打包前执行 `cargo build --release --locked -p finx-cli`，把 `target/release/finx` 复制进应用（release 配置为 thin LTO，见 Cargo.toml）。
- 一期只打 arm64。Intel Mac 以后用 `lipo` 合成通用二进制，或分别打包（DQ-10）。
- 打包脚本在复制后执行一次 `finx --version`，确认二进制能运行、版本与 `kernel.json` 一致，不一致就中止打包。

### 4.3 签名

- 内置内核与应用同一个签名身份：一期临时签名，三期 Developer ID + hardened runtime + 公证。
- `@electron/osx-sign` 会逐个签名应用里的 Mach-O 文件，内核随应用一起签，不需要单独处理。内核不需要额外的 entitlements：它只读写用户目录、启动子进程、访问网络，这些在 hardened runtime 下都允许。
- 三期公证时，内核作为应用的一部分一起提交。

### 4.4 体积

| 部分 | 体积 |
|---|---|
| Electron 应用（一期实测） | 约 300 MB |
| 内置内核（release，arm64） | 实测见 §14 |

内核只占应用体积的很小一部分，不值得为它引入下载或按需安装的复杂度。

### 4.5 开发模式

| 场景 | 用哪个内核 |
|---|---|
| 打包出的 FinxWork.app | `Contents/MacOS/finx` |
| `pnpm dev` | 仓库的 `target/debug/finx`（没有就提示先 `cargo build`） |
| 设置了 `FINXWORK_FINX=/path/to/finx` | 指定的二进制（调试内核时用） |
| 设置了 `FINXWORK_KERNEL=mock` | 主进程里的模拟服务（只做界面开发时用，不需要 Rust） |
| 浏览器里预览页面 | 页面里的模拟服务 |

`FINX_HOME` 照常生效：测试和演示可以用一个临时目录，完全不碰用户的 `~/.finx`。

## 5. 发现、拉起与握手

### 5.1 服务记录（D-37）

内核服务拿到单实例锁之后，把服务记录写进锁文件 `$FINX_HOME/run/finx.lock`：

```json
{"pid":48213,"version":"0.1.0","protocol_version":2,"socket":"/Users/me/.finx/run/finx.sock","exe":"/Applications/FinxWork.app/Contents/MacOS/finx","started_at":"2026-10-29T08:12:03Z"}
```

- 锁文件以"不截断"的方式打开，**拿到锁之后**再清空并写入。否则第二个启动者在拿锁失败之前就已经把正在运行的服务的记录清空了。
- 服务退出时删除 socket 与锁文件（已有逻辑）。
- 记录只是辅助信息：版本以握手结果为准（§5.5）。它的用途是在**无法握手**时（协议不兼容、服务卡死）拿到进程号，用信号请它退出；以及在诊断页面显示"是谁拉起的、从哪个文件运行"。
- 读记录的一方用 `kill(pid, 0)` 判断进程是否还在；进程已不在的记录视为残留。

### 5.2 启动流程

```
应用启动 ─▶ 守护器.ensure()
              │  同时：开始解析登录环境（只在需要拉起时等它，§7.4）
              ▼
        连接 finx.sock（300 ms 超时）
         ├─ 成功 ─▶ 控制连接 initialize ─▶ 按 §5.5 判断版本 ─▶ ready
         └─ ENOENT / ECONNREFUSED（没有服务，或残留的 socket 文件）
              ▼
        等登录环境 ─▶ spawn 内置 finx serve --listen unix:// --idle-exit 600
              ▼
        按 10、20、40、80、160、200…ms 重试连接（总时限 10 s）
         ├─ 连上 ─▶ initialize ─▶ ready
         ├─ 子进程提前退出 ─▶ 读它的错误输出 ─▶ failed（带原因）
         └─ 超时 ─▶ failed（"内核没有响应"）
```

- **热启动**（内核已在运行，最常见）：一次连接 + 一次 initialize，约 1 ms。
- **冷启动**：再加环境解析（实测约 140 ms，与登录 shell 的配置有关）和内核启动（`finx serve` 到能回复 initialize ≤ 10 ms，protocol-design §12.2）。环境解析与第一次连接尝试并行进行。
- 页面在 ready 之前照常显示（侧栏是空的、底部显示"正在启动内核…"），ready 后再建立页面连接。

### 5.3 拉起参数

| 项 | 值 | 理由 |
|---|---|---|
| 命令 | `<内置 finx> serve --listen unix:// --idle-exit 600` | 默认端点；10 分钟没有连接也没有任务时自己退出，不常驻占内存 |
| 进程关系 | `detached`（新会话），拉起后 `unref` | 退出应用不影响内核（IG3） |
| 工作目录 | 用户主目录 | 内核按每个会话的 cwd 工作，与自己的工作目录无关；不能用应用包里的目录（只读，而且可能被系统移到随机路径） |
| 环境 | 登录环境（§7），另加 `FINX_HOME`（如果应用自己有）、`FINXWORK_PARENT=1` | 让模型执行的命令与用户在终端里一致；`FINXWORK_PARENT` 只用于诊断 |
| 标准输入 | `/dev/null` | — |
| 标准输出、错误输出 | 追加到 `$FINX_HOME/logs/serve.out.log` | 内核的日志本来就写 `logs/finx.*.log`；这里只会出现启动失败的报错和 panic。**不能用管道**：应用不读之后，管道写满会让内核卡住 |

### 5.4 等待就绪

- 不需要内核额外发"就绪"信号：socket 能连上就是就绪。轮询的间隔从 10 ms 开始翻倍，最多 200 ms，所以冷启动只多出最多一个间隔的等待。
- 拉起后守护器监听子进程的 `exit`。在连上之前子进程就退出了，说明启动失败，读 `serve.out.log` 本次追加的部分作为原因：
  - 报"another finx service is already listening"：别人刚好抢先拉起了，继续重试连接即可（§5.6）；
  - 报 socket 路径过长：§5.7；
  - 其他：进入 failed，界面显示原因与"查看日志""重试"。
- 连上之后不再关心子进程（它可能比应用活得久）。

### 5.5 握手与版本策略

守护器在控制连接上发 `initialize`（protocol_version = 应用支持的版本，client_info.name = `finxwork-supervisor`），然后对照 `kernel.json`：

| 情况 | 判断 | 处理 |
|---|---|---|
| 版本相同 | `server_info.version == kernel.json.version` | ready |
| 版本不同，协议兼容 | initialize 成功 | ready，记下"待替换"。没有任务在跑时立即替换；有任务在跑时继续使用，等全部任务结束后替换（§6.4） |
| 协议不兼容 | initialize 返回 -32602 | 读服务记录，向进程发 SIGTERM（内核会中断任务、保存日志、5 秒内退出，protocol-design §3.8），等它退出后拉起内置版本。没有服务记录（太旧的版本）时，提示用户在终端里结束它，并给出命令 |
| 连得上但不回应 | initialize 5 秒没有结果 | 同"协议不兼容"：按记录发 SIGTERM，10 秒后仍在就 SIGKILL |

- "替换"就是：控制连接发 `server/shutdown` → 内核关闭全部会话（都是空闲的，没有损失）并退出 → 守护器拉起内置版本 → 页面按 §6.2 重连。用户看到的只是底部状态闪一下"正在重连…"。
- 替换会断开其他客户端（例如用户在终端里开着的连接）。它们按协议的约定重连即可；命令行的 `exec`、`chat` 不经过服务，不受影响。
- 替换只做一次：如果刚由应用自己拉起的服务仍然不符合（例如 `kernel.json` 与二进制不一致这种打包错误），守护器保留它并记录，不会反复重启。打包脚本会核对两者一致。
- 应用不会把一个**更新**的内核换成自己内置的**更旧**版本吗？会。应用只信任自己内置的版本，这样它测试过的组合就是它运行的组合。调试新内核时用 `FINXWORK_FINX` 指定（§4.5）。

### 5.6 竞争与单实例

| 竞争 | 结果 |
|---|---|
| 同一应用开了两个实例 | 不会发生：主进程启动时申请单实例锁（已有），第二个实例把窗口交给第一个后退出 |
| 应用与命令行同时拉起内核 | 内核的单实例锁保证只有一个拿到锁；另一个报"already listening"退出。守护器把这个报错当作"别人已经拉起了"，继续重试连接 |
| 守护器连接时 socket 文件残留（内核崩溃留下的） | 连接返回 ECONNREFUSED，守护器拉起新内核；新内核拿到锁后先删除残留文件再绑定（已有逻辑） |
| 两个窗口同时需要内核 | `ensure()` 在守护器里只有一份进行中的 Promise，所有调用方等同一个结果 |

### 5.7 socket 路径过长

macOS 的 Unix socket 路径不能超过 103 字节。默认路径 `~/.finx/run/finx.sock` 远在限制之内；只有用户把 `FINX_HOME` 设到很深的目录时才会超过。守护器在拉起前检查长度，超过时直接进入 failed，说明原因和解决办法（缩短 `FINX_HOME`），不去拉起一个注定失败的进程。

## 6. 运行期：断线、崩溃与升级

### 6.1 守护器状态机

| 状态 | 含义 | 界面 |
|---|---|---|
| `starting` | 正在连接、解析环境或拉起内核 | 底部账户区："正在启动内核…" |
| `ready` | 控制连接已握手 | "已连接 · finx 0.1.0"（版本不同、待替换时加"· 稍后更新"） |
| `reconnecting` | 内核断开，正在恢复（带第几次） | "正在重连内核…"；页面上的会话保持只读显示，输入框可以继续编辑但不能发送 |
| `failed` | 无法恢复，需要用户处理 | 原因 + "重试""查看日志" |

转移：

```
starting ──连上并握手──▶ ready ──控制连接断开──▶ reconnecting ──恢复──▶ ready
    │                       │                         │
    └──失败──▶ failed ◀──────┴──── 60 秒内崩溃 3 次 ──┘
failed ──用户点重试──▶ starting
```

- `reconnecting` 的重试间隔：0、200 ms、500 ms、1 s、2 s、5 s，之后每 5 s 一次。每次都完整地走 §5.2（服务可能需要重新拉起）。
- **崩溃循环保护**：60 秒内内核服务第 3 次异常退出时停在 failed，不再自动拉起，避免一个启动即崩溃的内核把电脑拖慢。界面给出最近的错误输出与日志路径。
- 状态通过桥推给所有窗口（`onKernelState`），页面只根据状态显示，不自己判断。

### 6.2 页面重连

页面连接是每个窗口自己的。守护器回到 ready 后通知页面，页面：

1. 重新建立页面连接（向主进程申请新的 MessagePort），`initialize`；
2. 重新订阅会话列表（`sessions/subscribe`），用返回的完整列表替换本地列表；
3. 对当前打开的会话发 `session/resume`（内核重启后会话没有加载；没重启时等同于接入），用新快照**整体替换**本地状态（protocol-design §3.4 第 3 条：seq 的作用域是一次加载）；
4. 输入框里没发出去的草稿、附件、滚动位置保留在页面，不受影响。

没有打开的会话不需要做什么：列表推送会带来它们的新状态。

重连期间发出的请求直接失败（RpcClient 在连接断开时让所有挂起的请求以 `disconnected` 失败，desktop-design §6.1），界面提示"内核正在重连，稍后再试"，草稿保留。

### 6.3 任务在内核重启时的命运

- **内核被替换**（§5.5、§6.4）：只在没有任务运行时发生，不打断任何任务。
- **内核崩溃**：正在运行的任务随进程结束。会话日志里这个任务只有开始、没有结束，下次加载时内核会补记一条"已中断"（已有逻辑），界面显示"任务被中断，再发一条消息就会接着做"。
- **协议不兼容时的强制替换**：发 SIGTERM，内核中断任务并保存日志，结果同上。这只在应用升级跨越了协议版本、并且旧内核恰好有任务在跑时发生。

### 6.4 应用升级

1. 用户在内核有任务运行时升级应用并重新打开。
2. 新应用的守护器连上旧内核：协议兼容时进入 ready（待替换），一切照常可用，任务继续。
3. 控制连接订阅会话列表；每次列表推送后检查：没有状态为 running 或 awaiting_approval 的会话时，发 `server/shutdown` 替换。
   - 内核的版本号不随应用发版变化。所以守护器还会记下自己启动的内核文件的 inode：旧内核还在跑、应用路径上的文件却已经换了，也判为待替换（desktop-release §4.6，DD-25）。
4. 替换后页面按 §6.2 重连。

### 6.5 应用退出

- 退出应用时守护器只关闭自己的连接，**不**结束内核：任务继续在内核里跑（IG3）。没有任务也没有连接的内核在 10 分钟后自己退出（`--idle-exit 600`）。
- 内核里有任务在跑时退出应用，不弹确认框：任务不会因此中断。
- 以后的登录自启（DQ-09）只改变"谁第一个拉起内核"，不改变上面的任何行为。

### 6.6 睡眠、磁盘与其他

| 情况 | 行为 |
|---|---|
| 系统睡眠后唤醒 | 本机 socket 不受睡眠影响，连接照常可用 |
| 磁盘满 | 内核写日志失败会结束会话并报错；页面显示内核给出的错误 |
| 用户删除了 `~/.finx` | 内核下次启动时重建目录；已经在运行的内核的 socket 文件被删后，新连接会失败，守护器按 ECONNREFUSED 处理：拉起新内核，新内核拿锁时发现旧内核仍持有锁（锁文件被删除后它们拿的是不同的文件），两个内核可能同时存在。这种情况极少，旧内核空闲后自己退出 |

## 7. 登录环境

### 7.1 为什么需要

从访达、程序坞或 Spotlight 启动的 macOS 应用，进程环境来自 launchd：

| 变量 | 终端里 | 图形界面启动 |
|---|---|---|
| PATH | 用户配置的完整 PATH（Homebrew、cargo、nvm……） | `/usr/bin:/bin:/usr/sbin:/sbin` |
| 用户导出的密钥（`DEEPSEEK_API_KEY` 等） | 有 | 没有 |
| LANG | 通常是 UTF-8 | 常常没有，命令输出中文变成问号 |

内核给模型执行的命令继承内核自己的环境，所以内核必须带着登录环境启动。

### 7.2 解析方法

1. 取用户的登录 shell：`os.userInfo().shell`（来自目录服务，比 `$SHELL` 可靠），没有时用 `/bin/zsh`。
2. 执行 `<shell> -i -l -c '<命令>'`：`-l` 读登录配置（`.zprofile`），`-i` 读交互配置（`.zshrc`，大多数人的 PATH 和变量写在这里）。命令是：

   ```sh
   printf '%s' '<随机标记>'; /usr/bin/env -0; printf '%s' '<随机标记>'
   ```

   用随机标记截出中间的部分，按 `\0` 切分（变量值里有换行也不会切错）。shell 配置自己打印的内容（欢迎语、提示）都在标记之外，被丢掉。
3. 给这个 shell 的环境加上 `FINXWORK_RESOLVING_ENVIRONMENT=1`，用户可以在配置里据此跳过耗时的部分；标准输入为 `/dev/null`，配置里等待输入的提示会立即读到文件结束。
4. 结果里去掉只与那次 shell 有关的变量：`FINXWORK_RESOLVING_ENVIRONMENT`、`SHLVL`、`_`、`PWD`、`OLDPWD`。
5. 没有 `LANG` 也没有 `LC_ALL` 时补上 `LANG=en_US.UTF-8`。

fish、bash、zsh 都接受 `-i -l -c`。

### 7.3 超时与回退

- 时限 10 秒（某些 nvm、conda 配置很慢）。超时或 shell 出错时回退到：应用当前环境 + PATH 前面补上存在的常用目录（`/opt/homebrew/bin`、`/opt/homebrew/sbin`、`/usr/local/bin`、`~/.cargo/bin`、`~/.local/bin`）。
- 回退时在诊断信息里记一条原因，界面不打扰用户。

### 7.4 时机与缓存

- 应用启动时就开始解析，与第一次连接尝试并行；只有需要拉起内核时才等它的结果。内核已在运行时（最常见），解析的结果用不上，也不耽误任何事。
- 结果只缓存在内存里，不写磁盘（其中可能有密钥）。
- 用户改了 shell 配置之后，设置里的"重启内核"会重新解析并在空闲时替换内核。

### 7.5 安全

- 解析出的环境只交给内置内核这一个子进程，不发给页面，不写日志。
- 内核本来就会从工具子进程的环境里去掉密钥变量（technical-design §11），从登录环境带来的密钥同样受此保护。

## 8. 密钥与首次使用

### 8.1 来源与优先级

内核按顺序找一个服务商的密钥（finx-llm `AuthConfig::ApiKey`）：

1. `models.toml` 里写明的 `api_key`；
2. `api_key_env` 列出的环境变量（登录环境里有的话就在这里找到）；
3. **新增**：内核的凭据存储（macOS 钥匙串，§8.2）。

显式配置和环境变量优先，与命令行的惯例一致。界面会显示密钥来自哪里（"来自环境变量 DEEPSEEK_API_KEY""来自钥匙串"），所以不会出现"填了没用却不知道为什么"的情况。

`api_key_command` 方式（运行命令取密钥）不变，不与凭据存储叠加。

### 8.2 钥匙串存储（D-39）

| 操作 | 实现 |
|---|---|
| 写入 | `security -i`，从标准输入读命令：`add-generic-password -U -s finx -a <provider> -l "finx: <provider>" -w "<key>"` |
| 读取 | `security find-generic-password -s finx -a <provider> -w`；退出码 44 表示没有 |
| 删除 | `security delete-generic-password -s finx -a <provider>` |

- 每个内核进程对每个服务商最多读一次钥匙串，结果缓存在内存里；写入和删除同时更新缓存。读一次约 20 ms，只在第一次请求这个服务商时发生。
- 服务名 `finx`、账户名为服务商 id，用户可以在"钥匙串访问"里看到、修改、删除。

### 8.3 协议（D-38）

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `auth/set` | provider、api_key | `{}` | 把密钥存入凭据存储。服务商不存在，或者它不用 API key 认证时返回 invalid_params |
| `auth/delete` | provider | `{}` | 删除凭据存储里的密钥；本来没有也算成功 |

`models/list` 的结果新增：

```ts
providers: Array<{
  id: string;                      // "deepseek"
  name: string;                    // "DeepSeek"
  auth: "api_key" | "command" | "none";
  credential: "missing" | "config" | "env" | "stored" | "command" | "not_required";
  credential_source?: string;      // credential 为 env 时是变量名
  key_env: string[];               // 可以放密钥的环境变量
}>;
defaults: { model: string; thinking: ThinkingLevel; permission_mode: PermissionMode };
```

- 密钥本身永远不出现在任何结果或事件里（protocol-design §9）。
- `defaults` 是新会话的默认设置（来自用户配置），新会话页用它显示初始的模型、思考强度与权限模式。

### 8.4 界面流程

**首次使用**：启动后页面第一次拿到模型列表时，如果**没有任何一个模型可用**（全部 `available: false`），主窗口整窗显示独立的引导页，而不是在新会话页里要密钥（2026-10-29 起）：

- 设置窗口的"模型"页只有两组列表，与其他设置页同样的分组行，每行是标志、名称、一行状态和一个操作：
  - **用千问办公的账号**（原"本机应用"）：千问办公，标志是本机安装的千问办公自己的图标（主进程用系统的 Quick Look 画出，FinxWork 不带它的图标）。状态是"已连接 · N 个模型 / 已安装 x.y / 未登录 / 未安装 / 登录已失效…"，操作对应连接、断开、重新连接、打开千问办公、重新检查。
  - **用 API Key**（原"API 服务"）：有密钥的服务商，状态是"密钥来源 · N 个模型"（钥匙串、环境变量 X、models.toml、命令提供）。钥匙串里的密钥可以移除：点"移除"后再点"确认移除"（`auth/delete`，随后重新取 `models/list`）；来自环境变量或配置文件的只显示一个锁，悬停说明去哪里删。组末是"添加 API 服务"：弹出服务商磁贴，选一家后粘贴密钥（`auth/set`），与首次启动引导页同一组件。
- 任务因认证失败（ErrorInfo.kind 为 `auth`）结束时，失败说明里给出"设置密钥"按钮，打开同一个密钥表单（浮层）。
- 模型菜单（输入框的模型按钮、失败卡片的"换个模型"）只列可用的模型，没有密钥的服务商从设置 › 模型添加（2026-10-30 起）。唯一的例外是当前模型：它没有密钥时仍留在菜单里，标出"未设置密钥"，选中后同样打开这个表单。
- 模型目录与发现方案（[model-catalog-design.md](../kernel/model-catalog-design.md) §10）已落地（2026-10-30）：菜单只列 `shown && available` 的模型，当前模型不在其中时补在第一行并说明原因；设置页每个服务商显示"显示 N / 共 M 个模型 · 更新时间"，新增"管理模型"浮层（逐个开关、搜索、刷新列表）；密钥表单处理 `auth/set` 的验证结果。

### 8.5 安全

- 页面只经协议提交密钥，提交之后不保留（输入框清空，状态里不存）。
- 密钥经 socket 到内核（同一用户、0600），再经标准输入到 `security`；不经过命令行参数、日志、协议的任何结果。
- protocol-design §9 规划的协议调试日志（`FINX_DEBUG_RPC=1`，尚未实现）实现时，必须先把 `auth/set` 的参数替换为 `"<redacted>"` 再写日志。

### 9.1 版本 2 对齐

内核已经是协议版本 2（protocol-design v0.4）。桌面端随之修改：

| 方面 | 一期（模拟服务） | 对齐后 |

| 协议版本 | 1 | 2 |
| 权限模式 | read-only、ask、auto-edit、full-auto（审批模式） | manual、accept-edits、bypass-permissions（权限模式）；字段 `permission_mode`，Op `set_permission_mode` |
| 模型列表 | 按服务商分组的 ProviderEntry | `ModelSummary` 平铺列表 + `providers` + `defaults`（§8.3） |
| 会话摘要 | 模拟服务的扩展字段 | 内核实现的字段（§9.3） |

界面上的名称：

| 模式 | 中文 | 英文 | 说明 |
|---|---|---|---|
| manual | 询问权限 | Ask Permissions | 写文件、运行命令前都先问 |
| accept-edits | 自动接受编辑 | Accept Edits | 工作区内的文件修改直接执行，命令仍然先问 |
| bypass-permissions | 完全访问 | Full Access | 除拒绝规则、询问规则和关键路径删除外，一律直接执行 |

### 9.2 类型生成

- `node packages/protocol/scripts/generate.mjs` 读取 `crates/finx-protocol/schema.json`，写出 `packages/protocol/src/generated.ts`：每个 definition 一个类型，`x-methods` 生成方法表，`x-server-notifications`、`x-client-notifications` 生成通知表，`x-protocol-version` 生成常量。
- `index.ts` 只做两件事：导出生成的类型，以及补几个派生类型（`EventMsg` 是去掉 seq、ts 的事件；`EventType`；方法表的 `[参数, 结果]` 形式）。
- 测试重新生成一遍并与提交的文件比较，不一致即失败，提示运行生成脚本。

### 9.3 内核补充的能力

desktop-design §7 的 P1–P6 按下表在内核实现（D-38）。都是版本 2 之内的增量修改，由 `ServerCapabilities` 声明，旧客户端忽略即可：

| 编号 | 能力 | 协议 | capability |
|---|---|---|---|
| P1 | 会话列表推送 | `sessions/subscribe`（参数同 `session/list`，结果是第一页）之后，这个连接收到 `sessions/changed { sessions, deleted }`；`sessions/unsubscribe` 结束 | `sessions_subscribe` |
| P2 | 摘要字段 | SessionSummary 新增 `title?`、`state`（idle、running、awaiting_approval、failed）、`model?`、`archived`、`task_started_at?` | 同上 |
| P3 | 改名 | `session/rename { session_id, title }`；标题写进会话日志的 title 条目（日志格式里已有） | `session_metadata` |
| P4 | 归档 | `session/archive`、`session/unarchive { session_id }`；写进新的 archived 条目 | `session_metadata` |
| P5 | 历史里的任务边界 | TranscriptItem 新增 `task_end { task_id, outcome, reason?, error?, usage?, ts }` | `transcript_task_end` |
| — | 默认设置与密钥状态 | `models/list` 新增 `defaults`、`providers`；`auth/set`、`auth/delete`（§8.3） | `auth` |
| — | 服务记录 | 锁文件里的一行 JSON（§5.1） | 不需要 |

细节：

- **何时推送**：会话被创建、加载、卸载、删除；任务开始与结束；审批出现与答复；模型改变；改名、归档；新会话的第一条用户消息（带来 preview）。流式增量、工具进度、接入数变化**不**推送，列表不会因为一个长任务的输出而频繁更新。
- **未加载会话的状态**：内核扫描日志（与 `session/list` 现有的扫描同一遍）时读出最后一个任务条目：失败的为 failed，其余为 idle；模型取最后一个 settings 条目；归档取最后一个 archived 条目。扫描只解析这几类条目，长会话的大量消息行仍然只做一次子串判断。
- **已加载会话的状态**：来自会话镜像（protocol-design §3.3）：有待审批项为 awaiting_approval，有运行中任务为 running，否则看最后一个任务是否失败。
- **改名、归档未加载的会话**：服务层直接给日志追加一个条目（拿日志的独占锁；会话正被另一个进程打开时返回 session_busy）。已加载的会话经过会话中枢交给内核写入（新的 Op：`set_title`、`set_archived`），内核发出事件 `title_changed`、`archived_changed`，镜像与快照里的 SessionInfo 随之更新。
- P6（历史中工具调用的描述）暂不做：客户端已经能从工具名和参数得到同样的描述（`@finx/client` 的 `describe`），等出现第三方工具时再做。

### 9.4 模拟服务

模拟服务继续保留，用于浏览器预览、界面开发和不需要 Rust 的测试。它实现与内核**同一份**协议（同样由生成的类型约束），不再有"提议中"的私有字段。

## 11. 安全

- 内核只监听 Unix socket：目录 0700、socket 0600，每个连接检查对端 uid（已有）。页面拿到的能力不超过同一用户的任何进程连上 socket 能拿到的能力（desktop-design §3.1）。
- 页面不能指定内核路径、拉起参数或环境：这些都在主进程里决定，页面只能请求"重试""重启内核"。
- 守护器只对服务记录里的进程发信号，并且先确认这个进程的可执行文件名是 `finx`（`ps -o comm= -p <pid>`），防止记录被篡改后误杀别的进程。
- 密钥：§8.5。

## 12. 诊断

- **设置 → 关于**显示：内核状态、版本、协议版本、可执行文件路径、谁拉起的（本应用或其他）、socket 路径、`FINX_HOME`、登录环境是否解析成功。
- 操作：**重启内核**（重新解析登录环境；有任务在跑时先确认）、**在访达中显示日志**（`$FINX_HOME/logs`）。
- 设置 `FINXWORK_TRACE=1` 启动时，守护器把状态变化打印到主进程的输出，不含环境变量的值。写入文件的主进程日志随三期一起做。
- 启动失败时，界面直接显示内核错误输出的最后几行。
