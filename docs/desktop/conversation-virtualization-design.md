# 对话区只画看得见的部分

| 项 | 内容 |
|---|---|
| 版本 | v0.1 |
| 日期 | 2026-11-08 |
| 状态 | 方案，待实施 |
| 关系 | desktop-design.md §9.2 的后续（一万个会话、每个五千条消息的压测）；不改内核与协议 |

## 1. 为什么做

一段对话打开时只取最后一页，往上翻时每页留在页面里。翻到头（6004 条、2000 行）时 DOM 有 97 万个节点、JS 堆 249 MB、渲染进程 1.4 GB；补上一页要 209～328 ms，最长阻塞 133 ms；这时模型写回复，主线程 61%，打字最长 80 ms（desktop-design §9.2）。Bot 的对话只有一段、从不新建，长了以后同样如此。

量下来，成本在三处，都和挂在页面里的行数成正比：

| 现象 | 实测 | 原因 |
|---|---|---|
| 节点多 | 20 页、697 行时 31.9 万个节点，89% 在代码块里 | 代码高亮每个词一个元素；用户消息每行约 14 个节点 |
| 每页越补越慢 | 50 页时一页 180～250 ms，其中约 46 ms 是表格测量 | 表格挂载时读尺寸；读的若是屏幕外的回复，浏览器得把被 `content-visibility` 跳过的整行排出来 |
| 写回复时卡 | 约 1700 行时主线程 52%，布局 4 秒 223 ms，React 每次都要比较这 1700 行 | 每次更新都要排整段对话；`content-visibility` 只省了屏幕外回复的内部，行本身和用户消息都还在 |

对照实验：同样 1700 行，只让最后 40 行参与布局（其余 `display:none`），写回复时主线程 52% → 28%，布局 223 → 7 ms。隐藏的节点仍在，样式遍历、React 比较和内存都没省；真不挂载，这几项也会跟着消失。

上一版设想过"最多留几页"：代码多的会话十页也有十几万节点，写回复仍在 40% 左右；而且往回看时下面的页被放掉，新回复来了、往下翻都得重新取。不采用。

先修表格测量、去掉跟随到底时的强制读取也不单独做：后者只是把这一帧本来要做的布局提前，不是多出来的；前者多出来的部分来自屏幕外的行，不挂载之后就没有了。虚拟化完成后再量一次，有残留再处理（§5 第 4 步）。

## 2. 目标与不做的事

目标（在 `e2e/stress.mjs --scenario deep` 上量，同一台机器、同一份脚本）：

| 指标 | 现在 | 目标 |
|---|---|---|
| 读完 5000 条后：DOM 节点 / JS 堆 / 渲染进程 | 97 万 / 249 MB / 1.4 GB | ≤ 5 万 / ≤ 60 MB / ≤ 500 MB |
| 任意深度补上一页：耗时 / 最长阻塞 | 209～328 ms / 133 ms | ≤ 80 ms / ≤ 50 ms |
| 读完后模型写回复：主线程 | 61% | 与只开最后一页时相差 ≤ 5 个百分点 |
| 任意深度打字，按键到画出（最长） | 96 ms | ≤ 50 ms |
| 滚轮往上读进没画过的历史 | — | 无超过 50 ms 的帧；无空白帧 |
| 往上读时上方的行量出真实高度 | — | 正在读的那一行移动 ≤ 2 px |
| 短对话（不足一屏半） | — | 行为与现在一致，所有行都在页面里 |

不做：

- 不改分页协议，不减少客户端保存的消息数据。读过的历史都留在内存里（5000 条的原始数据约 7 MB），只是不画。
- 不加对话内查找。将来要做时搜数据、再跳过去（§3.6 的 `scrollToKey`），连没取到的历史都能搜，浏览器自带的查找做不到。
- 不改外观与交互：间距、对齐、悬停栏、跟随到底、离开底部的规则都保持现状。
- 回到一个会话时仍只画最后一页（`latestPage`），不在这一轮恢复上次读到的位置。

## 3. 方案

### 3.1 数据与挂载分开

对话页照旧从全部已取到的条目算出 `steps`（`settledSteps` + `withStreaming`，不变）。每行要传的 `previous`、`final`、`merged`、`current`、`working` 也照旧在整份 `steps` 上算好，得到行列表 `rows`。之后只把可视区附近的那一段画出来：

```
.cscroll
  .dbody
    (归档提示) (更早的历史)
    .tr  data-rows=总行数
      .vspace  上方没画的行的总高度
      .vrow × 窗口里的行
      .vspace  下方没画的行的总高度
      (重试卡) (进行中那一行) (后台任务行)
```

画出来的行和空白块都在文档流里，不用绝对定位：现有的跟随到底、补页时保持位置（`fromEnd`）、浏览器原生的滚动锚定照常工作，样式也基本不动。

**什么都不画的行不进列表。** 现在有两种：并到最后一句话里的任务结束行（`merged`）；工具组里的项全都显示在别处，进行中的调用与正在写的思考在进行中那一行（`runs`、`thinks`），等审批的调用在审批卡片里。现在它们渲染为 `null`，放进容器会多出一个空行的间距。

### 3.2 行容器与样式

每行套一个 `.vrow`，`data-step-key` 从里面的 `.um`、`.am` 移到它身上（工具组、子智能体卡片现在没有这个属性，以后统一有了）。

- `.tr` 是带 `gap` 的纵向 flex，时间分隔线和用户气泡是两个兄弟。`.vrow` 也是同样 `gap` 的纵向 flex（`gap: var(--sp-2)`，与 `.tr` 同一个令牌），宽度占满。
- 选择器改为以 `.vrow` 为父：`.markdown-chat .tr>.am` → `.vrow>.am`；`.tr>.um` → `.vrow>.um`；`.tr>:not(.am)` → `.tr>:not(.am,.vrow)` 加上 `.vrow>:not(.am)`。
- 删掉 `.tr>.am` 上的 `content-visibility:auto` 和 `contain-intrinsic-block-size`。窗口外的行本来就不挂载；窗口里但不在屏幕上的行如果被跳过，量到的会是 180 px 的占位高度，会污染高度缓存。
- `.vspace{flex:none;overflow-anchor:none}`：原生滚动锚定不会选空白块当锚点。
- 测试与压测脚本数行改读 `.tr[data-rows]`，不再数 DOM 里的行。

### 3.3 行高

- **量到的高度**：所有挂载的 `.vrow` 共用一个 `ResizeObserver`，读 `borderBoxSize`，按行的 key 存进 `Map<key, number>`。key 在流式结束转成历史时不变，所以写回复时量到的高度直接沿用。
- **没量过的行先估算**：按行的种类（用户消息、回复、工具组、子智能体卡片、汇报、任务结束、提示）取本次会话里量到的同类平均值，一行都没量过时用固定的初始值。估算只影响滚动条的比例和远距离跳转的落点：屏幕上看到的内容由 §3.5 保持不动。先用平均值，滚动条跳动明显时再按字数和代码行数细化。
- **宽度变了**（窗口缩放、开关侧面板）：挂载的行由观察器重新量；没挂载的行沿用旧宽度下量到的值，作估算用，下次挂载时更新。

位置用前缀和：`P[0]=0`，`P[i+1]=P[i]+h[i]+gap`。行数或任一行高变化时整表重算，6000 行也只是一次线性扫描。行数只在补页、新消息时变；高度只在挂载的行变化时变。

空白块的高度沿用侧栏的写法，扣掉它自己带来的间距：上方是 `P[first]-gap`（`first>0` 时），下方是 `P[n]-P[end]-gap`（`end<n` 时）。

### 3.4 窗口

- 可视范围：`.tr` 在滚动内容里的起点，加上 `scrollTop` 和 `clientHeight`，在 `P` 上二分查找，得到 `[a, b)`。
- 上下各多画一屏（像素计），一次滚轮连拨不会露出空白。窗口按 8 行一档移动，不是滚一像素就重画一次；换档时只挂载新进来的行，其余行 `memo` 不动。
- **钉住**：下面这些行无论在不在窗口里都保持挂载，窗口取它们与可视范围的并集。
  - 选区两端所在的行，以及中间的行（`selectionchange`）：拖选、复制不会因为行被卸载而断掉。
  - 有焦点的行（`focusin` / `focusout`）：键盘操作中的按钮不会被卸载。
  - 正在跳过去的目标行（§3.6），落定后放开。
- 停在底部时窗口自然包含最后几行；离开底部时，正在写的那一行可以不挂载。它变高只影响看不到的下方，回到底部时再量。

### 3.5 滚动位置

沿用现有规则，按情况分别处理：

1. **停在底部**：跟随到底仍由 `.dbody` 上已有的 `ResizeObserver` 完成。
2. **往上补一页**：新行都在窗口上方，只是上方空白块变高。现有的 `fromEnd`（补页前记下离底部的距离，渲染后还原）保持画面不动，不用改。
3. **上方的行从估算高度换成真实高度**：发生在往上读、行从上方一屏的余量进入挂载时，这时还看不到它们。
   - Chromium 的滚动锚定（样式里没有关掉它）会自动补偿位移；锚点在视口里，不会选到空白块。
   - 原生锚定有不生效的情形，例如滚动位置为 0 时。所以现有的锚点逻辑（记住视口顶端那一行和它的偏移，在 `ResizeObserver` 回调里纠正）要保留，并真正承担兜底。锚定已经补偿过时，它算出的偏差是 0，两者不会叠加。
   - 第 2 步用"正在读的那一行移动 ≤ 2 px"检查两者叠加后的结果。
   - 找"视口顶端那一行"改用前缀和二分，不再遍历所有行逐个 `getBoundingClientRect`。
4. **拖滚动条到很远的位置**：落点按估算算出窗口。窗口里的行用真实高度，上方空白块仍是估算之和，所以落地后不会再跳，只是滚动条比例略有偏差，之后随测量逐渐变准。

离开底部、回到底部的判定（只有人的滚轮、触摸、按键、拖滚动条之后往上才算离开）完全不变。

### 3.6 跳到某一行

`scrollToKey(key, { block })` 替代 `querySelector` 加 `scrollIntoView`：

- 先钉住目标行，把滚动位置设到它估算位置附近（离得超过三屏时立即跳到它上方一屏，再平滑滚过去，避免平滑滚动穿过几千行时一路挂载卸载）；
- 等它挂载并量到真实高度后，再对它调用 `scrollIntoView` 完成最后一段，然后放开钉住。

用在两处：

1. 重发托盘的"定位到这条消息"（`Chat.tsx` 里的 `find`）；
2. Bot 定时任务面板的"跳到这次运行的消息"（`BotPage.tsx` 里的 `showBubble`，按 `data-run` 找行改为按运行 id 找 key）。

目标若在还没取到的历史里，和现在一样不动。消息内的脚注与标题跳转在同一行里，点击时这一行必然挂载着，不受影响。

### 3.7 行卸载后回来

- **展开状态**：工具组、单个工具、思考过程、子智能体卡片、汇报、失败详情、Mermaid 的源码切换，现在是组件内部的 `useState`，卸载就丢失。改为 `useRowState(id, initial)`，存在会话级的 `Map` 里，id 用行的 key 或调用 id；会话离开缓存（`kept`）时一起清掉。表格全屏、图片大图是盖住页面的弹层，打开时滚不动，不用改。
- **重新挂载的成本**：Markdown 要重新解析，代码要重新请求高亮。高亮在 Worker 里，已有 32 块 / 2 MiB 的缓存；Mermaid 有 30 张图的缓存。解析目前只在组件实例内缓存。先量"滚轮往上读进没画过的历史"那一项，有超过 50 ms 的帧，再加一个按原文缓存解析结果、有大小上限的缓存，不先做。

### 3.8 其他

- **复制与全选**：拖选跨很多屏时，中间的行被钉住，能完整复制。在对话里按 ⌘A，只会选中已挂载的部分（约三屏），现在是所有已取到的行。见待定问题 Q1。
- **无障碍**：`.tr` 仍是 `role="log"`；新消息总在底部且挂载着，读屏照常播报。
- **短对话**：总高度不足窗口时所有行都挂载，行为与现在一致，只是多了一层 `.vrow`。

### 3.9 Bot 页

同一套机制：共用 `useVirtualRows` 和行容器，各自负责自己的行组件与跟随逻辑。差异：

- 连续两条同一方的气泡靠相邻兄弟选择器收紧间距（`.um+.um`、`.um:has(+ .um)`、`.bm+.bm`），有了容器就不是兄弟了。改为渲染时算出 `joined`（与上一条同一方），加类名。顺带去掉 `:has(+ …)`：大页面里这类选择器的样式失效成本高。
- `showBubble` 改用 `scrollToKey`（§3.6）。
- 核对"新消息出现动画"（`fresh`）：`seen` 只在第一次渲染时建立，往上补的历史目前也会播放动画。要求是只有打开后新到的消息才动画，补进来的历史和重新挂载的行都不动。

## 5. 实施步骤

每一步结束时都过一遍单元测试、类型检查，以及 `e2e/run.mjs --since origin/main` 选出的脚本。

**第 0 步：先有一份能信的基线**（小）

- `e2e/conversation.mjs` 的"回到底部后继续跟随"在 main 上一直失败，而它测的正是要改写的那段逻辑。先在断言里打出实际距离，查清是程序的问题还是测试的时序问题，修掉。要求：连续三次通过。
- 用当前分支跑一次 `stress.mjs --scenario deep`，留下 JSON 作改前数字。

**第 1 步：核心机制**（中）

- 写 `virtual.ts` 和它的单元测试：空列表、单行、全部量过、部分估算、窗口在头部、尾部、中间、钉住范围在窗口外、行数变化后的边界。
- 写 `useVirtualRows`、`useRowState`。这一步不接页面，界面无变化。

**第 2 步：会话页接入**（大）

- 按 §3.1～§3.8 和 §4 改 `Chat.tsx`、样式和行组件。
- 改 e2e 与压测脚本，加 §6 的检查。
- 完成标准：§2 的目标全部达到；`conversation`、`content-actions`、`resend`、`markdown`、`send-modes` 通过；明暗两种主题、窄窗口下截图与改前一致。

**第 3 步：Bot 页接入**（中）

- 按 §3.9 改。
- 压测加 Bot 深对话场景（一个 Bot、五千条消息），目标同 §2。
- `bot-messages`、`bot-panels`、`bot-routines`（含跳到运行消息）通过。

**第 4 步：复测与收尾**（小）

- 复测表格测量：屏幕外的行不挂载后，补页和滚动中若仍有它造成的长帧，改为在 `ResizeObserver` 回调里读；没有就不动。
- 更新 desktop-design §9.2 的数字和"做法"一节；记下决策。

## 6. 验证

**压测**（`stress.mjs --scenario deep`，加断言）：

- §2 表中各项。
- 往上读的每一页记录耗时与最长阻塞。
- 读完后：
  - 用滚轮从底部读到顶部，无空白帧（同侧栏的空白检测）；
  - 拖滚动条到顶再回到底，两帧内有行。

**对话 e2e 新增**（真实应用加真实内核）：

- 往上读到窗口外，再用重发托盘"定位到这条消息"：目标出现在视口中间。
- 选中跨三屏的一段文字后继续往下滚，选区内容完整（`getSelection().toString()` 含首尾两行的文字）。
- 展开一个工具组，滚出窗口再滚回来，仍是展开的。
- 往上读时记录视口顶端那一行的位置，上方的行挂载前后移动 ≤ 2 px。
- 原有检查：
  - 打开在底部；
  - 发消息后跟随；
  - 往上读时回复不拉回；
  - 回到底部继续跟随；
  - 悬停栏可点；
  - 静默任务不占脚本；
  - 切回只画最后一页。

**人工过一遍**：

- 真实长会话里快速拖滚动条。
- 改窗口宽度。
- 开关文件面板和浏览器面板。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 估算不准导致画面跳动 | 修正只发生在看不见的上方，由原生滚动锚定补偿，自定义锚点兜底；用"移动 ≤ 2 px"的检查盯住 |
| 跟随到底出问题 | 第 0 步先修好对话 e2e，第 2 步加新检查；跟随规则本身不改 |
| 快速滚动时重新挂载造成卡顿 | 上下各留一屏、按档移动；量到超过 50 ms 的帧再加解析缓存（§3.7） |
| 卸载丢状态 | 展开状态上移（§3.7），焦点与选区钉住（§3.4） |
| 样式漏改造成间距或对齐变化 | §3.2 列出了全部依赖 `.tr` 子元素和相邻兄弟的规则；截图对比 |
| 测试数 DOM 行数的地方失效 | 统一改读 `data-rows`；`run.mjs --since` 选出的脚本都要过 |

## 8. 决策

| 编号 | 决策 | 理由 | 章节 |
|---|---|---|---|
| DD-168 | 对话区只挂载可视区上下各一屏的行；读过的历史数据全部留在内存里，不放掉、不重新取 | 成本随挂载的行数增长，数据本身很小；只限页数的做法每页仍很重，往回看还得重新取 | §1、§3.1 |
| DD-169 | 行留在文档流里，用上下两块空白代替没画的行；不用绝对定位，也不用文件树那套虚拟列表（它按绝对定位排布） | 跟随到底、补页时保持位置、原生滚动锚定、现有样式都能照常工作；需要的只是范围计算和测量，侧栏已有同样的写法 | §3.1、§3.5 |
| DD-170 | 行内的展开状态按行 key 存在会话级，行卸载再挂载后保持 | 虚拟化后行随时会被卸载，状态不能留在组件里 | §3.7 |
