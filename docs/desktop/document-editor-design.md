## 0. 阅读说明

| 术语 | 定义 |
|---|---|
| 文档 | 用户或智能体在 FinxWork 里打开、查看、修改的一个文件（一期只有 PDF） |
| 文档栏 | 会话页里显示文档的一栏，与对话并排（§7.1） |
| 外壳 Shell | 文档栏里与格式无关的部分：标题栏、工具栏、修订记录、保存、引用到对话 |
| 画布 Surface | 文档栏里按格式实现的部分：显示内容、选中、在内容上画标记。每种格式一个 |
| 后端 Backend | 内核里按格式实现的部分：解析、提取、渲染、执行操作、保存。每种格式一个 |
| 锚点 Anchor | 文档里一个位置或一段范围的描述，人和智能体都用它指代内容（§4.2） |
| 操作 DocOp | 对文档的一次原子修改（§4.3） |
| 修订 Revision | 一批操作，由一个人或智能体一次提交，是撤销、审批、显示的单位（§4.4） |
| 工作副本 | 内核为打开的文档保存的副本，修改先落在这里，保存时才写回原文件（§5.2）。每个文件只有一份，所有会话共用 |
| 文档状态 | 工作副本、修订记录、是否有未保存的修改。属于文件（§5.2） |
| 视图状态 | 一个会话的文档栏开着哪份文档、看到哪一页、选中了什么。属于会话（§7.1） |

编号：决策用 DE-xx，待定问题用 EQ-xx。

## 1. 目标与范围

### 1.1 目标

| 编号 | 目标 | 含义 |
|---|---|---|
| G1 | 在对话旁边看文档 | 不用切到别的应用；智能体提到的页、段落一点就到 |
| G2 | 人和智能体改同一份文档 | 两边的修改在同一条修订记录里，同样能撤销、同样能看清改了什么 |
| G3 | 选中内容就能问 | 选一段文字或框一块区域，作为引用带进输入框 |
| G4 | 改动可控 | 智能体的修改照审批模式处理，看得到改前改后；原文件在保存前不变 |
| G5 | 格式可扩展 | 加 Office 时只加一个后端和一个画布，外壳、协议、工具、交互不变 |

### 1.2 一期范围（PDF）

- 查看：连续滚动、缩放、缩略图、目录、搜索、文字选中。
- 引用：选中文字或框选区域，带进输入框。
- 出处：智能体回复里引用的文档内容带出处标记，点一下跳到原文并高亮（§9.4.7）。
- 修改（人和智能体）：高亮、下划线、删除线、便签、自由文本框、手绘、图形；填写表单；页面的插入、删除、旋转、重排；合并其他 PDF。
- 修订记录、撤销与重做、保存与另存为。

### 1.3 不在一期

- **改正文文字**：PDF 没有段落结构，字体通常只嵌了用到的字，改字只能"擦掉再覆盖"，字形和排版会变（§9.3）。一期不提供；以后作为"覆盖式修改"单独提供，并明确告诉用户效果。
- **涂黑**（真正删除内容）放到二期：不可逆，需要单独设计确认流程（§13）。
- 多人协作、云端文档、签名。
- Office 格式（§10 只约束接口，不实现）。

## 2. 设计原则

1. **一份文档，两只手。** 人在界面上的每个动作和智能体的每次工具调用，都变成同一种 DocOp，进同一条修订记录，经同一条路径执行。界面上没有"只有人能做"或"只有智能体能做"的修改。
2. **外壳统一，画布按格式。** PDF 是固定版式，Word 是流式排版，强行用一个画布会两头都做不好。统一的是外壳、锚点、操作、修订、协议和交互约定；画布只负责显示和选中。
3. **能力声明，而不是猜测。** 后端声明自己支持哪些操作（§4.5），工具栏和工具说明都按声明生成。格式不支持的操作不显示，而不是点了报错。
4. **原文件最后才动。** 修改都落在工作副本，保存时才写回原文件。撤销不依赖文件系统。
5. **状态跟着文件，视图跟着会话。** 同一份文件在哪个会话里打开都是同一个状态：一个会话里做的高亮，另一个会话里马上能看到。会话只记自己在看哪份、看到哪。
6. **沿用已有的交互。** 打开文件、审批卡片、步骤行、附件方块、快捷键都用现有的样子（desktop-design §5），不为文档另起一套。

## 3. 总体架构

```
┌────────────────────────────── 页面（React，沙箱） ──────────────────────────────┐
│  对话 ── 输入框（引用方块）                                                       │
│  文档栏：外壳（工具栏 · 修订记录 · 保存 · 引用）                                   │
│          └─ 画布接口 ── PdfSurface（pdf.js） │ 以后：DocxSurface …                │
│        ▲ 协议（doc/*，经 MessagePort）       ▲ 文档字节（finxdoc:// 流式读取）       │
└────────┼─────────────────────────────────────┼─────────────────────────────────┘
         │                                     │ 主进程：只按令牌转发，不解析
┌────────┼─────────────────────────────────────┼──────────── finx serve ───────────┐
│  finx-server：doc/* 方法、文档事件                                                │
│  finx-core：doc_* 工具（延迟加载组 `doc`）· 审批                                  │
│  finx-docs：DocStore（服务级，每个文件一份：工作副本 · 修订日志） ── Backend 接口     │
│                       └─ PdfBackend（PDFium + 我们的版面分析） │ 以后：OfficeBackend  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

| 层 | 统一的部分 | 按格式的部分 |
|---|---|---|
| 页面 | 文档栏外壳、引用、修订记录、保存、快捷键 | 画布 |
| 协议 | `doc/*` 方法、文档事件、Anchor、DocOp 的 JSON | Anchor 与 DocOp 里的格式专属变体 |
| 内核 | DocStore、修订、撤销、审批、工具 | 后端 |

## 4. 统一模型

### 4.1 文档

```ts
type DocInfo = {
  doc_id: string;            // 由原文件的规范路径得出，同一文件在所有会话里相同
  path: string;              // 原文件的规范路径（解析符号链接后）
  format: "pdf";             // 以后："docx" | "xlsx" | "pptx"
  layout: "paged" | "flow";  // PDF 是 paged；Word 是 flow
  pages?: number;            // paged 才有
  outline: OutlineItem[];
  capabilities: Capability[];  // §4.5
  revision: number;          // 当前修订号
  dirty: boolean;            // 工作副本与原文件不同
};
```

### 4.2 锚点

锚点是人和智能体指代内容的共同语言：选中文字、引用、搜索结果、智能体的修改位置，都用它表示。

```ts
type Anchor =
  | { kind: "page"; page: number }
  | { kind: "region"; page: number; rect: Rect }                      // 框选区域，PDF 坐标
  | { kind: "text"; page: number; quads: Quad[]; text: string }       // 选中的文字，quads 是逐行的四边形
  | { kind: "flow"; start: FlowPos; end: FlowPos; text: string };     // 以后的流式文档
```

- **坐标为准**：PDF 的锚点以页面坐标定位，两个引擎在几何上一致（§9.4.1）。
- **带上原文**：文字锚点总带 `text`，由内核按坐标取出，不用 pdf.js 的文字。智能体看到的是"第 3 页：'违约金为合同总额的 20%'"，不是一串坐标；提交时按原文核对，位置变了也能按原文重新定位。
- **短编号**：内核给读出的每段文字一个会话内的短编号（如 `p3.b12`），智能体引用和提交修改时用它，不用抄坐标（§8）。
- **页号从 1 开始**，与界面显示一致，避免智能体和人说的"第 3 页"不一样。

### 4.3 操作

```ts
type DocOp =
  // 批注
  | { op: "annotate"; anchor: Anchor; style: "highlight" | "underline" | "strike"; color?: string; note?: string }
  | { op: "note"; anchor: Anchor; text: string }
  | { op: "text_box"; anchor: Anchor; text: string; font_size?: number }
  | { op: "ink"; page: number; strokes: Point[][]; color?: string; width?: number }
  | { op: "shape"; anchor: Anchor; shape: "rect" | "ellipse" | "line" | "arrow"; color?: string }
  | { op: "remove_annotation"; id: string }
  // 表单
  | { op: "fill_field"; name: string; value: string | boolean }
  // 页面
  | { op: "insert_pages"; at: number; from: { path: string; pages?: number[] } | { blank: true } }
  | { op: "delete_pages"; pages: number[] }
  | { op: "rotate_pages"; pages: number[]; degrees: 90 | 180 | 270 }
  | { op: "move_pages"; pages: number[]; to: number }
  // 元数据
  | { op: "set_metadata"; title?: string; author?: string };
```

- 操作只描述"要什么结果"，不暴露 PDFium 的 API。换引擎时操作不变。
- 每个操作都能算出逆操作或者由后端回放，撤销不依赖文件快照之外的东西（§5.2）。

### 4.4 修订

```ts
type Revision = {
  revision: number;
  author: { kind: "user" } | { kind: "agent"; call_id: string };
  session_id: string;     // 在哪个会话里提交的；人的修订也记，界面据此显示来源并能跳回那个会话
  summary: string;        // "第 3 页添加了 2 处高亮"，由内核按操作生成
  ops: DocOp[];
  anchors: Anchor[];      // 改动的位置，界面用来跳转和闪烁
  at: string;
};
```

- **一个修订是一次提交**：智能体一次 `doc_edit` 调用是一个修订；人的一次拖动、一次填写也是一个修订。
- **撤销按修订**：⌘Z 撤销这份文档最近一个修订，不管是谁、在哪个会话里提交的。这台机器上只有一个人，按文件撤销最符合直觉；智能体的修订也能这样撤掉。
- 修订记录只追加；撤销是加一个"撤销到第 N 版"的标记，重做把它去掉。界面显示有效的修订。

### 4.5 能力声明

```ts
type Capability =
  | "view" | "text" | "search" | "outline"
  | "annotate" | "note" | "text_box" | "ink" | "shape"
  | "forms" | "pages" | "metadata"
  | "redact"          // 二期
  | "replace_text";   // 以后，覆盖式
```

后端在打开文档时给出能力，另外给出 `save_in_place: boolean`：原文件只读、或文件损坏只能修复打开时为 false，只能另存为（§9.4.3）。加密且禁止修改的 PDF 只有 `view` 与 `text`；扫描件没有 `text`，界面提示"这份文件是扫描件"。工具栏按钮和 `doc_edit` 的说明都由能力生成。

## 5. 内核：finx-docs

新 crate，与 finx-browser、finx-desktop 并列。finx-core 只依赖它的接口。

### 5.1 后端接口

```rust
trait Backend: Send + Sync {
    fn format(&self) -> Format;
    fn open(&self, bytes: &[u8], password: Option<&str>) -> Result<Box<dyn OpenDoc>>;
}

trait OpenDoc: Send {
    fn info(&self) -> DocInfo;
    fn text(&self, range: PageRange) -> Result<Vec<TextBlock>>;     // 带锚点的文字
    fn markdown(&self, range: PageRange) -> Result<String>;          // 给智能体读，由版面分析生成（§9.2.3）
    fn find(&self, query: &str) -> Result<Vec<Anchor>>;
    fn render(&self, anchor: &Anchor, dpi: u32) -> Result<Png>;      // 给智能体看，也用于审批预览
    fn apply(&mut self, ops: &[DocOp]) -> Result<Applied>;           // 返回改动的页与锚点
    fn save(&self) -> Result<Vec<u8>>;                               // PDF 用增量保存
}
```

### 5.2 DocStore：工作副本与修订

- **归属**：文档状态属于文件，不属于会话（DE-10）。DocStore 在常驻服务里，每个文件只有一个实例，打开了它的会话都引用这一个。
- **位置**：`$FINX_HOME/docs/<doc_id>/`，`doc_id` 由原文件的规范路径得出。里面是 `base.pdf`（上次保存或打开时原文件的副本）、`revisions.jsonl`（修订日志）、`current.pdf`（当前状态）、`meta.json`（原路径、打开时的修改时间与哈希）。删除会话不影响它。
- **当前状态** = `base` 依次应用有效修订。每次提交后写 `current.pdf`；撤销时从 `base` 回放到目标修订（PDF 的回放在毫秒级，必要时每 20 个修订存一个检查点）。
- **并发**：多个会话（人或智能体）对同一文档的提交在 DocStore 里排队，一次执行一个，修订号连续。提交带 `base_revision`，落后时先按锚点的原文重新定位，定位不了返回 `doc_stale`（§6）。
- **保存**：先写同目录的临时文件再改名替换，保留权限与扩展属性；加密和带签名的文件有专门的限制（§9.4.3）。写之前核对原文件的修改时间和哈希与 `meta.json` 一致；不一致说明被外部程序改过，不覆盖，返回 `doc_conflict`，界面让用户选"另存为"或"重新载入"。保存后 `base` 换成刚保存的内容，修订记录保留但标出保存点。
- **外部改动**：文档打开期间监视原文件；没有未保存的修改时自动重新载入，有时在文档栏顶部提示，处理方式同上。
- **原文件移动或改名**：`doc_id` 跟着路径走，原路径找不到时，打开新路径按新文件处理；旧目录里未保存的修改在文档栏提示"有一份未保存的修改，原文件已不在"，可以另存为。
- **清理**：已保存且 30 天没打开的文档目录自动删除；有未保存修改的不删。设置里能看到占用并手动清理。
- 会话恢复时，文档栏重新打开它上次在看的文档，看到的是文档当前的状态（可能已被其他会话改过）。

### 5.3 审批

`doc_edit` 是写类工具，按会话的审批模式处理，与 `edit` 一致：

| 模式 | 智能体的修订 |
|---|---|
| 询问 | 弹审批卡片，第二行是改动页的改前/改后缩略图（§7.5） |
| 自动编辑 | 直接提交到工作副本 |
| 绕过权限 | 同上 |

- 改到工作副本是可撤销的，所以"自动编辑"下不问；**写回原文件**（`doc_save`）按 `write` 的规则处理，受保护路径、项目信任照常生效。
- 人在界面上的修改不经过审批，与人在编辑器里改代码一样。

## 6. 协议

新增方法（客户端 → 服务端），都带 `session_id`（用来记修订的来源和会话的视图状态）：

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `doc/open` | path、password? | DocInfo、token | 文件已被打开（任何会话）时接入同一个 DocStore，否则新建；token 用于读字节（§7.3） |
| `doc/close` | doc_id | `{}` | 这个会话不再看它；文档状态保留，没有会话再引用时 DocStore 卸载，目录留在磁盘上 |
| `doc/view` | doc_id、page、selection? | `{}` | 记下这个会话的视图状态（看到哪一页、选中了什么），恢复会话和给智能体的上下文块（§7.4）都用它 |
| `doc/resolve` | doc_id、page、quads 或 rect | Anchor | 人选中或框选后，由内核按坐标取出文字，生成锚点（§9.4.1） |
| `doc/annotations` | doc_id、pages | 每页的批注 | 批注层的数据（§9.4.2） |
| `doc/apply` | doc_id、ops、base_revision | Revision | 人的修改。base_revision 落后时（智能体刚提交）先重定位锚点，失败返回 `doc_stale` |
| `doc/undo`、`doc/redo` | doc_id | revision | |
| `doc/save` | doc_id、path? | `{}` | path 给出时是另存为 |
| `doc/revisions` | doc_id | Revision[] | |
| `docs/list` | — | 每份文档的 DocInfo 与引用它的会话 | 设置里的占用与清理；有未保存修改的文档一览 |

新增事件：

| 事件 | 发给 | 内容 | 用途 |
|---|---|---|---|
| `doc_opened` | 这个会话（`session/event`） | DocInfo | 智能体用 `doc_open` 打开时，界面打开文档栏 |
| `doc/changed` | 所有接入了引用这份文档的会话的连接（通知，不属于某个会话） | doc_id、Revision 或撤销/重做后的修订号、changed_pages、改动页的批注、是否需要重新载入 | 任何会话里的提交、撤销、重做之后，所有显示它的文档栏按 §9.4.2 刷新 |
| `doc/saved`、`doc/reloaded` | 同上 | doc_id、path | 保存点、外部改动后的重新载入 |

- **为什么 `doc/changed` 不走 `session/event`**：文档状态不属于某个会话，按会话发会让同一个修订在多个会话里各发一份、各记一份。按文档发、每个连接只收一份，与 `sessions/changed` 的做法一致。
- **会话日志里记什么**：只记本会话里发生的事，`doc_edit` 的工具调用照常记录（含修订号与摘要）。别的会话里的修改不进本会话日志，智能体通过 `doc_read` 的修订摘要知道（§8）。
- 修订的完整内容在文档目录的 `revisions.jsonl`。

## 7. 界面

### 7.1 文档栏的位置

- 文档栏就是**文件面板**（file-panel-design §3）：PDF 和其他文件是同一排标签，从目录树、对话里的文件方块、引用打开的都进这里；不再有单独的文档栏（2026-11-03 合并）。PDF 由 pdf.js 显示，标签条下面多一行自己的工具（§7.2）；其他文件没有这一行。
- 文档栏在对话**右侧**，与对话并排，中间可拖动分隔线。打开时侧栏保持原样（不自动收起，2026-11-03 改），信息卡片让位。
- 窗口太窄放不下时（对话 + 文档栏的最小宽度），文档栏铺满内容区，对话收成右下角的输入框和一个"返回对话"按钮。
- 文档栏的**视图**属于会话：切换会话时显示那个会话在看的文档、停在它上次看到的页；面板的标签切换这个会话打开过的其他文件。智能体打开的文档只加一个标签，不弹出面板。
- 文档栏的**内容**属于文件：两个会话看同一份 PDF，看到的是同一个状态，一边改了另一边马上更新。

### 7.2 外壳

- **两行**：第一行是文件面板共用的标签条，右端是文件的"⋯"菜单和目录树开关（file-panel-design §3.2）；第二行是 PDF 自己的工具：目录与缩略图、框选、页码、缩放、搜索（⌘F）。以后的未保存圆点、修订记录、批注工具按能力（§4.5）加在第二行。
- **工具栏**：选择（默认）、高亮、批注、文本框、画笔、图形、页面。按能力显示（§4.5）。颜色等次要选项点工具后出现在工具栏下方一行。
- **修订记录**：标题栏里的时钟按钮，展开为右侧的一列：每行是谁（人或智能体的图标）、摘要、时间；不是本会话提交的，下面一行灰字写来源会话的标题，点它切到那个会话。点一行跳到改动处；悬停显示"撤销到这里"。
- **保存**：⌘S。未保存的修改在关闭会话、退出应用时不会丢（工作副本在），所以不弹"是否保存"，只在标题旁一直显示圆点。

### 7.3 PDF 画布

- 用 **pdf.js** 显示页面正文：文字层（选中、复制、搜索高亮）、按需渲染、目录与缩略图、表单。
- 批注不由 pdf.js 画，而是画在文档栏自己的批注层上，可以点选、拖动、删除（§9.4.2）。
- 选中文字后，页面把四边形交给内核（`doc/resolve`）换成锚点；pdf.js 自己的选中文字只用于复制（§9.4.1）。
- 字节经 `finxdoc://<token>/current.pdf` 读取。主进程注册这个 scheme（与已有的 `app://` 同样做法），只认 `doc/open` 给出的令牌，令牌只对应 `$FINX_HOME/docs/<doc_id>/` 里的那份工作副本；支持 Range 请求，大文件按需读取。页面拿不到任意路径。
- **修改的即时反馈**：人画高亮时，批注层先画出来（乐观显示），`doc/apply` 返回后换成内核给的正式数据，不重载页面；失败时撤掉并提示原因。只有页面操作和外部改动才重新载入（§9.4.2）。

### 7.4 和对话的联动（G1、G3）

- **打开**：对话里的文件方块、工具步骤里的路径、模型回复里的文件链接，是 PDF 时点它在文档栏打开（今天是在访达中显示）；⌥ 点击仍在访达中显示。从访达拖进窗口也打开。
- **引用**：选中文字或框选区域后，出现一个小浮条："问 finx"（⌘L）与"复制"。点"问 finx"后，输入框上方多一个引用方块，和附件方块同样大小，写着"合同.pdf · 第 3 页"和前两行原文，悬停有 ×。发出时作为一个文本块附在消息里：路径、锚点、原文；框选区域额外附一张裁剪图（模型支持图片时）。
- **智能体在改**：`doc/changed` 到达时，文档栏滚到改动处并让锚点闪烁一次；人正在别处阅读时不抢滚动，只在标题栏显示"finx 修改了第 5 页 ›"。修改来自另一个会话时，不滚动，只显示提示，写明来源会话。
- **出处标记**：模型回复里的文档引用链接（§8）画成一个小的上标标记，悬停显示"合同.pdf · 第 12 页"和原文的前一行，点它在文档栏跳到那里并高亮出处；文档没打开时先打开。锚点已经找不到时（页被删了），标记变灰，悬停说明原因。
- **步骤行**：对话里 `doc_edit` 的步骤行是"在 合同.pdf 第 3 页添加了 2 处高亮"，点它在文档栏跳到那里；展开看操作列表。
- **当前上下文**：文档栏打开时，每次发消息都带一个很短的上下文块"正在看：合同.pdf 第 3 页"，模型就能理解"这一页""这段"。不带全文。

### 7.5 审批卡片

沿用 desktop-design §5.5 的三行卡片，只换第二行：

- 第一行："修改 合同.pdf？" + 修订摘要。
- 第二行：每个改动页一对缩略图，改前在左、改后在右，改动处描边；超过 3 页时注明"还有 N 页"。点缩略图在文档栏里放大对比。
- 第三行：拒绝… / 本会话都允许 / 允许 ⌘↩，与其他审批相同。

## 8. 智能体工具

与浏览器、电脑操控一样作为延迟加载的组 `doc`（computer-use-design §5），系统提示词里只占一行目录。

| 工具 | 类别 | 说明 |
|---|---|---|
| `doc_open(path)` | 只读 | 打开文档（文档栏随之打开），返回 DocInfo 与目录 |
| `doc_read(doc, pages?, format?)` | 只读 | 按页读文字，`markdown`（默认）或带锚点的 `blocks` |
| `doc_find(doc, query)` | 只读 | 返回锚点和上下文 |
| `doc_view(doc, anchor, dpi?)` | 只读 | 渲染一页或一块区域为图片，看版式、图表、扫描件 |
| `doc_edit(doc, ops)` | 写 | 一次提交一个修订；说明按能力生成 |
| `doc_save(doc, path?)` | 写 | 写回原文件或另存为，按 `write` 审批 |

- **别人改过的地方**：文档可能被其他会话或人改过。`doc_read`、`doc_open` 的结果开头列出智能体上次读之后的修订摘要（最多 10 条，"第 7 页：用户添加了 3 处高亮"），智能体不会对"自己没做过的修改"感到困惑。
- **和 `read` 的关系**：`read` 读到 PDF 时，结果末尾提示"用 doc_read 按页读取"，而不是报"二进制文件"。
- **锚点的来路**：智能体的锚点只能来自 `doc_read`、`doc_find` 或用户的引用，`doc_edit` 里用短编号（`p3.b12`）或"短编号 + 其中的一段原文"指定位置。内核按原文核对（§9.4.1），对不上时报错并给出最接近的位置，避免高亮到错的地方。
- **引用出处**：使用规则要求智能体在回复里引用文档内容（尤其是数字）时附上出处链接 `[第 12 页](finxdoc:<doc_id>#p12.b3)`。界面把它画成出处标记（§7.4）；命令行里它就是一段普通的 Markdown 链接，仍然可读（DE-13）。

## 9. PDF 的实现

### 9.1 引擎分工

| 用途 | 引擎 | 理由 |
|---|---|---|
| 界面显示、文字层、搜索 | pdf.js（页面里） | 成熟，自带查看器的全部交互，Apache-2.0 |
| 读、修改、保存、给智能体渲染、锚点字框 | PDFium（内核里，零期后改定，DE-16） | 增量保存、保留加密、不破坏签名、表单外观、内存都过了零期验证（§9.2.2）；读出的原文在真实研报上比 pdf_oxide 准确（§9.2.3）；BSD-3 |
| 版面分析（行、块、阅读顺序、标题） | 我们自己（`PdfBackend` 里，基于 PDFium 的字框，DE-17） | PDFium 不做版面分析 |

零期最初的选型是 pdf_oxide 一家包办，后来改为 PDFium 写、pdf_oxide 读，最后定为全部 PDFium。过程与数据见 §9.2.1～§9.2.3。

界面（pdf.js）与内核（PDFium）渲染出来可能有细微差别。用户看到和保存的始终是同一份 PDF 文件，差别只影响智能体 `doc_view` 看到的图，可以接受。

### 9.2.1 零期验证结果（2026-11-02）

验证程序在 `tools/doc-spike/`（不属于 finx 工作区），对照 pdf_oxide 0.3.78（本地源码）。三个独立阅读器：pdf.js 5.4（Node 渲染）、PDFKit（预览.app 用的引擎）、poppler。本机没有 Acrobat，Acrobat 一项留待人工核对。语料：自己生成的中文报告（CoreText 嵌入苹方，含两栏与表格）、500 页 53 MB 与 1000 页的大文件、手写的 AcroForm，加上 pdf_oxide 仓库的样本（其中 `1.pdf` 是一份真实的中文券商研报）。

| 编号 | 结果 | 实测 |
|---|---|---|
| V1 中文批注 | **不过关** | pdf_oxide 写的批注都没有外观流（它有 `AppearanceStreamBuilder`，但写批注时没有调用）。文本框：pdf.js 中英文都不显示；poppler 显示英文，中文只剩"12.5%"；只有 PDFKit 正确。文本框的 `/DA` 只能是 Helvetica 这类标准字体 |
| V2 加密与签名 | **不过关** | ① pdf_oxide 写出的 AES-256 加密文件缺少 R6 必需的 `/Perms`：pdf.js 打不开，PDFKit 显示空白，只有 poppler 正常。② 加密文件改过之后整份重写，加密消失（两个样本都是）。③ 加密文件拒绝增量保存。④ 它自己签名的文件没有签名字段（无 AcroForm），poppler 认不出签名，无法用它造样本；但由 V7 可知：整份重写必然破坏签名，增量保存又写不出批注，所以**带签名的文件目前无法在不破坏签名的前提下加批注**。真实签名文件待补测 |
| V3 坐标与文字 | **有条件过关** | 按"四边形内的字符"取文字，与 pdf.js 归一化后比对：生成的中文报告 100%（259 段），真实中文研报 98.1%（1081 段），英文论文 95.0%（3742 段），多栏表格 100%。前提是不用 `extract_chars`（它把 ﬁ、ﬃ 等连字和部分字形输出成"�"，中文报告上只有 39%），而用 `extract_spans` 加每段的 `char_widths` 累加出字位。剩下的不一致：研报模板里叠在正文上的隐藏标签（`[Table_Summary]`）、TeX 用单独字形拼的重音（´e）、长段落里字位累加的漂移造成边界多一个或少一个字。竖排文字未覆盖 |
| V4 大文件 | **时间过关，内存不过关** | 500 页 53 MB：打开约 0.25 s；从基础版本回放 20 个修订并整份重写 0.40 s（目标 < 1 s）；不改动的整份重写 0.12 s。单次提交若每次重新打开约 0.4 s，常驻打开时只剩写出的 0.12 s。**进程峰值内存 570～800 MB**（目标 < 300 MB）；1 MB 的 500 页文件只有 43～56 MB，内存与文件大小（图片）成正比 |
| V5 批注外观 | **过关（有保留）** | 高亮、下划线、删除线、手绘、矩形、椭圆、直线虽然没有外观流，三个阅读器都自己补画，样子一致。便签的图标三者各不相同；Acrobat 未核对 |
| V6 表单 | **英文过关，中文不过关** | 文本框与复选框的值都写对了，增量保存与整份重写都可以（表单走 `modified_objects`）。字段外观用 Helvetica 生成：中文值在 pdf.js 里是乱码，poppler 里空白，只有 PDFKit 正确。打开 `cjk-form-fonts` 对字段外观**没有作用**；它只作用于压平：压平后中文在三个阅读器里都正确，但**复选框的勾丢了** |
| V7 增量保存 | **不过关** | `write_incremental` 只写 `modified_objects` 和元数据，经 `save_page` 加的批注、页面改动都不写（`document_editor.rs:1597`）：保存后文件只多一段空的 xref，批注全部丢失。整份重写正常 |
| V8 损坏与超大 | **有条件过关** | 都没有崩溃。1000 页打开 0.53 s。截掉 30% 的 53 MB 文件修复打开要 **12.5 s**，第 1 页的文字**悄悄变成乱码**（字体对象丢了）；随机改坏 40 个字节的文件同样悄悄出乱码；破坏 `startxref` 的文件能正常修复 |
| V9 体积 | 记录 | 带 `rendering` 与 `signatures` 的验证程序 11.1 MB（`signatures` 我们用不到）；加 `cjk-form-fonts` 再多 5.9 MB，到 17.0 MB |

**总的结论**：pdf_oxide 适合做**读**的一侧——提取文字（用 spans）、给智能体渲染、读表单、页面结构；作为**写**的一侧现在还不能直接用：批注没有外观流、增量保存写不出批注、加密写出的文件不合规。所以写入路径要由我们补齐或换引擎（DE-15、EQ-10）。**后续**：读取侧也发现了数据错误（§9.2.3），最终不用 pdf_oxide。PDFium 对照（§9.2.2）之后写入改用 PDFium（DE-16），下面第 2、3、5 条随之解决，第 1 条只剩中文字体子集。

对方案的改动：

1. **外观流自己生成**（DE-15）：文本框、便签、表单字段的外观由 `PdfBackend` 生成，中文用嵌入的字体子集。pdf_oxide 压平表单时已经能嵌入中文字体，这部分可以复用或照着做；高亮等类型调用它现成的 `AppearanceStreamBuilder` 即可（只是没接上）。
2. **增量写入自己做或修上游**（DE-15）：把新增和改动的对象（批注、页面字典的 `/Annots`、表单）追加到文件末尾、写 xref 与 trailer。这是带签名文件能加批注的前提，也是保存快的前提。
3. **加密**（DE-14 收紧）：不用 pdf_oxide 写加密。加密的文件能看、能在工作副本里批注，不能保存回原文件；另存为只能存成不加密的，并明说。
4. **文字锚点**（§9.4.1 补充）：内核用 spans 和字宽算字位，不用 `extract_chars`；`doc/resolve` 除了文字，还返回内核认定的字框，界面**按这些字框重画选区**——人看到被选中的，就是引用出去的那几个字。过滤看不见的文字（渲染模式 3、被裁掉的、与正文重叠的模板标签）。漂移的根治靠修上游的 `extract_chars`（连字的 ToUnicode 多字符映射）。
5. **内存**（§9.4.5 补充）：DocStore 每个文件只持有一个解析后的实例，空闲 5 分钟卸载；同时打开的大文件（> 20 MB）超过 2 个时先卸载最久没用的。上线前用单实例重测，目标仍是 < 300 MB。
6. **损坏文件**（§9.4.5 补充）：打开超过 3 s 先显示载入中、可取消；pdf_oxide 走过修复路径时，文档栏顶部提示"这份文件可能已损坏，显示和提取的文字可能不准确"，智能体读到的结果开头带同样的提醒。
7. **`cjk-form-fonts` 不用**（EQ-08 结案）：它解决不了字段外观，压平还会丢复选框。外观需要的中文字体由我们按需取系统字体子集嵌入，不随程序打包。

### 9.2.2 PDFium 对照（2026-11-02，EQ-10）

同一套用例在 PDFium 上重跑：PDFium 156.0.8076（pdfium-binaries 构建，经 pypdfium2 5.14 调用原始的 `FPDF*` 接口），脚本 `tools/doc-spike/scripts/pdfium_check.py`。签名样本用 `cryptography` 手工生成（AcroForm 签名字段 + 分离式 PKCS#7，增量追加），poppler 校验为"Signature is Valid"，补上了 EQ-11 缺的样本。

| 编号 | pdf_oxide | PDFium | PDFium 的实测 |
|---|---|---|---|
| V1 中文批注 | 不过关 | **有路** | 普通文本框（FreeText）同样不生成外观，pdf.js 不显示。但"图章批注 + 文字对象 + 嵌入字体"（`FPDFText_LoadFont` + `FPDFAnnot_AppendObject`）在三个阅读器里中文都正确。PDFium 嵌入整个字体、不做子集：用 Arial Unicode（23 MB）时 3 页的文件变成 15 MB，所以字体子集要我们先做好再交给它 |
| V2 加密 | 不过关 | **过关** | pypdf 生成的标准 AES-256 文件、仓库里的 AES 样本：加批注后增量保存与整份重写都**保留原加密**，三个阅读器用密码打开，批注内容都正确解密。PDFium 不能新建加密，我们也不需要 |
| V2 签名 | 不过关 | **过关** | 签名文件上加批注、增量保存：签名仍然有效（签名范围不变）。整份重写则摘要不符，签名失效（预期之中，pdf_oxide 整份重写也一样） |
| V3 坐标与文字 | 有条件过关 | 相当 | 用 `get_text_bounded` 按框取字：生成的中文报告 100%，真实研报 93.3%，英文论文 95.2%，多栏表格 100%。不一致的类别与 pdf_oxide 相同（隐藏的模板标签、拼出来的重音），换引擎解决不了 |
| V4 大文件 | 内存不过关 | **过关** | 53 MB、500 页：打开 0.002 s（按需加载），加一个高亮并增量保存 0.054 s，加 20 个后整份重写 0.067 s，**进程峰值 92 MB**（pdf_oxide 570～800 MB） |
| V5 批注外观 | 过关（有保留） | 过关（有保留） | 高亮、下划线、删除线、手绘三者一致；矩形、椭圆没有外观流，pdf.js 不画（PDFKit、poppler 画了），需要我们给出外观 |
| V6 表单 | 中文不过关 | **基本过关** | 经表单填写环境（`FORM_ReplaceSelection`）填写，值正确，PDFium 自己生成字段外观，增量保存。中文在 PDFKit、poppler 里正确，在 Node 的 pdf.js 里是方框：PDFium 只**引用**了系统的宋体、冬青黑体，没有嵌入。在别的电脑上能否显示取决于对方有没有字体补位，需要我们把字体子集嵌进去 |
| V7 增量保存 | 不过关 | **过关** | 原文件字节原样保留，批注、表单都追加在末尾 |

**结论（EQ-10 结案）**：写入改用 PDFium（DE-16；§9.2.3 进一步改为读写都用 PDFium）。它补上了 pdf_oxide 写入侧的全部硬伤——增量保存、保留加密、不破坏签名、表单外观、内存——剩下要我们做的只有一件事：**中文字体子集**，用在文本框（图章 + 文字对象）和表单字段的外观里。

分工：

| 用途 | 引擎 |
|---|---|
| 修改与保存（批注、表单、页面操作、增量写入） | PDFium |
| 给智能体渲染（`doc_view`）、审批卡片的缩略图 | PDFium（比 pdf_oxide 的渲染成熟，也省得再带 tiny-skia） |
| 锚点的字框（`doc/resolve`） | PDFium 的逐字字框（`FPDFText_GetCharBox`），与写入用同一个解析结果 |
| 给智能体读（原文 + 我们的版面分析） | PDFium（§9.2.3 修订；原为 pdf_oxide） |
| 界面显示 | pdf.js（不变） |

代价与注意：

- PDFium 是 C++ 原生库（约 5 MB，三个平台各一份），Rust 里经 `pdfium-render` 动态加载；随应用打包、签名、核对哈希，与 agent-desktop 的做法一样（computer-use-design §4）。
- PDFium 的接口**不是线程安全的**，崩溃也接不住：所有 PDFium 调用放在单独的工作进程里排队执行（§9.4.8）。
- 普通文本框（FreeText）不用 PDFium 的默认外观，中文文本框写成"带外观的 FreeText"（外观由图章同样的方式生成后经 `FPDFAnnot_SetAP` 挂上）还是直接用图章，原型阶段再定；矩形、椭圆的外观我们给出。
- §9.2.1 里"增量写入自己做或修上游"（第 2 条）、"不用 pdf_oxide 写加密"（第 3 条）、内存（第 5 条）随之解决；第 1 条只剩中文字体子集。

### 9.2.3 读取对照：给智能体读也用 PDFium（2026-11-02）

§9.2.2 原本把"给智能体读"留给 pdf_oxide，理由是它能输出 Markdown、识别阅读顺序与表格，但这个理由没有实测。用真实的中文券商研报（`1.pdf`，国泰君安，Aspose 生成）第 1 页对比 pdf_oxide 的 `to_markdown` 与 PDFium 的原文（`get_text_range`）：

| 原文（PDFium） | pdf_oxide 的 Markdown |
|---|---|
| 维持在 20-25%之间 | 维持在 20 25%之间 |
| 达到了 10%-20%，其中打新贡献在 5%-10% | 达到了 10% 20%，其中打新贡献在 5% 10% |
| 王政之(分析师) | 王政之分析师 |
| 021-38674944 | 021 38674944 |
| 三和管桩（003037.SZ） | 三和管桩（**003037.SZ** |

- **原因**：研报里的"-""(""）"等标点用另一种字体，pdf_oxide 把它们切成只有一个标点的文字段（提取本身不丢：全文 7692 个字符与 pdf.js、PDFium 完全一致），**转 Markdown 时这些单字的段被扔掉**，第 1 页的文字段里有"-"，Markdown 里一个也没有。对金融文档，"20-25%"读成"20 25%"是数据错误。
- **其他问题**：页边竖排的"证券研究报告"被插进正文段落（"研 比超过一半""究 比从较均衡"）；"证书编号"被判成二级标题。
- **PDFium**：按内容顺序给出原文，标点完整，段落连贯，页边竖排的字集中在页末，不打断正文；没有标题、表格等结构。
- 这个标点问题报给 pdf_oxide 上游，不影响我们的选型。

**结论（DE-16 修订）**：读与写都用 PDFium，不再引入 pdf_oxide。理由：

1. **只有一套文字模型**：智能体读到的文字、锚点的短编号、选区的字框、批注写入的位置，都来自同一次解析（DE-11 的本意）。两个引擎分工，内核里就又有两套文字。
2. **一个依赖、一个工作进程**：内存 92 MB（pdf_oxide 570～800 MB），崩溃隔离只做一份。
3. pdf_oxide 被看好的那部分（Markdown、表格）恰恰在真实样本上出了数据错误，而表格识别从未验证。

代价：PDFium 只给原文与逐字字框，版面分析由我们在 `PdfBackend` 里补一层（DE-17）：

- **行与块**：按字框把字聚成行、行聚成块，处理多栏；页边的竖排字、页眉页脚、页码单独归类，不进正文（研报的"请务必阅读正文之后的免责条款部分"、竖排的"证券研究报告"）。
- **标题**：按字号与字重判断，只标明显的。
- **表格**：一期不做自动识别；复杂表格由智能体用 `doc_view` 看图，并配合出处标记（DE-13）让人核对。以后在字框上加简单的表格识别。
- **输出**：`doc_read` 的 `markdown` 由这层生成（段落、标题、页码分隔），`blocks` 带短编号与字框。PDFium 的内容顺序在研报上已经可用，这一层可以先做薄。

### 9.3 改正文文字（以后）

不论哪个引擎，改 PDF 里的字都只有两种做法：擦掉原文所在的矩形再叠一段新文字（pdf_oxide 的 `set_text`），或改写原来的文字对象（PDFium 的 `FPDFText_SetText` 加 `FPDFPage_GenerateContent`，会重写整页的内容流）。两种都有同样的问题：新字可能不在嵌入的字体子集里，只能换字体；不会重新排版，新文字较长时会溢出。所以这项能力以后单独提供为"覆盖式修改"，界面上明确标出，并在审批卡片里展示改后的效果。

### 9.4 技术难点与对策

按风险从高到低排列。

#### 9.4.1 两个引擎看到的文字不一样

pdf.js 给界面提取文字层，PDFium 给智能体提取文字。两者对同一页的文字顺序、连字（ﬁ）、行尾连字符、多栏、中文之间的空格，处理都可能不同。不处理的话，人选中的"那段话"与智能体读到的对不上，智能体说"高亮这句"时画到别处。

对策（DE-11）：

- **坐标为准，文字核对。** 锚点的根本是 PDF 页面坐标里的四边形（§4.2）。两个引擎在几何上一致，在文字上不一定。
- **文字只有一个来源：内核。** 人在界面上选中后，页面只把四边形交给内核（`doc/resolve`，§6），内核用 PDFium 的逐字字框取出这块区域里的文字，填进锚点的 `text`，同时返回它认定的字框，界面按这些字框重画选区（零期 V3 的结论，§9.2.1 第 4 条）。引用方块、发给模型的原文、修订摘要都用这份文字。pdf.js 的文字层只负责让人能选、能复制、能搜。
- **宽松匹配。** 智能体提交的文字锚点，内核把 `text` 与坐标处的文字都归一化（Unicode NFKC、合并空白、去掉行尾连字符、去掉中文之间的空格）后比对；对不上时在同一页按原文找最接近的位置，找到就报告给智能体"位置有偏差，最接近的是……"，不自动改。
- V3 验证这条路；不过关时连文字层也改由内核提供（§9.2）。

#### 9.4.2 修改之后怎么刷新

pdf.js 不能只替换一页，整份重新载入会闪，滚动和缩放要重新恢复。每画一个高亮就重载，体验不可接受。

对策（DE-12）：按修改的类别走两条路。

| 修改 | 画在哪里 | 刷新方式 |
|---|---|---|
| 批注（高亮、下划线、删除线、便签、文本框、手绘、图形） | 文档栏自己的批注层，数据来自内核的批注列表（`doc/annotations`）。pdf.js 只画页面正文，不画这些类型的批注 | 不重载：`doc/changed` 带来改动页的批注，批注层就地更新 |
| 表单 | pdf.js 的表单层 | 更新字段值，不重载 |
| 页面（插入、删除、旋转、重排）、外部改动、撤销跨过页面操作 | pdf.js | 重新载入（Range 请求，只取看得见的部分），恢复到原来的页与相对位置 |

- 批注层是可以交互的：点选、拖动、改颜色、删除，都生成 DocOp，正好对应"一份文档两只手"。
- 人画批注时批注层先画出来（乐观显示），`doc/apply` 返回后换成内核给的正式数据；失败时撤掉并提示原因。
- 自己画批注和其他阅读器画外观流，样子可能有细微差别；以保存后的文件为准，V5 核对。
- **考虑过不用的做法**：pdf.js 自带批注编辑器，也能在页面里直接写出 PDF。用它会让人的修改绕开内核，人和智能体走两条路，违背 DE-02。它的交互可以借鉴，写文件必须在内核。

#### 9.4.3 保存弄坏文件

对正式文件来说，这是最不能出的错。三处要专门处理（零期已验证，§9.2.2）：

- **加密**：用 PDFium 保存时保留原有加密，增量保存与整份重写都验证过；pdf_oxide 写出的加密文件不合规，不用它写（DE-14）。工作副本 `current.pdf` 同样是加密的，经 `finxdoc://` 给 pdf.js 时由页面在 `doc/open` 的结果里拿到一次性的口令，口令不落盘、不进日志。
- **数字签名**：只有增量保存（只往文件末尾追加）能保住原签名有效（PDFium 已验证）；整份重写会让签名失效。带签名的文件只走增量保存；撤销以后必须整份重写的情况（例如撤销了已保存的修订），保存前提示"原签名将失效"。
- **原子写入**：先写到同目录的临时文件，再改名替换；保留原文件的权限与扩展属性；iCloud、网络盘上的文件单独测。

#### 9.4.4 中文

文本框、便签框、表单字段里写中文，需要把字形嵌进文件，否则别的电脑上可能显示成方框或空白（零期：PDFium 只引用宋体、不嵌入时，pdf.js 显示方框）。中文字体很大（几十 MB），只嵌用到的字（子集），一个批注通常只有几 KB；PDFium 整个嵌入时，3 页的文件涨到 15 MB（§9.2.2）。

**字体来源（DE-18）**：用系统自带的字体，不随应用打包。只用嵌入许可（OS/2 表的 `fsType`）允许放进可编辑文件的字体：

| 系统 | 字体 | 嵌入许可 | 用法 |
|---|---|---|---|
| macOS | 冬青黑体 Hiragino Sans GB W3 / W6 | 可编辑嵌入 | 默认（常规 / 粗体） |
| macOS | 黑体 Heiti SC Light | 无限制 | 冬青黑体缺字或不在时 |
| macOS | 宋体 Songti SC Light / Bold | 可编辑嵌入 | 需要宋体时 |
| macOS | 苹方 PingFang SC（各字重） | 仅预览打印 | **不用**：嵌了它的文件按许可不应再编辑；它还是按需下载的系统资源，不保证每台电脑都有 |
| macOS | 宋体 Songti SC Black | 禁止嵌入 | 不用 |
| Windows、Linux | 候选为微软雅黑、Noto Sans CJK | 待核对 | 做到这两个平台时读 `fsType` 确认后补上 |

- **找字体**：经系统的字体服务按名字查（macOS 用 CoreText），不写死路径；`.ttc` 里按名字挑出要的那一个字重。
- **做子集**：在 Rust 里做（如 `subsetter`），按批注的文字取字形，生成小字体交给 PDFium 嵌入。
- **缺字**：首选字体没有的字（生僻字、符号），按上表的顺序换下一个字体，一个外观里可以有多个子集。
- **再次编辑**：子集只含当时的字。批注的文字改了，按新内容重新生成这个批注的外观和子集。每个批注各带一个子集，字会有重复，但每个只有几 KB。
- 每次选用前读一遍 `fsType`，许可变了（系统更新换了字体）就跳到下一个候选。

#### 9.4.5 大文件的性能

招股书、年报动辄 500 页、几十 MB。

- 撤销靠"从基础版本回放"，大文件上可能要几秒。每 20 个修订存一个检查点，回放从最近的检查点开始；平时的提交只对 `current.pdf` 做增量追加，不重写整份。
- 智能体读文档用 `doc_read` 按页分段，不一次读完；`doc_find` 先定位再读。
- 界面经 Range 请求按需读取，看不到的页不渲染。
- 零期实测（PDFium，53 MB、500 页）：打开 0.002 s，一次提交（加批注 + 增量保存）0.054 s，加 20 个后整份重写 0.067 s，进程峰值 92 MB（§9.2.2）。检查点间隔可以放宽到 50 个修订。

#### 9.4.6 多个会话同时改

文档状态共用之后（DE-10），智能体读完文档、准备提交的这段时间里，人可能删了一页，它手里的页码就错位了。

一期正文文字不会变（DE-06），会变的只有页码和批注。所以提交落后时的重新定位（§5.2）只需要两步：按其间的页面操作换算页码，再按原文核对。不需要 OT、CRDT 这类协同编辑的合并算法。以后支持改文字或 Office 时，再引入更完整的方案。

#### 9.4.7 表格和数字是否准确

金融用户最在乎财务报表里的表格和数字。一期不做表格的自动识别（§9.2.3）；无论提取多准，模型都可能抄错数字。

对策（DE-13）：不只追求提取精度，而是**让智能体说出的每个数字都能追溯到原文**。`doc_read` 的 `blocks` 和 `doc_find` 的结果里每段带一个短的锚点编号，智能体在回复里引用时写成链接（§8），界面把它画成可点的引用标记，点一下文档栏跳到那里并高亮出处，人可以自己核对。扫描件先用 `doc_view` 让模型看图；OCR 以后再做。

#### 9.4.8 依赖的风险

只有一个引擎：PDFium（读、写、渲染、字框）。

- **PDFium 是 C++ 原生库**：恶意或损坏的文件让它崩溃时，`catch_unwind` 接不住，会带走整个 `finx serve`（所有会话）。所以 PDFium 跑在一个单独的工作进程里（`finx doc-worker`，由 DocStore 拉起，一个进程服务所有文档，崩溃后自动重启并重新打开文档），内核与它用管道通信。这也顺带解决了 PDFium 不是线程安全的问题。
- 固定 PDFium 的版本，升级前跑语料回归（§12）。
- 只在 `PdfBackend` 里使用，类型不出现在 `Backend` 接口以外；需要换引擎时只换 `PdfBackend`。
- 限制单个文件的大小和渲染像素数（§11）。

## 11. 安全

- 页面只能经令牌读工作副本，不能读任意路径；令牌在这个会话关闭文档或会话卸载时失效。
- 所有修改都在内核里执行，页面发的是 DocOp，不是文件字节。
- PDF 里的 JavaScript、启动动作、嵌入文件一律不执行；pdf.js 关掉脚本（`isEvalSupported: false`、`enableScripting: false`）；链接只开 http、https，与对话里的链接规则一致。
- 文档内容是不可信数据：`doc_read` 的结果与网页内容同等对待，文档里写给智能体的"指令"不当真。
- PDFium 跑在单独的工作进程里（§9.4.8），崩溃不影响内核；限制单个文件的大小和渲染像素数。

- **锚点**：语料上 pdf.js 的选中四边形经 `doc/resolve` 得到的文字，与 pdf.js 自己的文字归一化后比对（V3 的回归版）；页面操作之后旧锚点的重新定位。
- **保存**：加密文件不能保存回原文件；带签名文件保存后签名仍有效；保存中途被杀进程，原文件完好。
- **一致性**：同一组操作分别经 `doc/apply`（人）和 `doc_edit`（智能体）提交，得到相同的文件与修订。
- **端到端**（AGENT.md 的要求）：`pnpm dev` 下打开一份真实合同，选中一段问 finx，让它高亮所有金额并填写签署日期；在询问模式下核对审批卡片的缩略图；撤销智能体的修订；保存后用预览.app 打开核对。
- **语料**：取 pdf_oxide 仓库测试语料的子集，加上扫描件、加密、表单、超大文件各几份。
