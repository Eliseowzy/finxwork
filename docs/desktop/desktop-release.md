## 1. 目标与约束

### 1.1 目标

| 编号 | 目标 | 含义 |
|---|---|---|
| RG1 | 只依赖 GitHub | 检查和下载都只访问 GitHub（github.com 和它的下载域名）。不需要官网，不自建服务，也不用第三方更新服务 |
| RG2 | 不打扰 | 后台检查、后台下载，提示放在不挡事的位置。从不替用户重启，重启也不打断正在运行的任务 |
| RG3 | 安全 | 只会装上用同一个 Developer ID 签名的新版本。GitHub 账号失守，也装不上别人的代码；不会降级 |
| RG4 | 发布可靠 | 一个版本的所有文件同时出现；有问题的版本能撤回 |
| RG5 | 首装即用 | 下载 DMG，拖进“应用程序”就能打开。App 和 DMG 都公证过，离线也能通过 Gatekeeper |

### 1.2 约束

- **源码仓库是私有的。** 没有登录的用户下载不了私有仓库 Release 里的文件；App 里也不能放能读私有仓库的令牌（§2.2）。
- **Squirrel 的要求。** 应用必须签名（Developer ID）；更新包必须是 zip；应用所在的位置要能写，磁盘映像里的、被系统隔离运行（App Translocation）的都不行（§5）。
- **包的大小。** zip 约 139 MB，其中 Electron 占大头。Squirrel 不支持增量更新，也不支持断点续传。
- **国内访问 GitHub 不稳定。** 检查和下载失败都静默退避重试（§4.5），走系统的代理设置。RG1 是明确要求，所以不设镜像（DQ-19）。

## 2. 方案选择

### 2.1 更新引擎（DD-18）

| 方案 | 优点 | 问题 |
|---|---|---|
| **Electron 自带的 autoUpdater（Squirrel.Mac），JSON 更新源** | 内置，不增加依赖；校验下载的应用与正在运行的应用满足同一个指定要求；应用退出后整体替换 bundle，不会留下半新半旧的应用 | 没有下载进度，不支持增量更新；只覆盖 macOS（Windows 在四期另做） |
| electron-updater | 有下载进度；Windows 支持增量更新 | 绑定另一套打包工具的产物格式；读私有仓库要令牌；在 macOS 上底层还是 Squirrel |
| Sparkle | 原生、成熟，appcast 用 EdDSA 签名 | 要在 Electron 应用里嵌入原生框架，还要多管一把 EdDSA 私钥 |
| update.electronjs.org | 不用自己写更新源 | 是第三方服务器，违反 RG1；只支持公开仓库 |

选第一种。基线（hermesh 桌面端）用的就是这一套，已经在两个签名版本之间实际更新过。

### 2.2 产物放在哪里（DD-20）

| 方案 | 结论 |
|---|---|
| 公开源码仓库，直接用它的 Release | 可行，但公开源码是另一个层面的决定（DQ-14） |
| **新建公开的发布仓库，只放 Release** | 采用。源码仍然私有；地址固定，任何人不登录就能下载 |
| App 内置令牌，读私有仓库的 Release | 不采用。令牌可以从 App 里提取出来，拿到它就能读源码 |
| GitHub Pages | 不采用。私有仓库开 Pages 要付费方案，而且这已经相当于自建官网 |

### 2.3 怎样发现新版本（DD-19）

| 方式 | 结论 |
|---|---|
| **固定地址 `releases/latest/download/<文件名>`** | 采用。GitHub 会把它重定向到最新发布里的同名文件。不走 API，没有限额；草稿和预发布不会被当成最新 |
| REST API `GET /repos/{owner}/{repo}/releases/latest` | 不采用。匿名调用每个 IP 每小时只有 60 次，公司或校园网共用出口时很容易超限 |
| Release 的 Atom 订阅 | 不采用。要解析 XML，里面也没有附件信息 |

### 2.4 同类应用的做法

| 应用 | 机制 | 检查 | 下载 | 提示 | 重启 |
|---|---|---|---|---|---|
| VS Code | Squirrel.Mac | 启动时和后台 | 后台 | 齿轮菜单里的“重新启动以更新”，带角标 | 从不自动重启 |
| Slack | Squirrel.Mac | 后台；应用菜单里可以手动检查 | 后台 | 帮助图标上的角标 | 从不自动重启 |
| Claude | Squirrel.Mac，JSON 更新源，按架构分开 | 启动时和后台 | 后台 | “重新启动以更新到 x.y.z” | 从不自动重启 |
| 1Password 8 | 自研 | 后台；“关于”里可以手动检查 | 可选自动安装 | 主窗口里的重启提示 | 从不自动重启 |

它们的共同点：后台检查，下载不打扰用户，提示放在角落，从不在用户眼皮底下重启，也都不弹对话框。finxwork 照这几条做。

## 3. 打包产物（DD-27）

`scripts/build-app.mjs` 每次构建一个架构，输出到 `FINXWORK_DIST`（默认是仓库根目录的 `dist/`）：

| 文件 | 用途 |
|---|---|
| `FinxWork.app` | 应用本身 |
| `finxwork-macos-<arch>.dmg` | 首次安装用：打开后左边是 finxwork，右边是“应用程序”，中间一个箭头，拖过去就装好了。DMG 本身也签名、公证、钉入票据 |
| `finxwork-macos-<arch>.zip` | 已安装的应用更新时下载它（Squirrel 只收 zip）。里面的应用已经公证、钉入票据 |
| `RELEASES-darwin-<arch>.json` | 更新源，只有会更新的构建才生成 |

更新源的内容（Squirrel 的 JSON 格式）：

```json
{
  "currentRelease": "0.1.1",
  "releases": [{
    "version": "0.1.1",
    "updateTo": {
      "version": "0.1.1", "name": "0.1.1", "pub_date": "2026-10-29T08:00:00Z",
      "notes": "https://github.com/finxwork/finxwork-releases/releases/tag/v0.1.1",
      "url": "https://github.com/finxwork/finxwork-releases/releases/download/v0.1.1/finxwork-macos-arm64.zip"
    }
  }]
}
```

`url` 指向的是这一版自己的 zip（带版本号的地址），不是“最新的 zip”。这样更新源里写的版本和 zip 一定对得上。

构建的其他变化：

- **签名身份默认自动选。** 没有设置 `FINXWORK_SIGNING_IDENTITY` 时，取钥匙串里第一个 `Developer ID Application`，找不到再用临时签名。设成 `-` 就强制临时签名。临时签名的构建不检查更新（§8）。
- **内核用 `dist` 配置编译**（fat LTO、`codegen-units=1`）。可执行文件比 `release` 小约四分之一，启动时间相同（technical-design 已有结论）。
- **跨架构构建不运行内核**：在 Apple 芯片上打 x64 包时，这台机器可能没装 Rosetta，跑不了 x86_64 程序。所以 x64 内核的版本号从 `cargo metadata` 读取，架构用 `lipo` 核对；本机架构的包仍然直接运行内核，确认它签名后还能启动、版本号也对得上。另一个架构的内核要用 Rust 的对应目标（`x86_64-apple-darwin` 或 `aarch64-apple-darwin`）编译，缺少时构建脚本自动用 rustup 装到仓库固定的工具链（rust-toolchain.toml）上，再开始编译（`scripts/rust-target.mjs`）。
- **更新地址在构建时写进应用**（electron-vite 的 define，见 `main/build.ts`）。发布构建一律指向发布仓库的 GitHub Release。只有测试构建能改成别的地址（`FINXWORK_RELEASES`），也只有测试构建能用自己的数据目录（`FINXWORK_TEST_HOME`）。运行时没有任何办法修改这两项。
- **DMG 用 dmgbuild 生成。** 它装在 `node_modules/.cache` 下的独立 Python 虚拟环境里，依赖锁定版本和哈希（`build/dmg/requirements.txt`）；窗口布局见 `build/dmg/settings.py`。背景图由 `scripts/make-dmg-background.swift` 画成 1× 和 2× 两张，箭头用品牌蓝。
- **公证。** 应用打成 zip 提交，DMG 直接提交，都等到 Accepted 后钉入票据，再用 `spctl` 按 Gatekeeper 的标准复核。没有通过时打印 Apple 的日志，列出被拒的文件和原因。

## 4. 更新机制

### 4.1 地址（DD-19）

记发布仓库的 Release 地址为 B，即 `https://github.com/finxwork/finxwork-releases/releases`：

| 用途 | 地址 |
|---|---|
| 最新发布的更新源 | `B/latest/download/RELEASES-darwin-<arch>.json` |
| 某个版本的更新源 | `B/download/v<版本>/RELEASES-darwin-<arch>.json` |
| 某个版本的 zip | `B/download/v<版本>/finxwork-macos-<arch>.zip` |
| 更新说明 | `B/tag/v<版本>` |

`<arch>` 是正在运行的应用的架构（`process.arch`）。在 Apple 芯片上用 Rosetta 运行的 x64 版本，会一直读 x64 的更新源。

### 4.2 两步：先自己判断，再交给 Squirrel（DD-21）

1. 主进程用 `net.fetch` 读最新发布的更新源（不走缓存，30 秒超时）。404 表示还没有任何发布，或者没有这个架构的发布，按“已是最新”处理。
2. 比较版本：只有比当前版本高时才继续（数字逐段比较，`0.10.0` 比 `0.9.1` 新，正式版比它的预发布版新）。
3. 把 Squirrel 的更新源设成**这个版本自己的**更新源（`B/download/v<版本>/…`），然后让它检查。Squirrel 下载 zip，确认里面的应用满足正在运行的应用的指定要求，才报告“已下载”。

为什么要钉住版本：最新发布可能在两次读取之间变化，比如正好撤回了一个版本。如果 Squirrel 自己再去读 latest，装上的可能是应用没比较过的版本，甚至是更低的版本。钉住之后，Squirrel 只会装应用比较过的那一个。

### 4.3 安装与重启（DD-23）

- 下载并校验好的更新**在应用退出时安装**：Squirrel 的安装程序等应用退出后整体替换 bundle，下次打开就是新版本。
- “重新启动以更新”调用 `quitAndInstall`：关闭窗口、退出、替换、打开新版本。应用从不自己重启。
- **重启不打断任务。** 退出应用时不会结束内核（desktop-kernel-integration §6.5），任务继续在内核里跑。新版本的应用连上还在运行的旧内核，等到没有任务时再替换它（§4.6）。窗口的视图状态和新会话草稿存在页面的本地存储里，重启后还在。

### 4.4 界面

- **应用菜单** finxwork › “检查更新…”：打开设置 › 关于，并立即检查。更新就绪后，这一项换成“重新启动以更新到 x.y.z”。开发构建和临时签名的构建里，这一项是灰的。
- **侧栏底部提醒**：在有已就绪或可下载的版本时出现，写着版本号，带一个“重新启动”（或“下载”）按钮和一个“稍后”。“稍后”让同一个版本在 24 小时内不再提醒，重启应用后也有效；菜单里的入口还在，退出时照样会安装。
- **设置 › 关于 › 软件更新**：一行状态，包括上次检查的时间、正在检查或下载的转圈、失败的原因（可以展开看技术详情）；右边是当下唯一该做的那个按钮（检查更新、下载更新、重新启动以更新或重试），有新版本时附上“更新说明”链接。下面是“自动下载更新”开关，默认打开。
- 没有弹窗、声音或系统通知。更新说明在 GitHub Release 页面上，更新后不会自动打开（应用内显示见 DQ-18）。

### 4.5 节奏与失败

- 启动 30 秒后第一次检查；如果上次成功检查还不到 4 小时，就推到满 4 小时再查。之后每 4 小时一次。
- 失败后按 5 分钟、30 分钟、2 小时退避。失败次数在重启后仍然有效。
- 系统唤醒、网络恢复后 10 秒补查一次，但仍然遵守上面的间隔和退避。
- 手动检查不受间隔和退避限制；已经在检查或下载时，手动检查不会再发起一次。
- 这些记录存在应用 profile 的 `updates.json` 里：上次成功检查的时间、上次尝试的时间、连续失败次数、“稍后”的版本和截止时间、是否自动下载。
- 失败分三类，各自有一句给用户的话：读不到更新源（网络）、应用在只读位置（§5）、下载或校验失败。下载好的更新不受后续失败影响，状态一直是“已就绪”。

### 4.6 内核跟随应用（DD-25）

desktop-kernel-integration §6.4 的替换判断有三条：内核版本和应用内置的不同、缺少必需能力、内核文件在服务启动后被改过（开发时重新编译）。更新之后，这三条可能都不成立：

- 内核的版本号来自 Cargo（现在是 `0.1.0`），不会随应用每次发版改变。
- Squirrel 从 zip 解出的内核保留了构建时的修改时间，可能比旧内核服务的启动时间还早。

结果是用户一直开着应用时，旧内核会一直跑下去。

现在的做法是：守护器每次自己启动内核，都在应用的 profile 里记下进程号和内核文件的设备号、inode（`kernel-starts.json`）。握手时，如果服务记录里的进程号正是记下的那个，而应用路径上的文件已经换了 inode，就判为待替换，在没有任务时替换。

Squirrel 替换的是整个 bundle，新内核一定是新的 inode；文件没换就不会误判。这个判断也覆盖开发时重新编译、手动覆盖安装这些情况。

如果更新跨越了协议版本，旧内核无法握手，只能按 desktop-kernel-integration §6.3 强制替换，旧内核里正在跑的任务会被中断。所以发版时应当尽量避免协议不兼容的升级。

## 5. 安装位置（DD-24）

- 打包后的应用如果不在“应用程序”文件夹（`/Applications` 或 `~/Applications`）里，会在打开任何窗口之前询问：“移到‘应用程序’文件夹”或“不移动”，并且可以勾选“不再询问”。
- 选择移动后，由 Electron 的 `moveToApplicationsFolder` 完成复制、需要时向用户要管理员授权，然后重新打开。“应用程序”里已经有一份时，会先问一句再替换，旧的那份移到废纸篓。移动失败时，提示用户在访达里自己拖过去，应用照常运行。
- 原因：Squirrel 替换不了磁盘映像里的应用，也替换不了被系统隔离运行的应用（直接从“下载”文件夹打开的、带隔离标记的应用）。放在其他位置也容易留下好几份副本。
- 不移动也能用。如果应用正好在只读位置，更新会失败，设置里会说明要先把它移到“应用程序”文件夹。
- 开发运行、测试构建，以及设置了 `FINXWORK_USER_DATA` 或 `FINX_HOME` 的隔离运行，都不会询问。

## 6. 发布流程（DD-26）

### 6.1 发布仓库

- `finxwork/finxwork-releases`：公开仓库，只有 Release 和一个说明安装方法的 README，不放源码。仓库名是 `src/shared/update.ts` 里的常量 `releaseRepo`，构建脚本、发版脚本和应用都从这里读。
- 建议打开 GitHub 的 Release 不可变设置（immutable releases）：发布之后，附件和标签都不能再改。这样即使令牌泄露，也改不了已经发布的版本。
- 只有维护者有写权限，账号开两步验证。

### 6.2 发布一个版本

```bash
pnpm release                 # arm64 和 x64
pnpm release --arch arm64    # 只发一个架构
pnpm release --dry-run       # 构建、公证、检查，但不上传
```

`scripts/release.mjs` 的步骤：

1. **检查前提**，任何一条不满足就在开始构建之前停下：
   - `package.json` 的版本号合法；
   - `apps/desktop/releases/<版本>.md` 里写了这一版的变化；
   - 工作区是干净的；
   - 有公证凭证；
   - 要发另一个架构时，仓库固定的 Rust 工具链（rust-toolchain.toml）有那个架构的目标；没有就在这一步装上，装不上就停下。rustup 不在 PATH 里时，到 `~/.cargo/bin` 下找；
   - 发布仓库能访问，**而且是公开的**：私有仓库对未登录的应用一律返回 404，应用会当成“已是最新”，永远收不到更新；
   - 仓库里还没有这个标签，包括上次中断留下的草稿；
   - 版本号比当前的最新发布高。
2. **构建每个架构**（`build-app.mjs`）：签名、公证、钉入票据，生成 DMG、zip 和更新源。再确认更新源里写的确实是这一版自己的 zip。
3. **创建草稿 Release，上传所有文件，然后一次性发布并设为 latest。** 草稿不会成为最新发布，所以在全部文件就位之前，已安装的应用读到的一直是上一版。上传或发布中途失败时，草稿留在仓库里，脚本会提示去网页上补完，或者删掉草稿后重跑。
4. **预发布版本**（版本号带 `-`，比如 `0.2.0-beta.1`）发布成 GitHub 的预发布，不会成为 latest，已安装的应用收不到。

### 6.3 版本号

- 唯一来源是 `apps/desktop/package.json` 的 `version`。它写进应用的 `CFBundleShortVersionString`；`CFBundleVersion` 是构建时间戳；标签是 `v<版本>`。
- 内核有自己的版本号（Cargo），它不需要随应用变化（§4.6）。

### 6.4 撤回有问题的版本

- **推荐的做法是向前修复**：尽快发布一个更高的修复版本。已经下载了问题版本的应用，会在下次检查时拿到修复版。
- 也可以在 GitHub 上把上一个版本重新设为 latest。应用只升不降，所以已经更新的用户会停留在问题版本，直到修复版发布；还没更新的用户不会再收到问题版本。已经下载好的更新，退出时照样会安装。
- 打开不可变设置后，不能再删除已发布版本的附件，向前修复是唯一的办法。

### 6.5 凭证

- Developer ID 证书和私钥只在本机钥匙串里。公证用 App Store Connect API 密钥（和 movieclaw 是同一把），通过 `FINXWORK_NOTARY_KEY_PATH`、`_KEY_ID`、`_ISSUER` 传入，也可以先用 `xcrun notarytool store-credentials` 存进钥匙串，再用 `FINXWORK_NOTARY_PROFILE` 指定。
- 凭证不进仓库，也不上传 GitHub。GitHub 只需要 `gh` 的登录，用来创建 Release 和上传文件。在 CI 里发版要另做决定（DQ-16）。

`update-e2e.mjs` 的流程：

1. 用钥匙串里的 Developer ID 签名，构建两个版本 A（0.0.1）和 B（0.0.2）。只签名、不公证，因为 Squirrel 只校验签名。
2. 在本机起一个服务器，按 GitHub 的路径布局：`latest/download` 重定向到 B 的发布。
3. 运行 A，手动检查，等到“已就绪”。确认侧栏出现了提醒，也确认请求的顺序：应用读的是最新发布的更新源，Squirrel 读的是 B 自己的更新源和 B 的 zip。
4. 重新启动以更新。确认原来 A 所在的路径上现在是 B，而且 B 在运行；并确认 A 启动的内核被替换成了新的进程。

测试版本的 profile 和 FINX_HOME 都在一个临时目录里，这个目录写死在测试构建里，所以 Squirrel 重新打开的 B 也用它，不会碰到用户自己的 finxwork、设置和 finx。结束后，Squirrel 在 `~/Library/Caches` 下按 Bundle ID 留下的目录也会删掉（测试前就存在的不动）。设置 `FINXWORK_E2E_SHOTS=<目录>` 时，还会在“已就绪”时截下侧栏提醒和设置 › 关于。

2026-10-29 在本机（Apple 芯片，Developer ID `G4LW3GC2T7`）连续跑了两次，都通过：

- 状态依次是“检查中 → 下载中 → 已就绪（0.0.2）”。
- 本机服务器依次收到三个请求：最新发布的更新源、v0.0.2 的更新源、v0.0.2 的 zip。
- 重新启动后，原路径上的应用变成了 0.0.2 并且在运行。
- A 启动的内核（进程 13110）被新应用替换为 13263。
- 两次构建约 4 分钟，内核已编译过时更快；更新本身不到 1 分钟。

## 8. 安全（DD-22）

| 威胁 | 应对 |
|---|---|
| GitHub 账号或令牌被盗，有人上传恶意更新 | Squirrel 只安装满足指定要求的应用：Team ID 一致，Bundle ID 一致。签名私钥只在本机钥匙串，攻击者签不出能装上的包 |
| 降级到有漏洞的旧版本 | 应用只接受比当前版本高的版本；Squirrel 被钉在这个版本自己的更新源上（§4.2） |
| 中间人篡改 | 全程 HTTPS；即使被篡改，最后还有签名校验兜底 |
| 页面被攻破后滥用更新 | 页面只能发出“检查、下载、安装、稍后、开关自动下载”这几个请求，不能指定任何地址或文件 |
| 运行时改掉更新地址 | 地址是构建时常量；熔断开关不允许从 asar 以外加载代码，也禁用了 `NODE_OPTIONS` 和 `--inspect` |
| 私有源码泄露 | 应用不带任何令牌；发布仓库里只有构建产物 |
| 临时签名的构建 | 没有稳定的签名身份，Squirrel 无法校验，所以这类构建不检查更新 |
