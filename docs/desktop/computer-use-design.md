## 1. 方案摘要

- **名字**：电脑操控（英文 Computer Use），原来叫"桌面控制"。
- **工具**：`cua_apps`、`cua_launch`、`cua_snapshot`、`cua_act`、`cua_screenshot`（CUA 即 computer use agent），原来是 `desktop_*`。参数和行为不变。
- **延迟加载**：电脑操控和浏览器的工具都不放进工具列表，系统提示词里各占一行目录，用到时先 `tool_search`，再经 `call_tool` 执行（§5）。
- **默认开启**：不再需要先"连接"。开关只有一个，在"设置 › 电脑操控"。
- **不是连接器**：不出现在输入框"+ › 连接器"里，也不出现在"自定义 › 连接器"里。
- **系统授权照样要**：默认开启不等于有权限。macOS 的辅助功能（必需）和屏幕录制（截图时需要）要用户自己在系统设置里打开，设置页把这件事放在开关下面，写清楚授权是做什么用的。
- **询问**：每个应用每个对话第一次用到时先问一次，允许了就同时允许查看和操作（以前查看、操作分开问）；`[desktop.apps]` 只有允许和禁止两档（§4）；绕过权限模式下不问，理由同前：命令行本来就能驱动同样的应用，"禁止"在任何模式下都有效。

## 2. 为什么改

- 作为连接器时，要先在"自定义"里找到它、点"连接"、授权、再点"完成"，很多人发现不了这个能力。
- 真正绕不过去的只有系统授权；FinxWork 自己的开关只是一次同意，放在设置里、默认开，就够了。
- 连接器是"接进来的外部东西"，电脑操控和读文件、运行命令一样是 FinxWork 本来就有的能力，放进连接器反而让连接器的概念变乱。

## 3. 开关与默认

| `desktop.enabled` | 结果 |
|---|---|
| 不写 | 桌面端连着时开，命令行里关（与内置浏览器的 `browser.enabled` 相同） |
| `true` | 开 |
| `false` | 关：会话里没有电脑操控的工具，智能体无法操作其他应用 |

- 项目配置只能关（`enabled = false`）、只能把应用设为 `deny`，不能打开它，也不能改 `executable`（D-178，不变）。
- 开关变化推到已经打开的对话，在各自下一次模型请求之前生效（connectors-entry-design D-224，不变）。

## 4. 设置 › 电脑操控

页面上只有两块：开关和应用权限。系统授权不常驻在页面上，缺了才提示。

1. **开关**："允许 FinxWork 控制你电脑上的应用"，下面一行说明：
   - 平时：说明开着与关掉的区别；
   - **没有辅助功能权限**：开关显示为灰色（关），下面一行用橙色写"需要先完成授权，电脑操控才能使用"，后面是"去授权"。点开关或"去授权"都打开授权对话框。配置里的开关值不变，授权之后就是开着的；用户关过的，在对话框里点"完成"且已授权时重新打开；
   - **开着但没有屏幕录制**：写"给窗口截图还需要屏幕录制权限"和"去授权"，不算出错；
   - **组件缺失**：agent-desktop 随 FinxWork 一起打包（`Contents/MacOS`，固定版本、核对过哈希），开发版由 `scripts/dev-agent-desktop.mjs` 把同一份放在调试版 finx 旁边（`pnpm dev`、`pnpm build` 时）。万一缺了，写"电脑操控的组件缺失，请重新安装 FinxWork"，开关不能用，不给安装命令；
   - **不是 macOS**：写"这台电脑不支持电脑操控"，开关不能用。
2. **授权对话框**："授权电脑操控"，一段话说明两项授权各做什么、授权之后每个应用第一次用到时仍会先问；下面是辅助功能（必需）和屏幕录制（可选），各自显示"已授权"或"打开系统设置"；回到应用时状态自动刷新，权限刚打开时可能需要重启 FinxWork。
3. **应用权限**：只有两档，允许和禁止。每行是应用的图标和名字，右边两个小图标按钮：锁（开着的锁是允许，锁上是禁止，点一下切换）和删除（删除之后，下次用到时重新询问）。手动添加的应用是允许。关着时只显示、不能改；没有辅助功能权限时提示先完成授权。
   - **配置**：`[desktop.apps]` 的值是 `allow` 或 `deny`；以前的 `act` 等同 `allow`，`read` 仍然只允许查看、操作前再问，下次在页面上改动时变成两档之一。
   - **审批**：每个应用每个对话只问一次，"本会话允许使用 X"同时允许查看和操作；勾"记住"写入 `allow`。发消息、付款、删除之前，智能体仍会先停下来问你，与应用级别无关。
4. **输入框"+"菜单**：浏览器开关下面一个"电脑操控"快捷开关，就是第 1 条的开关，点了菜单不关。还不能用时是灰的，旁边写"需要授权"或"组件缺失"，点一下打开"设置 › 电脑操控"；不是 macOS 时不显示。它不是连接器，连接器菜单和自定义页里都没有它（connectors-entry-design §14）。

## 5. 延迟加载

电脑操控和浏览器的工具，与按需加载的 MCP 服务器（mcp-design §7）用同一套机制。

### 5.1 为什么

- **开销**：电脑操控 5 个工具的定义约 5,700 字符，使用规则约 1,060 字符；浏览器 8 个工具约 7,100 字符，再加上它的使用规则。两者默认开启，每次请求都要带上，比读写文件、运行命令这些核心工具（约 2,700 字符）还多。不用它们的对话也一直付出这部分。
- **缓存**：模型用的服务商（DeepSeek）不支持在对话中途加入工具而不改动请求前缀。所以不采用"搜到以后加进工具列表"，那样每加载一次，整个前缀的缓存就失效一次；而是像 MCP 一样经 `call_tool` 执行，工具列表和系统提示词在整个对话里不变。

### 5.2 模型看到什么

| 层 | 内容 |
|---|---|
| 目录 | 系统提示词最后的 `<deferred_tools>` 段，每组一行：`browser`、`cua`，排在按需加载的 MCP 服务器前面。只在对应的功能开着时出现 |
| 定义 | `tool_search`：查询里提到组名、某个工具名或它的一部分（如 `navigate`、`snapshot`），或者概述里的词，就返回整组的定义；用 `server: "cua"` 也可以。组第一次出现时附上它的使用规则（原来写在系统提示词里的那几条） |
| 调用 | `call_tool(name, arguments)`，`name` 就是工具名，如 `browser_navigate`、`cua_snapshot` |

- **整组返回**：组很小，工具之间要配合使用（先 `snapshot` 再按 ref `act`），一次给全省得来回搜。
- **不重复**：自上次压缩以来给过的定义和规则，再搜时只列名字。
- **直接调用也执行**：模型看过定义之后直接调用 `browser_navigate` 而不经过 `call_tool` 时，照样执行，不报"未知工具"。

### 5.3 经 call_tool 执行，判断照旧

`call_tool` 把调用交给目标工具本身，凡是按工具判断的地方都按目标工具来：

- **审批**：来源（`origin_for`）是内置工具，不是 MCP，所以照常按网站、按应用询问；绕过权限下你的浏览器仍然询问；
- **权限范围**（authorities）、执行前检查、参数整理、能否并行（`kind_for`）都取目标工具的；
- **显示**：`tool_started` 的标题是目标工具自己的描述（如"open example.com"、"read the window of 访达"）。桌面端从 `call_tool` 的参数里取出目标工具名和参数，审批框和历史记录按目标工具显示。

### 5.4 代价

- 每个对话第一次用浏览器或电脑操控时，多一步 `tool_search`。
- 搜到的定义追加在历史里，压缩之后需要时再搜一次。
- 工具列表多了 `tool_search` 和 `call_tool` 两个定义（已经有按需加载的 MCP 服务器时本来就有）。
