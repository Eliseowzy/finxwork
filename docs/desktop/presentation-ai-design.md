## 方案摘要

- **现状**：FinxWork 的 PPT 编辑器能看、能改字、能拖形状、能调页序，工具栏只有加粗/斜体/字号/颜色/对齐/十几种形状/排列四件套。对照 PowerPoint "开始"一栏，大约做到了 25%；"插入 / 设计 / 切换 / 动画 / 审阅 / 视图"基本是空的。智能体还不能操作打开着的文稿。
- **底子比看上去好**：NimbleOffice 引擎（WASM/Yrs）已经有表格行列、批注、节点式 z 序、版式切换、备注、复制页、**智能体提议（propose / preview / accept / reject）和审阅界面**、带版本校验的批量编辑（`applyEdits`，失败码含 `StaleVersion`、`ContentMismatch`）。很多能力"引擎有、界面没接"。
- **两条线并行**：
  1. **编辑能力**：自己做工具栏外壳（不用 NimbleOffice 自带的），按"常用 80%"补齐：格式刷、项目符号/编号/行距/缩进、对齐与分布、组合、表格、图表、主题与版式、动画与切换、批注、大纲视图。缺的在 fork 里补。
  2. **AI 能力**：不做"聊天框旁边放个 PPT"，而是让 AI 长在画布上——选中即改、一页三个版式候选、整份"体检"并一键修、从材料生成（用用户自己的模板）、图表数字链接到表格、讲稿与彩排。所有 AI 改动都是**可预览、可逐页接受、一步撤销**的提议。
- **架构关键决策**（§6）：内核在 doc-worker 里持有权威的 DeckSession，编辑器作为 Yrs 副本加入；人和智能体走同一套操作，智能体的写入默认是提议。地址用稳定 ID 不用下标。
- **和 WorkBuddy 的差异**（§2）：它是"腾讯文档编辑器 + 85 个按下标寻址的工具 + 一套 JSX 生成 DSL"，生成时**禁止模型看渲染结果**、改稿只能事后按版本撤销。我们反过来：本机光栅化让模型看图自检；所有修改先成提议再落地；生成落到用户模板的版式和占位符上，生成物是"正常的、可继续编辑的 PPT"。
- **路线**：P0 四周（工具栏外壳 + 基础补齐 + 智能体读写与提议），P1 四周（选中即改、版式候选、体检），P2 六周（材料生成、模板品牌、数据链接），P3 按需（动画切换、图表数据编辑、演讲辅助）。

## 1. 现状盘点

### 1.1 FinxWork 现在有什么

| 层 | 现状 | 位置 |
|---|---|---|
| 编辑器 | `@nimbleoffice/pptx-react` 0.5.1，Canvas 绘制、Worker 内 WASM 引擎 | `apps/desktop/src/renderer/src/docs/pptx/PresentationView.tsx` |
| 工具栏 | 撤销重做、字体、字号、加粗斜体下划线、文字颜色、四种对齐、填充/边框颜色与宽度、圆角与形状调整、18 种预设形状、插图、文本框、置顶置底、新建页（按版式）、删页、放映、备注、导出 PNG | NimbleOffice 内置，`zh-CN.ts` 是汉化 |
| 宿主 | `pptx/read`、`pptx/write`（哈希冲突检查 + 原子写）、`pptx/font`（本机字体）、`pptx/metafile`（EMF/WMF→SVG） | `crates/finx-core/src/pptx.rs`、`crates/finx-protocol/src/pptx.rs` |

### 1.2 引擎里有、界面没接的

从 `@nimbleoffice/pptx` 的接口看（`dist/*.d.ts`），下面这些已经能调用，只差界面或工具：

- **结构**：`insertSlide`、`duplicateSlide`、`deleteSlide`、`moveSlide`、`setSlideLayout`、`layouts`、`setSlideNotes`、`setSlideBackground`（批量步骤里）

- **表格**：`insertTableRow/Column`、`deleteTableRow/Column`、`checkTableEdit`
- **文字**：`formatText`（粗/斜/字号/颜色/字体/下划线/删除线/字距/上下标）、`setParagraphAlignment`、`setStoryParagraphs`、`findText`、`searchText`
- **批注**：`addComment`、`replyToComment`、`setCommentStatus`、`removeComment`

- **导出**：`exportStructured`、`exportMarkdown`、`thumbnail`
- **协同**：Yrs CRDT，`encodeStateVector`、`applyUpdate`、`PptxAsyncCollaborationOptions`

### 1.3 引擎里没有、要在 fork 里补的

| 能力 | 说明 | 难度 |

## 2. WorkBuddy 怎么做的

依据：本机 WorkBuddy 5.9.4 的安装包与内置插件 `workbuddy-pptx`（`~/.workbuddy-ai/plugins/cache/workbuddy-builtin/workbuddy-pptx/5.9.4-*/`），以及此前的渲染对照（`/tmp/ppt-bench/report.md`）。只读了它公开随包的技能文本和前端字符串，没有反编译原生库。

### 2.1 架构

```
WorkBuddy（Electron）
 ├─ 预览面板：腾讯文档 editor_sdk 前端（Canvas）+ 原生导入库（闭源）
 ├─ 本机服务 127.0.0.1:39099（editor_sdk，HTTP/MCP）
 │    └─ 一个文件一个 editor 实例（pool），file_id 是 UUID
 └─ Agent（CodeBuddy 内核）+ 技能 workbuddy-pptx
      ├─ 理解：slidep inspect → slides.md（逐页文字、表格、图表数据、形状坐标）
      ├─ 改稿：python edsdk.py call slide_* …（约 85 个工具）
      └─ 生成：每页写一个 .slide（受限 JSX：Box/Text/Image/Chart/Table/SVG/Diagram/Animation…，
               Flexbox 布局）→ slidep upsert-dsl 编译成 OOXML → slidep lint 布局检查
```

- **上下文注入**：每轮对话把当前预览的文档塞进系统提示 `<active_document type="local" path=… file_id=…/>`，模型据此"默认改正在看的那份"。
- **工具形态**：`slide_get_page_info`、`slide_set_text`、`slide_set_shape_properties`、`slide_add_chart`、`slide_update_chart_axis`、`slide_set_anim_trigger`、`slide_set_theme`、`slide_list_recent_ai_edits`、`slide_undo_ai_edit`……按 `page_index`、`shape_index`（0 起）寻址，单位磅。技能里反复强调"用一个查一个 schema，不许凭记忆拼参数"。
- **生成流程**：需求对齐（最多问 3 个）→ 收集材料/联网 → 风格路由（通用 / 学术 / 投资分析 / 红金政务 / 个人介绍 / 咨询）→ 写 DESIGN.md → 建空文件并立即在预览面板打开 → 逐页"配图 → 写 DSL → upsert → lint → 不过就改"。
- **设计规范写成文字**：1280×720 画布、60px 安全区、页脚固定 y=670、一页最多 4 个区、要有视觉主角、内容区填满 90%、不许靠拉间距撑满……共 488 行。
- **lint 规则**：`no-overflow`、`zero-size-text`、`component-overlap`、`child-containment`、`zero-position`。
- **对用户隐藏实现**：进度里只许说"内容大纲 / 风格设计 / 逐页制作 / 检查页面"，不许出现 DSL、lint、OOXML。

### 2.2 值得学的

1. **场景路由 + 成文的设计规范**：把"好看"拆成可检查的规则，模型照着做，质量下限稳定。投研、学术、政务各有一套调性。
2. **生成时实时可见**：先建文件、先打开预览，再逐页写，用户看着页一张张长出来，等待不焦虑。
3. **每页闭环**：写一页检查一页，不是全做完再返工。
4. **当前文档自动进上下文**：用户不用说"改哪个文件"。
5. **AI 编辑有账本**：`list_recent_ai_edits` + `undo_ai_edit`，能按版本撤销 AI 的某次修改。
6. **话术用用户的词**：这条我们也应该写进技能。

### 2.3 它的短板（也是我们的机会）

1. **AI 是"盲做"的**：技能明文禁止截图、导出、看渲染结果，只靠 5 条几何 lint。字号是否协调、配色是否刺眼、图是否压字、中文是否被自动缩到看不清（对照报告 p5 就是这样），模型都不知道。
2. **改动先落地、后撤销**：没有"先看再决定"。改错了只能找到版本号撤回，也不能只接受其中几页。
3. **下标寻址很脆**：`shape_index` 随插入、删除、z 序变化漂移；技能只能要求"每次编辑后重新读取"。多步改稿里改错对象的风险很高。
4. **工具太碎**：85 个工具、每个都要先查 schema，一次简单改稿要好几轮往返，慢且费 token。
5. **生成物是"DSL 画出来的"**：Flexbox 盒子编译成绝对定位的形状，和用户公司模板的母版、占位符无关。生成后再套公司模板、或在 PowerPoint 里改版式，会很别扭。
6. **AI 只在聊天里**：画布上没有 AI 入口（从前端字符串里没找到选区浮条、版式建议一类的界面），所有操作都得回到对话框打字。
7. **渲染保真度**：对照测试里均差最大（12.7 vs NimbleOffice 8.3），自动缩放过激。
8. **闭源、依赖腾讯文档本机服务**：不是我们能复用的东西，但说明"嵌一个现成编辑器 + 套工具"能很快出效果，护城河在 AI 流程和规范，不在编辑器本身。

## 3. 用户视角：谁、在什么时刻、要什么

不从"PowerPoint 有什么按钮"出发，从做 PPT 的真实时刻出发。

| # | 时刻 | 用户心里的话 | 现在的痛点 | 我们给什么 |
|---|---|---|---|---|
| J1 | 明天要汇报，手里只有一份报告/表格/会议记录 | "帮我变成 12 页，用公司模板" | 从空白页开始最痛苦；AI 生成的往往不是公司模板，还得重排 | 从材料生成，落在用户模板的版式上（§5.2.4） |
| J2 | 一页写满了字，很丑 | "让这页好看点，内容别动" | 不会设计；挪框挪半小时 | 一页三个版式候选，点一下换（§5.2.2） |
| J3 | 改一段话 | "这段精简成三点""换个正式点的说法" | 复制到 ChatGPT 再贴回来，格式全丢 | 选中即改，保留格式（§5.2.1） |
| J4 | 交稿前 | "有没有错别字、字体乱了、数对不上、页码漏了" | 一页页肉眼检查 | 整份体检 + 一键修（§5.2.3） |
| J5 | 季度更新 | "Q3 数据出来了，把图表和数字都换掉" | 逐个改图表数据，容易漏 | 图表/数字链接到表格，源变了提示刷新（§5.2.5） |
| J6 | 拿到别人的 deck | "这份讲了什么？第 7 页那个数哪来的？跟上一版改了啥？" | 翻半天 | 读懂、问答带出处跳页、两版对比（§5.2.6） |
| J7 | 要上台 | "帮我写讲稿、控制在 10 分钟、老板可能问什么" | 没人帮彩排 | 讲稿、计时、彩排反馈、问答预演（§5.2.7） |
| J8 | 同一份内容给不同人 | "给高管压成 5 页""出一版英文的" | 重做一遍 | 受众改写、保版式翻译（§5.2.8） |
| J9 | 日常手改 | "对齐这几个框""跟上一页标题一样的格式" | 基础操作缺（对齐分布、格式刷、项目符号） | §5.1 补齐 |

几个判断：

- **J9 是地基**。AI 再好，用户最后总要自己动手微调；基础操作缺一样，体验就断一次。所以 §5.1 不能省。
- **J2、J3、J4 是高频小事**，每次几秒，最能体现"AI 原生"。优先级高于 J1。
- **J1 是招牌**，但做不好最伤口碑（生成一堆不能用的页）。要在 J2 的版式能力和 J4 的检查能力之上做。
- 用户不分"金融/非金融"（定位见 memory：AI 服务于人），场景包（投研、学术、医疗汇报、政务…）作为可插拔的风格与规则包，核心不写死任何一个行业。

## 4. 设计原则

1. **先看再落地**：AI 对文稿的每次修改都是一个提议：画布上就地显示"之前/之后"，可以逐页、逐对象接受。接受后是一步撤销。用户可以在设置里对低风险操作（改错别字）打开"直接应用"。
2. **不写坏**：继承现有原则——外科式保存，不认识的结构保留原样；做不到就拒绝并说明，绝不输出一个 PowerPoint 打不开的文件。
3. **人和 AI 用同一套操作**：工具栏按钮、快捷键、智能体工具，最后都是同一组编辑步骤，进同一条撤销历史，标明来源（人 / 智能体）。
4. **AI 要看得见**：模型改完要看渲染图自检；确定性检查（溢出、重叠、对齐、对比度、字体集合）先跑，视觉评审再跑。
5. **尊重用户的模板**：生成和改版优先用文稿自己的母版、版式、占位符、配色和字体方案，而不是自带一套主题。
6. **AI 长在画布上，对话是兜底**：常用 AI 动作在选区浮条、右键菜单、⌘K 里直接触发；复杂任务才回到对话。两边看到的是同一个提议。
7. **数据有出处**：引用外部数据（表格、网页、文档）的数字带来源，能跳回去核对。
8. **本机优先**：渲染、字体、检查都在本机；只有模型推理和用户明确开启的生图走网络。文稿内容是不可信输入（防提示注入）。

#### 工具栏外壳

- **自己做外壳**，NimbleOffice 只当画布和命令层用。原因：它的工具栏布局、交互、汉化都不受我们控制；AI 入口要嵌进去；我们要上下文选项卡。
- **结构**：`开始 · 插入 · 设计 · 动画 · 放映 · 视图`，加上下文选项卡（选中形状出"形状格式"，选中表格出"表格"，选中图表出"图表"）。"切换"并进"动画"，"审阅"并进右侧的批注与 AI 面板。
- **文件面板比 PowerPoint 窗口窄**：默认用单行紧凑工具栏（图标 + 下拉），面板拉宽或全屏时展开成两行功能区。宽度断点自适应，放不下的进"更多"。
- **AI 不是第七个选项卡**：是工具栏最右侧常驻的"✦"按钮（打开 ⌘K）、选区浮条、右键菜单里的一组动作。

### 5.2 AI 能力

每项给：用户看到什么 → 怎么实现 → 依赖。

#### 5.2.1 选中即改（P1，最高频）

**用户看到**：选中一段文字或一个文本框，旁边浮出一行：`✦ 改写 ▾ · 精简 · 扩写 · 换成要点 · 翻译 ▾ · 问 finx`。选中形状/多个对象：`✦ 美化 · 对齐整理 · 转成图示`。选中表格：`✦ 转图表 · 突出关键数 · 精简`。点了以后，原位显示改后的样子（虚线框 + "接受 ⌘↩ / 再来一版 / 放弃"），保留原来的字体、颜色、项目符号。

- 改写子菜单：更正式、更口语、更有说服力、更简洁、改成结论先行；可自定义并保存成自己的常用指令。
- "问 finx"：把选区作为引用块带进对话（沿用表格的引用方块写法："方案.pptx · 第 4 页 · 标题 3"）。
- **溢出处理**：改后的文字放不下时，按序尝试 ① 让模型再精简 ② 在 `normAutofit` 允许范围内缩字号（最多两档）③ 提示用户。不悄悄缩到看不清（WorkBuddy 的反例）。

**实现**：
- 文本改写只换 run 的文字，样式按"原 run 边界映射"保留：模型输出带简单标记（`**粗**`、换行=段落、`- `=项目符号层级），由前端映射回 `setStoryParagraphs`，每段继承原段的 `pPr`、每个 run 继承最接近的原 run 样式。
- 走提议：`propose` → 画布叠加预览 → `acceptProposal`。用更小更快的模型（改写类不需要最强模型），首字 < 1s，流式写进预览框。
- 溢出检测用引擎的布局结果（`layoutProposalSlide` 给出文字实际高度），不靠估算。

#### 5.2.2 一页三个版式候选（P1，体现"AI 设计"）

**用户看到**：任意一页，右上角"✦ 版式"，或右侧面板常驻"设计建议"。给出 3–6 个候选缩略图，基于这页**现有内容**（标题、要点、图、数字）重新排版；悬停即在画布上预览，点击应用。内容一字不改。

候选来源分三类，混合排序：
1. **模板内**：文稿母版里已有的版式（两栏、图文、比较、标题+内容…），把内容填进对应占位符。最稳，最符合品牌。
2. **结构化转换**：识别内容结构 → 转成卡片阵列、时间线、流程、对比两栏、大数字（KPI）、金字塔、矩阵、要点+配图等十几种"图示"模板（替代 SmartArt）。
3. **数据页**：表格里有数，就给"转图表"候选，自动选图型（时间序列→折线，构成→环形/堆叠，对比→条形）。

**实现**：
- **版式意图 → 求解器 → 编辑步骤**，三段式：
  1. 内容分析（LLM，小模型即可）：把这页抽成结构化内容树：`{title, subtitle?, blocks:[{kind: bullets|paragraph|number|image|table|chart, items, emphasis}], takeaway?}`。
  2. 版式求解（确定性，Rust）：候选模板是参数化的"槽位图"（区域、比例、对齐基线、字号阶梯），按内容量算尺寸，跑文字度量（引擎的排版，不是估算）保证不溢出，打分（填充率、对齐、视觉主角、层级对比）。
  3. 生成编辑步骤：`setSlideLayout` / `addShape` / `setShapeRect` / `setStoryParagraphs` / 样式步骤，打包成一个提议。
- 配色、字体只从**文稿主题**取（`theme` 的 accent1–6、major/minor 字体），这样换出来的页不会和其他页打架。
- 求解器是纯函数，可以单测、可以批量跑语料打分（§9）。LLM 只做"理解内容"，不做像素决策——这是和 WorkBuddy"模型写 Flexbox"最大的不同，结果更稳、更快、更便宜。
- 视觉复核：候选在本机光栅化成缩略图（`pptx-raster`），可选再让视觉模型给前 6 个排序（P2 再开）。

#### 5.2.3 整份体检（P1）

**用户看到**：工具栏"✦ 检查"（或交稿前保存/导出时提示一次）。右侧面板分组列出问题，每条可点跳到页面并高亮对象，带"修复"按钮，也可"全部修复"（一个提议，逐页预览）。

| 类别 | 规则（确定性） | AI 补充 |
|---|---|---|
| 版面 | 文字溢出、对象出页、与安全区冲突、对象重叠压字、近似对齐（差 1–4pt）、同类页标题位置漂移 | 视觉评审："这页信息太密""主次不清" |
| 一致性 | 字体超过 3 种、非主题色、标题字号不统一、项目符号风格混用、页码/页脚缺失或不连续 | 术语前后不一致（"营收/收入"）、单位不一致（亿元/万元） |
| 内容 | — | 错别字、病句、标点全半角混用、中英文间距、数字与图表/表格不符、结论与数据矛盾 |
| 数据 | 链接的数据源已更新（§5.2.5） | 引用无出处 |
| 可访问性 | 对比度不足（WCAG AA）、图片无替代文字、字号过小（<12pt） | 生成替代文字 |
| 文件 | 图片分辨率不足、超大图片（建议压缩）、嵌入字体缺失 | — |

**实现**：
- 规则引擎放在 Rust（新模块 `finx-slide::check`，或 doc-worker 里）：输入是引擎快照 + 布局结果，输出 `Diagnostic { rule, severity, slide_id, shape_ids, message, fix?: EditStep[] }`。多数规则自带修复（对齐吸附、统一字号、替换为最近的主题色）。
- 文字类问题让模型批量看 `exportStructured` 的全文，按页返回带锚点（slide_id + shape_id + 字符区间）的问题，修复是 `ReplaceText` 步骤，靠 `ContentMismatch` 保证改的是原文。
- 同一套规则给智能体当"写完自检"工具（`deck_check`），也给 5.2.4 生成流程每页闭环用。

#### 5.2.4 从材料生成（P2，招牌）

**用户看到**：
1. 新建 → "✦ 用 AI 生成"，或在对话里拖进材料（报告 PDF/Word、表格、网页、会议记录、整个会话）。
2. 选模板：**我的模板**（用户导入过的 .potx/.pptx，记住）、文稿当前模板、或内置几套。
3. **大纲先行**：几秒内给出逐页大纲（标题 + 要点 + 计划的版式 + 数据来源），可直接编辑、拖动、删减、"这页拆两页"。确认后才开始做页。
4. 逐页生成，用户在面板里实时看到页一张张出现（学 WorkBuddy）；可以随时停、改某页再继续。
5. 完成后自动跑体检，列出需要人确认的地方（"第 6 页的市场规模来自网页，请核对"）。

**实现**：
- 管线：材料解析（已有 PDF / 表格 / 网页能力）→ 大纲（大模型，产出结构化 JSON）→ 每页：内容树 → **5.2.2 的版式求解器**（同一个！）→ 编辑步骤 → 体检 → 不过则修。
- **落在模板上**：先分析模板（`deck_template_profile`）：有哪些版式、每个版式的占位符类型与区域、主题色字体、页脚规则。求解器优先选"有对应占位符的版式"，把内容填进占位符；只有模板里没有的结构（时间线、KPI 卡片）才在占位符区域内画形状。这样生成物在 PowerPoint 里切换版式、改母版都正常。
- 图表：数据从表格来的，直接生成原生图表并建立数据链接（5.2.5）；数字一律带来源。
- 配图：P2 先用材料里的图和本机图标；生图作为可选项，用户明确开启并选服务商。
- 场景包：学 WorkBuddy 的"场景路由"，但做成可插拔的包（风格规则 + 版式偏好 + 写作规范 + 体检规则），核心不写死行业。首批：通用、投研、学术、工作汇报。

#### 5.2.5 数据活链接（P2，和表格能力打通）

**用户看到**：从表格生成或粘贴来的图表/数字，右上角有个小链条标记。源表格变了，打开文稿时提示"3 处数据已更新"，一键刷新（提议预览：图表新旧对比、文字里的数字高亮）。悬停数字看出处："模型.xlsx · 利润表!D15 = 12,871.19"。

**实现**：
- 链接存在 PPTX 自定义 XML 部件里（`customXml` 或形状的 `extLst`，PowerPoint 会原样保留），内容：源文件相对路径、表名、区域/单元格、取值时的快照与哈希。
- 刷新复用 `finx-sheet` 读取与重算（`sheet_calc`），图表数据更新写进图表部件和嵌入 xlsx。
- 文字里的数字：存 `{shape_id, run 区间, 源单元格, 显示格式}`，刷新时按显示格式重新格式化。

#### 5.2.6 读懂、问答、对比（P1）

- **读懂**：打开别人的 deck，"✦ 概要"给出一屏摘要（主线、每节一句、关键数字）；对话里问"第 7 页那个 30% 哪来的"，回答带页码出处标记，点了跳页并高亮对象。
- **两版对比**：选两个文件（或同一文件的历史版本），逐页对齐（标题+内容相似度匹配，处理插页删页），列出文字/数字/对象/版式变化，画布并排显示差异。用引擎的 `layoutProposalDiffSlide` 做页内高亮。
- 实现：`deck_open` 给结构摘要，`deck_read` 给带锚点的 Markdown，`deck_view` 给渲染图；对比是纯本机算法 + 模型写摘要。

#### 5.2.7 讲稿与彩排（P2/P3）

- **讲稿**：逐页生成演讲者备注，可设总时长（"10 分钟"）自动分配；口语化，标出过渡句。
- **问答预演**："✦ 可能被问的问题"按受众（老板、投资人、评委）给 10 个问题和建议回答，指出 deck 里支撑薄弱的页。
- **彩排**（P3）：放映时开麦，本机语音转写，结束后给每页用时、口头禅、漏讲的要点、语速。语音只在本机处理或经用户同意上传。

#### 5.2.8 整份改写（P2）

- **受众改写**："给高管压成 5 页"（合并、提炼结论页，生成新文件，不改原稿）、"给新人加背景页"。
- **保版式翻译**：整份翻译成英文/日文……逐框翻译后跑溢出检查，放不下先让模型压缩，再缩字号，最后报告给用户。中英文字体映射按主题的 `ea`/`latin` 槽位换。
- **批量替换**：术语、产品名、公司名、日期，模型理解变体（"Q3 / 三季度 / 第三季度"）。

#### 5.2.9 ⌘K 自然语言命令（P1）

**用户看到**：画布上按 ⌘K，输入"把这页三个卡片等宽等距，颜色统一成主题色""所有页标题改成 28 号""第 3 到 5 页删掉页码"。立即出提议预览。

**实现**：小模型 + 当前选区/页的结构 → `deck_edit` 的步骤。识别不了或范围太大，自动转到对话，带上上下文。也是一个统一的命令面板：普通命令（"插入表格""切换到大纲视图"）不走模型，直接模糊匹配。

## 6. 技术方案

### 6.1 总体架构

```
┌──────────────────────────────── 渲染进程（React） ───────────────────────────────┐
│ 对话 ── 引用块 / 出处标记 / 提议卡片                                              │
│ 文件面板 · 演示文稿                                                               │
│   FinX 外壳：功能区 · 上下文选项卡 · 选区浮条 · ⌘K · 右侧面板（设计建议/体检/批注）│
│   NimbleOffice 画布（pptx-react）── Worker（WASM 引擎，Yrs 副本）                  │
│        ▲ Yrs update / 提议 / 选区 ▼                                               │
└────────┼─────────────────────────────────────────────────────────────────────────┘
┌────────┼──────────────────────────────── finx serve ─────────────────────────────┐
│ finx-server：pptx/* 与 doc/* 方法、deck/changed、deck/proposal 事件               │
│ finx-core：deck 工具组（智能体）· 审批 · AI 动作编排（改写/版式/体检/生成）       │
│ finx-docs：DocStore ── DeckBackend                                                │
│ doc-worker 进程：pptx-edit DeckSession（权威）· 版式求解器 · 体检规则 · 光栅化    │
└──────────────────────────────────────────────────────────────────────────────────┘
finx-slide（纯 Rust）：NimbleOffice fork 门面 · fonts · check（体检规则）· layout（版式求解）
                       · template（模板分析）· link（数据链接）
```

### 6.2 关键决策：谁持有文稿

现在是"浏览器 Worker 持有文稿、整包序列化后交宿主写盘"。智能体要改打开着的文稿，有三种做法：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 桥接到前端 | 智能体工具经 RPC 转给渲染进程，调 `api.handleAsync().applyEdits/propose` | 改动最小，两周能通 | 面板没打开时智能体不能改；渲染进程崩了就断；无头生成要另起一套 |
| B. 内核权威 + 前端副本 | doc-worker 里开 `DeckSession`（pptx-edit，同一份 Rust 代码），编辑器用 `collaboration` 选项作为 Yrs 副本加入；人和智能体的编辑都经 CRDT 合并 | 面板开不开都能改；与表格的 DocStore 架构一致；保存只在内核；天然支持以后多窗口、多智能体并行 | 要接 Yrs 同步通道（引擎有 `encodeStateVector`/`applyUpdate`/`peer.rs`）；首次打开多一次同步 |
| C. 两份各自编辑、按文件合并 | 智能体改磁盘文件，前端检测冲突后重载 | 最简单 | 用户正在编辑时体验很差（现在的冲突提示就是这样） |

**建议 B**（PD-01，详细方案见 [presentation-kernel-authority.md](presentation-kernel-authority.md)），A 作为过渡：P0 前两周先做 A 跑通工具与提议，同时做 B 的同步通道，第三周切到 B。理由：AI 原生意味着智能体会经常在用户不看的时候改（生成、批量体检修复），A 撑不住；B 的每个零件 NimbleOffice 都有。

B 的细节：
- **打开**：`pptx/read` 改为 `deck/open`：内核读文件、建 DeckSession，返回 Yrs 状态 + 字体族；前端用 `collaboration.onReplica` 加入。字体和元文件的通道不变。
- **同步**：前端本地编辑立即生效（低延迟），update 经 RPC 发内核；内核的变更（智能体）推 update 给前端。用现有 RPC 的事件通道，不另起 WebSocket。
- **保存**：只有内核保存，沿用"基准哈希 + 路径锁 + 原子写 + 保存后自检"。前端 `PresentationDoc` 的保存队列退化成"请内核保存"。
- **撤销**：Yrs 的 UndoManager 按 origin 分栈：用户 ⌘Z 只撤用户自己的；AI 提议接受后作为一个单元，可在 AI 记录里单独撤（学 WorkBuddy 的 AI 编辑账本，但可视化）。
- **崩溃恢复**：内核定期把 Yrs 状态写进会话目录，渲染进程或 doc-worker 崩溃都能恢复未保存的修改。

### 6.3 操作模型

在引擎现有 `EditStep`（InsertText、ReplaceText、DeleteText、FormatText、SetParagraphAlignment、SetSlideNotes、SetSlideBackground、SetShapeRect、SetShapeFill、SetShapeStroke、SetShapeAdjust）基础上扩展，fork 里补：

```ts
type DeckOp =
  // 已有
  | { op: "insert_text" | "replace_text" | "delete_text" | "format_text" | ... }
  // 段落
  | { op: "set_paragraphs"; target: StoryTarget; paragraphs: ParagraphSpec[] }      // 文字+层级+符号+样式
  | { op: "set_paragraph_props"; target: TextTarget; bullet?: BulletSpec; level?: number;
      indent_pt?: number; line_spacing?: Spacing; space_before_pt?: number; space_after_pt?: number }
  | { op: "set_text_body"; shape: ShapeRef; vertical?: "horz"|"vert"|"eaVert"; anchor?: "t"|"ctr"|"b";
      autofit?: "none"|"shrink"|"resize"; insets_pt?: [number,number,number,number]; columns?: number }
  // 对象
  | { op: "add_shape"; slide: SlideRef; preset: string; rect: Rect; style?: ShapeStyle; text?: ParagraphSpec[]; name?: string }
  | { op: "add_picture" | "add_table" | "add_chart" | "add_connector"; ... }
  | { op: "transform"; shapes: ShapeRef[]; rect?: Rect; rotate_deg?: number; flip_h?: boolean; flip_v?: boolean }
  | { op: "group" | "ungroup"; shapes: ShapeRef[] }
  | { op: "z_order"; shape: ShapeRef; to: "front"|"back"|"forward"|"backward" }
  | { op: "delete_shapes"; shapes: ShapeRef[] }
  | { op: "fill_placeholder"; slide: SlideRef; placeholder: { type: string; idx?: number }; paragraphs: ParagraphSpec[] }
  // 表格、图表
  | { op: "table_edit"; shape: ShapeRef; ... }            // 行列、合并、单元格文字与样式
  | { op: "chart_data"; shape: ShapeRef; categories: string[]; series: SeriesSpec[] }
  | { op: "chart_style"; shape: ShapeRef; type?: ChartType; title?: string|null; legend?: ...; labels?: ... }
  // 页
  | { op: "insert_slide"; at: number; layout?: LayoutRef } | { op: "duplicate_slide" | "delete_slide" | "move_slide"; ... }
  | { op: "set_layout"; slide: SlideRef; layout: LayoutRef }
  | { op: "set_transition"; slide: SlideRef; kind: string; duration_ms?: number }
  | { op: "set_animation"; shape: ShapeRef; effect: string; trigger: "click"|"with"|"after"; order?: number }
  // 全局
  | { op: "set_theme_colors" | "set_theme_fonts"; ... } | { op: "set_section"; ... };
```

- **寻址用稳定 ID（PD-02）**：`SlideRef = { slide_id }`、`ShapeRef = { slide_id, shape_id }`，都是引擎快照里的 ID，插删不漂移。给模型看的摘要同时带"第 N 页"和 ID，模型说人话、调用用 ID。
- **带期望内容（PD-03）**：改文字的步骤带 `expect`（原文片段），引擎用已有的 `ContentMismatch` 拒绝过期修改；整批带 `DocumentVersion`，过期返回 `StaleVersion` 和最新摘要，智能体重读再改。这两样 WorkBuddy 都没有。
- **一批一个单位**：一次 `deck_edit` 的所有步骤要么都成为一个提议，要么都失败并说明哪一步、为什么；不允许半批落地。
- **对齐、分布、格式刷、快速样式**等界面命令在前端/内核算成上面的基本步骤，不进引擎。

### 6.4 提议与审阅

- 引擎已有提议的生命周期和审阅界面（"智能体提议 / 之前 / 提议 / 接受 / 拒绝 / 目标已更改"）。我们在外壳里补：
  - **画布内叠加**：当前页上直接显示提议后的样子，改动对象描边；左侧缩略栏带改动标记的页有小圆点。
  - **逐页、逐对象接受**：引擎提议目前是整体接受，fork 里补"按页拆分提议"（把一个提议的步骤按 slide_id 分组成子提议）。
  - **对话里的提议卡片**：沿用 desktop-design 的三行审批卡片："修改 方案.pptx？改了 4 页 · 替换 12 处文字、重排 2 页" + 缩略图前后对比 + 拒绝… / 本会话都允许 / 接受 ⌘↩。
- **审批模式**：读不需要审批；`deck_edit` 默认产生提议（等于"先问再改"）；用户可设"本会话直接应用"。写盘仍按现有 `write` 规则。

### 6.5 让 AI 看得见

- **确定性检查先行**：`finx-slide::check` 基于引擎布局结果（文字真实行高与溢出、对象包围盒），毫秒级，智能体每次编辑后自动附带结果。
- **渲染给模型看**：`deck_view(slide, region?)` 用本机光栅化出 PNG（`finx-slide::render_png` 已有），默认 1280 宽；改动前后可拼成一张对比图，省 token。
- **视觉评审**是可选的第二道：只在生成、版式候选排序、用户点"让它更好看"时调用，不是每步都调。
- 渲染保真是前提：把 memory 里记的已知缺口（CJK 粗体、标点度量、normAutofit、竖排、图表标题）排进 P0/P1 的引擎工作，并用 `tools/ppt-corpus` 的 PowerPoint 对照持续量化。

### 6.6 AI 动作编排

- **两类调用**：
  - **即时动作**（改写、精简、⌘K、单页版式）：不进对话历史，直接由前端发 `ai/action` 到内核，内核调模型（默认用快模型），返回提议。延迟目标：首个预览 < 1.5s。
  - **任务**（生成整份、整份体检修复、翻译整份、对比）：进对话，作为一次智能体回合，用 deck 工具组；面板实时显示进度。
- **提示词与技能**：PPT 技能文本放进 `finx-core/src/skills`，含：工具使用规则、写作规范、场景包、对用户只用用户术语（学 WorkBuddy）。场景包可由用户/团队扩展（目录 + manifest）。
- **上下文注入**：文稿打开时每轮附一个短块："正在看：方案.pptx · 第 4 页《市场规模》· 选中：标题 3"（与表格一致）。
- **模型选择**：即时动作用快模型；生成大纲、整份改写用强模型；视觉评审用支持图像的模型。都经现有 `finx-llm`，用户在设置里可换。

### 6.7 版式求解器（`finx-slide::layout`）

- **输入**：内容树、页面尺寸、可用区域（来自版式占位符或安全区）、主题（色、字体、字号阶梯）、候选模板集合。
- **候选模板**：参数化描述（JSON/Rust），例如"卡片阵列 n=2..6，横排或 2×k 网格，卡片内：图标?/标题/正文，等宽等距，基线对齐"。首批 15 个：标题+要点、两栏、图文左右、图文上下、三/四卡片、时间线横/竖、流程箭头、对比、大数字 KPI、引言、矩阵 2×2、金字塔、表格、图表+解读。
- **过程**：选模板 → 按内容量分配尺寸 → 调用引擎文字度量测量每个文本块（按字号阶梯下探，最多降两档）→ 打分 → 输出 DeckOp。
- **打分**：不溢出（硬约束）、填充率 60–90%、对齐线数量少、视觉主角突出（最大元素面积占比）、字号层级对比 ≥ 1.4 倍、与相邻页一致性（标题位置）。
- 纯函数，可快照测试；生成流程和版式候选共用。

### 6.8 模板分析（`finx-slide::template`）

- 读母版与版式：每个版式的名字、占位符（type、idx、区域、默认字号）、背景、装饰对象；主题色与字体；页脚/页码规则。
- 给版式打语义标签（标题页、节标题、标题+内容、两栏、比较、仅标题、空白、图片+说明），名字不规范的模板靠占位符组合推断，必要时让模型看一眼缩略图确认。
- 用户"我的模板"存在 `FINX_HOME/templates/`，只存文件和分析结果。

### 6.9 协议增量

| 方法/事件 | 说明 |
|---|---|
| `deck/open`、`deck/close` | 内核建/释放 DeckSession，返回 Yrs 状态、字体族、能力 |
| `deck/sync`（双向） | Yrs update |
| `deck/save` | 内核保存，返回新哈希 |
| `deck/proposal`（事件） | 提议新建/更新/接受/拒绝 |

| `deck/layouts` | 某页的版式候选（含缩略图） |

### 6.10 安全与隐私

- 文稿文字、批注、备注是不可信内容，里面写给智能体的"指令"不执行（同 PDF、表格的规则写进工具说明）。
- 渲染图和文字发给模型前，遵守用户的模型/隐私设置；企业用户可选"仅本机模型"时，视觉评审自动关闭。
- 数据链接只记录相对路径，不嵌入源数据全文。
- 生成图片、联网搜索素材都需要用户在本次任务里明确开启。

## 7. 智能体工具

延迟加载的 `deck` 组（与 `doc` 组同样的加载方式）。合并成少数几个粗粒度工具，避免 WorkBuddy 85 个工具反复查 schema 的往返。

| 工具 | 类别 | 说明 |
|---|---|---|
| `deck_open(path)` | 只读 | 打开（面板随之打开），返回**结构摘要**：页数、尺寸、模板版式清单、主题色字体、每页一行（页号、slide_id、版式、标题、对象数、是否有图表/表格/备注）。≤ 2,000 token |
| `deck_read(deck, slides, detail?)` | 只读 | 按页读：Markdown 正文 + 对象清单（shape_id、名字、类型、位置尺寸、占位符类型、文字与样式摘要）；`detail=full` 给段落与 run 级样式 |
| `deck_find(deck, query)` | 只读 | 文字/数字查找，返回锚点与上下文 |
| `deck_view(deck, slide, region?, compare_proposal?)` | 只读 | 渲染 PNG；可出提议前后对比图 |
| `deck_check(deck, slides?, rules?)` | 只读 | 体检，返回问题与可选修复步骤 |
| `deck_layouts(deck, slide, n?)` | 只读 | 版式候选（求解器结果，含每个候选的步骤和缩略图） |
| `deck_edit(deck, ops, note, version)` | 写 | 一批 DeckOp → 一个提议；返回提议 ID、每页改动摘要、自动体检结果 |
| `deck_generate(outline, template?, into?)` | 写 | 按大纲（结构化）生成/追加页，逐页回报进度；内部用求解器 + 体检闭环 |
| `deck_save(deck, path?)` | 写 | 同 `doc_save`，按 `write` 审批 |

使用规则（写进工具说明）：
- 引用数字附出处；改数字前先 `deck_find` 找全所有出现位置。
- 一组相关修改放一次 `deck_edit`，写清 `note`（"按 Q3 财报更新第 3–5 页的营收数据"）。
- 改完看 `deck_edit` 附带的体检结果；涉及版面的修改，至少 `deck_view` 看一次。
- 被拒绝（`StaleVersion`、`ContentMismatch`、`Unsupported`）时重读再改，不要绕过；`Unsupported` 告诉用户需要在 PowerPoint 里做。
- 对用户只说"页、标题、文本框、图表"，不说 slide_id、DeckOp、Yrs。

## 9. 验收与评测

- **保真**：`tools/ppt-corpus` 对照 PowerPoint 的像素差，每个版本出报告，均差不升。新增"编辑后保真"：对每个 DeckOp 做"改→存→PowerPoint 打开→导出图"的回归（PowerPoint 导出在本机脚本里跑）。
- **外科式**：每个 DeckOp 的保存都检查"未涉及部件逐字节不变"，沿用 `zipdiff.py`。
- **AI 质量**（放进 `finx-eval`）：
  - 改写：保留样式正确率（run 样式映射）、溢出率、人评。
  - 版式候选：50 页真实"难看页"语料，候选中至少一个被人评为"可直接用"的比例 ≥ 70%；零溢出。
  - 体检：人工标注 30 份 deck 的问题，召回 ≥ 80%、误报 ≤ 20%。
  - 生成：10 个题目 × 3 套模板，评"可直接用的页比例"、"数字出处正确率"（必须 100%）、生成时间。
  - 对照组：同题目同材料跑 WorkBuddy，盲评。
- **性能**：打开 50 页 20 MiB 文稿 < 3s 可编辑；同步延迟（智能体改 → 画布出现）< 300ms；即时动作首个预览 < 1.5s。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 前端 WASM 是发布版、原生是 fork，两边能力不一致 | 前端看到的和内核存的不一样 | 方案 B 后，前端 WASM 也从 fork 构建（自己出 npm 包或 vendored），一份代码两处用 |
| 动画/图表/主题的写入复杂度 | 写坏文件 | 不认识就保留原 XML；拒绝清单；保存后自检 |
| 生成质量不稳 | 口碑 | 大纲先行让用户把关；版式交给确定性求解器；体检兜底；先上 P1 再上生成 |
| 模型成本与延迟 | 即时动作卡顿 | 快模型 + 流式 + 只发相关页的结构，不发整份 |
| 视觉模型看图的隐私 | 企业用户顾虑 | 可关；本机模型模式下自动降级为纯规则检查 |
