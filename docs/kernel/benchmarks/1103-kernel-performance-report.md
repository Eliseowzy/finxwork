# 1103 内核场景仿真与性能压测最终报告

日期：2026-11-03（1103）

范围：模型与工具仿真资产、CLI / ACP / Unix socket / 原生 stdio、并发资源与启动性能。

代码基线：`e34315f7f07531850b40ebb0b3c52a49297a409f`；本批产出位于 `codex/kernel-simulation`。各阶段二进制与驱动 SHA-256 见随附数据。本文不包含测试机地址、登录别名或个人绝对路径。

## 1. 背景与结论

目标是让内核的模型调用、工具执行、长对话、协议处理和资源回收具备可重复、可审计的测试基础，再以同一工作负载检验性能优化。仅返回固定文本的模型 Mock 无法验证工具调用与续推，因此本批构建了协同工作的模型状态机、工具服务和真实内核负载驱动。

本批已实现五类场景，包含 220 轮连续任务；阶段 A 完成四协议各 200 并发和 1,792 个用户任务的完整套件验收。并发会话创建 P95 降低 33.2%、峰值物理内存降低 5.8%、吞吐提高 4.3%，但任务 P95 增加 13.3%。阶段 B 的 Linux 真任务启动 P50：CLI 7.841 → 3.090ms、ACP 9.576 → 4.227ms、Unix socket 9.265 → 4.922ms，分别降低约 60.6%、55.9%、46.9%。

**真实任务从新进程到首个模型请求的 2ms 目标尚未达到。** 本地查询命令的 2ms 均值门槛已经通过。常驻进程的亚 2ms 调用成绩不算冷启动成绩。阶段 A 的并发/内存数据不能视为最终阶段 B 二进制的并发复测结果。

## 2. 目标、指标与验收标准

| 项目 | 标准与当前状态 |
|---|---|
| 正确性 | 真实内核完成任务，调用参数、工具证据、回执、状态迁移及最终产物一致；契约错误必须失败。已通过相应场景验收 |
| 长对话 | 每个完整长场景超过 200 轮；本批为 220 轮，并强制覆盖上下文压缩 |
| 并发 | 四协议分别验证 200 个并发任务；阶段 A 已通过，后续优化仍需重复验证容量与尾延迟 |
| 真任务启动 | Linux 新进程创建 → 首个模型 HTTP 请求到达，目标 P50 ≤ 2ms；目前三种主要模式均未达标 |
| 本地命令 | `hyperfine -N` 原始进程墙钟均值 ≤ 2ms，预热后每次新进程，无 shell、无基线扣除；已通过 |
| 资源 | 观测 CPU、RSS、物理 footprint、线程、FD、关闭后内存；先正确再优化，不以牺牲尾延迟换取单项成绩 |
| 性能回归 | 仿真驱动默认比较启动、任务 P95、建会话 P95、峰值 footprint，20% 为报警阈值，不等同于性能目标 |
| 失败判定 | 超时、模型/工具契约错误、审计不一致、缺失有效内存采样均非零退出，不纳入成功样本 |

P50/P95/P99 描述延迟分布；阶段占比用逐样本区间的**均值**计算，不能用不同阶段的 P50 直接相减或相加。内存峰值取同一采样时刻所有存活目标进程之和的最大值。

## 3. 测试环境与条件

| 条件 | 环境 A：并发与 macOS 复测 | 环境 B：Linux 启动测试 |
|---|---|---|
| CPU / 内存 | Apple M2 Max，12 核，64 GiB | AMD EPYC-Milan，1 vCPU，约 2 GiB RAM |
| 操作系统 | macOS 27.2，arm64 | Debian 13.7，Linux 6.12.113+deb13-amd64，x86_64 |
| 工具链 / 构建 | Rust 1.99.1，release，thin LTO / 4 codegen units | Rust 1.99.1；优化前 GNU release，最终静态 musl dist，fat LTO / 1 codegen unit |
| 启动计时 | Python Popen 前开始，包含 Python 启动准备 | C 父进程在 fork 前取 CLOCK_MONOTONIC，包含 fork/exec/装载 |
| 统计 | 协议启动预热 10 次、采样 100 次 | CLI/协议真任务预热 10 次、采样 200 次；本地命令及阶段诊断采样 100 次 |

每个用例使用私有 HOME、FINX_HOME 和项目目录，模型目录指向本地测试服务，不使用真实模型密钥。并发采样间隔为 10ms，驱动自身 CPU/RSS 单独记录；驱动、Mock 与被测进程在同一主机运行。三组并发对照交错执行前后版本；启动对照轮换用例顺序，尽量分散背景负载影响。

启动测试使用 `hello`、零额外用户技能、内置工具定义、本地 HTTP SSE；不包含 DNS、TLS、真实推理或外部 MCP 服务启动。正式运行仍保留配置读取、日志和会话持久化。文件系统为暖缓存，每个样本重新创建进程；首次私有目录调用另行记录，不能解释为清空操作系统缓存的统计结果。Linux 构建方式变化也计入收益，不把全部改进归因于算法。

## 4. 仿真资产与测试体系

模型侧提供 OpenAI Chat Completions SSE，工具侧提供 MCP Streamable HTTP/stdio；运行的是实际内核。模型根据已验证的工具结果生成下一步调用，工具维护场景状态并计算结果。资料、企业和数值均为合成测试资产。

| 场景 | 用户轮次 | 每轮含工具的模型阶段 / 工具调用 | 验收重点 |
|---|---:|---:|---|
| 宏观研究 | 1 | 8 / 10 | 并行取数、口径处理、情景加权、证据审查；政策变化 -26.25bp |
| 企业研究 | 1 | 9 / 11 | 年报、分部、可比估值与敏感性；中枢 42，区间 32.4–51.6 |
| 财务研究 | 1 | 9 / 12 | 三表勾稽、现金利润比、压力测试；FCF 80、压力 FCF 26 |
| 编程任务 | 1 | 6 / 7 | 读取问题、预期测试失败、版本化补丁、边界回归、差异审查 |
| 长程任务 | 220 | 3 / 3 | 每轮读状态、核对交易、提交检查点；最终余额 24310 |

每轮另有最终模型回复，压缩会增加请求。长程场景常规为 880 次模型请求、660 次工具调用。编程工具维护虚拟源码并计算测试结果，不是任意源码执行沙箱；这批资产评价内核编排、协议和资源表现，不评价真实模型的研究能力。

调用必须满足精确参数、唯一调用 ID、匹配结果和摘要回执；跨步骤引用来自实际工具观察。漏结果、串会话、错参或损坏证据会失败。回执用于一致性校验，不是安全认证。上下文压缩通过已验证检查点恢复。仿真计划文本是人工编写的测试内容。

| B4：历史会话优化 | 大日志持久化摘要投影，设备/inode/大小/mtime/ctime 严格失效，64 KiB 上限、私有权限、原子替换；异常回退扫描，恢复会话不依赖投影 |

## 8. 三种模式耗时明细与瓶颈

以下是**墙钟均值及占总耗时比例**，不是 CPU 采样占比，也不是 P50 的相减。每行覆盖互不重叠的时间区间，合计为整条启动链路；包括进程调度、客户端协议往返和 Mock 的调度等待。暖文件缓存、每次新进程、正常日志及持久化、零额外用户技能，没有外部 MCP 启动、DNS、TLS 或真实模型推理。

| 阶段 | CLI | ACP | Unix socket |
|---|---:|---:|---:|
| 进程创建、装载至 main | 0.443 ms / 13.7% | 0.467 ms / 10.3% | 0.591 ms / 11.3% |
| 命令行参数解析 | 0.444 ms / 13.7% | 0.286 ms / 6.3% | 0.399 ms / 7.6% |
| Tokio 运行时构建 | 0.108 ms / 3.3% | 0.410 ms / 9.0% | 0.466 ms / 8.9% |
| HOME / 凭证入口、日志初始化 | 0.467 ms / 14.4% | 0.386 ms / 8.5% | 0.559 ms / 10.7% |
| 配置、模型目录、连接管理、服务对象 | 0.372 ms / 11.5% | 0.479 ms / 10.6% | 0.599 ms / 11.4% |
| 会话依赖、技能、提示词与内核创建 | 0.617 ms / 19.0% | 0.691 ms / 15.2% | 0.646 ms / 12.3% |
| 协议接入、RPC 与任务交接 | 0.118 ms / 3.7% | 1.068 ms / 23.6% | 1.214 ms / 23.1% |
| 上下文、HTTP 客户端及请求构造 | 0.217 ms / 6.7% | 0.185 ms / 4.1% | 0.247 ms / 4.7% |
| 本机 HTTP 发送与 Mock 调度 | 0.452 ms / 14.0% | 0.561 ms / 12.4% | 0.528 ms / 10.1% |
| **合计** | **3.239 ms** | **4.531 ms** | **5.248 ms** |

CLI 的“协议接入、RPC 与任务交接”只有进程内的任务提交与交接，没有协议握手。服务模式的这一行是两个区间之和：服务对象就绪到 session/new 处理开始，以及 Kernel::start 返回到任务执行开始。后一个区间包含会话注册、响应构造、客户端收到回复后发送 prompt，以及内核任务调度，不能整体归因于 JSON 编解码。

同源正式构建在前一轮 200 次无插桩测试中的首请求均值为 CLI **3.200 ms**、ACP **4.448 ms**、socket **5.148 ms**。诊断采样总耗时分别高约 1.2%、1.9%、1.9%；这是两轮测量差异，不能全部归因于插桩。性能成绩仍以无插桩报告为准。

### 各阶段进一步拆分

- **CLI 基础启动**：参数解析 0.444 ms，日志本身 0.344 ms，配置与工作区解析 0.177 ms，模型注册及其前置 MCP 配置处理 0.154 ms，连接管理器 0.041 ms。参数解析已按子命令延迟构建，仍有进一步降低固定开销的空间。
- **运行时**：CLI 当前线程运行时约 0.108 ms；ACP/socket 服务运行时约 0.410/0.466 ms。区间还含分发到运行时前的少量工作。服务采用工作线程池，包含可用 CPU 探测与线程创建；不能为降低启动数字直接牺牲并发处理能力。
- **会话准备**：CLI 的工具与环境依赖 0.150 ms，内核创建 0.466 ms；ACP 是工作区重新解析及依赖 0.203 ms、内核 0.487 ms；socket 是 0.192/0.454 ms。三个模式的技能扫描约 0.159–0.178 ms，提示词构建约 0.061–0.066 ms。会话日志对象创建约 0.029–0.033 ms，这里不含整个任务后续落盘耗时。
- **ACP 接入**：服务就绪到 initialize 处理开始 0.222 ms，initialize 处理到回复入队 0.049 ms，回复入队到 session/new 处理开始 0.235 ms；内核建好到任务开始 0.563 ms。源码显示建会话还构造配置选项并通告技能命令，但本次没有独立测量两者各自的时间，不能将最后一项全部归因于它们。
- **socket 接入**：目录权限、锁文件和服务记录约 0.145 ms；删除旧 socket 与 bind 约 0.041 ms；bind 完成到 accept 约 0.409 ms；accept 到 initialize handler 约 0.078 ms；initialize handler 到回复入队仅 0.021 ms。0.409 ms 区间包含权限设置、异步记录同步的调度、客户端 100 μs 连接探测和服务 accept 调度，不是纯 bind 或网络传输时间。
- **首请求准备**：HTTP 客户端构建三个模式约 0.051–0.055 ms；之后的鉴权、请求构造、序列化到 send 入口约 0.054 ms。没有观察到这些项占据主要比例。send 入口到 Mock 接收的 0.452–0.561 ms 则包含首次 TCP 连接、发送及双方调度，并非真实互联网延迟。

### 下一轮优化优先级

1. **服务接入与任务交接**：ACP/socket 合计约 24%/23%。继续细化 hub 注册、响应生成、stdio 线程和任务唤醒的时间，优先减少不必要的队列或调度往返；socket 同时改进连接发现的测量分辨率，明确观察者成本。
2. **共享初始化**：参数解析、日志初始化、配置/模型目录、内置工具注册。配置与目录类缓存要有明确失效规则，不能以忽略用户修改来换启动成绩。
3. **服务运行时启动**：约 0.4–0.47 ms。尝试优化线程及 CPU 配额探测路径，并同时验证多会话并发、取消和阻塞工具，保留吞吐与正确性。
4. **技能与提示词准备**：本例技能扫描约 0.16–0.18 ms；需要带 25/200 个用户技能复测，判断其扩展趋势。

进程装载和本机 HTTP/Mock 调度仍是真实端到端计时的一部分，不减掉它们。当前数据不支持将 TLS、外部工具启动或模型推理列为本次测试的瓶颈，因为本例没有执行这些工作。
