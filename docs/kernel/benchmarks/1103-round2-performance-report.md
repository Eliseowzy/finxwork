# 1103 第二轮：性能优化与损益

日期：2026-11-03

基线：`692cb94`（1103 批次合入后的主干）。本轮提交：`946c0c9`（去掉空闲连接上限）、`30e8112`（仿真驱动可按会话分连接）、`7582190`（会话日志共用硬盘冲刷）、`675ae81` 与 `7b48695`（日志默认级别不再解析过滤表达式）。原始对照数据见 [2026-11-03-round2-ratchet.json](2026-11-03-round2-ratchet.json)。

## 1. 结论

目标是逐项把性能提升 50%，任何一项都不许退化，也不能影响用户体验和产品功能。

| 指标 | 基线 | 现在 | 变化 | 50% |
|---|---:|---:|---:|---|
| 200 个会话满载：任务 p95 | 541 ms | 286 ms | −47% | 达到（单独对照 −50%） |
| 同上：每秒完成的任务 | 354 | 669 | +89% | 达到（约 2 倍） |
| 首包 100 ms 的 200 个会话：任务 p95 | 1885 ms | 1501 ms | −20% | 未达到，其中约 1.1 s 是模拟的模型与工具等待 |
| 服务端 CPU（两种负载） | — | — | −13% ～ −14% | 未达到 |
| 启动：Linux CLI / ACP / socket 首请求 p50 | 3.25 / 4.23 / 4.84 ms | 3.19 / 4.29 / 4.79 ms | ±2% 以内 | 未达到 |
| 启动：macOS CLI / ACP / socket 首请求 p50 | 6.21 / 8.24 / 8.35 ms | 6.32 / 8.21 / 8.41 ms | ±2% 以内 | 未达到 |
| 长任务（3000 轮）：每轮指令数 | 8.6 M | 8.6 M | 0 | 未达到 |
| 峰值占用 | 155 MiB | 157 ～ 170 MiB | 持平到 +9% | 未达到；增加来自保留空闲连接（D-96，已接受） |

正确性：四个协议各 448 个任务、210 次压缩全部通过。基线满载时 4 次中有 3 次出现会话失败（工具服务的连接被重置），现在为 0。

## 2. 方法

- 同一台机器、同一个驱动，基线与候选交替运行，取中位数，用双侧 Mann-Whitney U 检验。变化超过 2% 且 p < 0.05 才算显著；启动类指标在两次重编之间会有 ±2% 的漂移，必须复现才算数。
- macOS：Apple M2 Max 12 核，release 构建，启动用 Python 计时（每项 100 次）。Linux：1 vCPU 的 AMD EPYC-Milan，静态 musl dist 构建，fork 之前取时（每项 200 次）。
- 负载：`finx-sim` 原生协议、宏观研究场景、200 个会话，每边 4 次。真实延迟模式（首包 100 ms、块间 1 ms、工具 10 ms、共用一条连接）代表一个窗口里的多个会话；满载模式（不等待、每个会话一条连接、3 波）代表多个客户端。
- 原来所有会话共用驱动的一条连接，满载时 session/new 的回复排在大量流式事件之后，量到的主要是这段排队，现在可以按会话分连接（`--connection-per-session`）。

## 3. 本轮改动

| 改动 | 收益 | 代价 |
|---|---|---|
| 会话日志共用硬盘冲刷（D-97）：macOS 上各自 fsync，再共用一次 F_FULLFSYNC | 满载任务 p95 −50%、吞吐 2 倍、CPU −10%；真实延迟 p95 −20%、吞吐 +25% | 无。落盘保证不变，单个会话的耗时不变 |
| 去掉每个 host 32 个空闲连接的上限（D-96） | 任务延迟 −2% ～ −9%，CPU −7%，不再因连接被重置而失败 | 突发后的空闲连接留到 30 秒超时；峰值占用 +1% ～ +9% |
| 日志默认用固定级别 | 省掉过滤表达式的解析，Linux 上测不出差异 | 无 |

撤回的做法：把日志文件改到第一行日志到来时再打开。它只是把工作挪了位置：socket 模式下正好撞上第一个 session/new，使其变慢 20 ～ 55 µs，已撤回（`7b48695`）。

## 4. 没有达到 50% 的指标

### 4.1 启动

耗时摊在各阶段的冷代码上，不是计算本身：
- clap 第一次解析要 557 µs，之后每次 34 µs；
- 一次 `finx exec` 有 389 次缺页，空进程只有 56 次；
- Linux 上 CLI 各阶段：参数解析 0.41、建会话 0.45（其中技能扫描 0.19）、配置与模型目录 0.35、本机发送 0.42、进程装载 0.36、日志 0.23 ms。

| 做法 | 预计收益 | 代价 |
|---|---|---|
| 逐项少做事：技能扫描不再为提示读其他应用的目录、内置技能免读盘、推迟不必要的初始化 | −5% ～ −10% | 改动分散，风险低 |
| exec / acp / serve 的手写快速解析，其余交给 clap | −0.3 ms（Linux CLI 约 −10%） | 两套解析需要差分测试，新增参数时要维护 |
| PGO 加函数排序 | −10% ～ −20%（未实测） | 发布构建多一轮插桩、采样、重编，时间约 2 ～ 3 倍；要改 CI 与发布流程，需安装 llvm-tools |
| macOS：不再链接 CoreFoundation / Security / CoreServices，用到时再加载 | 每次启动 −1 ms（macOS CLI 约 −15%） | 证书校验、时区、文件监听改成手写 FFI，安全敏感，风险高 |

在这台 macOS 上，只要链接 CoreFoundation 或 Security，启动时装载的镜像就从 82 个变成 704 个。文件监听库 `notify` 链接的 CoreServices 只再多约 0.1 ms。
- 四项全做，预计 −30% ～ −45%，达到 50% 没有把握。
- 用户感知：启动 3 ～ 8 ms，而模型首包通常在 300 ms 以上；桌面端的常驻服务每次打开 App 才启动一次。
- **建议**：只做第一项；后三项除非有大量短命令调用的场景，否则不值得。

### 4.2 长任务每轮开销

3000 轮的任务每轮约 860 万条指令、1 ms CPU。按采样，大头是：
- write / edit 工具的原子写入（写屏障加 rename），占 33%；
- 每轮把整段历史重新序列化成请求体，占 18%；
- bash 子进程，占 5%。

| 做法 | 预计收益 | 代价 |
|---|---|---|
| 缓存每条消息的序列化结果，只序列化新增部分（Q-96） | 每轮 CPU −15% ～ −20% | 每个运行中的长会话多占一份上下文大小的内存，约 0.3 ～ 0.8 MB，内存这一项会退化 |
| 更快的 JSON 转义（SIMD） | −5% ～ −8% | 新依赖或 unsafe 代码 |
| 去掉写工具的写屏障 | 约 −30% | 崩溃时用户文件可能损坏（D-104），**不建议** |

不牺牲安全或内存，最多约 −25%。

### 4.3 服务端 CPU

已降 13% ～ 14%。剩下的热点分散：日志写入的系统调用、新建会话日志的 open/stat、malloc、JSON。另外 tokio 阻塞线程池的锁等待很多，因为会话日志每一批都要 `spawn_blocking` 一次。

| 做法 | 预计收益 | 代价 |
|---|---|---|
| 会话日志改由专用写线程处理，不再每批 `spawn_blocking` | −3% ～ −5%，尾延迟更稳 | 低 |
| 请求之间共享系统提示词和工具定义，不再每次深拷贝 | −2% ～ −4% | 低，改动 Context 类型 |
| 缓存系统提示词加工具定义的序列化片段 | −2% ～ −3% | 每个会话几十 KiB |
| 新建会话日志时不重复创建目录 | 高频新建时 −2% ～ −4% | 低 |

合计预计再降 10% ～ 15%，总计约 −25%。到 50% 需要跨会话合并事件和日志写入，属于架构改动。

### 4.4 内存

本轮没有处理。
- 长会话：压缩之前的历史不再留在内存（Q-92），可省掉多次压缩后约八成的历史内存；代价是翻看旧记录要从日志读回。
- 200 个会话的峰值：需要先做一次堆分析，看连接读缓冲、请求体缓冲和会话状态各占多少。

### 4.5 真实网络下的首包（建议新增的指标）

本地明文 Mock 测不到 DNS、TCP 与 TLS 建连，连真实服务商时通常要 100 ～ 300 ms，这才是用户能感觉到的部分。
- 先给基准加一个 HTTPS 加网络延迟的场景；
- 再评估在新建会话或开始输入时提前建连：首条消息的首包可以少一次握手。

## 5. 需要决策的事项

1. **启动**：PGO、快速参数解析、macOS 框架按需加载三项代价高、用户感知弱。建议不做，只做低风险的逐项优化。
2. **长任务**：是否用内存换 CPU（Q-96）。建议暂不做。
3. **内存**：是否做 Q-92。建议先做堆分析再定。
4. **真实网络首包**：建议补基准，并评估提前建连。
5. **Q-19 与 Q-95**：共用冲刷已经消除了并发排队，改用普通 fsync 只能再省单个任务结束时的约 4 ms。建议维持现状。
