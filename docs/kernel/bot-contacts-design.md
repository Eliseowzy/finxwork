## 方案摘要

- **定位**：模型的能力会趋同，一个 Bot 和另一个 Bot 的差别是它背后的 context：数据、记忆、权限、它代表谁。主人自己的 context 都可以交给自己的 Bot；A2A 解决的是够得着别人的 context。
- **通讯录里的好友是另一个主体的代理人**：一家机构的、另一个人的。不是"会另一种本事的 Bot"，所以不给本地 Bot 预设人设和专属技能（§12）。
- **一期：外部 Bot 直接聊**。"新建 Bot"改成"添加 Bot"，多一种来源：粘贴链接，服务读对方的 A2A 名片，主人看过确认，列表里多一个人。对话由对方回答，本机只转发和记录。
- **外部 Bot 复用现有的一切**：它仍然是一个 Bot 会话。对方的回复由内核记成和 `send_to_user` 相同的条目和事件，所以列表的最近一句、未读、在忙、通知、气泡、文件预览都不用改。
- **发出去的只有主人打的字和贴的图**。现在的附件、正在看的文件、网页批注都是桌面端拼给本地模型看的文字块，里面是本机的绝对路径，对外部 Bot 一律不拼。给对方发文件一期不做。
- **外部 Bot 碰不到这台机器**：没有工具、文件、浏览器，只能回文字和文件。一期它的回复不进任何本地模型的上下文。
- **二期方向：代办**。直接聊只是把 A2A 当传输用。它真正的用处是主人的 Bot 带着主人的 context，替主人去和对方的 Bot 谈："帮我约下周二的号"。做法沿用 Bot 调度会话的那一套，发出去的每句话先给主人看。
- **第一个对方**：本机的 a2a-demo，一个接了大模型的聊天服务。传输这一层对着它实测通过（§5.7）。它没有自己的数据，能验证"连得上、聊得通"，验证不了"对方有我没有的 context"，所以入口先用配置项藏着（§5.8）。
- **工作量**：一期约 16 人天（§10）。

## 1. 定位与目标

### 1.1 定位

主人的判断（2026-11-14）：驱动 Bot 的模型，能力最终会趋同。Bot 之间真正的差别是交给它们的东西，也就是 context。

由此得到三条：

1. **A2A 用来接入别的主体的 context**（D-710）。医院的号源和病历、银行的账户、朋友的日程，这些对方不会也不能交给主人的 Bot，只能让对方的 Bot 守着，两边对话。
2. **能装到自己 Bot 上的，不做成外部 Bot**。一样东西如果是工具加做法，就做成连接器或技能，在主人的 Bot 里、带着主人的 context 运行。只有对方必须保留自己的状态、规则和判断时，才是外部 Bot。
3. **本地不预设"不同本事的 Bot"**（D-711）。同一个主人、同一个模型，把自己的 context 预先切成几份没有理由。

A2A 协议本身也是这个假设：它把每个智能体当黑盒，只看名片上声明的能力和交换的消息，不关心里面是什么模型、什么工具、什么记忆。协议里没有人设、角色模板这类概念；名片上的 `skills` 是对方声明的"我提供什么服务"，供发现和选择用。

### 1.2 目标

| 编号 | 目标 |
|---|---|
| CG1 | 加一个外部 Bot 像加好友：看得到是谁、哪家的、能办什么，确认一下就加上 |
| CG2 | 主人始终清楚自己的话发给了谁、发了什么 |
| CG3 | 外部 Bot 伤不到这台机器和主人的其他数据 |
| CG4 | 内核不认识任何对端和协议，只认一个对端接口 |
| CG5 | 二期能代办：主人的 Bot 带着主人的 context 去和外部 Bot 谈 |

原则：

- **复用**：外部 Bot 是 Bot 会话。日志、列表、未读、通知、气泡、文件预览照用。代办沿用 Bot 调度会话的做法（Bot 方案 §10）。
- **在拥有它的那一层改**："谁来回答"放在任务循环那一步，"给对方发什么"放在拼输入那一步，别处不打补丁。
- **最小可用**：每期只做跑通所需的，其余列进 §14 和"不做"。

**不做**：

- 专长 Bot、人设、Bot 自己的技能（PRD DD-99 不变，理由见 §12）。
- 把自己的 Bot 发布成 A2A 名片让别人加。需要一个公网可达的服务，桌面应用没有。所以外部 Bot 不能主动找上门，只能主人这边先开口。
- 外部 Bot 的市场、评分、排行、精选名单。
- 给外部 Bot 定时发消息。
- 群聊、外部 Bot 之间互相说话（Bot 方案 §16，三期）。
- ACP 接入本机智能体（§12）。
- A2A 的 gRPC 和 HTTP+JSON 绑定、推送通知、名片签名的验证、OAuth 和双向 TLS。

### 1.3 本地的多个 Bot

"为什么要建第二个本地 Bot"这个问题还在。按上面的定位，答案是让每个 Bot 的 context 各自成立：

- **记忆**：工作的事和家里的事各是一段对话，互不混。现在的 Bot 已经是这样（一个 Bot 一段对话、一个文件夹、一组定时任务）。跨对话的长期记忆在 Bot 方案 §16，没有做。
- **授权范围**：这个 Bot 能用哪些连接器、能看哪些文件夹、能联系哪些外部 Bot。现在所有 Bot 共用一套。

这两样由主人自己定，不由预设的模板定。它们不在本文范围内，只有一处例外：二期要有"这个 Bot 能联系谁"（§6.3），那是第一个按 Bot 分的授权。

## 2. 现状

- **来源两种**：第一次 `bots/subscribe` 时自动建的 FinxBot；`bots/create` 新建的。代码里建 Bot 只有这两处（`crates/finx-server/src/bots.rs` 的 `make_default_bot`、`bots_create`）。
- **都是同一种东西**：身份（`bot.json`）加一个 finx 内核会话，提示词是同一份 `bot.md`。差别只有名字、头像、模型、思考强度、权限模式，以及各自的对话、文件夹和定时任务。
- **主人的消息怎么拼**：协议的输入只有文字和图片两种（`UserContent::Text`、`Image`）。附件、正在看的文件、网页批注、文档引用、交给它的标签页，都是桌面端拼出来的文字块（`composer/attachments.ts` 的 `toInput`、`steps.ts` 的 `attachedBlock`、`files/state` 的 `viewingBlock`），写给本地模型看：一行说明，下面是本机的绝对路径。
- **ACP**：`crates/finx-acp` 让编辑器驱动 finx，finx 是被驱动的一方。反过来驱动别的智能体的能力没有。
- **A2A**：没有。

## 3. 名片与来源

做完一期以后 Bot 有三种来源，用户看到的是同一个列表：

| 来源 | 谁回答 | context 是谁的 |
|---|---|---|
| 默认 Bot（FinxBot） | 本机内核 | 主人的 |
| 新建的 Bot | 本机内核 | 主人的 |
| 外部 Bot | 对端 | 对方的 |

`bot.json` 升到版本 2，外部 Bot 多一个 `source`。没有 `source` 的是本地 Bot，旧文件照常读（D-700）。

```json
{ "version": 2, "id": "0193…", "name": "某医院预约助手", "…": "…",
  "source": {
    "kind": "remote", "protocol": "a2a",
    "card_url": "https://example-hospital.cn/.well-known/agent-card.json",
    "endpoint": "https://example-hospital.cn/a2a",
    "card_sha256": "…", "card_read_at": "2026-11-14T12:00:00Z",
    "description": "查询科室排班，预约和改约门诊。",
    "provider": "某某医院",
    "skills": [{ "name": "查排班", "description": "按科室和日期查医生出诊时间。" }],
    "accepts": ["text", "image"],
    "auth": "api_key",
    "noticed": false
  } }
```

- 名字和头像加进来以后归主人，可以改，相当于备注。名片更新不会改掉它们（§5.6）。
- 凭证不进 `bot.json`。它在钥匙串里的名字固定是 `bot.<bot_id>`（§5.6）。
- `noticed`：第一次发消息前的提示看过了（§4.3）。记在这里，换一台设备的界面也不再问。

## 4. 用户看到的

### 4.1 入口

- 导航第一行"新建 Bot"改成"添加 Bot"，Bot 模式下仍是 ⌘N（DD-180）。
- 点开的表单两段：
  - **新建**：现在的表单原样（名字、头像、模型、思考强度）。
  - **添加别人的 Bot**：一个输入框，占位"粘贴对方给的链接"，下面一句说明："对方是另一家机构或另一个人的 Bot。你发给它的内容会发到对方那里。"
- 配置项 `bots.external` 没打开时（§5.8），导航和表单都和现在一样，没有第二段。

### 4.2 加一个外部 Bot

1. 粘贴链接，按 ↩。输入框下面转圈："正在读取名片…"。
2. 出确认页（DD-182），从上到下：
   - 头像、名字、一句说明；
   - **提供方和域名**，域名用等宽字体完整显示，带端口。名片没写提供方时这一行只有域名；
   - 能办什么：名片的 `skills`，一行一个，名字加一句说明，最多显示 6 条，多的折叠；
   - 一段固定的话："你发给它的文字和图片会离开这台 Mac，发到 {域名}。它看不到你的其他对话和文件，也操作不了这台电脑。"对方在回环地址上时（§5.8）前半句换成"你发给它的文字和图片会发给这台 Mac 上的另一个服务（{域名}）。"，第一次发消息前的提示（§4.3）同样换；
   - 需要凭证时，一个输入框（Key 或令牌），下面一句"保存在这台 Mac 的钥匙串里"；
   - 按钮："添加"和"取消"。
3. 点"添加"，列表里多一个 Bot，进到它的对话。

出不了确认页时，输入框下面一行红字说明原因：

| 情况 | 文字 |
|---|---|
| 连不上、超时、不是 HTTPS、内网地址 | 读不到这个链接上的名片。 |
| 不是名片，或缺必要的内容 | 这个链接上的不是一张能用的名片。 |
| 没有支持的接入方式，或要登录 | 它用的接入方式这个版本还不支持。 |
| 名片里的接口地址和名片不在同一个地址 | 名片指向了另一个地址（{接口的域名}），不能添加。 |

名片上 `provider`、`iconUrl` 都是可选的。没有图标时随机配一个小角色，和新建 Bot 一样。

### 4.3 看得出来是谁

- **列表**：外部 Bot 的头像右下角有一个小标记（链接形状），本地 Bot 没有（DD-183）。
- **顶栏**：外部 Bot 的名字下面一行小字是域名。
- **第一次发消息前**：输入框上方一张提示（和 PRD §6.4 第一次选模型的提示同一个位置和形状）："你发给 {名字} 的内容会发到 {域名}。"，一个"知道了"。每个外部 Bot 一次。

### 4.4 Bot 设置

| 行 | 本地 Bot | 外部 Bot |
|---|---|---|
| 名字、头像 | 有 | 有（本机的备注） |
| 说明 | 没有 | 名片的说明、提供方、域名、能办什么 |
| 模型、思考强度 | 有 | 没有 |
| 权限模式 | 有 | 没有：它在本机什么也做不了 |
| 凭证 | 没有 | 需要凭证的有：换一个、清掉 |
| 静音、清空、删除 | 有 | 有。清空也让对方那边的对话重新开始（§5.5） |

### 4.5 外部 Bot 的对话

- 气泡、文件、提问和本地 Bot 一样（PRD §6.6）。对方在处理时头像在动。
- **输入框只有三样**：打字、贴图片、引用对话里的话（§5.4）。没有"+"菜单里的添加文件和文件夹，没有 `/` 的技能和命令，从文件面板、内置浏览器往输入框送的批注和引用不接。
- 对方收不了图片时（名片只写了文字），贴图片会提示"{名字} 收不了图片"。
- 没有授权窗口，没有"它在忙"的子智能体气泡，没有定时任务的时钟图标。
- 文件面板有（对方发来的文件在里面）。链接照常在内置浏览器打开，对方操作不了浏览器。
- 对方文字里写的本机图片不显示，文件标签只认它自己发来的文件（DD-185，§8）。
- 对方出错或连不上时是失败卡，可以重试，和本地 Bot 的失败相同（PRD F16）。
- 对方很久不回时，可以不等了（§5.5，DD-186）。

## 5. 一期：外部 Bot 直接聊

### 5.1 用到 A2A 的哪些部分

| 用 | 不用 |
|---|---|
| Agent Card：`name`、`description`、`iconUrl`、`provider`、`skills`、`supportedInterfaces`、`capabilities.streaming`、`securitySchemes`、`securityRequirements`、`defaultInputModes` | `signatures`（§5.2）；扩展名片（`GetExtendedAgentCard`） |
| JSON-RPC 绑定 | gRPC 绑定；HTTP+JSON 绑定 |
| `SendStreamingMessage`；名片的 `capabilities.streaming` 不为真时用 `SendMessage`，回来的任务没结束就用 `GetTask` 轮询 | 推送通知的四个方法：要公网可达的回调地址 |
| `GetTask`、`SubscribeToTask`：断线后接上 | `ListTasks` |
| `CancelTask`：清空、删除、不等了 | |
| 认证：无、API Key（放请求头）、HTTP Bearer | OAuth2、OpenID Connect、双向 TLS；API Key 放查询串或 Cookie |

- **选接口**（D-709）：取名片 `supportedInterfaces` 里 `protocolBinding` 为 `JSONRPC`、`protocolVersion` 为 `1.0` 的那一项；它带 `tenant` 时请求里原样带上。没有这样的一项时不能添加。
- **版本头**：每个请求带 `A2A-Version: 1.0`。实测不带时对方按 0.3 处理，返回 `VERSION_NOT_SUPPORTED`（§5.7）。
- **认错误**：按 JSON-RPC `error.data[]` 里的 `reason`（`TASK_NOT_FOUND` 这类大写的名字），不按数字的错误码。
- 规范还在变，开工时按当时的版本再核一遍方法名和字段（本文核对的是 2026-11-14 的 1.0.0）。

### 5.2 读名片

`bots/preview { url }`，服务层做，桌面端不直接访问对方：

1. **找名片**：链接本身返回 JSON 就用它；否则取它的源，读 `/.well-known/agent-card.json`。
2. **限制**：只走 HTTPS；不跟到别的主机的跳转；10 秒超时；名片最大 256 KB。解析到内网和本机地址的拒绝，连接建立后再按实际连上的地址判断一次（防 DNS 重绑定）。本机地址的例外见 §5.8。
3. **校验**：必填字段齐全；选得出接口（§5.1）；凭证方案是支持的三种之一。
4. **接口必须和名片同源**（D-706）：协议、主机、端口都相同。不同就拒绝，错误里带上接口的域名。
   - 这条会拦住配置不当的对方。a2a-demo 的接口地址取自它自己的配置项 `PUBLIC_URL`（默认 `http://localhost:9999`），用 `http://127.0.0.1:9999` 去读名片，名片里写的仍是 `localhost`，同源检查不过。这是对的：换成 `localhost` 去加就行。
5. **不验签**（D-714）：名片有 `signatures` 也不看，确认页不显示任何"已验证"。原因见 §12。
6. **图标**：服务层下载 `iconUrl`（同样的限制，最大 1 MB），解码后重新编码成 256 × 256 的 PNG，和上传头像走同一条路。渲染进程不加载对方的地址。下载失败当作没有图标。
7. **收什么**：`defaultInputModes` 里有 `text/*` 记 `text`，有 `image/*` 记 `image`。一期只认这两样（§5.4）。没有 `text` 的不能添加。
8. **哈希**：对用到的字段（名字、说明、提供方、接口、凭证方案、收什么、`skills` 的名字和说明）按固定顺序重新序列化后取 SHA-256。名片里无关的内容变了不算变。
9. 返回预览（§7）。

确认时 `bots/add` 再读一次名片，哈希和预览时不同就拒绝（`bot_card_changed`），让主人重新看。

### 5.3 对话怎么跑：对端任务

外部 Bot 的会话仍然是一个内核会话，头部除了 `bot` 再记 `peer`。区别只在任务循环：不拼提示词、不请求模型、不执行工具，把主人的话交给对端，把对端说的记下来（D-703）。

```rust
/// 替一个会话回答的外部服务。内核不知道它用什么协议。
#[async_trait]
pub trait Peer: Send + Sync {
    /// 发一条消息，返回对端这一轮的事件。
    async fn send(&self, message: PeerMessage, thread: &PeerThread, cancel: &CancellationToken)
        -> Result<BoxStream<'static, PeerEvent>, PeerError>;
    /// 接上一个还没结束的任务：先查，结束了就把结果作为事件给出，没结束就订阅。
    async fn resume(&self, thread: &PeerThread, cancel: &CancellationToken)
        -> Result<BoxStream<'static, PeerEvent>, PeerError>;
    /// 叫停，尽力而为。
    async fn cancel(&self, thread: &PeerThread);
}

/// 发给对端的：主人的字和图，别的没有。
pub struct PeerMessage { pub id: String, pub text: String, pub images: Vec<PeerImage> }

/// 对端那边这段对话和当前任务的标识。
pub struct PeerThread { pub context_id: Option<String>, pub task_id: Option<String> }

pub enum PeerEvent {
    /// 对话和任务的标识：第一个事件，之后变了再给。
    Thread(PeerThread),
    /// 对端还在做。只用来证明连接是活的。
    Working,
    /// 对端说的一段完整的话。
    Said { text: String },
    /// 对端给的文件的内容，还没落盘。
    File { name: String, media_type: Option<String>, bytes: Bytes },
    /// 对端在等这边回答。
    Asked { text: String },
    Done,
    Failed(PeerError),
}
```

- **位置**：`Peer` 和 `run_peer_task` 在 `finx-core`（新 `peer.rs`，`task.rs` 里 `run_task` 的旁边），内核不依赖网络库。A2A 的实现在新的 `crates/finx-a2a`，由服务层建好放进 `KernelDeps.peer`。
- **会话中枢不变**：`Hub` 拿到的仍然是一个 `Kernel`，照样发 Op、收事件。任务的开始和结束走 `task_main`、`finish_task` 现有的路，所以"在忙"和失败卡不用另做。

**启动和恢复**（D-716）：

- `StartOptions.model` 现在是必填的字符串，`start_bot_session` 没有可用的模型时返回 `no_model`。对端会话不需要模型：`StartOptions` 加 `peer: Option<PeerRef>`，有它时不解析模型，头部的模型记 `a2a`，思考强度和权限模式用默认值，不拼系统提示词，不挂任何工具。主人没配模型也能加外部 Bot、和它说话。
- 恢复会话走的是通用的 `load_session`。它看到头部有 `peer`，按头部的 `bot.id` 从登记表取 `source`，重新建一个 `Peer` 放进 `KernelDeps`。Bot 已经不在或不再是外部的，会话打不开，返回 `bot_not_found`。

**记什么、不记什么**：

- 主人的话照常 `record_user`。本地 Bot 在每句话后面记一条给模型的回话提示（`EntryKind::ReplyNudge`），对端会话不记：`session.rs` 里的条件从"是 Bot"改成"是 Bot 且不是对端会话"。
- 没回话的提醒（`bot::owed`）、日期更新、改名的环境更新、信件、压缩、上下文检查，对端任务都不做。
- 历史只在本机，按 `history_limit` 分页读，不会因为长而需要压缩。
- **不适用的操作**返回 `bot_not_supported`：换模型和思考强度、换权限模式、压缩、从前面某一句重来（对方回不到那句之前）。中断可以用（§5.5）。

**对端说的话怎么记**（D-704）：和本地 Bot 调一次 `send_to_user` 时完全相同的条目和事件。

| 顺序 | 条目 | 事件 |
|---|---|---|
| 1 | 一条助手消息，内容是一次 `send_to_user` 调用；`provider` 记 `a2a`，`model` 记对方的域名 | `MessageCompleted` |
| 2 | | `ToolStarted { name: "send_to_user", args }` |
| 3 | 工具结果，成功，文字"Sent."；带文件时 `details` 是 `{ files, text }` | `ToolCompleted` |

- 服务层的 `Registry::on_event` 从第 2、3 步的事件算最近一句和未读，客户端的 `botChat.ts` 从第 1 步的调用和第 3 步的结果画气泡。两边都不用知道外部 Bot 的存在，通知、搜索、引用也是。
- 文件的 `details` 用 `bot.rs` 现有的 `sent_file` 生成（大小、是不是图片、宽高），形状和本地 Bot 的一致。
- 这不是伪造：`send_to_user` 的含义是"这是唯一送到主人那里的东西"，对端任务替对端调用它，决定什么送到主人那里。日志里从 `provider` 和头部的 `peer` 看得出不是本机模型说的。
- 没有私有文字：对端的中间输出不记。

**A2A 到气泡的对应**：

| 对端给的 | `PeerEvent` | 记成 | 主人看到 |
|---|---|---|---|
| 第一个事件 `task`，带两个标识 | `Thread` | 条目 `PeerThread` | 没有变化 |
| 任务 `SUBMITTED`、`WORKING`，不管带不带文字 | `Working` | 不记 | 头像在动 |
| 直接回一条 Message，文字 | `Said` | `send_to_user { type: text }` | 一个文字气泡 |
| Artifact 的文字，分片收齐以后 | `Said` | `send_to_user { type: text }` | 一个文字气泡 |
| Artifact 或 Message 里的文件（`raw`） | `File` | 存进 Bot 的文件夹，`send_to_user { type: attachment }` | 文件气泡，点开是预览 |
| 文件给的是地址（`url`） | 并进 `Said` | 不下载；地址写进文字 | 气泡里一个链接，主人点了在内置浏览器打开 |
| 结构化数据（`data`） | `File` | 存成 `.json` 文件，按文件发 | 文件气泡 |
| `INPUT_REQUIRED` | `Asked` | `send_to_user { type: question }`，不带选项；任务标识留着 | 提问气泡；主人的下一句发给同一个任务 |
| `AUTH_REQUIRED` | `Failed` | 任务失败，错误 `bot_auth_required` | 失败卡："{名字} 需要重新验证"，按钮打开 Bot 设置的凭证 |
| `COMPLETED` | `Done` | 任务正常结束 | 头像不动了 |
| `FAILED`、`REJECTED` | `Failed` | 任务失败，原因取 `status.message` 的文字 | 失败卡，可以重试 |
| `CANCELED` | `Done` | 任务结束 | 没有变化 |

`finx-a2a` 把 A2A 的事件变成 `PeerEvent` 时的规则：

- **整条才出**：分片的 Artifact 收到最后一片才给 `Said`，主人只看到写完的话（Bot 方案 BG3）。对方处理中发来的进展文字不显示：有的服务把逐字的输出当进展发，显示出来会刷屏。
- **分片怎么拼**：同一个 `artifactId` 的文字直接相连，中间不加任何分隔。`append`、`lastChunk` 不出现时按假算（对方省略缺省值，第一片就没有这两个字段）。最后一片可以是空文字，只为带 `lastChunk`。不流式时对方把各片放在同一个 Artifact 的多个 `parts` 里，同样直接相连。流结束了还没见到 `lastChunk` 的 Artifact，在终态到来时按已收到的算完整。
- **以 Artifact 为准，不重复出气泡**：a2a-demo 在 `COMPLETED` 的 `status.message` 里把完整的回复又放了一遍。一个任务给过文字的 Artifact，`COMPLETED` 的 `status.message` 就不再给 `Said`；没有给过时，它才是回复。
- **空的不出**：去掉首尾空白后是空的文字不给 `Said`。任务结束时一个 `Said`、`File`、`Asked` 都没有，记一条失败 `no_reply`，和本地 Bot 没回话相同（Bot 方案 D-321）。
- **流的外壳**：每个 `data:` 行是一个完整的 JSON-RPC 响应，`result` 里是 `task`、`statusUpdate`、`artifactUpdate`、`message` 之一（附录 B.2）。
- **活着的证明**：收到的事件不产生别的 `PeerEvent` 时（比如中间的分片）给一个 `Working`。对端任务靠它判断 60 秒有没有动静（§5.5）。

**对端给的文件**（`run_peer_task` 落盘）：

- 存进 `bots/<id>/files/`。文件名只取对方给的名字的最后一段，去掉路径分隔符和控制字符，开头的点换成下划线，最长 120 个字符；没有名字时用 `file` 加按类型猜的扩展名。重名时在扩展名前加 `-2`、`-3`。
- 单个最大 50 MB，一个任务合计 200 MB。上限在传输层就生效：边读边数（文件按解码后、文本按收下的字节计），到了上限就停止读取、结束这一轮，任务失败（`bot_peer_too_large`），不会先把整个文件读进内存再判断。
- 同一个任务的几个文件合成一个文件气泡，这个任务的文字作为它上面的话。

### 5.4 给对方发什么

**只发主人打的字和贴的图**（D-715）。

- 现在主人的消息里，除了字和图，还有桌面端拼的文字块（§2）：附件的绝对路径、正在看的文件、网页批注、文档引用、标签页。它们是写给本地模型的，对方既读不了这些路径，也不该看到它们。
- 所以对外部 Bot，桌面端换一种拼法：
  - 文字：主人打的字，原样。
  - 图片：贴进来或拖进来的图，作为 `Image`。对方不收图片时输入框拦下。
  - 引用对话里的话：写成普通的 Markdown 引用（每行前面加 `> `），放在主人的字前面。不用给本地模型的那种引用块。
  - 其余一概不拼：`attachedBlock`、`viewingBlock`、网页批注、文档引用、标签页、技能提及。输入框上对应的入口不出现（§4.5，DD-184）。
- 开头的 `/` 不当命令：`Op::Prompt` 的 `commands` 对对端会话一律按假处理，主人打的 `/compact` 这样的字原样发给对方。
- 服务层再守一道：对端会话的 `prompt` 里，文字块以 `Attached files` 开头的直接拒绝（`unsupported_content`，这个错误现在就有）。这只防桌面端自己的疏漏，别的块没有固定的开头，靠第 11 节第 6 条的测试守着。
- `finx-a2a` 发的 A2A 消息：`messageId` 用本机这条消息的 id，`role` 是 `ROLE_USER`，`parts` 是一个 `{ text }` 加每张图一个 `{ raw, mediaType }`；有 `contextId` 就带上，对端在等回答时带上那个任务的 `taskId`。别的什么都不带：没有系统提示词、指令文件、技能清单、环境信息、别的对话、本机路径。
- 一条消息里的图片合计最大 20 MB，超了在输入框提示。
- **给对方发文件一期不做**（D-715）。协议的输入没有文件这种内容（desktop-design §7 的 P11 还没做），硬做就得让内核去认桌面端的文字块。做的条件和做法都定了：等出现第一个要收文件的真实对方时，先给协议加文件输入，再让对端任务把它作为 `raw` 发出去，到那时 `accepts` 加 `file`。不为它另开一条认文字块的路。

### 5.5 对话的延续、等待和重试

- **对话标识**：对端第一次回复给的 `contextId` 记在会话日志里（条目 `PeerThread { context_id, task_id }`），以后每次请求都带上。它属于这段对话，不属于 Bot，所以不放 `bot.json`。`taskId` 只属于当前这个任务：对方在等回答（`INPUT_REQUIRED`）时，主人的下一句带着它发出去；任务结束或失败以后，新的一句不带它（失败的任务仍留在日志里，供失败卡上的重试先 `resume`）。
- **主人连着发**：用现有的插话队列。对端的任务还在跑时，新的一句排着，等它结束或者开始等这边回答时再发，一句一次请求，按顺序。主人的话不打断对方（和 Bot 方案 D-351 一致）。
- **清空**：先对没结束的任务发 `CancelTask`（遇到 `TASK_NOT_CANCELABLE`、`TASK_NOT_FOUND` 当作已经停了），再按 Bot 方案 §2.1 清空。新对话不带 `contextId`，对方那边也是新的开始。删除同理。
- **对方忘了**：带着旧的 `contextId` 被拒绝时，去掉它重发一次，并在对话里记一行"对方那边的对话重新开始了"（附录 A.1）。
- **对方悄悄忘了**：有的对方不拒绝不认识的 `contextId`，只是当成新对话。a2a-demo 就是这样：对话记在内存里，只留最近 20 轮，服务一重启就没了，而且不报错。这种情况本机察觉不到，也不提示。
- **断线**：流上 60 秒没有任何事件，或者连接断了，走 `resume`：先 `GetTask`，结束了就把结果给出，没结束再 `SubscribeToTask`（对已经结束的任务订阅会被拒绝，所以先查）。连着三次接不上，任务失败。`GetTask` 返回 `TASK_NOT_FOUND`（对方重启过）时任务失败，原因写"对方已经没有这个任务了"。
- **不等了**（DD-186）：对端的任务超过 2 分钟没结束时（桌面端从任务开始的时间算），对话底部出一行小字"{名字} 还没回"，旁边一个"不等了"。点了就是会话现有的中断（`Op::Interrupt`）：对端任务收到取消，向对方发 `CancelTask`，本机这个任务按中断结束；排着的话和会话页按停止时一样回到输入框，主人可以再发。不加新的协议方法。Bot 模式本来没有停止键，因为本地 Bot 的长活在后台、不挡说话；对端的任务挡着后面的话，而且卡住的可能是别人的服务。
- **重试**：失败卡上的重试，在已经拿到任务标识时先 `resume`（对方可能其实做完了，只是回程断了），拿不到结果才重发；重发用同一个 `messageId`。还没拿到任务标识就失败的，直接重发。这样能减少但不能杜绝对方把同一句话处理两遍，协议不保证去重。
- **重启**：应用重启后，有没结束的任务的外部 Bot 在两个时机补查：应用启动时逐个查一遍；主人打开这个 Bot 时。合盖期间对方做完的，这时补进对话，算未读。
- **不在后台常驻**（D-707）：没有任务在跑的外部 Bot 不保持连接。

### 5.6 凭证和名片的变化

**凭证**：

- 名片的 `securityRequirements` 决定要不要：不要的直接加；要 API Key（请求头）或 Bearer 的，确认页上填。别的方案加不了，提示"它用的接入方式这个版本还不支持"。
- 存钥匙串，名字 `bot.<bot_id>`，走现有的 `credentials/set`（`credentials/*` 加一个 `bot.` 前缀）。
- 请求时按名片的方案放进对应的请求头。凭证只发给登记的那个接口地址，跳转到别的主机时不带。
- 对方拒绝凭证（HTTP 401、403）时任务失败，错误 `bot_auth_required`。
- 删除 Bot 时删掉凭证。

**名片变了**：打开外部 Bot 时，离上次读名片（`card_read_at`）超过一天就重读一次，读不到不挡对话。

| 变了什么 | 怎么办 |
|---|---|
| 说明、能办什么、提供方、图标、收什么 | 更新 `source` 和 Bot 设置里的说明。主人换过的头像不动；没换过的跟着换 |
| 名字 | 不自动改。Bot 设置里显示"对方现在叫 {新名字}"，主人可以点一下采用 |
| 接口的路径变了，主机没变 | 更新 `endpoint`，不问 |
| 凭证方案变了 | 停下来（D-708）：对话顶部一张提示说明变了什么，主人确认以后才继续发消息 |
| 接口换了主机 | 同源的规则不允许，这张新名片不被接受，照常用上次的，Bot 设置里标出"对方的名片指向了另一个地址" |
| 名片读不到了 | 照常用上次的。连续七天读不到，Bot 设置里标出 |

名字不自动改是防冒充：加的时候叫"张三的助手"，过后悄悄改成"银行客服"。

### 5.7 第一个对方：a2a-demo

主人给的第一个对方是本机的 `~/a2a-demo`：用官方 Python SDK（`a2a-sdk` 1.0 以上）写的聊天服务，后面接一个 OpenAI 兼容的大模型。在它的目录里 `uv run a2a-chatbot` 启动，跑在 `http://localhost:9999`，接入说明见它的 `docs/integration-guide.md`。

2026-11-14 对着它实测：

| 看什么 | 实测 | 对方案的影响 |
|---|---|---|
| 名片的位置 | `/.well-known/agent-card.json` | 与 §5.2 一致 |
| 接口 | 两项：`JSONRPC` 和 `HTTP+JSON`，都是 1.0 | 取 `JSONRPC`，与 D-709 一致 |
| 地址 | `http://localhost:9999` | 不是 HTTPS，又是本机地址，要开 `bots.allow_local`（§5.8） |
| 名片里的接口地址 | 取自它的配置 `PUBLIC_URL`，不随访问的地址变 | 要用 `http://localhost:9999` 加，用 `127.0.0.1` 过不了同源（§5.2） |
| 凭证 | 没有 `securitySchemes` | 不用凭证 |
| 签名、提供方、图标 | 都没有 | 确认页要能缺提供方和图标（§4.2） |
| 收什么 | 只有 `text/plain` | `accepts` 只有文字，贴图片被输入框拦下。实测只发文件时对方回 `REJECTED` |
| 流式一轮的事件 | `task`（`SUBMITTED`）→ `statusUpdate`（`WORKING`）→ 若干 `artifactUpdate`（一个 token 一片）→ 一片空的带 `lastChunk` → `statusUpdate`（`COMPLETED`，`status.message` 里是完整回复） | 分片的拼法、不重复出气泡（§5.3）。全文见附录 B.2 |
| 不流式 | `SendMessage` 直接返回结束的 `task`，回复同时在 `artifacts` 和 `status.message` 里，Artifact 的各片是多个 `parts` | 同上 |
| 多轮 | 第二句带第一句返回的 `contextId`，对方记得上一句。不带时对方自己生成 | 与 §5.5 一致 |
| 空消息 | `REJECTED`，原因在 `status.message` | 进失败卡 |
| 查、停、订阅已结束的任务 | `GetTask` 正常；`CancelTask` 回 `TASK_NOT_CANCELABLE`；`SubscribeToTask` 回 `UNSUPPORTED_OPERATION` | §5.5：先查再订阅；清空时这两种当作已经停了 |
| 不存在的任务 | `TASK_NOT_FOUND` | §5.5 |
| 不带版本头 | `VERSION_NOT_SUPPORTED` | §5.1 |
| 错误的样子 | JSON-RPC 的 `error`，`data[0].reason` 是上面这些大写的名字 | §5.1：按 `reason` 认 |

它**没有**覆盖的：对方给文件、对方反问（`INPUT_REQUIRED`）、要凭证、长任务断线后接上、处理中卡住。这些靠 `tools/` 里测试用的 A2A 服务（§9）。

它是什么、不是什么：a2a-demo 背后是一个大模型加一段对话记忆，没有自己的数据和权限。按 §1.1 的定位，它不是"另一个主体的 context"，只是另一个模型。它适合用来把传输这一层做对，不能用来判断这个功能对用户有没有用。

### 5.8 配置项

`config.toml` 加一节 `[bots]`（配置是严格校验的，新的键要进 `config.rs`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `bots.external` | `false` | 打开以后才有"添加别人的 Bot"的入口，`bots/preview`、`bots/add` 才可用。已经加过的外部 Bot 不受它影响 |
| `bots.allow_local` | `false` | 打开以后，回环地址（`localhost`、`127.0.0.1`、`::1`）上的名片和接口可以用 HTTP，也不算内网地址。别的内网地址和别的 HTTP 仍然拒绝。请求回环地址时不走系统代理 |

- 一期的开发和验收在两个都打开的情况下做。
- **`bots.external` 什么时候默认打开**（D-717）。两个条件都满足时：
  - 有一个公网上的、有自己 context 的对方（一家机构的或另一个人的），对着它跑过 §11 里标"真"的各条；
  - §11 的其余各条对着测试用的服务全部通过。

  在那之前，想用的人自己在配置里打开。默认打开时不附带任何推荐名单。
- **`bots.allow_local` 一直是开发用的开关**（D-718），不出现在设置界面里，不默认打开。本机的服务用的是主人自己的 context，按 §1.1 它不是"另一个主体"；要接自己跑的模型，走模型连接，要接自己跑的工具，走连接器。默认拒绝本机地址还有一个好处：一个贴进来的链接不能让服务层去碰本机的端口。

## 6. 二期方向：代办

这一节是方向，开工前另行细化。写在这里是因为它决定了一期的几处取舍：外部 Bot 必须是会话，对端接口必须和"谁在说话"无关。

### 6.1 是什么

一期里主人自己和外部 Bot 说话，A2A 只是传输，相当于一个通用的聊天窗口。主人的 context（日程、偏好、文件、以前说过的话）用不上，每次都要自己复述。

代办是主人对自己的 Bot 说一句，由它去谈：

> 主人对 FinxBot："帮我约下周二上午的呼吸科。"
>
> FinxBot 看了主人的日程，周二上午十点以后有空。它要对"某医院预约助手"说的第一句话先给主人看："预约下周二（11 月 17 日）上午十点以后的呼吸科门诊。"主人点"发送"。
>
> 对方回："10:30 有号，李医生。需要就诊人姓名和证件号。" FinxBot 知道姓名，证件号它没有，问主人。
>
> 主人答了。FinxBot 把要发的内容再给主人看一次，发出去。对方回预约成功和一份预约单。
>
> FinxBot 告诉主人："约好了，周二 10:30，李医生。预约单在这。"并问要不要记到日程里。

两边的 context 各自留在各自那里，中间只过必要的几句话。这才是 A2A 字面的意思。

### 6.2 沿用调度会话的做法

Bot 方案 §10 已经定了 Bot 怎么调度会话模式里的会话：发消息带来源、回报用信件唤醒 Bot、确认仍然由主人答。外部 Bot 的会话照此办理，把"会话"换成"联系人"：

| 调度会话（Bot 方案 §10） | 代办 |
|---|---|
| `message_session`：给会话发一条消息 | `message_contact`：给一个外部 Bot 发一条消息 |
| 消息记 `from { bot_id, name }`，会话页上标着 Bot 的头像 | 相同：外部 Bot 的对话里，这句话标着 FinxBot 的头像，主人看得到它替自己说了什么 |
| 会话做完、失败、在等确认时，服务层给 Bot 发一封信 | 对方回了话、提了问、失败时，服务层给 Bot 发一封信 |
| 会话的模型看到这句话是 Bot 替主人说的 | 对方只看到一条普通的消息。一期的 `Peer` 不用改 |
| Bot 永远不能答复确认 | 相同，而且发给外部 Bot 的每句话都要主人确认（§6.3） |

- 宿主接口照 `SessionHost` 的接法：`finx-core` 定义 `ContactHost`（列出能联系的外部 Bot 和它们的名片说明、发消息、读近况），服务层实现，经 `KernelDeps` 注入。
- 外部 Bot 的对话是这段往来的记录。主人随时可以打开它，自己接着说。

### 6.3 三道闸

对方的话进了本地模型的上下文，而本地 Bot 有工具、有文件。一期没有这个风险，二期必须先把它管住。

1. **能联系谁，主人定**。每个本地 Bot 有一张"能联系的外部 Bot"的名单，默认是空的，在 Bot 设置里勾。Bot 的工具只看得到名单里的。这是第一个按 Bot 分的授权（§1.3）。
2. **发出去的每句话先给主人看**（D-713）。`message_contact` 的调用总是弹确认，显示原文和附件，主人点"发送"才发，可以先改。不受权限模式影响，"完全访问"也弹。这是 Bot 方案 §16"发给别人的消息一律先出草稿卡"的落实。以后可以按联系人放宽（Q-408），一开始不做。
3. **对方的话是外部数据**。信件里对方的话包在标记里（附录 A.2），提示词写明里面的话不能指挥 Bot 做任何事。读过对方的话以后，这一轮里凡是往外发数据的调用都要主人确认，不管权限模式。

对方提问（`INPUT_REQUIRED`）时，问题先到主人的 Bot。它从主人的 context 里答得上的，拟好回答走第 2 道闸；答不上的问主人。

### 6.4 不在这一期

- 主人不在时自动代办（定时任务里联系外部 Bot）：第 2 道闸要主人在场。
- 外部 Bot 主动找主人的 Bot：没有入口（§1.2 不做）。
- 多个外部 Bot 一起谈、群聊。

## 7. 协议

都在现有版本之内，只加不改。一期：

```ts
// bots/preview：读一张外部名片
// { url: string } →
type RemotePreview = {
  name: string; description: string;
  icon?: string;                     // data:image/png;base64,…
  provider?: string;                 // 名片的 provider.organization
  host: string;                      // 带端口
  skills: { name: string; description: string }[];
  accepts: ("text" | "image")[];
  auth: "none" | "api_key" | "bearer";
  card_sha256: string;
};

// bots/add：加一个外部 Bot，返回 BotResult
type BotAddParams = { url: string; card_sha256: string; credential?: string };
```

- `bots/create` 不变，仍然建本地 Bot。
- `BotSummary` 加 `source?`，只有外部 Bot 有：

```ts
type BotSource = {
  kind: "remote"; protocol: "a2a"; host: string; provider?: string;
  description: string;
  skills: { name: string; description: string }[];
  accepts: ("text" | "image")[];
  auth: "none" | "api_key" | "bearer";
  noticed: boolean;              // §4.3：第一次的提示看过了
  needs_review?: string;         // §5.6：凭证方案变了，主人还没确认
  offered_name?: string;         // §5.6：对方的新名字
  card_problem?: "moved" | "unreachable";   // §5.6
};
```

- `bots/update` 加三个可选的字段：`noticed: true`、`accept_review: true`、`adopt_name: true`。
- "不等了"用会话现有的 `interrupt`，不加方法（§5.5）。
- 对端会话上不适用的操作（`set_model`、压缩等）返回 `bot_not_supported`。
- 错误码（接着现有的往下排，开工时定号）：

| 名字 | 含义 |
|---|---|
| `bot_card_unreachable` | 读不到对方的名片：连不上、超时、不是 HTTPS、内网地址 |
| `bot_card_invalid` | 不是名片，或缺必填的字段；`data.message` 说明哪里 |
| `bot_card_unsupported` | 没有支持的接口、凭证方案不支持、不收文字 |
| `bot_card_moved` | 名片里的接口和名片不同源；`data.host` 是接口的域名 |
| `bot_card_changed` | 确认时名片和预览时不一样了 |
| `bot_auth_required` | 对方拒绝了凭证，或中途要验证 |
| `bot_not_supported` | 这个操作对外部 Bot 没有意义，或 `bots.external` 没打开 |

- 命令行不加命令：现在命令行没有 Bot 的入口（Bot 方案 §2.1）。
- ACP 投影（`finx acp`）不变：Bot 会话本来就不在它的会话列表里。

## 8. 安全与隐私

| 风险 | 怎么防 |
|---|---|
| 主人不知道话发给了谁 | 确认页的固定说明（§4.2）；列表和顶栏的标记（§4.3）；第一次发消息前的提示 |
| 发出去的比主人以为的多 | 一期只发主人打的字和贴的图（§5.4，D-715）。附件的路径、正在看的文件、批注这些文字块对外部 Bot 不拼，服务层再拦一道，测试抓请求核对。二期每句话先给主人看（§6.3） |
| 对方的话操纵本机的模型 | 一期没有这条路：对方的回复不进任何本地模型的上下文，只给人看（D-705）。二期有，靠 §6.3 的三道闸 |
| 对方的话操纵主人 | 防不住内容本身，靠标记让主人知道这是外人说的 |
| 对方的文字让应用去联网 | 已经防住，不用改：应用页面的内容安全策略是 `img-src 'self' data: blob:`（`apps/desktop/src/main/index.ts`），回复里的图片只显示替代文字（`session/Markdown.tsx` 的 `ReplyImage`），所以对方写的远程图片地址不会被请求，做不成"已读"探测 |
| 对方的文字指向主人本机的文件 | 要改（DD-185）。Bot 页打开了 `LocalImages`：文字里写的本机图片路径会读出来显示，文件标签点开是预览。本地 Bot 这样做是因为模型常把图写成 `![图](chart.png)`。外部 Bot 关掉 `LocalImages`；文件标签只认 `bots/<id>/files/` 里的，别的路径显示成普通文字。对方看不到这些文件，但不该由外人的一句话决定应用在主人面前展示哪个本机文件 |
| 对方给的文件 | 文件名清洗后存在 Bot 自己的文件夹，写不到别处（§5.3）。当作下载的文件：一打开就会运行的只在访达里显示，HTML 在单独的进程里预览（PRD DD-159）。大小上限在传输层边读边数（单个 50 MB、一轮 200 MB），超了就停止读取并让任务失败。`url` 不自动下载 |
| 冒充 | 确认页完整显示域名；接口必须和名片同源；名字不自动跟着对方改（§5.6）。不显示任何"已验证"（D-714） |
| 借服务层探内网 | 读名片、下载图标、请求接口都拒绝内网和本机地址，连上以后按实际地址再判断一次；不跟跨主机的跳转 |
| 凭证泄露 | 只进钥匙串；只发给登记的接口地址；接口换不了主机（§5.6） |
| 对方要更多权限 | 没有可要的：对端会话没有工具，不会出现授权窗口。`AUTH_REQUIRED` 只当作"凭证不行了"，不当作任何授权 |
| 对方拖着不回 | 流上 60 秒没动静就重新查；2 分钟后主人可以不等了（§5.5） |

## 11. 测试与验收

一期。标了"真"的同时对着 a2a-demo 跑，其余对着 `tools/a2a-fake`：

2. （真）发一句话回来一个气泡；对方分片回的只出一个完整的气泡，不因为 `COMPLETED` 里重复的那份多出一个；列表的最近一句和未读都对。
3. （真）连聊两句，第二句问第一句说了什么，答得上。
4. （真）连发三句：按顺序各发一次，回来三个气泡。
5. 对方给文件：存进 Bot 的文件夹，气泡点开是预览；名字是 `../../x`、`.bashrc`、重名、超大的各一个，都落在文件夹里且名字被清洗。对方给地址：是链接，没有下载。
6. （真）抓请求核对：`parts` 里只有主人打的字和贴的图；带 `A2A-Version`；没有系统提示词、路径、回话提示和别的内容。在文件面板开着一个 PDF 时发消息，请求里没有它。
7. 输入框：没有添加文件和技能的入口；对方不收图片时贴图被拦下；引用一句话，发出去的是 `> ` 开头的引用。
8. 对方反问：出提问气泡，主人的回答带着同一个 `taskId`。
9. 断流后接上；60 秒没动静后重新查；应用重启后，没结束的任务的结果补进对话并算未读。
10. 对方卡住：2 分钟后出现"不等了"，点了以后对方收到 `CancelTask`，头像不动了，排着的话回到输入框，再发能发出去。
11. 重试：对方做完了但回程断了，重试不重发，直接拿到结果。
12. （真）清空：下一句不带 `contextId`，对方不记得之前的话。
13. 拒绝的情况各一个：HTTP 链接、内网地址、跳到别的主机、名片超大、缺必填字段、只有 gRPC 接口、要 OAuth、接口和名片不同源（用 `127.0.0.1` 加 a2a-demo）。
14. 名片变了：改名字不自动生效；凭证方案变了要确认，确认前发不出去；接口换主机的新名片不被接受。
15. 凭证：在钥匙串里，`bot.json` 里没有；删除 Bot 后钥匙串里没有；对方回 401 时是"需要重新验证"的失败卡。
16. 没配任何模型时，能添加外部 Bot 并聊通。
17. 对端会话上 `set_model`、压缩、从某一句重来返回 `bot_not_supported`；主人打 `/compact` 原样发给对方；`bots.external` 关着时没有入口，`bots/add` 被拒绝，已有的外部 Bot 照常用。
18. 对方的文字里写远程图片地址：没有网络请求，显示替代文字。写本机图片路径：不显示图片。写本机文件的链接：不是文件标签；它自己发来的文件的链接照常能点开。
19. 本地 Bot 不受影响：新建、对话、列表与改动前相同；提示词逐字相同；版本 1 的 `bot.json` 照常读。

## 12. 设计取舍

**为什么不给本地 Bot 预设人设和专属技能（专长 Bot）**

"加第二个 Bot 没有理由"是真问题，一个直接的办法是做一批预设的 Bot：每个带一段专长说明，加上只对它打开的技能。没有选它：

- **它切的是主人自己的 context**。专长说明和那些技能本来都可以直接给 FinxBot。同一个主人、同一个模型，把自己的东西预先切成几份没有理由。
- **它要解决的事已经有机制在做**。技能本来就是用到才加载；发现并打开一个技能，现在由文件卡和"自定义"负责。
- **专长说明里的话，技能里已经写了**。影像技能自己就写着"你不是医生"。
- **Bot 方案 §2.3 的结论不用动**。Bot 没有人设，客户端和文件都不往提示词里加东西。

本地多个 Bot 的理由是记忆和授权范围不同（§1.3）。

**为什么一期不验名片的签名**

- 协议规定了怎么签（JWS），没有规定信谁的钥匙：钥匙要么按签名头里写的地址（`jku`）去取，要么来自客户端自己信得过的钥匙库。照名片自己给的地址取钥匙来验，只证明"名片和它自己指的钥匙对得上"，谁都做得到；信得过的钥匙库我们没有。
- 要让签名有意义，得有一份信得过的钥匙或签发方的名单，这是另一件事，现在没有。
- 在此之前，HTTPS 加同源已经给了能给的保证：名片和接口都来自主人在确认页上看到的那个域名。确认页显示的也正是域名。
- 显示一个"已验证"的对勾而背后没有信任链，比不显示更糟。

**为什么一期不给对方发文件**

- 主人的消息里，附件现在是一段文字：一行说明加绝对路径，由本地模型用工具去读。协议的输入没有"文件"这种内容。
- 要发文件，要么让内核去认桌面端这段文字的格式，要么先给协议加文件内容。前者把桌面端的写法变成内核的约定；后者是对的，但它是一件独立的事（desktop-design §7 的 P11），不该夹在这里做。
- 第一个对方只收文字。

**为什么先做直接聊，再做代办**

- 直接聊没有注入的风险，对方的话只给人看。代办要先有 §6.3 的三道闸。
- 代办需要的东西一期都要做：通讯录、名片、对端接口、往来的记录。
- 主人需要一个地方看到自己的 Bot 替自己说了什么，也需要在它谈不下去时自己接着说。这个地方就是一期的对话页。

**为什么代办不做成"外部 Bot 是本地 Bot 的一个工具"**

把对方包成一个工具（发一句、等回话、返回结果）最省事，没有选它：

- 往来只留在本地 Bot 的私有上下文里，主人看不到它说了什么。
- 对方的长任务、反问、过后才给的结果，塞不进一次工具调用。
- 调度会话已经定了"发消息加回报"的做法，两处应当一样。

**为什么不做 ACP**

- 能加的是本机装好的命令行智能体，普通用户没有。
- 更根本的：那些智能体在本机运行，用的是主人自己的 context，按 §1.1 它们不是"另一个主体"。想用另一个模型，在 Bot 设置里换模型就是了。
- §5.3 的 `Peer` 不带协议，真有人要时可以再加一个实现。

**为什么对端的话记成 `send_to_user`，不另设一种条目**

- 另设一种，服务层的 `on_event`、客户端的 `botChat.ts`、通知、搜索、引用、列表摘要都要各加一个分支，以后每加一种消息类型都要加两遍。
- `send_to_user` 已经有文字、文件、提问三种，正好对上 A2A 的三种结果。
- 代价是日志里有一次本机没有执行过的"工具调用"。用助手消息的 `provider`、`model` 和会话头部的 `peer` 标明来历。

**为什么外部 Bot 没有后台常驻的连接**

- 每个外部 Bot 常驻一条连接，数量不设上限时不可控。
- 合盖和断网时反正收不到，重连和补查的逻辑一样要写。
- 代价是合盖期间做完的结果要等启动或打开时才补上。

### B.2 一轮流式对话（a2a-demo 实测，标识缩短了）

请求：

```
POST http://localhost:9999/
Content-Type: application/json
A2A-Version: 1.0

{"jsonrpc":"2.0","id":"t1","method":"SendStreamingMessage","params":{"message":{
  "messageId":"0193…","role":"ROLE_USER","parts":[{"text":"只回答两个字：收到"}]}}}
```

响应是 `text/event-stream`，每个事件一行 `data:`：

```
data: {"result":{"task":{"id":"450d…","contextId":"19da…","status":{"state":"TASK_STATE_SUBMITTED"},"history":[…]}},"id":"t1","jsonrpc":"2.0"}

data: {"result":{"statusUpdate":{"taskId":"450d…","contextId":"19da…","status":{"state":"TASK_STATE_WORKING","timestamp":"…"}}},"id":"t1","jsonrpc":"2.0"}

data: {"result":{"artifactUpdate":{"taskId":"450d…","contextId":"19da…","artifact":{"artifactId":"a02f…","name":"response","parts":[{"text":"收到"}]}}},"id":"t1","jsonrpc":"2.0"}

data: {"result":{"artifactUpdate":{"taskId":"450d…","contextId":"19da…","artifact":{"artifactId":"a02f…","name":"response","parts":[{"text":""}]},"append":true,"lastChunk":true}},"id":"t1","jsonrpc":"2.0"}

data: {"result":{"statusUpdate":{"taskId":"450d…","contextId":"19da…","status":{"state":"TASK_STATE_COMPLETED","message":{"messageId":"e47d…","role":"ROLE_AGENT","parts":[{"text":"收到"}]},"timestamp":"…"}}},"id":"t1","jsonrpc":"2.0"}
```

按 §5.3 的规则，五个事件给出的 `PeerEvent` 依次是：`Thread`、`Working`、`Working`（第一片，先攒着）、`Said { "收到" }`（最后一片到了）、`Done`。第三个事件没有 `append` 和 `lastChunk`，按假算；最后一个事件里重复的"收到"不再给。

续聊时在 `message` 里加 `"contextId":"19da…"`。错误的样子：

```json
{"error":{"code":-32001,"message":"Task not found","data":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","reason":"TASK_NOT_FOUND","domain":"a2a-protocol.org","metadata":{}}]},"id":4,"jsonrpc":"2.0"}
```
