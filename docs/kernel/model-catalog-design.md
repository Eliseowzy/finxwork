## 方案摘要

- **要解决的问题**：用 API Key 接入的服务商，可选的模型现在只来自手写的内置目录和用户的 models.toml。内置目录只给 DeepSeek 写了模型，用户加了 Kimi、GLM 或 Anthropic 的密钥之后，菜单里一个模型也没有；写了的也会过时。
- **两件事分开解决**：
  - **有哪些模型**：问服务商自己。有密钥之后，用服务商的模型列表接口查一次，结果缓存在本机。
  - **每个模型的参数**（上下文窗口、输出上限、能否推理和有哪些档位、是否收图片、价格）：多数列表接口只返回 id，所以参数来自一份公开维护的模型目录（models.dev），再叠加 finx 自己的修正和用户的 models.toml。
- **参数的来源**，前者覆盖后者，按字段合并：用户 models.toml → 渠道的声明（finx 内置修正、账号连接自己的目录） → 列表响应里自带的参数 → 公共目录里这个渠道的行 → 公共目录里模型厂商的行 → 默认值。API、Token Plan、订阅都走这同一次合并。
- **每个渠道只回答三件事**：怎么连上、有哪些模型、思考的开关和预算怎么发。模型能做什么由模型 ID 到公共目录查，不用每接一个渠道就抄一遍。
- **公共目录的更新**：
  - 随版本打包一份只含 finx 支持的服务商、只含用得到的字段的快照，约 200 KB，按服务商分段，用到哪家才解析哪家；
  - 仓库每周自动拉取一次上游，提交 PR，人工审阅后合并；
  - 常驻服务启动时，本机缓存超过 24 小时就在后台刷新一次，之后每 24 小时一次。失败继续用手上的版本。
- **列表的刷新时机**：保存密钥时（顺便验证密钥）、常驻服务启动时（缓存超过 24 小时的服务商）、用户手动刷新。一次性命令（`finx exec` 等）从不联网查目录。
- **哪些模型进菜单**：
  - 先过滤掉用不了的：嵌入、图像、语音这类非对话模型，以及已知不支持工具调用的模型；
  - 默认显示参数已知、未停用的对话模型；某家这样的模型超过 12 个（聚合服务商动辄几百个），默认只显示发布日期最新的 12 个；
  - 用户可以逐个显示或隐藏，选择单独保存，以后新出的模型仍按默认规则出现。
- **永远能用**：列表只决定菜单里显示什么。会话正在用的模型、配置里的默认模型、`provider/model-id` 手写的模型，即使不在列表里也照常解析和调用。
- **重复的端点**：DeepSeek 的 Anthropic 兼容端点与 DeepSeek 共用一个账户，不单独查列表，它的模型默认不进菜单。
- **启动零成本**：常驻服务的刷新都在后台进行；一次性命令只多读一个服务商的目录分段（预算 0.5 ms 以内）。没有密钥的服务商不发任何请求。
- **协议**：`models/list` 只列有凭据的服务商的模型，每个模型带 `shown`、`known`、`deprecated`；服务商带列表状态。新增 `models/refresh`、`models/show`；`auth/set` 先验证密钥再保存。
- **分期**：一期是本文的全部主体，约 1.5 周；二期是模型不存在时自动刷新、本机服务查上下文窗口、账号连接的定期刷新、分段计价。

## 0. 阅读说明

- **编号**：本文的决策编号为 D-130–D-149、D-330–D-340（§15），待定问题为 Q-120–Q-129、Q-146–Q-148（§16）。
- **术语**：
  - **服务商**：总方案 §4.8 的 Provider，例如 `deepseek`、`kimi`。
  - **列表**：服务商通过接口告诉我们它现在提供哪些模型 id。
  - **公共目录**：models.dev 维护的开放模型目录（`https://models.dev/api.json`），覆盖两百多家服务商。
  - **投影**：从公共目录里只取 finx 支持的服务商、只取 finx 用得到的字段，转换成 finx 自己的格式。
  - **内置修正**：`crates/finx-llm/catalog/builtin.toml`。本方案之后，它主要描述服务商（端点、鉴权、compat），模型部分只写公共目录缺失或不对的字段。
  - **渠道**：一种接入方式，也就是一个服务商条目：API、Token Plan、账号连接（订阅）都算。同一个模型可以经多个渠道使用。
  - **渠道行、厂商行**：公共目录里一个模型可能有多行。渠道行是这个渠道自己的，例如 `alibaba-token-plan-cn` 的 `glm-5.3`；厂商行是做这个模型的厂商自己的，例如 `zhipuai` 的 `glm-5.3`。
- **不变的部分**：线协议适配、鉴权解析（总方案 §4.9）、凭据存储（D-39）、账号连接（model-connections-design.md）都不变。

## 1. 现状与目标

### 1.1 现状

| 项 | 现在的做法 | 问题 |
|---|---|---|
| 模型从哪里来 | 内置目录加 `~/.finx/models.toml`，编译时固定 | 内置目录只有 DeepSeek 写了模型；OpenAI、Anthropic、千问、Kimi、GLM、OpenRouter 加了密钥后菜单是空的 |
| 是否最新 | 手工维护（Q-08） | 服务商上新、下线、改价格，finx 要发版才知道 |
| 密钥是否有效 | `auth/set` 只保存，不验证 | 填错密钥要到第一次对话失败才知道 |
| 菜单 | `models/list` 列出目录里的全部模型，没有密钥的标"未设置密钥" | 没接入的服务商也占位；同一个模型因为两个端点出现两次 |
| 本机服务 | Ollama 免鉴权，永远"可用" | Ollama 没开或没装对应模型时，菜单里照样有 |
| 未列出的模型 | `provider/model-id` 可以直接用，参数取默认值 | 只有命令行和配置能用，界面上选不到 |

账号连接（千问办公）不在此列：它连接时向来源应用取在线目录，已经是最新的，只是连上之后不再刷新（§14 二期）。

### 1.2 目标

| 编号 | 目标 | 含义 |
|---|---|---|
| G1 | 跟官方一致 | 菜单里的模型是服务商现在真正提供的；新模型不用等 finx 发版 |
| G2 | 参数可靠 | 上下文窗口、推理档位、图片输入、价格有权威来源，并能逐字段修正 |
| G3 | 不打扰 | 加了密钥就能用；几百个模型的服务商不会把菜单撑爆；离线时一切照旧 |
| G4 | 零启动成本 | 不拖慢 `finx exec` 和常驻服务启动（总方案 §1.4）；没有密钥的服务商不发请求 |
| G5 | 安全 | 密钥只发给它所属服务商的端点；外来的列表和目录都当作不可信数据校验 |

### 1.3 非目标

- 不做模型评测或推荐，只按事实（参数、发布日期、是否停用）决定默认显示。
- 不自动切换会话正在用的模型，即使服务商下线了它。
- 不为公共目录之外的服务商自建一套目录服务。

## 2. 总体设计

```
                      ┌──────────────── 构建时 ────────────────┐
  models.dev ──每周──▶ │ 同步脚本 → 投影 → 快照（入库，人工审阅） │ ──编译进 finx──┐
                      └────────────────────────────────────────┘                │
                                                                                ▼
  models.dev ──常驻服务，24 小时一次──▶ ~/.finx/models/catalog/*.json ──┐   公共目录（取较新者）
                                                                       ├─▶ 参数合并 ◀── 内置修正、models.toml
  服务商 /models ──保存密钥、启动、手动──▶ ~/.finx/models/lists/*.json ──┤
                                                                       │
                              ~/.finx/models/selection.json ──────────┘
                                                                       ▼
                                                        models/list：每个模型的参数、
                                                        shown、known、deprecated
```

职责：

| 模块 | 负责 |
|---|---|
| finx-llm `catalog` | 解析内置修正和 models.toml；按字段合并成 `Model`；一个渠道能提供哪些档位（§18.2） |
| finx-llm `directory` | 所有渠道共用的一次合并（§4.1）：每个模型找到它的目录行，叠加列表和渠道的声明 |
| finx-connections | 账号连接（订阅）：把应用自己的目录转成渠道的声明，交给同一次合并（§4.7） |
| finx-llm `discovery`（新） | 各服务商的列表请求、响应校验、结果缓存读写 |
| finx-llm `public_catalog`（新） | 内置快照与本机缓存的选择、在线刷新、投影与校验 |
| finx-server | 刷新时机（§3.2、§5.2）、`models/*` 与 `auth/set` 的协议、`models/changed` 通知 |
| 同步脚本（仓库 `scripts/`） | 构建时生成快照；每周的上游同步 |

数据流只有一个方向：缓存和快照只是输入，合并结果不写回任何文件。删掉 `~/.finx/models/` 下的缓存只损失时间，不损失设置（选择单独存放，§7）。

## 3. 有哪些模型：服务商的列表

### 3.1 列表接口

内置服务商的列表请求如下。地址都由服务商的 `base_url` 拼出，所以用户改了 `base_url`（代理、私有部署）也跟着走。

| finx 服务商 | 请求 | 鉴权 | 公共目录中的服务商 | 说明 |
|---|---|---|---|---|
| deepseek | `GET {base_url}/models` | `Authorization: Bearer` | `deepseek` | |
| deepseek-anthropic | 不单独请求 | — | `deepseek` | 用 deepseek 的结果（§3.5） |
| openai | `GET {base_url}/models` | `Authorization: Bearer` | `openai` | |
| anthropic | `GET {base_url}/v1/models?limit=1000` | `x-api-key`、`anthropic-version` | `anthropic` | 按 `has_more`、`last_id` 翻页 |
| qwen | `GET {base_url}/models` | `Authorization: Bearer` | `alibaba-cn` | |
| kimi | `GET {base_url}/models` | `Authorization: Bearer` | `moonshotai-cn` | |
| glm | `GET {base_url}/models` | `Authorization: Bearer` | `zhipuai` | 是否提供待实测（Q-120），不提供时走 §3.4 的退路 |
| openrouter | `GET {base_url}/models` | `Authorization: Bearer` | `openrouter` | 响应自带上下文窗口和价格（§4.1 第三层） |
| ollama | `GET {base_url}/models` | 无 | — | OpenAI 兼容接口，列出本机已下载的模型（§3.6） |

- **通用形状**：OpenAI 兼容接口返回 `{"data": [{"id": "…"}, …]}`，取每项的 `id`；`name` 或 `display_name` 有就作为展示名的候选（优先级低于公共目录和内置修正）。
- **用户新增的服务商**：models.toml 里新增的服务商按它的线协议选择请求方式：`openai-chat` 用 OpenAI 兼容接口，`anthropic-messages` 用 Anthropic 接口。可以用新字段关闭或改写（§11.2）：

  ```toml
  [providers.my-proxy]
  api = "openai-chat"
  base_url = "https://llm.example.com/v1"
  api_key_env = "MY_PROXY_KEY"
  list_models = "/v1/models"   # 默认 "/models"；false 表示不查列表，只用 models.toml 里写的模型
  catalog_id = "openai"        # 参数到公共目录的哪一家去找；默认不找
  ```

- **请求体之外的约定**：User-Agent 与推理请求相同（总方案 §4.14）；每次请求 10 秒超时；不自动重试（刷新本来就会再来）。

### 3.2 何时查询（D-130）

| 时机 | 做什么 | 说明 |
|---|---|---|
| 保存密钥（`auth/set`） | 用新密钥查一次列表，成功后才保存（§3.3） | 顺便验证密钥 |
| 常驻服务启动 | 对每个有凭据、缓存超过 24 小时的服务商，在后台查一次；之后每 24 小时一次 | 同时最多 4 个请求；不阻塞任何协议请求 |
| 用户手动刷新 | `models/refresh`（设置页的"刷新列表"、`finx models --refresh`） | 立即查，忽略缓存时间 |
| 密钥来源变了 | 环境变量、models.toml、钥匙串里的密钥变化后，下一次 `models/list` 发现凭据和缓存记录的不一致，就在后台刷新这家 | 缓存记下凭据的来源和指纹（§7），不存密钥本身 |

- **一次性命令不联网**：`finx exec`、`finx chat`、`finx models`（不带 `--refresh`）只读缓存；没有缓存时退回公共目录（§3.4）。
- **没有凭据不请求**：凭据缺失的服务商从不发列表请求，也不在 `models/list` 里列模型。
- **刷新结果有变化**时发 `models/changed`，客户端重新取 `models/list`（协议方案已有这个通知）。

### 3.3 保存密钥时的验证（D-131）

`auth/set` 改为先验证、再保存：

| 列表请求的结果 | `auth/set` 的结果 |
|---|---|
| 成功 | 保存密钥，写入列表缓存，返回 `{ verified: true, models: <数量> }` |
| 401 / 403 | 不保存，返回错误 `key_rejected`，附服务商的错误信息（截断到 500 字符） |
| 404 / 405（服务商没有列表接口） | 保存，返回 `{ verified: false }`，这家记为"不提供列表" |
| 网络错误、超时、5xx | 保存，返回 `{ verified: false }`；后台稍后重试一次 |

理由：密钥错了要在填的时候就知道；但服务商临时不可用不该挡住用户保存。

### 3.4 校验、限制与退路

- **响应校验**：
  - 响应体最大 32 MiB，超过即失败；
  - 每家最多 5,000 个模型；
  - id 必须是 1–256 字节的可打印字符，不含控制字符和空白；不合格的单个条目丢弃，其余照收；
  - 去重，保持服务商给出的顺序。
- **整体失败的退路**：列表请求失败、服务商不提供列表、或者 `list_models = false` 时：
  1. 有旧缓存就继续用旧缓存，标记"上次刷新失败"和原因；
  2. 没有缓存时，用公共目录里这家的模型，加上内置修正和 models.toml 里写的模型，来源记为 `catalog`；
  3. 都没有时，这家没有可选模型，但 `provider/model-id` 仍可直接使用。
- **models.toml 里写明的模型**总是在列表里，即使服务商的列表里没有它（来源记为 `config`）。

### 3.5 共用账户的端点（D-132）

DeepSeek 同时提供 OpenAI 兼容和 Anthropic 兼容两个端点，同一个账户、同一把密钥。以前两个服务商各列一遍模型，菜单里 DeepSeek-V4.1-Flash 出现两次。

- 服务商新增字段 `list_from = "<另一个服务商 id>"`：不单独请求，直接用那一家的列表。内置的 `deepseek-anthropic` 设为 `list_from = "deepseek"`。
- 这样的服务商的模型默认不显示（§6.2），设置页里可以单独打开。
- 用户新增的服务商也可以用这个字段。
- **密钥不共享**：`list_from` 只共享列表。保存的密钥仍按服务商 id 存放，`deepseek-anthropic` 要么读到同一个环境变量 `DEEPSEEK_API_KEY`，要么单独保存一次；没有凭据时它的模型不列出（v1.1）。

### 3.6 本机服务

Ollama 免鉴权，以前它的模型永远"可用"。改为：

- **可用由列表决定**：最近一次列表请求因连接失败或超时而失败时，它的模型不列出；本机没开 Ollama 时，菜单里就没有它。服务商回答 404（没有列表接口）不算失败，写在 models.toml 里的模型照常可用。
- **刷新更频繁**：本机请求几乎没有成本，常驻服务每次 `models/list` 前，如果距上次查询超过 60 秒，就先查一次本机（同步等待，最多 300 ms）。
- **参数**：本机模型不在公共目录里。服务商写了 `list_details = "ollama"`（内置的 ollama 已写）时，列表之后对每个模型调用 `POST /api/show`，取上下文窗口（`model_info` 里的 `*.context_length`）和能力（`tools`、`vision`、`thinking`），每个最多等 2 秒；取到的参数让它算作参数已知。
- 别的免鉴权服务商（`auth = "none"`）同样处理。

## 4. 模型的参数

### 4.1 来源（D-133、D-330）

一个模型的每个字段，按下面的顺序取第一个有值的来源。所有渠道都走这一次合并，没有别的路径（D-330）：

| 顺序 | 来源 | 典型内容 |
|---|---|---|
| 1 | 用户 `~/.finx/models.toml` | 用户自己的修正、私有模型 |
| 2 | 渠道的声明 | 内置修正 builtin.toml：公共目录缺失或不对的字段。账号连接：应用自己的目录（§4.7） |
| 3 | 列表响应自带的参数 | OpenRouter 列表里的上下文窗口、价格 |
| 4 | 公共目录里这个渠道的行 | 大多数模型的全部参数 |
| 5 | 公共目录里模型厂商的行 | 渠道在目录里没有这个模型时才查（§4.5），不含价格和停用状态 |
| 6 | 默认值 | 上下文 128,000、不推理、不收图片；输出上限**不设**，请求里不带（§4.8） |

- **按字段合并**，与总方案 §4.8 models.toml 的合并方式相同：上层只写了 `context_window`，其余字段仍取下层。
- **`known`**：有目录行（渠道的或厂商的）、列表带了详情、或者渠道的声明写了模型能做什么（上下文、输出、推理、档位、图片任一项）。只写名字不算：它们留在菜单里，但标"参数未知"（D-337）。
- **未知时的默认值各有理由**：输出上限未知就不设（§4.8），猜错会截断回复，不设没有代价。图片未知按不收图：把图片发给不收图的模型，这个会话之后每次请求都会失败，比丢掉一张图严重得多；现在绝大多数模型都能找到目录行，真正未知的会标"参数未知"，用户可以在 models.toml 写 `input`。
- **合并只在需要时做**：常驻服务在 `models/list` 时合并整家；一次性命令只合并它要用的那一个模型。

### 4.3 推理档位的推导（D-134，v1.2 改写）

v1.2 起，模型的思考强度用服务商自己的档位，从公共目录的 `reasoning_options` 直接得出，不再映射到 finx 的统一等级。推导规则、请求参数和切换模型时的状态规则见 §18。

### 4.4 价格与币种（D-135）

- **公共目录的价格一律是美元**，每百万 token，与 finx 的单价单位相同。投影时记币种 USD。
- **价格为 0 视为未知**，与总方案 §4.8 一致，界面显示"费用未知"。
- **人民币计价的服务商**：内置修正写官方人民币价格，并在模型上写 `currency = "CNY"`。模型级的币种是新增字段，覆盖服务商的 `currency`。价格和币种必须来自同一层：上层只写了价格没写币种时，取上层所在服务商的币种，不与下层的币种混用。
- **分段计价**（按上下文长度分档）：一期只用基础价，二期再支持（Q-124）。
- **推理 token 单价**：finx 的 output 已包含推理部分（总方案 §4.3），公共目录单列的推理单价一期不用。

### 4.5 模型 ID 到目录行（D-331）

服务商的字段 `catalog_id` 写它在公共目录里的 id，表见 §3.1 和 token-plans.md。一个模型按下面的顺序找它的目录行，找到第一行就用，不把两行拼起来：

1. **渠道行**：在 `catalog_id` 那一家里按 ID 查。
2. **厂商行**：渠道没有 `catalog_id`，或它那一家没有这个模型，就依次查模型厂商的行（`public_catalog::MAKERS`：DeepSeek、智谱、月之暗面、MiniMax、小米、腾讯混元、OpenAI、Anthropic、Google、xAI，最后是百炼）。比较时不分大小写，并去掉厂商前缀：`minimax-m3` 就是 `MiniMax-M3`，`deepseek/deepseek-flash` 就是 `deepseek-flash`。

三条边界，都来自实际数据（2026-11-04 的公共目录和本机的账号目录）：

- **渠道行优先**。同一个模型在不同渠道上确实不一样。在 11 个国内渠道上比较 79 组渠道行和厂商行（数值误差 6% 内算一致）：上下文 78 组一致、图片 76 组、输出上限 62 组、思考档位只有 53 组。所以上下文和图片可以放心借，档位和输出上限要优先用渠道自己的。例如 `deepseek-v4-pro`：DeepSeek 官方有低、高、最高，百炼只有高、最高，火山 Coding Plan 只有开关。
- **只查厂商，不查全库**。公共目录有两百多家，按原始 ID 全库查会串：`auto` 能撞上 3 家不相干的聚合商，其中一家写着 100 万上下文。
- **厂商行只借模型能做什么**：上下文、输出、推理、档位、图片、发布日期、是否对话模型。价格和停用状态是厂商自己的事，不算这个渠道的（D-331）。请求里的模型 ID 永远是渠道的叫法，目录的叫法不会发出去。

| 渠道 | 目录的来源 |
|---|---|
| API（`deepseek`、`qwen`、`kimi`、`glm`、`openai`、`anthropic`、`openrouter`） | 各自的渠道行 |
| Token Plan（百炼、腾讯、火山 Coding Plan、智谱、Z.ai） | 各自的渠道行，没有的查厂商行。腾讯的行只有 2 个，其余靠厂商行 |
| 火山 Agent Plan、用户新增的服务商（没写 `catalog_id`） | 只有厂商行 |
| 账号连接（订阅） | 应用目录优先（§4.7），缺的字段查厂商行 |

### 4.6 内置修正的新角色

builtin.toml 保留：

- 全部服务商条目：端点、鉴权、compat、`catalog_id`、`list_models`、`list_from`；
- 模型条目只写公共目录缺失或不对的字段。每一条修正都写一行注释说明原因，方便上游修好之后删掉。Token Plan 的预置条目只写 ID（必要时加展示名），因为"套餐里有哪些模型"目录回答不了，"模型能做什么"目录回答得了。
- 每家的第一个模型条目还有一个作用：这家是第一个能用的服务商、又没配 `model` 时，新会话从它开始（§6.5）。只为这个写的条目也只有 ID。

迁移后，DeepSeek 的模型条目只剩展示名：推理档位由公共目录推导，结果与原来手写的一致（§4.3）。人民币价格暂未写入，原因是还没有核实过的官方价格（Q-125）；在此之前用公共目录的美元价。同步程序发现某条修正与公共目录一致时，在报告里提示可以删掉（§5.1）。

### 4.7 账号连接（D-330）

账号连接（千问办公、Qoder、ChatGPT）读应用自己的目录，把它转成渠道的声明（`declared_model`）。这份目录最了解这条线路，所以排在目录行前面：

| 模型 | 应用目录说 | 公共目录说 | 用哪个 |
|---|---|---|---|
| ChatGPT 订阅的 `gpt-6-sol` | 上下文 272,000 | 1,050,000 | 272,000 |
| Qoder 的 Qwen3.8-Max（`qmodel_38max`） | 上下文 200,000 | 1,000,000 | 200,000 |

应用目录没说的字段才查厂商行：`gpt-6-sol` 的输出上限来自 OpenAI 的行。连接的模型名（`flash`、`qmodel_38max`）目录查不到，就保持未知，不猜。这些模型不按 token 计费，也就没有价格（厂商行本来就不借）。

### 4.8 输出上限未知（D-335）

没有任何来源说明输出上限时，不再猜一个数：

- **OpenAI 兼容接口**：请求不带 `max_tokens`，由服务商决定。以前的默认值 8,192 真实地截断过回复：千问办公的目录不给上限，本机 628 条 flash 回复的最大输出正好 8,192，其中 3 条因长度被截断。
- **Anthropic 接口**：`max_tokens` 必填，只能给一个数，用 8,192，它在所有模型上都有效。
- **预留空间**：提示词要给回复留的空间按 32,000 算（与已知上限的模型请求默认值相同），因为这样的请求没有上限。

## 5. 公共目录的更新

### 5.1 随版本打包的快照（D-136）

- **同步程序** `cargo run -p finx-llm --example sync_catalog`（`--input <文件>` 读本地文件，`--check` 只报告、过期时退出码为 1）：
  1. 下载 `https://models.dev/api.json`；
  2. 只取 builtin.toml 里出现过的 `catalog_id` 和模型厂商（§4.5），按 §4.2 投影；任何一家投影失败就退出，快照必须完整；
  3. 写到 `crates/finx-llm/catalog/public/<catalog_id>.json`，每家一个文件，键按字母排序、格式固定，diff 可读；
  4. 打印变化报告：新增、删除的模型，变化的参数，与公共目录一致、可以删掉的内置修正。
- **文件格式**：第一行是服务商 id 和取得时间，之后一行一个模型（按 id 排序）。diff 一目了然，也让一次性命令只解析要用的那一行（§5.3）。
- **投影后的体积**：按 2026-11-04 的上游数据，共 17 家，合计 668 个模型，其中 OpenRouter 376 个；入库的 17 个文件合计约 230 KB（OpenRouter 约 128 KB）。上游完整文件约 6 MB，不进仓库。
- **每周同步**：`.github/workflows/model-catalog.yml` 每周一运行同步程序，有变化就提 PR，正文附变化报告。上游删除了模型时，PR 标题注明，审阅时确认。
- **编译进二进制**：每家一个 `include_str!` 常量，运行时按需解析（§5.3）。

### 5.2 运行时刷新（D-137）

- **谁刷新**：只有常驻服务（`finx serve`）。启动时，本机缓存不存在或超过 24 小时就在后台刷新一次；之后每 24 小时一次。一次性命令从不刷新。
- **怎么刷新**：
  1. 请求 `https://models.dev/api.json`，带上次的 `ETag`；304 表示没有变化，只更新检查时间；
  2. 响应体最大 32 MiB，10 秒超时，只接受 HTTPS；
  3. 用与同步脚本相同的投影代码处理；一家投影失败或上游没有这一家，只跳过这一家并记日志，它保留原来的缓存（D-338）。这样 models.toml 里写错一个 `catalog_id`，或上游改了一家的名字，不会让所有家都刷新不了；
  4. 按家写入 `~/.finx/models/catalog/<catalog_id>.json`，先写临时文件再 rename；
  5. 有变化就发 `models/changed`。
- **用哪一份**：每家分别比较本机缓存和内置快照的上游时间戳，取较新的一份。所以升级 finx 之后，新版本带的快照不会被本机的旧缓存盖住。
- **不需要人工审阅**：运行时刷新只影响本机，不提交、不分发；上游删掉的模型，本机也跟着删掉。会话正在用的模型不受影响（§6.4）。
- **关闭**：`[models] network = false` 时不刷新公共目录，也不在后台查列表（§11.1）。

### 5.3 性能（D-138）

| 场景 | 额外开销 | 做法 |
|---|---|---|
| `finx exec` 启动 | 预算 0.5 ms 以内；实测无可见差别 | 只解析要用的那个模型：比较本机缓存与内置快照的文件头，在较新的一份里找到这个模型的那一行，只解析这一行，再读这家的列表缓存 |
| `finx models` | 预算 3 ms 以内；实测约 +1 ms | 只解析有凭据的服务商。整家合并 OpenRouter 的 381 个模型（解析约 0.55 ms，合并约 0.25 ms） |
| 查厂商行 | 不是任何厂商的模型：查一次索引，约 0.1 µs | 构建时生成厂商模型名的哈希有序表，所以大多数查不到的 ID 不碰快照；本机有过一次成功的目录刷新才逐家查，因为缓存可能比这个版本新。结果按 ID 记住，每次请求不再查。整家合并时每家厂商只读一次 |
| 常驻服务启动 | 0 | 所有刷新都在后台任务里，第一次 `models/list` 前才解析目录 |
| 常驻服务内存 | 约 1 MB | 解析后的目录常驻；刷新时整份替换 |
| 二进制体积 | 实测 +1.5 MB（18.9 → 20.4 MB） | 快照约 0.2 MB，其余是新增的代码 |

实测（2026-10-30，Apple Silicon，release，各 30 次取中位数，与改动前的同一提交对比）：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| `bench_startup.py` 的 `finx exec`，首个模型请求 | 11.02 ms | 11.09 ms |
| `finx exec -m openrouter/anthropic/claude-sonnet-5.5`（端点不可达，测到退出） | 8.04 ms | 7.99 ms |
| `finx models --provider deepseek`，有 OpenRouter 密钥 | 6.29 ms | 7.29 ms |
| `finx models --json`，有 OpenRouter 密钥（输出 381 个模型） | 6.31 ms | 7.89 ms |

`finx models --json` 最初多出 8 ms，原因是 JSON 逐行写进按行刷新的标准输出；改为缓冲输出后降到上表的数字（这个改动对所有 `--json` 命令都有效）。

v1.3 的实测（2026-11-04，Apple Silicon，release，与改动前的同一提交交替运行，`tools/bench/ratchet.py`，每项 200 次）：

| 指标 | 结果 |
|---|---|
| `finx exec` 到首个模型请求的执行指令数 | −0.42%（50.56M → 50.35M，这个数几乎不受机器负载影响） |
| `finx exec` 的内存峰值 | −64 KiB |
| 二进制体积 | −82 KiB（34.42 → 34.34 MB）：快照多了 10 家，但去掉了账号连接那条单独的路径和手写的重复数据 |
| ACP、socket 到首个模型请求 | +0.3%～+0.9%，不显著 |
| 并发负载（realistic、saturated 两组 22 项） | 全部持平 |
| 第一次 `session/new`（socket） | 多轮之间 +1.3%～+4.4%（最多约 40 µs）。分段测量时，模型解析是这一步里唯一变化的部分，改为哈希索引之前多约 10 µs。其余差距随构建布局变化：只加几行计时、其他代码相同的构建上是 +1.5%，不显著。第二个会话不受影响 |

工具说明里已经写明启动指标在两次构建之间漂移约 2%，判定回退前要重复测量。这里的差距没有一次在所有指标和所有构建上都复现，指令数和内存都在下降，所以不算回退；以后如果在别的改动上继续出现，再回头看。

## 6. 哪些模型进菜单

### 6.1 资格过滤（D-139）

列表里的模型，满足下面任一条就不是这里要的对话模型，不进 `models/list`：

- 公共目录的 `type` 是 `embedding`、`image`、`video`、`speech`、`transcription`、`reranking`、`realtime`；
- 公共目录说输出不含文本；
- 公共目录明确说不支持工具调用（`tool_call = false`）：finx 是智能体，模型必须能调用工具。

公共目录里查不到的模型不过滤，作为"参数未知"列出。用户在 models.toml 里写明的模型不过滤。

### 6.2 默认显示规则（D-140）

`shown` 表示模型是否出现在模型菜单里。一个模型默认显示，当且仅当：

1. 参数已知（`known = true`）；
2. 没有停用（`deprecated = false`）；
3. 它的服务商不是 `list_from` 型的（§3.5）；
4. 在同一家满足前三条的模型里，按发布日期排在最新的 12 个之内。没有发布日期的排在最后，日期相同按 id 排序。

此外：

- **models.toml 写明的模型**、**配置里的默认模型**总是默认显示。
- 第 4 条只对聚合服务商起作用（OpenRouter 有几百个模型）；DeepSeek、Kimi 这样的服务商通常不到 12 个，全部显示。
- 12 是常量，不做配置项；用户的单独选择（§6.3）足够应对例外。

### 6.3 用户调整（D-141）

- 用户可以逐个显示或隐藏模型（`models/show`）。选择存为两个集合：显示的 `show` 和隐藏的 `hide`。
- 最终结果 = （默认显示 ∪ `show`）− `hide`。
- 只存用户改过的模型，所以以后新出的模型仍按默认规则出现；用户隐藏过的不会因为刷新又冒出来。
- 选择以 `provider/model-id` 为键，服务商删掉密钥再加回来，选择仍在。

### 6.4 已在用的模型永远能用（D-142）

列表和显示规则只影响菜单。下面这些情况都照常解析和调用：

- 会话正在用的模型，即使它已从列表消失、被隐藏或被服务商停用；
- 配置里的默认模型；
- 命令行或配置里写的 `provider/model-id`，即使列表里没有。

解析顺序：先按 §4.1 合并参数；四层都没有时用默认参数，并像现在一样发出 warning（总方案 §4.8）。真正调用时服务商说模型不存在，按普通的请求错误返回；二期在这种错误之后自动刷新这家的列表（§14）。

### 6.5 新会话默认用哪个模型（standalone-cli-design D-506、D-534）

内核不替用户假设模型。顺序是：点名的，配置写明的（没有密钥也算），第一个能用的服务商声明的第一个模型（被隐藏或没声明时，用这家显示中没停用、发布最晚的），都没有就没有默认模型，由各入口提醒去设置。完整规则和各入口的表现见 standalone-cli-design.md §7.2。

## 7. 存储

```
~/.finx/models/
├── catalog/<catalog_id>.json     公共目录投影的本机缓存（§5.2）
├── catalog/state.json            上游时间戳、ETag、上次检查时间
├── lists/<provider>.json         服务商列表的缓存（§3）
└── selection.json                用户的显示与隐藏选择（§6.3）
```

- 目录 0700，文件 0600，与总方案 §9.1 一致。写入一律先写临时文件再 rename，多个进程同时读写不会看到半个文件。
- **列表缓存**的内容：

  ```json
  {
    "version": 1,
    "fetched_at": "2026-10-30T09:12:00Z",
    "source": "provider",
    "credential": { "kind": "stored", "fingerprint": "9f2c…" },
    "error": null,
    "models": [
      { "id": "deepseek-flash", "name": null, "context_window": null, "cost": null }
    ]
  }
  ```

  - `source`：`provider`（服务商的列表）、`catalog`（退回公共目录，§3.4）、`unsupported`（服务商没有列表接口）。
  - `credential.fingerprint`：密钥 SHA-256 的前 8 字节，十六进制。只用来发现密钥换了（§3.2），不可逆，也不足以验证密钥。
  - `error`：上次刷新失败的原因（kind 与总方案 §4.11 相同，加上一句说明），成功时为 null。
  - 模型条目里的参数只来自列表响应本身（§4.1 第三层），多数服务商只有 `id`。
- **选择**：

  ```json
  { "version": 1, "show": ["openrouter/qwen/qwen3.8-max"], "hide": ["deepseek/deepseek-v4-pro"] }
  ```

- **缓存可以随时删掉**：`catalog/`、`lists/` 删掉之后，下次用内置快照，常驻服务在后台重新查；只有 `selection.json` 是设置。
- 总方案 §9.1 的目录布局补上 `models/`。

## 8. 协议

都在协议版本 2 之内，由 capabilities 的 `model_discovery` 声明。

### 8.1 `models/list` 的变化（D-143）

- **只列有凭据的服务商的模型**。没有凭据的服务商仍在 `providers` 里，但不列模型；ACP 的 `config_options` 本来就只给可用的模型，不受影响。
- **例外**：配置里写明的默认模型即使它的服务商没有凭据也列出，`available = false`，好让新会话页显示它并引导设置密钥。配置没写时不列，也不假设一个；`defaults.model` 给出内核算出的默认模型，什么都没接入时不出现（§6.5）。
- **ModelSummary 新增**：

  ```ts
  shown: boolean;        // 是否进模型菜单（§6）
  known: boolean;        // 参数是否已知（§4.1）
  deprecated: boolean;   // 服务商已停用
  released?: string;     // 发布日期，YYYY-MM-DD
  cost?: { input: number; output: number; cache_read?: number; cache_write?: number; currency: "USD" | "CNY" };
  ```

  `thinking_levels` 改为去重后的档位（§4.3）。
- **ProviderSummary 新增**：

  ```ts
  listing?: {
    source: "provider" | "catalog" | "unsupported" | "config";
    fetched_at?: string;      // 上次成功查询的时间
    refreshing: boolean;      // 正在后台刷新
    error?: { kind: string; message: string };
    models: number;           // models/list 里属于这家的模型数
    shown: number;            // 其中显示的数量
  };
  ```

  没有凭据的服务商没有 `listing`。

### 8.2 新方法与改动（D-144）

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `models/refresh` | provider?、catalog? | `{ providers: ProviderSummary[] }` | 立即刷新指定服务商（省略则刷新所有有凭据的）；`catalog: true` 时同时刷新公共目录。等刷新结束才返回，单个服务商最多 10 秒 |
| `models/show` | model、shown | `{}` | 显示或隐藏一个模型（§6.3）；`shown` 与默认规则相同时，从选择里删掉这一项 |
| `auth/set`（改） | provider、api_key | `{ verified: boolean, models?: number }` | 先验证再保存（§3.3）；密钥被拒绝时返回错误 `key_rejected`（新错误码 −32021） |
| `models/changed`（已有） | — | — | 列表或公共目录刷新后有变化、选择改变时发出 |

### 8.3 ACP

ACP 的模型选项（`config_options`）改为只给 `shown && available` 的模型，加上会话当前的模型。原因与桌面菜单相同：编辑器的下拉框不该被几百个模型撑爆。

## 10. 桌面端

- **设置 › 模型 › 用 API Key**：
  - 每个服务商一行，状态改为"密钥来源 · 显示 8 / 共 23 个模型 · 2 小时前更新"；刷新失败时显示原因；

- **密钥表单**：`auth/set` 返回 `key_rejected` 时，表单留在原处，显示"密钥无效"和服务商的说明；`verified: false` 时保存成功，提示"暂时无法验证密钥，已保存"。

- 菜单里不再出现没有凭据的服务商的模型，2026-10-30 的"只显示可用模型"改动（`menuModels`）改为按 `shown` 过滤。

## 11. 配置

### 11.1 config.toml

```toml
[models]
network = true          # false：不在后台刷新公共目录和列表；手动刷新、保存密钥时的验证不受影响
```

不提供刷新间隔、默认显示数量、公共目录地址等配置项：这些是实现常量，改动它们没有明确的用户场景。需要离线或内网部署时用 `network = false`，模型写在 models.toml 里。

项目配置（`.finx/config.toml`）里的 `[models]` 一律忽略，与总方案 §11.7 中项目配置不能定义或修改服务商一致。

## 12. 安全与隐私

| 风险 | 对策 |
|---|---|
| 密钥被发到别处 | 列表请求只发往这个服务商自己的 `base_url`，与推理请求的地址规则相同；带密钥的请求不跟随重定向。`list_from` 型的服务商不发请求，所以不会把一家的密钥发给另一家 |
| 恶意或损坏的列表 | §3.4 的大小、数量、id 格式限制；模型名只用于展示 |
| 恶意或损坏的公共目录 | 只接受 HTTPS；32 MiB 上限；投影逐家校验，一家失败只跳过这一家；目录里的值只是参数，不会改变请求发往哪里——端点和鉴权只来自内置修正和 models.toml |
| 参数被篡改导致超额消耗 | 公共目录给出的 `max_output_tokens` 只是上限之一，请求的 max_tokens 仍按总方案 §4.13 计算；上下文窗口过大最多导致服务商返回上下文超限，由内核压缩后重试（总方案 §6.4） |
| 暴露使用习惯 | 公共目录请求不带任何凭据和本机信息，只有 User-Agent；不想访问外网时用 `network = false` |
| 密钥写进缓存 | 缓存只存密钥指纹（§7），不可逆，也不足以验证密钥 |
| 项目配置改写模型来源 | 项目配置不能定义服务商、不能改 `[models]`（§11.1） |

## 18. 思考强度（v1.2，v1.3 修订）

### 18.1 档位

finx 原来有一套统一等级（不思考、极少、少量、适中、深入、最深），再映射到各家的值。几个问题：

- 不同等级落到同一个值上（DeepSeek 的"适中"实际发 `high`），名字和行为对不上；
- 不能关闭推理的模型也显示"不思考"，选了之后什么都不发，服务商照常推理；
- 没有"让服务商决定"的选项，每次都替用户选一个档位；
- 少了 OpenAI 的 `xhigh`；
- 换模型后不支持的档位悄悄降到低一档。

改为服务商自己的档位（D-145）：

| 档位 | 中文 | 含义 |
|---|---|---|
| `default` | 默认 | 不发送任何推理参数，由服务商决定。任何模型都可以选 |
| `off` | 不思考 | 关闭推理 |
| `on` | 思考 | 开启推理，不指定强度；只给有开关、没有档位的模型 |
| `minimal` `low` `medium` `high` `xhigh` `max` | 最少、低、中、高、超高、最高 | 服务商的档位，发送的值就是档位名 |

配置、协议和会话日志里沿用原来的名字，原来的六个值都还合法；新增 `default`、`on`、`xhigh`，配置的默认值从 `off` 改为 `default`。

### 18.2 每个模型提供哪些档位（D-146、D-332、D-334）

档位 = 目录写明的控制方式 ∩ 渠道发得出去的。这样菜单里的每个选项都真的生效。

- **来自目录行**（§4.5 找到的那一行）：
  - 有档位（`effort`）：就是这些值。"不思考"要真能关掉：`none` 是档位之一，或者有开关（`toggle`）且渠道会发开关。finx 没有对应档位的值（例如某家自造的名字）不提供。
  - 只有预算（`budget_tokens`），且渠道会发预算：提供 `low、medium、high、max`，"不思考"的条件同上。Anthropic 接口上老模型不发预算就不思考，所以也提供 `off`。预算的数值按总方案 §4.13 的表，并限制在模型的范围内；`max` 是模型能接受的最大预算（D-339）。
  - 只有开关，且渠道会发开关：提供 `off、on`。渠道不会发开关时没有档位。
  - 什么控制方式都没写：不提供档位，只有"默认"（D-334）。例外是 OpenRouter，它替每个模型翻译，给 `off、low、medium、high`。
  - 例：DeepSeek 是开关加 `low、high、max`，提供 `off、low、high、max`；GLM-5.3 只有 `low、high、max`，官方说关不掉，就没有"不思考"。
- **来自配置**：models.toml 的 `thinking = ["off", "high"]` 直接指定；没写 `thinking` 时，`thinking_levels` 里写了值的档位就是提供的档位（兼容旧写法），值是发送的内容。
- **没有目录行但模型能推理**（手写的模型、只有列表知道的模型）：按请求格式给一组保守的档位（deepseek、qwen、zai 格式是 `off、on`；openai 格式是 `low、medium、high`；openrouter 是 `off、low、medium、high`；anthropic 接口是 `off、low、medium、high、max`；没有格式就没有）。
- **不能指定推理**：模型不推理，或渠道的 `thinking_format` 明确写了 `none`，就不提供任何档位，界面隐藏思考强度，请求里也不发。
- `models/list` 的 `ModelSummary.thinking_levels` 就是这个列表（不含 `default`）。

### 18.3 请求（D-147、D-332、D-333、D-336）

发出的档位一定是模型提供的；不提供的（例如旧会话里存的 `medium`，或配置的默认值）按 `default` 处理。`default` 一律不发。其余按下面的规则，由模型的控制方式决定发什么，由渠道决定参数名：

**OpenAI 兼容接口**：

| 选的档位 | 发送 |
|---|---|
| 有档位的模型选一个档位 | `reasoning_effort: <值>`；模型有开关时同时打开开关 |
| 只有预算的模型选一个档位（`qwen` 格式） | 打开开关，加 `thinking_budget` |
| `off` | `none` 是模型的档位时发 `reasoning_effort: "none"`，否则发渠道的关闭开关 |
| `on` | 渠道的打开开关 |

每个渠道的 `thinking_format` 只说开关和预算怎么发（D-333）：

| `thinking_format` | 开关 | 预算 | 用它的渠道 |
|---|---|---|---|
| 不写 | 不知道：只有 `reasoning_effort: "none"` 能关 | 不知道 | 腾讯 Token Plan（Q-148）、Ollama |
| `openai` | `reasoning_effort: "none"` 关，不能单独开 | 无 | OpenAI、千问办公、Qoder |
| `deepseek`、`zai` | `thinking: {type: "enabled" / "disabled"}` | 无 | DeepSeek、智谱、Z.ai、Kimi、火山 |
| `qwen` | `enable_thinking` | `thinking_budget` | 百炼 API、百炼 Token Plan |
| `openrouter` | 全部放在 `reasoning` 下，由它翻译 | 同左 | OpenRouter |
| `none` | 什么都不发，也没有档位 | — | 明确拒绝这些参数的网关 |

模型没有开关时不发开关：GLM-5.3、Kimi K3 都明确说不需要也不应该发。

**Anthropic 接口**（D-336）：

| 模型 | 选一个档位时发送 |
|---|---|
| 只有档位（Opus 4.7 及之后、Fable） | `thinking: {type: "adaptive", display: "summarized"}`，`output_config: {effort: <值>}` |
| 只有预算（Haiku 4.5、Sonnet 4.5） | `thinking: {type: "enabled", budget_tokens: N}` |
| 两者都有（Opus 4.5、Opus 4.6、Sonnet 4.6） | 上面的预算，加 `output_config: {effort: <值>}` |

`off` 发 `thinking: {type: "disabled"}`，只有目录写了开关（或只有预算）的模型才提供。DeepSeek 的 Anthropic 兼容端点把 `adaptive` 当作 `enabled`，同样可用。

各请求格式的完整参数见总方案 §4.13。

### 18.4 切换模型时的状态（D-148、D-149）

会话保存的是用户的选择（一个档位，可以是 `default`）。规则只有三条：

1. **选档位**：选了模型提供的档位就用它，并记作"这个模型上次选的档位"；选 `default` 就忘掉这个记录。
2. **换模型**：当前档位新模型也提供（`default` 除外），就保留；否则用新模型上次选的档位；没有就用新模型配置的 `default_thinking`；再没有就是 `default`。
3. **新建会话或恢复会话**：客户端明确给了档位，就按第 1 条处理；没给（用配置的默认值或日志里存的值）就按第 2 条处理。

举例（DeepSeek 提供 `off、low、high、max`；本机的 Qwen3 Coder 没有档位；OpenAI 某模型提供 `none、low、medium、high、xhigh`）：

| 操作 | 结果 |
|---|---|
| DeepSeek 上选"最高" | 最高，记为 DeepSeek 的档位 |
| 换到 Qwen3 Coder | 默认（它没有档位，菜单里不显示这项）；界面提示"没有「最高」档，思考强度改为「默认」" |
| 换回 DeepSeek | 最高（上次在 DeepSeek 上选的） |
| 选"低"，再换到 OpenAI | 低（OpenAI 也有） |
| 选"超高"，再换到 DeepSeek | 低（DeepSeek 没有超高；上次在 DeepSeek 上选的是低），界面提示 |

- **记在哪里**：`~/.finx/models/selection.json` 的 `thinking`，按 `provider/model-id`。`models/list` 的 `ModelSummary.default_thinking` 就是"这个模型的起始档位"（上次选的，或配置的 `default_thinking`，或 `default`），新会话页和其他客户端用它决定切到这个模型时显示什么。
- **新会话页**：桌面端的草稿按同样的三条规则处理，自己也按模型记住在页面上选过的档位，创建会话时把档位传给内核，内核随之记下。
- **提示**：只有用户选过的档位因换模型而变化时才提示；从 `default` 换模型、或档位没变时不提示。

### 18.5 界面

- 模型按钮：模型名后面跟当前档位（"DeepSeek-V4.1-Flash 最高"）；模型没有档位时只显示模型名。
- 菜单："思考强度"一行打开子菜单，第一项"默认"（右侧注明"由服务商决定"），分隔线，然后是模型提供的档位。
- ACP 的 `thought_level` 选项同样是"默认"加模型提供的档位。

### 18.6 账号连接（千问办公）

账号连接的档位由连接从应用自己的目录得出（§4.7），写明的列表优先于目录行：

- **发送方式**：千问办公的网关是 OpenAI 兼容的 `chat/completions`，用 `reasoning_effort` 指定强度，所以连接的 `thinking_format` 是 `openai`。Qoder 在自己的传输层翻译。
- **档位**：目录项的 `is_reasoning` 为真，或 `thinking_config.enabled` 为真，就提供 `low、medium、high、xhigh、max`（千问办公允许的值）。`qwen3.7` 系列只能开关，提供 `off、on`。
- **"不思考"**：只给目录里**没有** `thinking_config` 的模型。2026-10-30 实测：`reasoning_effort: "none"` 让 flash、qwen3.8-max-preview 的推理变成 0；带 `thinking_config` 的 pro 仍然推理（40 余个 token），关不掉。
- **起始档位**：目录的 `thinking_config.effort`，没有时按千问办公自己的做法，qwen3.8-max 用 `xhigh`，其他用 `high`。不选档位时的效果因此与在千问办公里一致。
- **ConnectionModel** 新增 `thinking`、`default_thinking`，随连接的模型目录一起保存。

2026-10-30 的实测（同一道需要推理的题，pro 模型）：

| 档位 | 推理 token | 用时 |
|---|---|---|
| 默认（不发） | 171 | 5.4 s |
| 低 | 37 | 1.6 s |
| 中 | 112 | 4.5 s |
| 高 | 89 | 2.4 s |
| 超高 | 536 | 10.4 s |
| 最高 | 1,082 | 15.4 s |

网关接受全部五档，推理量随档位增长（中、高之间的差别在正常波动范围内）。

### 18.7 测试

- finx-llm：`reasoning_options` 推导（档位、开关、预算、未知值）、渠道能提供什么、各请求格式的参数（请求体快照）。
- **守卫**（`crates/finx-llm/tests/channels.rs`，D-340）：遍历每个内置渠道、它目录里的每个模型和每个预置：每个档位都必须改变请求；目录写了的档位都要提供；"不思考"必须真实；Token Plan 的预置必须有参数；不声明 `thinking_format` 的渠道要写进测试里说明。新增渠道或每周同步带来的问题，在这里就能看到。
- 端到端（`e2e_models.rs`）：`the_thinking_level_follows_the_model_and_is_remembered` 测切换规则；`each_channel_describes_its_models_and_sends_the_levels_it_offers` 通过真实的 `finx serve` 检查百炼、腾讯、智谱三个渠道的模型参数，并断言选了档位之后发给服务商的请求内容。
