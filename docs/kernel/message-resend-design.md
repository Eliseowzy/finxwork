## 方案摘要

- **语义**：点"撤回重发"不碰会话，只是原话回到输入框，气泡不动，模型接着跑，取消等于没发生过。按下发送的那一刻，会话才回到这条消息发出之前，同时发出新消息。回退和发送是一个动作，不存在"已经回退、还没发新消息"的状态。
- **内核只多一个 Op**：`resend { message_id, input }`。任务在跑就由内核先停；排队的话交还输入框；对话回到这条消息之前，再开始新任务。不提供单独的 `rewind`，它正是用户不要的那个中间状态。
- **日志几乎不用改**：会话日志本来就是一棵树，当前分支由最后一条顺着 `parent` 往回找。回退只追加一条已经定义好的 `branch` 条目，被撤回的内容原样留在文件里。上下文、预算、压缩、转录都只看当前分支，自动正确。回退到压缩之前的消息也不用特殊处理。
- **协议**：新事件 `session_rewound { message_id, removed_agents, returned_input }`，会话镜像和各客户端据此截断对话。capability `message_resend`。
- **要一并修的**：
  - 恢复会话时标题、归档、模型、权限模式、累计用量现在只读当前分支，回退后重启会丢失；权限模式还可能退回更宽松的旧值，这是安全问题。这些是会话级事实，改成按全文件读（§3.6）；
  - 被撤回段启动的子智能体要关掉，保留段启动的继续跑，它在被撤回段送达的汇报要重新投递（§3.5）；
  - 文件跟踪和工具搜索记录要清空，否则模型可以覆盖它从未读过的文件（§3.4）；
  - 撤回第一条消息时，会话列表的预览要跟着变（§4.4）。
- **模型看到的**：当时的上下文加一条新消息，不加任何提示词。回退点之前的前缀和当时的请求逐字节相同，提示缓存还在就能命中。
- **一期只回退对话，磁盘文件不动**：模型在被撤回段里改过的文件留在磁盘上，输入框上方的托盘里如实说明。磁盘文件回退放二期，`resend` 加一个可选字段即可，不影响一期的协议（§6）。用户已确认（D-383）。
- **桌面端**：消息悬停条多一个"撤回重发"。原话和附件（图片、文件、文件夹、网页片段、文档引用）、Skill 标签原样回到底部输入框（§5.4），对话区不放编辑框；输入框上方的托盘多一行，说明从哪条重发，那条气泡高亮；输入框里原来的草稿先暂存，结束后放回；↩ 发送，Esc 取消；不弹确认。
- **工作量**：内核与协议约 1 天，客户端与桌面端约 1 天，测试与真实模型验收约 0.5 天。

## 1. 语义

1. **点"撤回重发"不碰内核**。原话回到输入框，不发任何请求。气泡不动，模型接着跑，下面的内容接着长，别的窗口什么都看不到。取消就恢复原样。
2. **按下发送才回退，回退和发送是一个动作**。没有"回退了但还没发"的会话状态：别的窗口看不到，崩溃也基本留不下（§3.7）。
3. **任意一条自己发的消息都能选**。发了多少条、模型回了多少条都一样；压缩之前的、任务中途插话进去的都一样；任务在跑也可以。
4. **回到的是"这条消息发出之前那一刻"的对话**。模型收到的是当时的上下文加新消息，就像后面的内容从没发生过。界面上它们消失。内容不改直接发，就是"重新生成"，同一个操作。
5. **世界不回退（一期）**。磁盘文件、命令的副作用、浏览器状态、子智能体已经做完的事都留在原地（§6）。花掉的钱也不退，累计用量照算。消息自己带的附件不算世界，原样退回（§5.4）。
6. **设置不回退**。用当前的模型、推理等级和权限模式：输入框上显示的是什么就用什么；刚收紧的权限不能因为回退而放宽（D-375）。
7. **没有东西真的被删**。被撤回段留在日志文件里，只是不再属于对话。这也给以后的版本切换留了路（§7）。

主流产品的做法可以对照：

| 形态 | 怎么触发 | 磁盘文件 |
|---|---|---|
| 编辑器里的 agent | 在消息上原地编辑，发送时才生效 | 发送时问"回退文件并继续"还是"不回退继续" |
| 一个终端 agent | 菜单选一条消息，再选恢复对话、恢复代码或两者；原话回到输入框 | 只跟踪自己编辑工具碰过的文件；只被命令或子智能体改过的文件不管 |
| 另一个终端 agent 的服务接口 | 日志里追加回退标记，恢复时按标记裁剪 | 明确不管，交给客户端 |
| ACP 的会话回退草案（已关闭，未合入） | `session/edit_prompt` 单独成一个方法，理由是客户端要原子的编辑重发，否则 agent 会观察到"回退了但没有后续"的状态 | 明确不管 |

## 2. 现状

**已经有的：**

- 日志是树：`Entry.parent`；当前叶子是文件最后一条；`History` 顺着 parent 走出当前分支，`generation` 标记分支换过；`History::from_entries` 和单测已经覆盖带回退的日志（`crates/finx-core/src/history.rs`）。
- `EntryKind::Branch` 在日志格式里，含义就是"回退标记"，一直没有代码写它。
- `build_context`、`budget`、`compact`、`transcript_of`、`agents::restore` 都只看当前分支。
- 压缩不删条目，`transcript_of` 里压缩之前的消息照样有 `message_id`。回退到那里，分支上就没有那条 compaction，上下文自然回到未压缩的状态（总方案 §7.6.9 当初就留了这条路）。
- 用户消息的 id 在入队时定下，送达后就是 `message_id`（input-queue-design）。
- `finish_task` 在同一把锁里结束旧任务、预定新任务，新任务开始前不会有别的输入插进来。
- `hand_back` 和桌面端的 `putBack`、`fromInput` 能把消息连同附件放回输入框。

**缺的：**

- 写 `branch` 的入口和 Op；
- 让镜像和客户端同步的事件；
- 几处恢复逻辑"只看当前分支"其实不对（§3.6）；
- 子智能体和几份内存状态的处理（§3.4、§3.5）。

**为什么不用总方案原来规划的 `Rewind { to }`**：它要两步，先回退再发消息，中间那个状态会被别的窗口看到、被崩溃留下，用户改主意了也回不去；任务在跑时客户端还得自己编排"停止、等停完、回退、发送"。一个原子的 `resend` 把这些都消掉（D-370）。

## 3. 内核

### 3.1 Op

```rust
/// 从一条已经发出的用户消息重新开始：任务在跑就先停，对话回到这条消息之前，再发 input。
Resend {
    message_id: String,
    input: Vec<UserContent>,
    #[serde(default = "yes", skip_serializing_if = "is_yes")]
    commands: bool,               // 与 Prompt 相同：解析 /skill:名字
},
```

没有 `mode`：它总是立刻生效，不排队。

拒绝的情况发 `warning { code: resend_rejected }`，会话不变：

| 情况 | 说明 |
|---|---|
| 目标不在当前分支上，或不是 message 条目的 user 消息 | 别的窗口已经撤回了它；子智能体汇报（mail 条目）和内核加的环境消息也不算 |
| input 为空 | |
| input 是 `/compact`、`/context` | 它们不是消息，从旧位置发它们等于只回退不发送，违反语义第 2 条 |
| 已经有一个 resend 在等任务停下 | 第二个不替换第一个，免得第一个的话丢掉 |
| Bot 的会话 | 本方案只做会话模式 |

### 3.2 流程

```rust
fn on_resend(session, message_id, input, commands) {
    // 校验；像 on_prompt 一样解析 Skill；不通过就发 warning 返回
    let mut state = session.state.lock();
    let resend = Resend { target: message_id, input: Input { id: state.input_id(), .. } };
    if let Some(task) = &state.active_task {
        state.pending_resend = Some(resend);
        task.cancel.cancel();     // 只停这个任务，不像 Stop 那样停整棵树
        return;
    }
    let next = apply(session, &mut state, resend);
    drop(state);
    launch(session, next.task, next.work, TaskTrigger::User);
}

// finish_task 的那把锁里，旧任务的结束事件之后：
if let Some(resend) = state.pending_resend.take() {
    // 正常结束的那一支不取下一条输入；中断、失败两支不交还、不设 hold；
    // 交还统一在 apply 里做
    return apply(session, state, resend);
}

fn apply(session, state, resend) -> Next {
    let returned_input = hand_back(session, state);   // 还在排队的话
    rewind(session, state, &resend.target, returned_input);  // §3.3–§3.5，发 session_rewound
    Next { task: reserve(state), work: Work::Prompt(Some(resend.input)) }
}
```

事件顺序：

```
（任务在跑时）…… task_interrupted { returned_input: [] }
session_rewound { message_id, removed_agents, returned_input }
task_started
message_completed（重新投递的汇报，如果有）
message_completed（新消息）
turn_started ……
```

中间不发 `idle`。`pending_resend` 在 `state` 里，任务 3 秒的宽限照旧（总方案 §6.8）；等待审批中的调用按 abort 处理。

排队的话交还而不是留在队列（D-376）：它们是对着旧对话说的，继续自动发给模型可能不是用户的意思；放回输入框，用户看一眼再发。这和 Stop 的做法一致。

### 3.3 日志

`rewind` 只追加一条 `branch`，它的 `parent` 指向回退点；之后的条目接在它后面。"文件最后一条即当前叶子"的规则不变。

```
… ─ a1 ─ t2s ─┬─ u2 ─ a2 ─ r2 ─ t2e              被撤回段，留在文件里
              └─ b1 ─ t3s ─ u3 ─ a3 ─ …          当前分支
```

```jsonc
{"id":"b1","parent":"t2s","ts":1793224075025,"type":"branch"}
{"id":"b2","parent":"t5s","ts":1793224075026,"type":"branch","before_first":true}
```

- 回退点就是目标消息的 `parent`，可能是这个任务的 `task started`、`date` 或任务开头投递的 `mail`。它们都发生在这条消息之前，留在分支上，这样上下文前缀和当时完全一样。
- 这样会留下一条没有结尾的 `task started`。它不产生转录项，恢复时只看分支上最后一条 task 条目，不受影响。
- `before_first`：回退到第一条用户消息之前。列表扫描日志时靠它重置 `first_message`（§4.4）。一个布尔值比在摘要里记 id、比对 parent 简单。
- `History::rewind` 写入后重新走一遍分支，`generation` 加一。`TurnScan`、`ReportKey` 看到 generation 变了，自动重算。

### 3.4 回退时一并处理的状态

| 状态 | 处理 | 为什么 |
|---|---|---|
| `FileTracker` | 清空，等同恢复会话 | 模型在被撤回段读过的文件，它现在的上下文里并没有；不清空，write 的"必须先读"检查就被绕过，能覆盖它从未读过的文件。清空后写之前要重读，这也正合适：磁盘上的内容可能已经变了 |
| `mcp_shown`（工具搜索展示过什么） | 清空，等同压缩 | 否则下次搜索回答"definition shown earlier"，可那份定义已经不在上下文里了 |
| `hold` | 清除 | 新输入本来就结束 hold |
| `inbox` | 去掉被撤回段启动的子智能体的汇报，放回要重新投递的（§3.5） | |
| `state.usage` | 不动 | 钱已经花了 |
| 模型、推理等级、权限模式 | 不动 | 语义第 6 条 |
| `session_rules`、`site_grants` | 不动 | 是用户对这个会话的授权，不是对话内容 |
| 系统提示词 | 不动 | 内存里就是最新的；分支上的 `system_prompt` 条目如果旧了，恢复时已有的比较会补记 |
| `pending_model` | 不动 | 下一个任务的轮次边界照常生效 |
| 浏览器标签页 | 不动 | 世界不回退 |

### 3.5 子智能体

|  | 运行中 | 已结束 |
|---|---|---|
| **在被撤回段启动**（段里有它的 `agent_spawned`） | `Op::Shutdown` 停掉并关闭，从树上摘除；名字释放；之后到达的汇报丢弃 | 从树上摘除 |
| **在保留段启动** | 继续跑，汇报照常到 | 它在被撤回段送达的汇报重新放进 inbox，随新消息一起给模型 |

- **保留段的不停**（D-377）：撤回只放弃这条消息之后的事。很早以前派出去的长任务不该因为改了最后一条消息而中断，否则还要让模型再把它叫起来。
- **汇报要重新投递**：模型在保留段里看到的是"它在后台跑，汇报会以新消息到达"。汇报如果只留在被撤回段，模型就永远等不到。条目里有完整的 `mail` 和 `message`，放回 `inbox` 时 `wake: false`；`run_task` 开头的 `deliver_mail` 把它写在新消息之前。
- **丢弃在路上的汇报**：`on_mail` 查发送者还在不在树上。不在就丢弃，但照常 `mail_received`，`in_flight` 的计数不受影响。
- **事件**：`session_rewound.removed_agents` 让镜像和客户端把它们从列表里去掉。对话里的派出卡片随消息一起消失。
- **恢复**：`agents::restore` 只看当前分支，它们不会回来，无需改动。它们的日志留在磁盘上，头部带 `agent`，不进列表。
- **已知限制**：保留段的子智能体如果在被撤回段收到过 `send_message`，它记得这些话，子智能体的会话不回退。它之后的汇报可能提到模型不知道的事。这种情况少见，后果也只是多一点信息，一期接受。

### 3.6 恢复：区分会话级事实和分支内容

`Kernel::resume` 现在从当前分支上读全部状态。没有回退时这没问题；有了回退，被撤回段里的设置改动就读不到了。

| 内容 | 现在读 | 改成 | 不改的后果 |
|---|---|---|---|
| `settings`（模型、推理等级、权限模式） | 当前分支 | **全文件，按文件顺序** | 第 5 条消息前把权限从 bypass 收紧到 manual，再撤回第 4 条；重启后权限退回 bypass。**这是安全问题** |
| `title`、`archived` | 当前分支 | 全文件 | 改过的名字、归档状态重启后丢失 |
| 累计用量（`usage_of`） | 当前分支 | 全文件 | 花掉的钱重启后"消失"，运行时和重启后数字不一致 |
| 任务编号上限 | 当前分支 | 全文件 | 任务 id 在同一个文件里重复 |
| `system_prompt`、未结束的任务、子智能体 | 当前分支 | 不变 | 它们确实属于分支 |

`History::in_order()` 已经有了，改动不到十行。会话列表的扫描本来就按全文件读这些字段，改完两边一致。

### 3.7 崩溃一致性

| 进程退出的时机 | 恢复后的状态 |
|---|---|
| 收到 resend，旧任务还没停完 | 日志没动，旧对话还在，补记任务 interrupted。输入框里的话在客户端手里，见 §5.3 |
| `branch` 已写，新消息没写 | 回到了那一刻，新消息丢失。两条相隔微秒，通常在同一批写入里。这是语义第 2 条唯一的缝隙，接受 |
| 新消息已写，回复没完成 | 与普通崩溃相同 |
| 最后一行只写了一半 | 按总方案 §9.4 第 1 步丢弃 |
| 正常关闭会话时还有 resend 在等任务停下 | 这个 resend 取消，不回退：关闭过程中不启动新任务 |

`branch` 不单独 fsync。掉电时它和普通消息一样，可能丢到上一次任务结束，那样旧对话还在，同样一致。

### 3.8 上下文与缓存

- **前缀不变**：新请求 = 系统提示词 + 工具 + 回退点之前的消息 + 新消息。系统提示词和工具没变时，前缀与当时的请求逐字节相同，缓存还活着就能命中（Anthropic 5 分钟，DeepSeek 数小时）。`cache_key` 还是会话 id。追加式历史的原则没有破坏：回退后这条分支依然只追加。
- **用量校准**：`budget` 找分支上最后一条 assistant 的真实用量，再加上之后内容的估算，不用改。
- **回退到压缩之前**：上下文回到压缩前的完整内容，可能接近或超过软阈值，那么第一次请求前会再压缩一次，要花一次摘要的钱。任务开头的 `check_context` 已经覆盖，不用特殊处理。旧摘要留在被撤回段，不复用：它总结的内容里有被撤回的部分。
- **换了模型**：`previous_model` 和窗口变小的处理都是按分支算的，照常工作。
- **不加提示词**（D-379）：内核不告诉模型发生过回退。一期判断它不需要知道：模型读文件时看到的是真实内容，edit 匹配不上会报错，write 要先读。查到的产品文档也没有提到这样的提示。真实模型验收（§11）里模型每次都先读文件再动手，还会主动说明文件里已有别的内容，所以一期不加。以后如果发现模型被旧印象绕晕，再按 §7 加一条事实性的 `<environment_update>`。

## 4. 协议

版本 2 之内，capabilities 声明 `message_resend`。桌面端把它列入 `required`，否则同版本的旧服务不会被替换（input-queue-design 同样如此）。

### 4.1 Op 与事件

```rust
/// 对话回到了 `message_id` 之前：它和它之后的内容不再属于对话。总在新消息之前发出。
SessionRewound {
    message_id: String,
    /// 随被撤回段关闭的子智能体
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    removed_agents: Vec<String>,
    /// 还在排队的输入，交还输入框
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    returned_input: Vec<UserMessage>,
},
```

`WarningCode` 增加 `ResendRejected`。Op 的校验在内核做，服务层不预检：与 `withdraw` 一样，先后只有内核能判断，预检省不掉内核那一步。

### 4.2 会话镜像

```rust
EventMsg::SessionRewound { message_id, removed_agents, .. } => {
    // 截到这条消息之前；与 transcript_of(新分支) 相同
    self.transcript.truncate(位置);
    self.agents.retain(|a| !removed_agents.contains(&a.agent_id));
    self.failed = 从 transcript 重算;
}
```

"快照 + 之后的事件 = 从头接收"这条不变量继续成立，测试要覆盖（§8）。`usage` 不减。

### 4.3 历史分页

`before` 游标是下标。目标在客户端已加载的范围内时，游标仍然有效。不在范围内时（别的窗口撤回了更早的消息），新消息可能和旧游标对应的下标重叠，所以客户端不拼接，整体重新接入（§5.2）。

### 4.4 会话列表

- **已加载的会话**：`hub.rs` 的 `changes_summary` 遇到 `session_rewound` 时，如果转录里已经没有用户消息（mail 不算），就把 `base.preview` 清空。下一条用户消息照常成为预览（已有逻辑）。
- **未加载的会话**：`jsonl.rs` 的 `summarize_line` 增加读 `branch` 行，`before_first` 为真时把 `first_message` 清空。增量扫描和磁盘投影都是按行推进的，不用改。

### 4.5 ACP

不暴露。ACP 目前没有回退的方法，那份草案已关闭。内部事件走 `_ => {}`，ACP 客户端不受影响；`session/load` 回放的是当前分支。将来 ACP 定下来，`session/edit_prompt { messageId, newContent }` 一对一映射到 `Op::Resend`，不需要转换层。

## 5. 客户端与桌面端

### 5.1 交互

原话退回底部输入框，对话区不放编辑框（D-380）。

| 动作 | 界面 | 会话 |
|---|---|---|
| 悬停自己的消息，点"撤回重发"（Pencil 图标，在复制旁边） | 原话、附件、Skill 标签回到输入框（`fromInput`），焦点在输入框；托盘多一行；那条气泡高亮 | 什么都不发生 |
| 编辑中 | 气泡不动，对话照常长 | 模型接着跑 |
| 点托盘那一行的文字 | 滚动到那条气泡 | 无 |
| × 或 Esc（`/` 菜单开着时先关菜单） | 输入框回到原来的草稿 | 什么都不发生 |
| 又点了另一条消息的"撤回重发" | 换成那条的原话，刚才的改动不保留 | 什么都不发生 |
| ↩（⌥↩ 也一样） | 输入框锁住，等 `session_rewound`：对话截断，滚到底，新消息在最下面，输入框回到原来的草稿 | 回退并发送 |

```
 ┌────────────────────────────────────────────────────┐
 │ ✎  重发：把报告改成三段式…                       × │  托盘，和排队消息同一种行
 │    这条之后的内容会被撤回，模型改过的文件不会恢复  │
 ├────────────────────────────────────────────────────┤
 │ +  把报告改成五段式|                             ↑ │  输入框
 └────────────────────────────────────────────────────┘
    权限                                          模型
```

托盘第二行是一句安静的说明，按情况组合：

- 总有：`这条之后的内容会被撤回`
- 被撤回段有 Edit、Delete、Move 或 Execute 类的工具调用：`，模型改过的文件不会恢复`
- 任务在跑：`，正在进行的任务会停止`

重发状态下输入框有几处不同：

- 按钮始终是发送，不变成停止；内容清空时不能发。
- 不能插话或排队：↑ 不取排队消息，托盘里的排队行不提供"编辑"。要插话就先按 ×。
- 模型和权限选择器照常能改，重发就用改后的。换个模型重发很顺手。

不弹确认：发送就是确认。不把后面的内容压暗：发送之前会话就是没有变化，画面也不该变，只有目标气泡高亮。

**为什么退回输入框，而不是在气泡里原地编辑**：

- 产品里只有一个输入框。附件、拖放、粘贴、Skill 菜单、模型和权限都在那里，不用在对话区再造一个。
- 和排队消息的"编辑"是同一个动作（D-212）：话回到输入框，用户已经熟悉。
- 气泡一动不动，"点撤回时会话没有变化"看得见。
- 流式输出时，对话区里一个会变高的编辑框会和跟随滚动互相干扰。

**这样做的代价和对策**：

| 代价 | 对策 |
|---|---|
| 输入框离目标消息可能很远，看不出从哪条重发 | 托盘一行写明原话开头，点击可定位；目标气泡高亮 |
| 输入框里可能有写了一半的草稿 | 暂存，退出或发送后放回（§5.3） |
| 重发状态下不能给运行中的任务插话 | 按 × 退出；这种时候很少，发送本身也会先停任务 |

不显示按钮的地方：Bot 页面、子智能体的对话、已归档的会话。

### 5.2 `@finx/client`

```ts
case "session_rewound": {
  const at = v.entries.findIndex((x) => x.type === "message" && x.message_id === e.message_id);
  // 不在已加载范围：已加载的全部作废，标记 stale，useSession 整体重新接入
  const entries = at < 0 ? [] : v.entries.slice(0, at);
  // 截断；context 从剩下的条目重算；agents 去掉 removed_agents；failure 清除；
  // rewound 记下目标和一起消失的用户消息；returned 有内容就设上。usage 不减。
}
case "warning": // code 为 resend_rejected 时只记 refused，不进提醒
```

要改一处已有行为：`task_started` 现在会清 `returned`。`session_rewound` 或 `task_interrupted` 常常和紧随的 `task_started` 落在同一帧，交还的内容还没渲染就被清掉了。去掉这次清除；已放回的由 `Dock` 的 `handed` 挡住，不会重复。

`mock/server.ts` 同样模拟这个 Op。

### 5.3 草稿、不丢话，以及多窗口

- 重发状态 `{ messageId, stash, sending }` 放在 `Dock` 的 `drafts` 旁边，按会话存，切换会话还在。`stash` 是点撤回重发时输入框里原来的草稿，退出时放回，不和原话混在一起。
- 发送后，话留在输入框里并锁住，直到收到 `session_rewound { message_id }`。收到 `warning { code: resend_rejected }`、请求失败或连接断开时解锁，话还在。内核在回退之前崩溃，话也不丢。
- 重发状态下内核交还的消息（`view.returned`）放进 `stash`，不掺进正在改的原话。收到 `session_rewound` 时先还原 `stash`，再放交还的内容，顺序反了交还的内容会被覆盖。
- 编辑到一半，目标消息被别的窗口撤回了（`view.entries` 里已经没有它）：托盘那一行消失，输入框里的话变成普通草稿，原来的草稿接在后面，提示一句。
- 发送途中离开页面：话已经交给内核，草稿放回，不再等结果（D-385）。这时如果被拒，那段话就没了；被拒只发生在目标刚好被别的窗口撤回的那几毫秒，或者打的是 `/compact`（立刻被拒，来不及离开）。
- 断线重连或内核重启后的新快照：错过的事件不会再来，所以看快照（`view.attached` 变了）。消息还在就解锁，话还在；消息不在了，发送途中的算已生效，放回草稿，否则按上一条处理。
- 两个窗口同一瞬间撤回同一条：后一个被拒，但它也会看到自己目标的 `session_rewound`，会以为成功了。一个人同时操作两个窗口才会碰到，不处理。

### 5.4 附件

退回的消息连同附件原样回到输入框（D-382）。走的是 `fromInput`，和排队消息的编辑同一条路。这一节的结果来自用真实的 `toInput`、`fromInput` 跑的往返（i18n 用桩代替，没有在应用里跑）。

| 内容 | 退回输入框后 | 重发时发给模型的 |
|---|---|---|
| 图片 | 原图。base64 在消息里，日志、快照、事件都不裁 | 同一份数据 |
| 文件、文件夹 | 同一个路径 | 同一个路径。带的是路径不是内容，模型读到的是文件现在的样子 |
| 网页片段 | 说明、选择器和截图都在 | 相同 |
| 文档引用 | 页码、原文、批注和截图都在 | 相同 |
| Skill 标签 | `/skill:名字` 在文字里，变回标签 | 相同；Skill 的正文按发送时的版本重新读 |

**顺序**：附件按类型归组（图片、文件和文件夹、网页片段、文档引用），和气泡显示的顺序一样。不混用时，发给模型的内容和第一次逐字节相同。图片和带截图的片段混在一起时，图片在消息里的位置可能调换，截图编号跟着更新，指向不会错。

**消息里还有不是用户写的块：**

| 块 | 现在 | 处理 |
|---|---|---|
| 正在看的文档（`docViewingBlock`，文件面板发送时自动附加） | `userText` 跳过，不退回 | 不变。发送时按面板当前的状态重新附加，它说的本来就是"现在"看的那一页 |
| 交给会话的浏览器标签页（`giveOffered`、`store.start` 追加的两种文字块） | `userText` 当成原话：气泡里会露出这段英文，退回时也会进输入框 | 实现时一并修：`userText` 认出它们，不算原话；退回时变成一个附件 Tile，可以 × 去掉，重发时原样带上。不能直接丢：标签页不回退，它还归这个会话，而模型刚刚忘了这件事 |

## 6. 磁盘文件回退（二期）

**一期的代价要说清楚**：被撤回段改过的文件留在磁盘上，模型也不知道。用户想恢复就要自己用 Git。托盘里的说明如实告知。

**为什么分两期**：回退对话是所有问题的底座，协议上可以平滑扩展；磁盘文件回退是一套独立的记录机制，覆盖不全的部分还要想清楚怎么告诉用户。放在一起做，反而会拖慢验证核心语义。

二期的做法：

- **记录**：write、edit 改文件之前，把当时的内容存进会话数据目录 `file-history/<内容哈希>`，相同内容只存一份。改完在分支上追加 `file_change { path, before, after }`，before 为空表示新建。
- **回退**：`resend` 加 `restore_files: true`。沿被撤回段从后往前，每个路径取最早一条的 before 作为目标。当前哈希等于最后一条的 after 才恢复；不等说明被别的东西改过（用户、命令、文件面板），跳过并在 `session_rewound` 里列出。在 `PathLocks` 下写。
- **界面**：被撤回段改过文件时，托盘那一行多一个勾选"同时把文件恢复到这条消息之前（N 个文件）"。不弹窗。
- **盲区**：bash 改的文件；子智能体的改动（各有各的日志，收集起来要另算）。一个成熟产品的同类功能也有这些盲区，并在文档里写明了。
- **不用 Git 快照**：它能覆盖 bash，但无项目会话和非 Git 目录用不了，大仓库每条消息都要扫一遍，还会写进用户的对象库。以后可以作为有 Git 时的增强。
- **工作量**：约 2 天。

## 8. 测试与验收

**单元**：

- `History::rewind`：分支、叶子、`generation`；之后的 append 接在新分支上；从文件恢复结果相同。
- `resume`：§3.6 表里每一行，尤其是权限模式。
- `summarize_line`：`before_first` 重置预览；增量扫描与全量相同。
- 镜像：每个事件后接入，快照加之后的事件与从头接收一致，事件序列里包含 `session_rewound`。
- `@finx/client`：reducer；`returned` 在同一帧的 `task_started` 之后还在；目标不在范围时标记重新接入。
- `toInput`、`fromInput` 往返：§5.4 的每一种附件；混合顺序下截图编号仍然指向对的图片；标签页的块不进文字，重发时还在。

**内核端到端**（`crates/finx-core/tests/resend.rs`，ScriptedApi）：

1. 空闲时重发：新请求的 messages 等于当时请求的前缀加新消息，逐条相同。
2. 任务在流式输出、工具执行、等待审批时重发：旧任务先结束，只有一个新任务，没有 `idle`，事件顺序符合 §3.2。
3. 排队的插话和跟进从 `session_rewound.returned_input` 交还，不送达模型。
4. 撤回插话进去的消息：分支接在上一步的工具结果后面，请求合法。
5. 回退到压缩之前：请求里没有摘要，是完整的历史；超过阈值时先压缩一次。
6. 子智能体：§3.5 表里的四种情况；已在路上的汇报被丢弃；`settled()` 和 `idle` 正确。
7. 回退后 write 一个只在被撤回段读过的文件：被拒，要求先读。
8. 重发后关闭再恢复：转录是新分支，用量包含被撤回段，设置和标题是最新的，子智能体不回来。
9. 撤回第一条：`session/list` 的预览变成新消息，加载和未加载两种情况都对。
10. §3.1 表里的每种拒绝：warning 带 code，会话完全不变。

**桌面端端到端**（`apps/desktop/e2e/resend.mjs`，真实 finx 加 Electron，模拟模型）：

- 点撤回重发，气泡、别的窗口和内核日志都没有变化；取消后输入框回到原来的草稿；
- 编辑后发送，对话截断，新回复在下面，草稿回到输入框；任务运行中也一样；
- 附件和 Skill 标签带回输入框并原样发出；
- 关掉重开，看到的是新分支；
- 打包后的应用走一遍。

**真实模型验收**（结果见 §11）：

- 同一位置连续撤回重发，`cache_read` 接近前缀大小，证明缓存命中；
- 模型改过文件后撤回重发，跑多次，看它是否被旧印象绕晕，决定要不要 §7 的那条提示。

## 10. 决策与待定问题

### 10.1 决策

| 编号 | 决策 | 理由 | 章节 |
|---|---|---|---|
| D-370 | 撤回只发生在客户端；内核只有原子的 `resend`，不提供单独的 `rewind`，取代总方案 §8.1 的 `Rewind` | 回退的时刻就是发送的时刻；两步有中间状态，还要客户端编排 | §1 §2 |
| D-371 | 任务在跑时由内核先停再回退，调用方一步完成 | 只有内核知道任务何时真正结束；沿用 `finish_task` 同一把锁预定下一个任务的做法 | §3.2 |
| D-372 | 目标只能是当前分支上 message 条目的 user 消息；第二个 resend 在第一个未完成时被拒 | 汇报和环境消息不是用户说的话；拒绝比替换更不容易丢话 | §3.1 |
| D-373 | 回退点是目标消息的 parent；日志只追加 `branch`，被撤回段原样保留 | 符合追加式日志；上下文前缀逐字节不变；不丢数据，给版本切换留路 | §3.3 |
| D-374 | 模型、权限、标题、归档、累计用量、任务号是会话级事实，恢复时按全文件读 | 它们不属于某条分支；否则回退后重启会丢失，权限还可能放宽 | §3.6 |
| D-375 | 回退后用当前的设置，不恢复当时的 | 输入框显示什么就用什么；收紧的权限不能被回退放宽 | §1 |
| D-376 | 排队的输入交还输入框，不留在队列 | 它们是对着旧对话说的；不替用户决定，与 Stop 一致 | §3.2 |
| D-377 | 被撤回段启动的子智能体关闭并摘除；保留段的继续跑，它在被撤回段送达的汇报重新投递 | 只放弃这条消息之后的事；模型在保留段里等着那份汇报 | §3.5 |
| D-378 | `FileTracker` 和工具搜索记录清空 | 模型的上下文已经没有那些内容；等同恢复会话和压缩时的处理 | §3.4 |
| D-379 | 一期只回退对话，磁盘文件不动，不给模型加提示词 | 模型从工具结果能发现真实情况；提示词要有证据才加 | §3.8 §6 |
| D-380 | 桌面端原话退回底部输入框，不在对话区放编辑框；托盘一行标明目标，气泡高亮，草稿暂存；不弹确认，不压暗后面的内容 | 产品只有一个输入框，能力都能用，和排队消息的编辑一致；气泡不动，点撤回时会话没变看得见；发送就是确认 | §5.1 §5.3 |
| D-381 | 列表预览靠 `branch.before_first` 和转录重算，不新增摘要字段 | 扫描仍是按行增量；只差一个布尔值 | §3.3 §4.4 |
| D-382 | 退回的消息连同附件原样回到输入框，附件按气泡显示的顺序归组；系统附加的块不算原话，标签页的块作为附件带上 | 附件是消息的一部分；用户要求原样；模型不回退标签页就不知道它归自己 | §5.4 |
| D-383 | 模型改过的磁盘文件一期不恢复，托盘如实说明；二期加"同时恢复文件"的勾选 | 用户确认。回退对话是底座，先验证核心语义；`resend` 加可选字段即可，一期的协议不用动 | §6 |
| D-384 | 有 resend 在等时，轮次边界不再取排队的话 | 否则取消信号和边界撞上时，话先写进历史，再随被撤回段消失；放在状态锁里判断，没有窗口 | §11 |
| D-385 | 发送途中离开页面就放回草稿；新快照到来时按消息还在不在决定解锁或结束 | 输入框不会一直锁着；错过事件的情况不靠事件判断 | §5.3 |

## 11. 实现说明

**和方案的差别**：

- `take_steer`、`take_follow_up` 在有 resend 等待时什么都不取（D-384）。任务走到轮次边界的同时收到 resend，排队的话原本会先写进历史，再随被撤回段消失。这是写测试时发现的。
- 关闭会话时取消等待中的 resend，否则任务结束后会在关闭过程中启动一个没人管的新任务（§3.7）。
- 桌面端客户端多了 `view.attached`：每个快照一个新对象，用来判断事件可能被错过（D-385）。
- "文件不会恢复"的提示由 `changesFilesAfter` 判断：写、编辑、删除、移动、执行类的调用，加上 `spawn_agent`、`send_message`。
