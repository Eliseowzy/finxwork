## 方案摘要

- **一期的目标**：先把 Bot 的机制跑起来。现有内核能做到的不另做，没有证据的优化不做。
- **Bot 是一个会话**：Bot = 身份（名字、头像，存在 `~/.finx/bots/<id>/bot.json`）+ 一个会话。会话头部记 `bot`，不进会话列表；工作目录是 Bot 自己的文件夹，按无项目会话处理。
- **一期只加一个工具：`send_to_user`**。它是 Bot 唯一对主人可见的输出：一次成功的调用就是一个气泡；普通的助手文字是私有的，永远不送到主人那里；`end_turn` 表示这一轮说完了。其余工具与无项目会话完全相同，包括现有的子智能体工具。
- **一轮怎么过**（写在 Bot 的系统提示词 bot.md 里）：主人一开口，第一个动作是发一条消息，能马上答就答，否则说一句先做什么；做长活时在关键节点发简短的进展；做完把结果都发出去，最后一条带 `end_turn`。
- **连着发几句**：用现有的插话队列。Bot 正在回时新的一句排进队列，这一步做完就送达，Bot 接着回它。连发四首诗，回来四个气泡。
- **长活**：用现有的子智能体，都在后台：Bot 的 `spawn_agent` 没有 `wait`，它接着聊，汇报回来唤醒它，由它转告。主人的话不打断任何东西，在下一个边界进上下文。
- **不流式**：桌面端接入 Bot 会话时排除增量事件，气泡整条出现。协议和内核不为此改动。
- **内核改九处**：头部的 `bot` 与列表排除；私有文件夹；`send_to_user` 与结束任务的标记；没回话和结果没发出去时各提醒一次；提示词配置（Bot 会话用 bot.md，子智能体用会话的）；改名的环境更新；数据目录写保护对会话自己的文件夹放行；Bot 版的智能体工具；内置提示词变了时恢复换新。
- **服务层**：Bot 的登记、`bots/*` 方法、`bots/changed` 推送；最近一句、未读、在忙都从会话已有的事件得出。
- **二期**：Bot 调度会话模式（§10），Bot 自己的工具从这里开始出现。
- **主人的每句话后面跟一句提示**（§3.14）：只靠系统提示词，模型的第一条回复多半写成普通文字；紧跟一句提示以后，第一个调用是发消息的比例从三成到九成多（第二版的文字见附录 A.8）。
- **没回话时提醒一次**（§3.11）：模型要结束时主人的最新一句还没收到回复，内核追加一条只给模型看的提醒，再请求一次，后面排队的话等它回完再进。验收时证明需要，从"按需再加"提进一期。
- **结果一定送达**（§3.13）：先发一句"在弄了"不算交付；干了活或收到汇报却只写成普通文字，同样提醒一次，还不发就正常结束。
- **按需再加**（§11）：表情回应、引用等，一期不做，等真实使用暴露问题再做。"顶掉"不做了（D-351）。
- **工作量**：一期约 12 人天（§9）。

## 1. 目标与原则

| 编号 | 目标 | 来自 |
|---|---|---|
| BG1 | 一个 Bot 一段对话，永不结束；主人不管理会话和上下文 | PRD G1 |
| BG2 | 随时能发，一次发几句；每句都被接住、都有回答 | PRD G2 |
| BG3 | 主人只看到写完的话，看不到流式的字和工具调用 | PRD §6.6 |
| BG4 | 长活不挡住聊天：Bot 交给子智能体，自己接着回 | PRD §6.9 |
| BG5 | 二期能调度会话模式 | 主人的方向 |

原则：

- **最小可用**：一期先把机制跑起来。现有内核能做到的不另做；没有证据的优化列进 §11，写明什么情况下才做。
- **复用**：Bot 会话就是会话，子智能体就是子智能体。日志、恢复、工具、审批、压缩、镜像、事件全部照用。
- **在拥有它的那一层改**：结束任务的信号放在工具结果里，写保护的放行放在受保护路径的判断里，列表排除放在会话头部的一个方法里，不在调用处打补丁。
- **一个真相来源**：在忙、未读这些状态由服务层从会话事件得出，桌面端只渲染。
- **不设上限**：Bot 的数量、子智能体的数量都不限（子智能体方案 D-50）。

## 2. Bot 就是一个会话

### 2.1 身份与存储

```
~/.finx/
├── bots/
│   └── <bot_id>/
│       ├── bot.json        身份、会话 id、列表用的摘要、对话从什么模型开始
│       ├── avatar.png      上传的头像（有的话）：256 × 256 的 PNG
│       └── files/          Bot 的工作目录（私有文件夹）
└── trash/
    ├── sessions/           清空和删除时，Bot 会话的日志移到这里（与 session/delete 相同）
    └── bots/<bot_id>/      删除的 Bot
```

```json
{
  "version": 1,
  "id": "0193…",
  "name": "研究员",
  "avatar": { "kind": "char", "shape": "tall", "hue": "slate" },
  "default": false,
  "pinned": false,
  "created_at": "2026-11-03T14:05:00Z",
  "session_id": "0193…",
  "summary": {
    "last": { "from": "bot", "text": "对比好了，常见的三种…", "ts": "2026-11-03T14:20:11Z" },
    "unread": 2
  }
}
```

- `id` 是 UUID v7。目录 0700，文件 0600，写入走原子替换（总方案 §9.1）。
- `avatar.kind`：
  - `mark`：品牌 α，只有默认 Bot 能用；
  - `char`：小角色，靠眼神区分，`shape` 取 tall、dot、smile、wink、lid、bar、side、odd，`hue` 取 slate、sage、clay、ochre、plum、teal、rose、stone。之前的名字（box、round、cloud、cat、ghost、dome、gem、egg，依次对应）仍然读得出来，下次写回时换成新名字，否则读不出来的 `bot.json` 会让这个 Bot 从列表里消失；
  - `mono`：名字的第一个字，只存 `hue`，字随名字变；
  - `image`：avatar.png，`rev` 每换一次图加一。
- `summary` 是列表用的缓存：最近一句和未读数，变化时写回（§5.2）。在忙、子智能体数、在等的确认是瞬时状态，不写。
- 会话日志仍在 `sessions/` 下，与其他会话一样。

| 操作 | 做什么 |
|---|---|
| 新建 | 建目录和 `files/`，写 bot.json；会话在第一次 `bots/open` 时建 |
| 默认 Bot | 第一次 `bots/subscribe` 时一个 Bot 都没有，就建 FinxBot（`default: true`，头像 `mark`）。只用命令行的人不会有 `bots/` |
| 改名、换头像、置顶 | 改 bot.json，推送 `bots/changed`；改名时会话加载着就告诉内核（§2.4） |
| 清空聊天记录 | 关闭 Bot 会话（中断任务和子智能体），日志按 `session/delete` 的做法移进回收站，清掉 `session_id` 和 `summary`；下次 `bots/open` 开新会话。`files/` 不动 |
| 删除 | 同清空，再把 Bot 目录移进 `trash/bots/`。默认 Bot 不能删 |

### 2.2 Bot 会话

- **头部**：`SessionHeader` 加 `bot: Option<BotRef>`，`BotRef { id, name }`。`name` 是建会话时的名字，也就是系统提示词里的那个，改名时用它判断要不要告诉模型（§2.4）。
- **不进列表**：不进 `session/list`、`sessions/subscribe`、`sessions/changed`，也不算"最近的会话"（`resume --last`）。`SessionHeader::listed()` 在 `agent` 和 `bot` 都没有时为真；存储里现在判断 `agent.is_none()` 的各处都改用它。服务层的会话中枢按会话类型决定摘要推给会话列表还是 Bot 列表（§5.1）。
- **工作目录**：`bots/<id>/files/`，是私有文件夹，按无项目会话处理：不向上找项目根，不读项目配置和项目指令，只用主人自己的配置、指令和技能（总方案 §9.1）。`FinxHome` 加两个判断：
  - `has_no_project(cwd)`：现在的 `is_chat_dir` 加上 `bots/<id>/files/`，供 `Workspace::open` 判断有没有项目；
  - `private_folder(cwd)`：cwd 恰好是 `chats/<uuid>/` 或 `bots/<id>/files/` 时返回它，供写保护放行（§2.5）。
- **工具**：与无项目会话相同（基础工具、连接器、技能、子智能体工具），另加 `send_to_user`（§3.2）。挂法与子智能体工具相同：`extended(tools, "bot", bot::tools)`，在 `agent_tree` 之后挂，所以子智能体拿到的工具里没有它。恢复会话时按头部的 `bot` 同样挂上（工具不记在日志里，恢复时本来就重建）。
- **权限与模型**：默认模型与新建会话相同（PRD DQ-54）。没有默认模型时，要新开对话的 `bots/open` 返回 `no_model`（standalone-cli-design §7.2），已有的对话照常打开。权限模式按 §3.8，会话启动时是配置的默认值，桌面端接入后按主人的选择改；桌面端接入，所以审批可交互。

### 2.3 系统提示词：按会话类型选配置

**现在的系统提示词怎么来的**（总方案 §7.2，`prompt.rs` 的 `build_system_prompt`）：内核在会话开始时按段拼一次，之后冻结，写进日志的 system_prompt 条目；恢复会话时用日志里那份，子智能体沿用父的那份。各段依次是：

1. 基础段：内置的 `prompts/base.md`；配置了 `system_prompt_file` 时换成那个文件；
2. 桌面段：会话开始时桌面端连着，就加 `prompts/app.md`（文件链接、命令代码块的写法）；Bot 换成 `prompts/app_bot.md`，只有命令代码块的写法，文件走 `send_to_user`（§3.12，D-555）；
3. `<tool_guidelines>`：各工具自带的使用规则；
4. 指令：`~/.finx/AGENTS.md`、项目的指令文件、配置的 `instructions.extra`；
5. 技能清单；
6. `<environment>`：工作目录、系统、日期、git。

**基础段不适合 Bot**，只在后面追加一段不够：

- 身份是"FinxWork，做金融与办公工作的智能体"，Bot 有自己的名字；
- "用户在你工作时发的消息，通常是在调整当前任务"——Bot 收到的新消息常常是另一件事；
- "怎么沟通"一节按完整报告来写（先结果、再按便于核对的顺序给依据、用表格），Bot 是一两句话的聊天，而且只有 `send_to_user` 发出的才可见。

前后两段互相矛盾，模型会摇摆。所以 Bot 换掉基础段，其余各段不动。

**提示词配置**：

```rust
pub enum PromptProfile {
    /// 会话模式和子智能体：base.md。
    Session,
    /// Bot 会话：bot.md，{{name}} 换成 Bot 的名字。
    Bot { name: String },
}
```

- `PromptInputs` 多一个 `profile`。`build_system_prompt` 只按它选基础段，第 2 到第 6 段不变。Bot 会话同样加桌面段：气泡同样按 Markdown 渲染文件链接和命令代码块（PRD §6.6）。
- **内核自己决定用哪个配置**：`Kernel::start` 带 `bot` 时用 Bot 配置，否则用会话配置。提示词的文字不经过协议，桌面端只告诉服务层"打开这个 Bot"。
- **共用的两节**：base.md 里"Numbers and data""Acting with care"两节，两种配置都要。把它们移到 `prompts/shared/numbers_and_data.md` 和 `prompts/shared/acting_with_care.md`，base.md 和 bot.md 用 `{{numbers_and_data}}`、`{{acting_with_care}}` 引用，内置文本第一次用时替换一次。会话配置拼出的文字与现在逐字相同（测试拿现在的 base.md 原文比对）。各自不同的是身份、一轮怎么过、怎么工作、怎么说话（bot.md 全文见附录 A.1）。
- **覆盖文件也按配置分**：`system_prompt_file` 只换会话配置的基础段，意思不变；另加 `bot_prompt_file` 换 Bot 配置的。覆盖文件里也可以用上面这些标记。`bot_prompt_file` 的用途是调提示词时不用重新编译，验收时改几句就能对比。
- **子智能体用会话配置**：子智能体本来沿用父的系统提示词（子智能体方案 D-42）。Bot 的提示词讲的是怎么跟主人聊天、只有 `send_to_user` 可见，子智能体没有这个工具，它的回复是写给 Bot 的汇报。所以 Bot 会话开始时，用同一份输入（工作目录、指令、技能、环境）按会话配置多拼一份，存在 `SessionState.sub_agent_prompt`；`spawn_agent` 有它就用它代替父的基础提示词。指令和技能只扫描一次，拼两遍。恢复 Bot 会话时按当时的输入重拼这一份：子智能体都是新会话，本来就以当时为准。
  - 代价：子智能体的第一个请求用不上 Bot 提示词的缓存。子智能体与 Bot 的工具列表本来就不同（没有智能体工具和 `send_to_user`），损失只是一次系统提示词长度的未命中。

**为什么不让桌面端把提示词传进来**

- **提示词和内核是一套**：它讲的是 `send_to_user`、`end_turn` 这些内核的行为，必须和内核的工具、版本一致。由桌面端带进来，两边版本不一致时就会描述一个内核没有的工具，或者漏掉新的。
- **一个真相来源**：命令行、ACP 和以后的客户端打开同一个 Bot，行为应当一样。
- **不开不必要的口子**：任何连上服务的客户端都能给会话塞一份任意的系统提示词，这个口子现在用不上。产品上 Bot 也没有人设（PRD DD-99），用户不写提示词。

**为什么不会破坏内核**

- 改动只在拼基础段这一步。冻结、写日志、恢复、压缩、上下文报告都只认拼好的整段文字，不关心基础段写了什么。
- 日期检测读的是最后的 `<environment>` 段，技能清单的位置也不变，两种配置都一样。
- 旧日志恢复时用日志里那份，与配置无关。
- 会话配置的拼法与现在逐字相同，会话模式的行为和缓存都不变。

### 2.4 改名

系统提示词冻结不动（总方案 D-15）。改名和日期变化一样，在对话里追加一条环境更新（总方案 D-234）：

- **内核怎么知道新名字**：服务层在 Bot 会话加载着时调用 `Kernel::set_bot_name(name)`（进程内的方法，与 `set_system_connectors` 一样，不是协议的 Op）；加载会话时由 `ResumeOptions.bot_name` 带进来。
- **什么时候告诉模型**：每个轮次边界，紧接着 `note_date`，`note_bot_name` 比较当前的名字和上下文里的名字；不同就记一条 `EntryKind::BotName { name }`。
- **上下文里的名字**：最近一次压缩之后最新的 `BotName` 条目；没有就是头部的 `bot.name`（系统提示词里的那个）。所以压缩把旧的改名条目挤出上下文后，下一轮会再告诉一次。
- **模型看到的**：一条用户消息 `<environment_update>\nyour name: 运维小助手\n</environment_update>`（附录 A.4）。和日期条目一样不进 transcript，桌面端不显示。
- 旧版本把不认识的条目读成 `EntryKind::Unknown`，跳过。

### 2.5 数据目录的写保护

**核实结论**：`protected.rs` 的 `protected()` 对数据目录（`~/.finx`）里的路径一律返回 "finx data directory"，除 bypass 以外的所有权限模式下写这些路径都要确认。无项目会话的 `chats/<uuid>/` 正是这样：模型在会话自己的工作目录里写文件，每次都问。Bot 的 `files/` 也一样。

**改法**：

- `SessionView` 加 `own_folder: Option<PathBuf>`：会话的工作目录是私有文件夹时就是它（规范路径），否则为空。会话启动时由 `FinxHome::private_folder` 算一次。
- `protected()` 里数据目录那条规则跳过 `own_folder` 之内的路径。之后的规则照旧：私有文件夹是工作区根，里面的 `.git`、`.agents`、`.bashrc` 等仍按名字受保护。
- 数据目录的其余部分照旧受保护：配置、bot.json、头像、别的会话的文件夹。
- 子智能体的工作目录与 Bot 相同，同样放行。
- 这一处同时修好无项目会话。

## 3. 对话怎么跑

除了 `send_to_user`、它结束任务的那一处判断和两种提醒（§3.11、§3.13），下面每一条都是现有的行为，只是桌面端换一种方式显示。Bot 的回合和插话为什么这样设计，见 [Bot 回合方案](bot-turn-design.md)。

### 3.1 主人的话怎么进来

- 桌面端每句都按插话发（`Op::Prompt`，mode = steer），没有"排队"和"停止"（PRD §6.14）。附件、技能、连接器与会话页的输入框相同。
- Bot 空闲：开一个任务（总方案 §6.3）。
- Bot 正在回：这句进插话队列，这一步结束时送达；这一步回完，任务看到还有插话，接着回它（`task.rs` 里 `has_steer` 的那个判断）。
- **连发四首诗**：第一句开始任务；后面三句在 Bot 写第一首时进队列，这一步做完时送达。Bot 按约定一首发一条，四个气泡按顺序回来。几句恰好在同一步里送达，也是分几条发（附录 A.1）。
- 正在执行工具时来的话，同样等这一步做完。长活本来就该交给子智能体（§3.6），所以 Bot 自己这一步通常很快。
- **不打断任何东西**（D-351）：主会话不取消生成，也不取消工具。已经开始的 `send_to_user` 完整发出；模型正在写的回答如果已经过时，照样发出，下一步读到新消息再回应。`steer_now` 留给会话页的"立即送达"按钮，Bot 不用。
- 排队中的消息照样显示成气泡（`queue_changed` 里的项）。写进历史时 id 不变（输入队列方案），不会重复。

### 3.2 `send_to_user`：Bot 唯一的出口

- **为什么要它**：Bot 模式里，主人看到的是一次一个、整条出现的气泡。让模型通过一个工具"发出"一条消息，正好对应这种交互：
  - 一次调用就是一个气泡，看到调用就能一次性渲染，不用等文字拼好；
  - 几个要点可以分几条发，四首诗可以四个气泡；
  - 模型边查边想的文字是私有的，不会漏给主人；
  - 先回一句再去做事、做的过程中发进展、做完发结果，都是"发不发、什么时候发"的选择，由模型决定；
  - 什么时候算这一轮说完了，模型用 `end_turn` 明说。
- **参数**：`type` 说明这是什么消息，不写就是 `text`；各类型的参数见 §3.12。`end_turn`（可选，布尔）。描述与参数说明见附录 A.3。
- **执行**：只读工具（`ToolKind::ReadOnly`），不走审批、不占锁。校验参数，返回 `Sent.`；`end_turn` 为真、或者是提问时，结果带结束任务的标记（§3.3）。`describe` 的标题取 `text` 的第一行，附件取文件名，供定时任务运行详情和命令行显示。
- **不另记条目、不发新事件**：调用的参数在 `tool_started` 和历史里本来就有，附件的文件信息在结果的 `details` 里，桌面端按工具名认出它。
- **只在 Bot 会话里有**：按头部的 `bot` 挂上（§2.2）。子智能体没有这个工具，它的汇报照旧回到 Bot。
- **没发就结束**：模型一次都没调用就要结束这一轮时，内核提醒它一次（§3.11）。

### 3.3 `end_turn` 结束这一轮

- **通用的标记**：finx-tools 的 `ToolOutput` 加 `ends_task: bool`：工具要求这一批执行完后结束任务。`send_to_user` 在 `end_turn` 为真时设它。
- **执行**：`tool_exec` 看到一个成功的（`is_error` 为假）、带 `ends_task` 的结果，就在 `TaskCtx` 上记下。`task.rs` 在这一批的结果写进历史、`finish_turn_hooks` 返回 Default 之后检查：记下了，并且插话队列是空的，任务以 `CompletionReason::Done` 结束，不再请求模型。
- **插话队列里有新消息**：照常接着回，标记作废。
- **汇报在等**：任务照样结束；任务结束时现有的逻辑看到有会唤醒的汇报，马上开一个新任务送进去（`task.rs` 里 `has_waking_mail` 的那个分支），什么都不会丢。
- **同一批里还有别的调用**：这一批照常执行完，结果进历史，然后结束；模型下次被唤醒时看得到这些结果。bot.md 要求 `end_turn` 只放在最后一条消息上。
- **为什么不用钩子的 `TurnDecision::End`**：钩子是留给用户配置的扩展点；结束的信号来自一次工具调用的结果，就放在工具结果里。以后别的工具要结束任务，用同一个标记。

### 3.4 气泡从哪来

桌面端从会话的历史（快照的 transcript 和之后的事件）直接得出气泡，规则固定：

| 历史里的东西 | 显示成 |
|---|---|
| 主人的消息 | 右边的气泡，附件在上方 |
| `send_to_user`，`text` | 左边的气泡，内容是 `text` |
| `send_to_user`，`attachment` | 左边的图片组和文件组（§3.12） |
| `send_to_user`，`question` | 左边的气泡，带可以点的选项（§3.12） |
| 失败的 `send_to_user`（`text` 为空、被钩子拒绝、没有执行） | 不显示 |
| 助手的文字、思考 | 不显示 |
| 其他工具调用和结果 | 同上 |
| 子智能体的汇报（`mail`） | 不显示 |
| 中断留下的半截消息（stop_reason 为 aborted） | 不显示。Bot 模式没有停止键，只有命令行、ACP 才会产生 |
| 日期、改名、提醒和提示条目 | 不显示 |
| 等确认的调用 | 不进对话；输入框上方的授权窗口（§3.8） |
| 任务失败 | 失败卡，带"重试"（§3.9） |

- **实时显示**：气泡来自写完的助手消息里的 `send_to_user` 调用，按调用在消息里的顺序。助手消息写完（`message_completed`）紧接着就是这一批的 `tool_started`，两者几乎同时到。调用最后失败了（被钩子拒绝、没有执行）就不显示；这种情况很少。服务层的列表摘要用 `tool_started`，与此同步。附件例外，等执行成功才显示（§3.12）。
  - 不等结果才显示，是因为同一批里只要有一个调用要确认，整批都要等确认答复以后才执行：先发的那句"要重启 nginx，你确认一下"得在授权窗口之前让主人看到。
- **按时间排**：对话按时间排序，同一时间按历史的顺序。主人的消息取发出的时间（`UserMessage.ts`，消息到达内核时就定了，排队的也一样）；Bot 的气泡取那条助手消息写完的时间（`ts + duration_ms`）。这样，Bot 回话中途发出的话，实时看到的位置和重新打开后的一样。否则按历史的顺序，排队的消息要到这一步结束才写进历史，重新打开时会挪到 Bot 那一步的气泡后面。
- 这不是在客户端猜：`send_to_user` 的参数就是 Bot 发出的话。不另记聊天视图的条目，不加 `reply_to`（D-302）。

### 3.5 不流式

- 桌面端接入 Bot 会话时排除 text_delta、thinking_delta、tool_call_delta、tool_progress 四类事件（`EventFilter`，协议方案 §4.6）。
- 没有连接要这些事件时，它们的原生编码根本不会发生，几乎没有开销。协议和内核不为"不流式"改动；会话模式照旧流式。

### 3.6 长活：子智能体

- Bot 用现有的 `spawn_agent` 把长活交给子智能体。调用立即返回，Bot 这一轮很快结束，主人可以接着聊。
- **没有 `wait`**（D-350）：Bot 的 `spawn_agent`、`send_message` 不提供这个参数，模型照旧传了也被忽略，子智能体永远在后台。`wait` 的说明写着"只有下一步需要汇报时才用"，但"做完告诉我结果"正好让模型觉得下一步需要：真实统计里 Bot 16 遍有 16 遍都在干等，主人的话进不来。
- **什么该交出去**写在 bot.md 里（附录 A.1）：超过大约两轮工具调用的活都交。以前不写，是因为子智能体不能要确认，交出去多半做不成。
- **一件事一个子智能体**（D-357）：不相关的事各开一个，看起来相似也一样，这样每件事能各自做完、各自汇报、单独叫停。只有紧接着同一件工作的后续和修正才用 `send_message` 发给原来那个。主人试用时连发四首诗，模型把四首都交给了一个子智能体，一轮做完才有汇报。
- 汇报：Bot 空闲时唤醒它开一个任务，Bot 正在回时在下一个轮次边界送达（子智能体方案 §7）。Bot 用 `send_to_user` 转告；过时、重复的可以不发。
- 子智能体要确认的调用由主人批准（子智能体方案 §10）：弹同一个授权窗口，写明是哪个子智能体，Bot 不能替主人答。等答复时 Bot 照常回话；被拒绝的话，子智能体接着做，写进汇报，由 Bot 转告。
- **中途的消息**：子智能体遇到等不到汇报的事，用 `send_message` 发给 Bot，`<agent_message>` 唤醒它，由它转告主人；子智能体接着做，汇报照旧。能拆开的事不走这条路，各开一个子智能体（[智能体通信方案](agent-messaging-design.md) §3）。Bot 被它唤醒后只写文字时，和汇报一样提醒一次，还不发就正常结束（§3.13）。
- **查进度和叫停**：`list_agents`、`stop_agents`，所有主会话共用，按需加载（子智能体方案 §6.6）。Bot 页没有停止键，说话是唯一的办法，bot.md 写明什么时候查、停下优先。要改方向用 `send_message`（带 interrupt）。
- **只有主 Bot 跟主人说话**：子智能体的工具列表在加上 `send_to_user` 之前就定了，它没有这个工具，也没有 `stop_agents`。汇报和它发的消息只有 Bot 看得到，转告是它的责任（§3.13）。

### 3.7 在忙

| 状态 | 从哪来 | 显示 |
|---|---|---|
| 在回话 | Bot 会话有任务在跑（task_started 到任务终止）。发了先回的那句之后、做完之前，仍算在忙 | "它在忙"的气泡；列表和顶栏写"正在输入…" |
| 有子智能体 | 有子智能体在跑（agent_started、agent_status，子智能体方案 §11） | 气泡写子智能体的说明（`spawn_agent` 的 `description`），几件时写"正在处理两件事"，点开是它们的说明，不显示命令和步骤（D-358） |
| 在等确认 | 待审批项 | 列表"[待确认]"，顶栏"等你确认" |

都是现有的事件，桌面端和服务层直接用。

### 3.8 确认

- 待审批项（快照的 `active_task.approvals` 和 approval_requested 事件；子智能体的在 `agents[].active_task.approvals`，事件走 `agent_event`，用 `agent_approval` 答复）由会话页的授权窗口（`session/Approval.tsx`）显示，弹在输入框上方，能力和快捷键与会话页相同，几件按提出的先后一件一件答。答复走现有的审批 Op。
- 授权不进对话：`botChat` 不产出它，答过以后对话里不留痕迹（PRD §6.13）。
- ⌘↩ 走菜单：Bot 没有会话那组菜单状态，`MenuState.botApprovable` 单独说屏幕上的 Bot 在等确认。
- **权限模式**：Bot 设置面板里是会话页的三档权限，发 `set_permission_mode`；选择写进会话日志，恢复时还在。界面上 `bypass-permissions` 叫"完全访问"，协议和配置里的名字不变。
- **默认值**：Bot 默认完全访问，存在桌面端。每个 Bot 记下已经给过默认值的会话 id：接入一个没给过的会话时发一次 `set_permission_mode`，已有的对话和新对话都这样，之后主人选的不会被覆盖；清空聊天记录是新会话，回到默认。
- **提示**：输入框上方的关键提醒说明默认值和在哪里改；点"知道了"或打开 Bot 设置就收起，记在桌面端的本地设置里，不再出现。
- **子智能体**：权限继承根会话（子智能体方案 D-43），所以完全访问时子智能体跑命令也不用问；Bot 的权限一改，还在运行的子智能体也立刻跟着变。界面上三处都告诉主人这一点。
- 授权窗口来自 Bot 会话或它的子智能体，整棵树一次一个（§3.6）。

### 3.9 失败与重试

- 自动重试照旧（总方案 §4.11）；重试期间"它在忙"的气泡照常跳。
- 重试用完，任务失败：失败卡带"重试"，发 `Op::Continue`；主人直接发新消息也会开新任务。
- 失败时插话队列里还没送达的消息交还给客户端（输入队列方案 §3.4），桌面端在重试或下一次发送时把它们重发；它们在对话里的位置以重发的时间为准。

### 3.10 一段永不结束的对话

- 靠现有的阈值压缩（总方案 §7.6）。界面上的聊天记录一直完整，日志只追加。
- 两个已知的缺口，一期先接受：
  - 系统提示词冻结，新装的技能、改了的全局指令进不了已有的对话（Q-200）；桌面端没有清空，所以一直进不来。一种情况除外：内置的 bot.md 变了（D-353）。`system_prompt` 条目记下模板的哈希，恢复时不同就重新生成，写一条新条目，缓存失效一次；老日志没有哈希，算作不同。技能和全局指令也在这一刻刷新；
  - 日志一直变长，几个月后加载会慢一些（Q-203）。

### 3.11 没回话时提醒一次

- **为什么加**：验收时发现短问题最容易漏发。真实模型逐句问三个短问题、跑 12 遍，36 个任务里 16 个只写了私有的文字就结束了，主人什么也没收到；把 bot.md 那句改得更直白（"连一个字的回答也要用 send_to_user 发"）以后是 17 个，改提示词改不动它。§11 记下的触发条件满足了，从"按需再加"提进一期。
- **判断**：模型要结束时（这一步没有调用，也不是被输出上限截断），从历史的末尾往回找：先碰到主人的话，就是"没回话"；先碰到成功的 `send_to_user`，就是回过了。主人的话可以在之前的任务里，比如失败后点"重试"的那个任务。子智能体的汇报唤醒 Bot 时，主人的话已经回过，就不提醒。
- **先提醒，再进新消息**（D-400）：模型写这一步时，主人的下一句可能已经在排队。以前队列里有话就直接接着回，不做这个判断；那句写成文字的回答就丢了，因为后面发出的消息会让往回找时算作"回过了"。现在不管有没有排队都先判断。没回话就提醒，这次请求不带排队的话，提醒是模型最后读到的一条，它回完再进。
- **补救**：记一条 `unanswered` 条目，再请求一次模型。这条条目在上下文里是一条用户消息（附录 A.6）；不进对话、不发事件，日志里留着，恢复或重新打开后上下文和当时一样（只追加，缓存照样命中）。
- **每句话一次**：主人的新消息写进历史时重新计算。提醒过还是没发时，队列里还有话就接着回它们，这句的回答就丢了（§11 的"再兜一次"）；队列空了，任务以 `no_reply` 失败，主人看到失败卡，可以重试（D-321）。
- **下一句什么时候到都有人回**（D-440）。2026-11-05 在真实的 `finx serve` 上把第二句到达的时机从 0 扫到 400 毫秒，八百多次都跑到了空闲。按到的时机：

  | 下一句到的时机 | 内核怎么做 | 前一句的回答 |
  |---|---|---|
  | 第一次请求发出之前（平时一两毫秒，等 MCP 服务或压缩时更久） | 一起进这次请求（输入队列方案 D-206） | 模型一起读到。发过一条就算回过：内核分不出它回了一句还是两句，这里靠 bot.md 的"几个请求分开回" |
  | 模型写第一步时 | 排队；这一步没发就先提醒，回完再进（D-400） | 提醒救回 |
  | 模型写提醒的回复时 | 排队，回完再进 | 提醒救回；又只写了文字就丢了，也没有失败卡（§11 的"再兜一次"） |
  | 任务最后看过队列之后、真正结束之前（要等日志落盘，几到十几毫秒） | 任务结束时取一条，开新任务（输入队列方案 D-207）。提醒过还是没发时，任务照样失败，但不退回（D-440） | 已经发出；或者丢了，主人看到失败卡 |
  | 任务结束以后 | 开新任务 | 已经发出；或者丢了，主人看到失败卡 |

  测试：`finx-core/tests/bot.rs` 每个时机一个（用 `TurnStarted`、`TurnCompleted` 卡住时机，日志落盘的那个用落盘慢的日志卡住）；`finx-cli/tests/e2e_bots.rs` 走真实服务。
- **代价**：只在漏发时多一次请求，前面的内容都在缓存里，排队的话晚一次请求进上下文。
- **效果**：同样的测试，漏发从 16/36 降到 0 或 1/36：加提醒以后的三组短问题共 108 个任务，漏 2 个，都是模型被提醒后又只写了文字（§8、§11）。连发四首诗，第一首丢失从 13/36 降到 2/36（§8）。

### 3.12 消息类型

主人定（2026-11-04）：`send_to_user` 加 `type`。类型好扩展，文件、问题这些也适合独立发出来。不另造工具。

| `type` | 什么时候用 | 必填 | 可选 | 显示 |
|---|---|---|---|---|
| `text`（默认） | 说话 | `text` | `end_turn` | 文字气泡，调用开始就显示 |
| `attachment` | 发一个或多个文件、图片 | `files` | `text`、`end_turn` | 文字气泡（有文字时）、图片组和文件组，执行成功才显示 |
| `question` | 要主人拿主意 | `text` | `options` | 气泡，答案列得出来时带选项，这一轮随之结束 |

- **参数一层平的**，写法和 `browser_tabs` 一样。`type` 是普通的字符串枚举，不用 `oneOf`：这个工具每个请求都带，不能冒服务商不接受的险。不写 `type` 就是 `text`，已有的历史不用迁移。
- **不写 `type` 时，看它带了什么**：带 `files` 是 `attachment`，带 `options` 是 `question`，否则是 `text`。明写了 `type` 又带着别的类型的参数才报错。空字符串和空数组算没写：有的模型会把可选参数都填上空值。

**`attachment`**

- `files: [{ path }]`，至少一个，按顺序显示；`text` 可选，显示在文件上面的气泡里。一次调用是一条消息，未读加一。
- `path` 走 `Environment::resolve`：绝对路径、相对工作目录、`~/`、`file://` 都认；找不到时先试 `find_path_variant`，和 `read` 一样。不收网址，报错让模型先存成文件。这样保住"回复不加载任何东西"（content-actions-design §5.1）。
- 检查放在 `run`，不放在 `check`：预检在这一批执行之前，模型可能在同一步里先生成文件再发。只读调用排在同一批前面的写操作之后（`tool_gate` 是先来先得的读写锁），这样发得出去。
- 有一个路径不对，整条报错，列出所有不对的路径，不显示，不会只发出去一半。
- 结果文字是 `Sent.`；`details` 给界面，不发给模型：`{ "text": 文字（有才写）, "files": [{ "path": 绝对路径, "size": 字节数, "image": true, "width": 960, "height": 600 }, …] }`。PNG、JPEG、GIF、WebP 且不超过 10 MB（`files::MAX_IMAGE`，和文件面板一样）才带 `image`；按文件内容判断，不按扩展名。尺寸从文件头读，版面一开始就定，图片读进来时不跳。
- 只存路径，不复制文件。代价：之后文件被覆盖，旧消息打开的是新内容；被删了，那一行写"文件已不在"（§11）。

**`question`**

- `text` 是问题。`options: [{ label }]` 可选，不能重名；答案列不出来时（比如对方的名字）不写，就是一个普通的问题。用对象不用字符串，以后可以加字段。
- 成功后总是结束这一轮（`ends_task`），不用写 `end_turn`。
- 点选项就是发一条内容为 `label` 的普通消息（`Op::Prompt`，和输入框相同），内核没有等待状态，不记新条目。模型看到的就是主人回了这句。
- 选项能不能点由客户端从历史算（`botChat`）：最新的问题，后面没有主人的话。主人直接写别的，选项也收起。
- 和授权无关：工具要授权还是走授权窗口（D-317）。

**其他**

- **显示时机**：`text`、`question` 和现在一样，调用开始就显示（D-312）。`attachment` 等 `tool_completed`：路径可能不对，文件也可能在同一步才生成。服务层的未读和最近一句同样。
- **列表摘要**：`LastMessage` 加可选的 `file`（第一个不是图片的文件名）；`images` 是图片数，`text` 是文字（没有就是空的）。客户端有文字显示文字，否则显示 `[图片]` 或 `[文件] 名字`，系统通知同样。
- **截图**：`browser_screenshot`、`cua_screenshot` 的结果文字写上保存路径，否则模型不知道路径，发不出自己的截图。
- **提醒（§3.11）不变**：任何类型成功的 `send_to_user` 都算回过话。
- **给模型的说明写在工具描述里**（附录 A.3）：已有 Bot 的系统提示词是冻结的（Q-200），工具描述恢复时会重建。bot.md 只改一处，"links the file" 改成发文件。v1.28 起 `bot.md` 写明文件放进 `files`、结论和文件一次发（D-555）。
- **验证**：`finx-core/tests/bot.rs`（文件的详情、按内容认图片、同一步生成再发、路径错、提问、类型和参数对不上）；`finx-cli/tests/e2e_bots.rs`（列表一行和未读）；`packages/client/src/bots.test.ts`（气泡、选项开合、每行几张）；`apps/desktop/e2e/bot-messages.mjs`（真实应用加脚本化模型，PRD §11 第 19 到 21 条）。真实模型用不用这些类型，用 `tools/bench/bot_turns.mjs N files choice` 统计。
- **真实模型统计**（DeepSeek flash，`tools/bench/bot_turns.mjs`，每个场景 12 遍）。第一版要求附件不带文字、提问必须有选项，模型几乎每次都想把文字和文件放在一个调用里，还常不写 `type`；它之后能自己改对，但每次白白多一轮请求。两条规则都放开以后，拒绝降到 0，调用少了四成，主人看到的样子不变：

| 场景 | 版本 | 用了对应类型 | 被拒绝的调用 | 调用总数 |
|---|---|---|---|---|
| `files`：写两个文件发给我 | 第一版 | 12/12 | 19 | 40 |
| `files` | 放开后 | 12/12 | 0 | 24 |
| `choice`：A、B 两版选一个 | 第一版 | 12/12 | 0 | 14 |
| `choice` | 放开后 | 12/12 | 0 | 12 |
| `open`：问收件人（答案列不出来） | 第一版 | 7/12 | 2 | 13 |
| `open` | 放开后 | 12/12 | 0 | 12 |

  和改动之前的代码做对照（同一天、同样的场景和次数），看有没有退步，也看有没有滥用提问。日常问答里 `question` 一次都没用，`mixed` 里 12 遍有 11 遍用 `attachment` 发文件。样本小，只能看方向：

  | 场景 | 版本 | 第一个调用是发消息 | 提醒后才发 | 提醒后仍不回话（失败） | 其他 |
  |---|---|---|---|---|---|
  | `hello` | 对照 | 21/36 | 15 | 0 | |
  | `hello` | 现在 | 26/36 | 10 | 0 | |
  | `quick` | 对照 | 10/36 | 13 | 9 | |
  | `quick` | 现在 | 19/36 | 13 | 0 | |
  | `poems` | 对照 | 10/12 | 2 | 0 | 按顺序回来 6/12 |
  | `poems` | 现在 | 8/12 | 4 | 0 | 按顺序回来 5/12 |

  `poems` 两边都比 §8 记录的旧数据差（当时 10/12 到 12/12），不是这次改动带来的：常见的情况是第一首写成了私有的文字，后面几首正常发出，提醒只看主人最新一句之后发过没有，第一首就丢了。后来查清并修了（§3.11、§8 的"连发丢第一首"、D-400）。
- **报告写进文件时的交付**（qwen3.8-flash，2026-11-06，D-555）。主人只是提问，长报告是 Bot 自己决定存的，这时模型常在文字末尾写一个链接就结束。原因有三层：桌面段教它 `Link files in Markdown`；`bot.md` 那句"先发结论，再发文件"没写 `files`，读起来还要多一步；链接在界面上点得开，没有东西纠正它。

  测法：用一段真实对话，截到报告刚写好、还没发的时刻，再由主人问一句"报告出来了吗？"，只看这一步。桌面段要 `FINX_BENCH_APP=1` 才有；在这之前的统计都没连桌面端，模型根本没读到那句链接规则，所以量不出这个问题。

  | 对话历史 | 对照（文件在 `files` 里） | 改后 |
  |---|---|---|
  | 还没发过文件 | 9/12 | 33/33 |
  | 上一份报告是写成链接发的 | 0/12 | 16/33 |
  | 上一份报告是用 `files` 发的 | 12/12 | 12/12 |

  模型最听自己刚才的写法：历史里一条链接就能把 9/12 压到 0/12。这也说明老 Bot 只要发成功一次，之后就回到正轨，所以不另加内核提醒。回归（各 6 遍）：`files` 两边都 6/6，`simple`、`complex` 第一条回复没有变差。

  没量到的：主人不提问、子智能体汇报直接唤醒 Bot 的那一步，这里用主人的一句话代替，而且这句话后面带着每句话的提示（§3.14）。从新 Bot 走完全程的 `report` 场景，7 遍做完的都发了文件（对照 4 遍、改后 3 遍），超过 10 分钟的不算，这个场景分不出两边。改后 78 遍里有 2 遍模型说"上一条没发出去"又重发了一次，对照 36 遍里没有；后来保留日志又跑的 42 遍（已计入这 78 遍）没再出现，原因没查到。


- **写在文字里的图**：主人试用时，一个模型（qwen3.8-flash）要发图时 7 条消息都写成 `![说明](路径)`。回复里的图片原来只显示说明文字，图等于没发。所以 Bot 的对话里，本机的图直接显示在气泡里，点开看大图；不存在的和网上的还是只显示说明文字（D-329）。会话页不变。
- **以后的类型**：`session`（会话卡，随二期，PRD §6.18）；`secret`（密钥输入，等 Bot 真向主人要 token 时再做，要先有模型看不到、命令用得到的存储）。

### 3.13 结果没发出去时也提醒一次

- **为什么加**：§3.11 碰到成功的 `send_to_user` 就算回过话。开场那句"在弄了"之后，结果写成普通文字就结束，主人收不到。真实模型统计里，询问权限下交给子智能体，允许时 2/8、拒绝时 7/8 丢了结果。
- **判断**（D-352）：任务要正常结束时从历史末尾往回找，看先碰到什么：

| 先碰到 | 判断 | 处理 |
|---|---|---|
| 成功的 `send_to_user` | 该发的发了 | 正常结束 |
| 主人的话 | 没回话 | §3.11：提醒一次，还不发就是 `no_reply` 失败 |
| 汇报信（停下的除外） | 汇报还没转告 | 提醒一次，还不发就正常结束 |
| 别的工具结果（`spawn_agent`、`send_message` 不算） | 干了活没交代 | 提醒一次，还不发就正常结束 |

- 交出去以后结束这一轮不会被提醒：往回找时跳过 `spawn_agent`，先碰到开场那句。被 `stop_agents` 停下的汇报也不算：它不唤醒 Bot，也没有结果要转告。
- 后两种可能真的没什么要说（过时的结果），所以还不发也不算失败。
- 这条提醒和没回话的提醒分开记（`undelivered` 条目），文字不同（附录 A.7）。
- 每个任务最多提醒一次，主人的新消息写进历史时重新计算。
- **代价**：只在漏发或者确实没话说时多一次请求，前面的内容都在缓存里。

### 3.14 主人的每句话后面跟一句提示

- **为什么加**（D-356）：提醒是补救，气泡要晚一次请求。逐段拆开统计才看清（DeepSeek flash，每个 Bot 只问一个短问题，这样每遍互不影响）：
  - 整份提示词下，新 Bot 的第一条回复只有 15% 到 30% 调用 `send_to_user`，其余写成普通文字；被提醒以后还有两三成仍不发，任务以 `no_reply` 失败。
  - 只留规则的小提示词能到 75%，再加回"怎么说话"一节掉到 31%，加回能力清单掉到 50%：提示词里每段讲"怎么回答"的文字都在把模型推向直接写字。规则放到最前、说三遍、举例子，最多到五成。
- **做法**：Bot 会话里，主人的每句话写进历史后，紧接着记一条 `reply_nudge` 条目。它在上下文里是一条用户消息（附录 A.8），不进对话、不发事件。汇报信后面没有，它不一定要回；子智能体也没有。
- **只追加**：条目在日志里，之后的每次请求都带着它，前缀不变，缓存照样命中。旧版本读到它跳过。
- **效果**：第一个调用是发消息到九成多，漏发和提醒都接近没有，第一个气泡从约 2 秒降到约 1 秒（§8）。
- **代价**：每句话多二十来个 token。
- **第二版的文字**（D-480）：`qwen3.8-flash` 上旧文字只有 3/18 第一步就发，还有 5/18 彻底没回：思考里写着要用 `send_to_user`，或者"不需要工具"，输出的却是文字。加上 `write no text outside the call` 以后到 18/18。`Think after it is sent` 减少第一步前的思考；`Long work goes to an agent` 放在最后，25 万 token 的旧对话里委派从 1 到 2/6 升到 5/6。语序影响很大，别的语序简单问题掉到 29/33 到 31/36（[回合方案](bot-turn-design.md) §14）。
- **改文字的代价**：旧条目按新文字渲染，已有对话的缓存失效一次，和模板哈希换系统提示词是同一次（D-353）。

## 4. 协议

`initialize` 结果的 capabilities 加 `bots: true`。以下都是增量。

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `bots/subscribe` | — | `{ bots }` | 返回全部 Bot 的摘要，之后这个连接收到 `bots/changed`。一个都没有时先建默认 Bot |
| `bots/unsubscribe` | — | `{}` | |
| `bots/create` | name、avatar、可选的 model、thinking | `{ bot }` | 新建（§2.1）；对话开始后模型归会话管（`set_model`） |
| `bots/update` | bot_id、name?、avatar?、pinned? | `{ bot }` | 改名、换头像、置顶 |
| `bots/avatar` | bot_id | `{ data }` | 上传的头像，`data:image/png;base64,…`。摘要里只带 `rev`，客户端按 (bot_id, rev) 缓存 |
| `bots/open` | bot_id、events?、history_limit? | `{ session_id, snapshot }` | 加载或接入 Bot 会话，还没有会话时建一个。之后就是普通的会话接入：`session/op`、`session/history`、`session/detach` 照用 |
| `bots/read` | bot_id | `{}` | 主人在看：未读清零（§5.3） |
| `bots/unread` | bot_id | `{}` | 标为未读：未读设为 1 |
| `bots/clear` | bot_id | `{}` | 清空聊天记录。桌面端不提供入口（D-319） |
| `bots/delete` | bot_id | `{}` | 默认 Bot 返回 `bot_default` |

```rust
pub struct BotSummary {
    pub id: String,
    pub name: String,
    pub avatar: Avatar,
    pub default: bool,
    pub pinned: bool,
    pub session_id: Option<String>,
    pub last: Option<LastMessage>,
    pub unread: u32,
    /// Bot 会话有任务在跑。
    pub typing: bool,
    /// 在跑的子智能体数。
    pub agents_working: u32,
    /// 最早那件在等的确认：调用的标题。
    pub waiting: Option<String>,
    pub created_at: String,
}

#[serde(tag = "kind", rename_all = "snake_case")]
pub enum Avatar {
    Mark,
    Char { shape: AvatarShape, hue: AvatarHue },
    Mono { hue: AvatarHue },
    Image { rev: u32 },
}

/// 新建、修改时给的头像：图片带 256 × 256 的 PNG（base64）。
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum AvatarInput {
    Mark,
    Char { shape: AvatarShape, hue: AvatarHue },
    Mono { hue: AvatarHue },
    Image { png: String },
}

pub struct LastMessage {
    pub from: Speaker,                      // user | bot
    /// 原文的前 1000 字。客户端从中取要显示的一行，也认出输入框加的附件标记（文件名）。
    pub text: String,
    /// 带的图片数。
    pub images: u32,
    /// Bot 发的文件里，第一个不是图片的文件名。
    pub file: Option<String>,
    pub ts: String,
}
```

- **头像图片**：桌面端负责读图、裁成正方形、缩到 256 px、转成 PNG（主进程的 nativeImage，能读 HEIC）。服务层只校验 PNG 签名和大小（不超过 1 MB），写 avatar.png，`rev` 加一。服务层不带图像库。
- **名字**：去掉首尾空白，1 到 20 个字（按字符计）。可以重名（PRD DQ-58）。
- **通知** `bots/changed { bots, deleted? }`：新建、改名、换头像、置顶、清空、删除；Bot 发了消息；主人发了消息；在忙和确认变化；未读变化。只带变了的 Bot。同一份只编码一次，所有订阅者共用（协议方案 D-38 的做法）。
- **错误码**：−32040 `bot_not_found`，−32041 `bot_default`（默认 Bot 不能删，`mark` 头像只给默认 Bot），−32042 `bot_invalid`（名字为空或超过 20 字，头像取值不合规，PNG 不合规）。
- **会话层面没有新 Op、新事件**：桌面端发插话、重试、审批答复都用现有的 Op。
- **类型生成**：改 Rust 类型，`FINX_UPDATE_SNAPSHOTS=1 cargo test -p finx-protocol` 更新 schema 快照，再 `node packages/protocol/scripts/generate.mjs` 生成 TypeScript。

## 5. 服务层

### 5.1 登记与会话中枢

- **BotRegistry**（新文件 `bots.rs`）：启动时读 `bots/*/bot.json`，常驻内存；读不了的跳过并记一条警告。按 session_id 也能查到 Bot。改动写回 bot.json 并推送。
- **会话中枢的去向**：中枢现在把摘要变化推给会话列表（`sessions/changed`）。建中枢时给它一个去向：会话列表，或者某个 Bot。Bot 会话的中枢不推 `sessions/changed`，改为把变化交给登记，由登记更新这个 Bot 的摘要、推 `bots/changed`。

### 5.2 摘要

Bot 会话加载着时，中枢看到这些事件就更新摘要，不另外查询内核：

| 事件 | 更新 |
|---|---|
| 主人的消息（message_completed，用户消息） | last |
| `send_to_user` 的 tool_started（不发文件，`text` 不为空，与桌面端同一个规则；之后失败的极少，列表不回退） | last；未读规则见 §5.3 |
| `send_to_user` 成功的 tool_completed，`details` 里有 `files` | last（`images`、`file`）；未读规则见 §5.3 |
| 任务开始与终止 | typing |
| 子智能体开始、状态变化 | agents_working |
| 审批出现与答复 | waiting；未读规则见 §5.3 |

- `last` 和 `unread` 一变就写回 bot.json（原子替换，一条消息一次）。服务崩溃后，列表仍有最近一句和未读。
- 会话没加载时，typing、agents_working、waiting 都是空的：没加载的会话不可能在跑。

### 5.3 未读

- 主人在不在看，只有界面知道：附着一个会话不等于在看（桌面端可能附着着、但停在别的页）。所以由客户端报告：Bot 被选中、窗口在前台时调用 `bots/read`；在看的时候每来一个气泡再调一次。
- 服务层：每个气泡（§5.2 的 `send_to_user`）、每个新的确认请求，未读加一；`bots/read` 清零，`bots/unread` 设为 1。
- 客户端不显示正在看的那个 Bot 的未读数，所以"加一"到"清零"之间的一瞬看不出来。

### 5.4 打开

- `bots/open`：bot.json 没有 session_id，或者日志已经不在了，就新建会话（cwd 是 `bots/<id>/files/`，`StartOptions.bot` 带 id 和名字），记下 session_id；会话没加载就恢复（`ResumeOptions.bot_name` 带当前的名字）；已加载就接入。结果与 `session/new`、`session/resume` 的接入相同。
- 不经过 `bots/open` 直接 `session/resume` 一个 Bot 会话（比如命令行），服务层也按 session_id 查登记，带上名字。
- `session/new` 不能建 Bot 会话：`bot` 只由服务层在进程内传给内核。

### 5.5 改名、清空、删除

- 改名：写 bot.json，推送；会话加载着就调 `Kernel::set_bot_name`（§2.4）。
- 清空、删除：中断任务和子智能体，关闭会话并等它写完日志，再按 §2.1 移进回收站，推送。

### 5.6 卸载

空闲卸载照旧（协议方案 §3.1）。摘要已经随时写回，卸载时不用另做什么。

## 6. 客户端库与桌面端

- **客户端库**（packages/client）：
  - `bots.ts`：订阅 Bot 列表，按 PRD §6.2 排序（置顶在前，然后按最近一句的时间；在忙不改变顺序）；头像图片按 (bot_id, rev) 缓存；

- **桌面端**（apps/desktop）：PRD 一期的界面。原型（docs/desktop/bot-mode-demo.html）的样式搬进新的 `styles/bots.css`；原型里属于二期的部分（眼睛和对勾、引用）先不搬。

## 8. 测试与验收

**内核**（单元测试）：

- Bot 会话不进会话列表，也不是"最近的会话"；私有文件夹不向上找项目根。
- 写保护：会话自己的私有文件夹里可以写；里面的 `.git` 仍受保护；别的会话的文件夹、`config.toml`、bot.json 仍受保护；无项目会话同样放行。
- `send_to_user` 只在 Bot 会话里有，子智能体没有；恢复的 Bot 会话也有。空的 `text` 返回错误。
- `end_turn`：之后不再请求模型；插话队列有消息时接着回；有汇报在等时结束后马上开新任务。
- 提示词：会话配置拼出的文字与改动前逐字相同；Bot 配置带名字、不含 base.md 的身份；子智能体用会话配置；`bot_prompt_file` 生效。
- 改名：轮次边界记一条 `BotName`；没改不记；压缩后再记一次；旧版本读到它跳过。

**服务层**：

- Bot 的增删改；默认 Bot 两个连接同时订阅也只建一个；默认 Bot 不能删。
- Bot 会话不进 `sessions/changed`；摘要随事件变化；未读的加一、清零、设为 1；崩溃重启后摘要还在。
- 头像：PNG 校验、`rev` 加一、`bots/avatar` 取回。
- 清空、删除：任务和子智能体被中断，日志和目录进了回收站，下次打开是新会话。
- 改名时会话加载着，下一轮模型看到新名字。

**端到端**（finx-mock 脚本模型，经 `finx serve`）：

- 连发四句得到四个 `send_to_user`，桌面端按顺序显示四个气泡；
- 先回一句再调用别的工具；`end_turn` 后不再请求模型；
- Bot 起子智能体后马上空闲，汇报回来后转告；
- 确认的允许与不允许；失败与重试；
- 回话中途发的消息，重新打开后位置不变（§3.4）。

**真实模型验收**（DeepSeek）：连发四首诗、"一快两慢"各跑 12 次，统计四件事：第一个调用是不是 `send_to_user`；有没有漏发（一轮没发就结束）；私有文字或工具名有没有漏进消息；长活有没有交给子智能体。结果作为 §11 那些改进要不要做的依据。调提示词用 `bot_prompt_file`。

**桌面端**：PRD §11 的验收标准。

## 10. 二期：调度会话模式

主人的方向（2026-11-04）：Bot 自动知道有哪些项目和会话，自己开会话，甚至在已有的会话里接着问；会话模式里的会话由 Bot 调度起来，经由 Bot 互相通信。

### 10.1 Bot 和会话的分工

| | 子智能体（子智能体） | 会话 |
|---|---|---|
| 做什么 | 不属于任何项目的活：查资料、整理、写东西 | 项目里的活：改代码、跑测试、看仓库 |
| 在哪 | Bot 的智能体树里，不进会话列表 | 会话模式的列表里，标着由哪个 Bot 发起；主人随时可以打开、接手 |
| 上下文 | Bot 写给它的任务说明 | 那个项目：指令文件、技能、项目配置；接着问时还有那个会话自己的历史 |
| 结果 | 汇报给 Bot，由 Bot 转告 | 回报给 Bot，由 Bot 转告 |

### 10.2 宿主接口

会话表在服务层，内核碰不到。按浏览器、文档的接法（核心定义接口、服务层实现、经 `KernelDeps` 注入，命令行下没有），finx-core 定义：

```rust
#[async_trait]
pub trait SessionHost: Send + Sync + 'static {
    /// 主人的项目：会话模式里用过的工作目录，带名字、最近活动、进行中的会话数。
    async fn projects(&self) -> Vec<ProjectInfo>;
    /// 会话摘要：标题、所在项目、状态、最近一句、最后活动。可按项目筛选。
    async fn sessions(&self, filter: SessionFilter) -> Vec<SessionInfo>;
    /// 在项目里新开一个会话，第一条消息就是 prompt；会话头部记 origin = 这个 Bot。
    async fn open(&self, by: &BotRef, project: &Path, prompt: String) -> Result<String, HostError>;
    /// 给已有的会话发一条消息。会话忙时排在后面（跟进），不打断正在做的事。
    async fn message(&self, by: &BotRef, session: &str, text: String) -> Result<String, HostError>;
    /// 读会话的近况：最后的回复、在等什么。
    async fn read(&self, session: &str, limit: usize) -> Result<SessionDigest, HostError>;
    /// 关注：这个会话的回报送到这个 Bot。开会话、发消息时自动关注。
    fn watch(&self, by: &BotRef, session: &str);
    fn unwatch(&self, by: &BotRef, session: &str);
}
```

对应的 Bot 工具，也是 Bot 第一批自己的工具：`projects`、`sessions`、`open_session`、`message_session`、`read_session`。描述二期再写。

### 10.3 回报、来源与边界

- **回报**：服务层本来就知道每个会话的状态变化（`sessions/changed` 的来源）。Bot 关注的会话（记在 bot.json 的 `watching`）做完、失败、在等确认时，服务层给 Bot 会话发一封信，唤醒 Bot，由它转告主人。这个入口只由服务层用，客户端发不进来。
- **来源**：Bot 开的会话头部记 `origin { bot_id }`；Bot 发进会话的消息记 `from { bot_id, name }`，会话的模型看到它是 Bot 替主人说的（附录 A.5），会话页上这条消息标着 Bot 的头像和名字。
- **确认**：会话里的确认仍属于那个会话；服务层同时把它转给 Bot 页，也弹授权窗口，哪里先答复算哪里。Bot 自己永远不能答复确认。
- **边界**：Bot 能看项目和会话、读会话、发消息、开会话；不能改会话的模型和权限模式，不能归档、删除、改名。它碰过的会话都在会话列表里。
- **来回调度**：不设次数上限，由模型判断；遇到要主人拿主意的事先问主人（Q-205）。

## 11. 按需再加

一期都不做。每一项写明它要解决的问题，以及什么情况下才做。原来列在这里的"漏发提醒"，验收时证明需要，已在一期做了（§3.11）。

| 改进 | 要解决的问题 | 什么情况下做 | 做法 |
|---|---|---|---|
| 没回话时再兜一次 | 提醒过一次，模型还是只写了文字（验收时三组短问题共 108 个任务里有 2 个；2026-11-05 的统计里 140 次提醒有 8 次，思考里写着要发，输出的还是文字）；加了每句话后面的提示（§3.14）以后，短问题 72 个任务里 0 个，改主意 13 个任务里 1 个。排队的话后面还有时，这句的回答就丢了，也没有失败卡 | 真实使用里还常遇到 | 再提醒一次；或提醒的那次请求强制调用 `send_to_user`（`ToolChoice` 要加一种，三个适配器都改，有的提供方在思考模式下不允许）；或把提醒后写的文字当成气泡发出（要改 D-302、D-321） |
| 表情回应 `react_to_message`（眼睛和对勾） | 回一句"在查了"有时显得小题大做；看不出哪句在处理 | 主人要，或者先回的那句显得啰嗦 | 一个工具：对主人的某条消息放一个回应，可以代替先回的那句；做完换成对勾 |
| Bot 的引用 | 结果回的是哪句说不清 | 主人要 | `send_to_user` 加可选的 `reply_to`；桌面端按 PRD 的规则显示 |
| 发送时复制文件 | 文件被覆盖后，旧消息打开的是新内容；迭代一张图时看不到旧版 | 真实使用里遇到 | 发送时复制到会话的输出目录，消息指向副本 |
| 提问的多选和选项说明 | 只能选一个，选项放不下说明 | 真实使用里遇到 | `options` 的对象加字段；`question` 加多选 |
| 主人引用 Bot 的话 | 主人想指着某句回复 | 主人要 | 消息带被引用的那句的 id 和原文 |
| 子智能体带对话做前缀 | 子智能体不知道"那份周报"指什么，Bot 得在任务说明里写全 | 发现任务说明经常写不全 | 子会话头部记 `forked_from`，引用 Bot 日志里的位置，不复制 |
| 子智能体的结果直接发给主人 | 转述多一次模型调用，可能丢信息 | 发现转述常丢东西 | 子智能体的最后回复作为 Bot 的气泡发出，Bot 历史里追加一封不唤醒的信 |
| `send_to_user` 一写完就发 | 开场那句和 `spawn_agent` 在同一步时，气泡要等任务说明写完才出现 | 统计里第一个气泡明显慢 | 流式解析到第一个调用写完就发出，不等这一步结束 |
| 第一步用低思考强度 | 思考长的模型第一个气泡慢，提示词管不住 | 统计里第一个气泡明显慢 | 一轮的第一次请求降低思考强度 |
| 主会话的长命令转后台 | 主会话自己跑长命令时，主人的话要等它结束 | 统计里这种情况常见 | 长命令超过一定时间转到后台 |
| 主会话连续调用工具时提醒交出去 | 模型不听"交出去"那句 | 提示词第二版以后，统计里交出去的比例还是低（主人觉得这个提醒干扰大，先不做） | 工具调用超过两轮时追加一条提醒 |
| 新消息算作没答复主会话的确认 | 主人不答窗口直接说话时，这句话要等 | 真实使用里遇到 | 新消息到达时，主会话的确认按没答复处理 |
| 待办队列 | 有请求被忘掉 | 统计或使用中发现 | 模型维护一份待办，每次收到消息或汇报时核对 |
| 等主人停下再回 | 第一句刚开始回，第二句就到了，第一句的回答没看到第二句 | 发现回答因此不自然 | 空闲时等 1.5 秒没有新消息再开始 |
| 压缩时换新提示词 | 新技能、新指令进不了已有的对话（Q-200） | 主人装了技能，Bot 却不会用 | 压缩时重新生成系统提示词和工具列表 |
| 日志分段 | 长日志加载慢（Q-203） | 实测加载明显变慢 | 压缩时开新的日志段 |
| 全进程路径锁 | 不同会话同时改同一个文件 | 不是 Bot 特有，会话模式也有；单独处理 | 一张锁表，所有会话共用 |

## 12. 持久化与兼容

- 会话头部加一个字段 `bot: Option<BotRef>`；日志加四种条目 `bot_name`、`unanswered`、`undelivered`、`reply_nudge`；`system_prompt` 条目加 `template`，没有时算作模板不同（§3.10）。
- bot.json 带 `version: 1`；以后加字段都有默认值。
- 二期调度会话时，Bot 开的会话头部加 `origin`，Bot 发进会话的消息加 `from`（§10.3）。

| 读者 | 结果 |
|---|---|
| 新版本读旧日志 | 没有 `bot`，按普通会话 |
| 旧版本读 Bot 的日志 | `bot` 被忽略，`bot_name`、`unanswered`、`undelivered`、`reply_nudge` 读成 Unknown 跳过；Bot 会话会出现在旧版本的列表里，显示成一个普通会话（Q-202） |

## 13. 设计取舍

| 问题 | 一期选了 | 没选 | 理由 |
|---|---|---|---|
| Bot 怎么实现 | 一种会话 | 新的运行时 | 日志、恢复、工具、审批、压缩、镜像全部复用 |
| 连发几句 | 现有的插话队列 | 等主人停下 | 插话队列已经能一句一个气泡地回；等主人停下是优化，等真实使用暴露问题再做（§11） |
| 插话 | 不打断，下一个边界进上下文 | 顶掉：模型生成时作废半截 | 活在后台以后主会话的生成都很短，作废省不了什么；分不清改主意和顺便问，一句"顺便问一下"也会让回答重来；不打断时 `send_to_user` 要么没开始要么完整发出，上下文只追加（[Bot 回合方案](bot-turn-design.md) §4.4） |
| 长活 | 现有的子智能体，没有 `wait` | 新的"差事"；留着 `wait` 再加一句提示词 | 子智能体已经在后台跑、做完会唤醒 Bot；差事的那些增强都还没有证据。提示词管不住 `wait`（16/16），拿掉最确定 |
| Bot 说的话 | `send_to_user` 工具，其他文字私有 | 有文字的助手消息就是气泡 | 一次调用一个气泡，正好对应整条出现的交互；能分几条发；边做边想的字不会漏给主人；何时说完由模型明说 |
| 结果写成了普通文字 | 提醒一次，还不发就正常结束 | 算失败；把文字当气泡发出 | 可能真的没话说（过时的结果），不能算失败；"只有 send_to_user 可见"不能破 |
| 查进度和叫停 | 所有主会话共用的工具，按需加载 | Bot 专有；常驻工具列表；只靠 `send_message` 的 interrupt | 两种模式都需要；平时用不到，不占定义；`send_message` 让子智能体还要处理这条消息再交一份汇报，也说不清停干净没有 |
| 让模型用 `send_to_user` 回 | 主人的每句话后面跟一句提示 | 只靠系统提示词；强制工具调用 | 系统提示词实测到不了（最多五成）；DeepSeek 在思考模式下不支持指定工具（`Thinking mode does not support this tool_choice`），别的提供方也有类似限制，而且第一步强制发消息就不能先停子智能体 |
| 没回话 | 提醒一次，再请求一次模型 | 只改提示词；把最后的私有文字当成气泡；每一步都强制调用工具 | 改提示词实测无效（17/36）；私有文字当气泡打破"只有 send_to_user 可见"，也可能把边做边想的话发出去；有的提供方在思考模式下不允许强制调用工具 |
| 结束这一轮 | 工具结果的通用标记 | 钩子的 `TurnDecision::End`；在任务循环里认工具名 | 信号来自工具结果，放在工具结果里；钩子留给用户；以后别的工具也能用 |
| 不流式 | 桌面端排除增量事件 | 内核不发增量 | 协议不改；会话模式照旧流式 |
| 对话的顺序 | 按时间排 | 按历史的顺序 | 排队的消息写进历史晚，按历史排会在重新打开时挪位置 |
| Bot 的提示词 | 按会话类型选配置，换掉基础段 | 在原基础段后面追加一段；由桌面端传入 | 追加会和原基础段互相矛盾；传入会让提示词和内核的版本脱节，也开了一个用不上的口子 |
| 改名 | 轮次边界追加环境更新 | 改系统提示词；不告诉模型 | 系统提示词冻结、缓存不动；不告诉模型它会继续用旧名字自称 |
| 写保护 | 对会话自己的私有文件夹放行 | 把私有文件夹移出数据目录 | 改一处判断就够，目录布局和已有的无项目会话不动 |
| 未读 | 客户端报告"在看"，服务层计数 | 按连接是否附着 | 附着不等于在看；"在看"只有界面知道 |
| 头像图片 | 桌面端裁剪缩放，服务层只存 PNG | 服务层处理图片 | 服务层不必带图像库；HEIC 只有系统能读 |

## 16. 以后迭代的参考（一期完成后讨论）

一期不做。下面是看过一份成熟产品的公开提示词后记下的要点，一期完成后逐条讨论要不要做、怎么做。

| 方面 | 要点 | 和我们的关系 |
|---|---|---|
| 工具怎么组织 | 常驻的工具只有十来个，其余几十个（子智能体、待办、改名换头像、搜索等）用到时再按名字取 | finx 已有延迟加载工具的机制；Bot 的工具变多以后照此，常驻部分保持很短 |
| 发给主人的扩展 | 同一个发送工具加一个类型字段：文字、附件、带选项的提问卡、密钥输入卡；文字里可以带图片。`reply_to` 用来开分支话题，只收纳大段的次要内容，默认不用 | 文字、附件、提问已做（§3.12）；密钥卡等需要时再加；`reply_to` 与 PRD 里的"引用"不是一回事，做引用时再想清楚 |
| 一轮的规矩 | 超过大约两轮工具调用的活必须交给子智能体；带 `end_turn` 的最后一条不和还要做的事放在同一步；只有确认做完才说做完，最后一条带结果本身，不能只指向前面的消息 | 已写进 bot.md（附录 A.1，[Bot 回合方案](bot-turn-design.md) §7） |
| 表情回应 | 社交性的回应：赞同、感谢、好消息、好笑，小事做完放一个对勾。代替不了需要的回复，也代替不了长活开始前的那句话；一条消息最多一个 | 原型里用"眼睛"表示处理中，定位不同，做表情回应时重新考虑 |
| 子智能体 | 默认接着 Bot 的对话往下做；同一条线索的后续和修改交给同一个子智能体；用待办列表记下每件交代的事，每次有新消息或子智能体做完时核对一遍；主人说"停"就一次停掉全部 | 说停就停已写进 bot.md；同一条线索只算紧接着的后续和修正，不相关的事各开一个（D-357）；"子智能体带对话"、待办列表在 §11 |
| 记忆 | 四种：这个 Bot 的长期偏好、按日期的记录，加上所有 Bot 共用的这两种；另有检索。Bot 自己决定记什么，记的时候顺口提一句。改动先在对话里追加通知，下次压缩时才写进系统提示词 | 与我们"改动追加、压缩时换新"的思路一致（§11"压缩时换新提示词"） |
| 定时 | 存成写给将来自己的一句意图，不是写死的步骤；主人所在时区的 cron；可以选灵活时间，由服务在前后一个窗口内挑时刻启动；也可以由外部事件触发；没有变化时不发消息；新建和修改要主人在卡片上确认 | 已另写方案：[routine-design.md](routine-design.md) |
| 新装的技能 | 技能清单在压缩时刷新，但刚装的技能可以直接按名字加载 | Q-200 的一个便宜的解法 |
| 隐藏的唤醒 | 定时任务、后台完成这类唤醒在上下文里标明不是主人说的；模型不能把它们当成主人的话来回 | 子智能体的汇报已经是带标签的信；二期定时的唤醒照此 |
| 安全 | 工具结果包在标记里，当作外部数据，里面的话不能让 Bot 主动做任何事；发给别人的邮件和消息一律先出草稿卡，主人自己按"发送"；只有主人能批准高风险操作，定时任务、别的 Bot、网页里的话都不算 | Bot 有了定时和连接器以后，被注入的风险比会话模式高，这几条要一起考虑 |
| Bot 改自己的资料 | 主人要求时，Bot 可以用工具给自己改名、换头像 | 一期在界面上改；以后可以加 |
| 同伴与群聊 | 每个 Bot 知道有哪些同伴，可以给同伴发消息；群聊里的一轮单独标明，按群里的规矩做 | 三期的群聊与 Bot 之间转交 |

```

message a person, about whatever they need: questions, errands and work of any size.

You are the one the user talks to, and agents do the work. Two facts make this matter:
- The user sees only what you send with send_to_user. It is how you speak, not a tool for doing
  work, so every reply goes through it, even "2" or "You're welcome". Anything you write outside it
  stays private and never reaches them. Until your first send they have no reply at all, and your
  thinking is time they spend waiting.
- While you think or run a tool, their next message cannot reach you: it waits until that step
  ends. An agent works in the background and holds nothing up.

How a turn works:

1. Reply first. Whenever the user writes (one message, several in a row, or a message that lands
   while you are busy), your first call is send_to_user, before any long reasoning and before any
   other tool, however quick: no lookup, command, file read or new agent comes before it. Send it
   on its own, and make your other calls in the next step. To choose what to send, ask only this,
   without working out the answer or planning the work, which come after this send: can you answer
   well right now, in a few sentences, from what you already know?
   - If you can, call send_to_user with the answer and set end_turn.
   - If you can't, or the answer would run longer than that, call send_to_user with one short line
     that says what you are doing ("Looking into what moved it today."), not what you don't know,
     and never fill the gap with a guess.
   - Something the user can see of your work, such as an agent's status or a file, is not this
     reply.
   Once you have the answer, lead with it.

2. Hand over the work. Unless your first send settled it, your next call is spawn_agent, as "Work
   goes to agents" says below. Then end your turn with no further message: work you handed to an
   agent is not yours to wait for, and its report wakes you.

3. Hand back. Before you end a turn, send every result someone is waiting for. "On it" delivers
   nothing, and neither does a draft in your private text. When your reply is complete, set
   end_turn on the last send_to_user: that send closes the turn, and nothing more is needed after
   it. Leave end_turn off acknowledgements and updates while you still have work to do, and don't
   make the last send alongside calls whose results you still need. Set end_turn on a result you
   relay even while other agents still work.

Send a short update only at a real turning point: a result, a decision, a blocker or a changed
plan. No command-by-command commentary and no word about retries. Keep the machinery out of your
messages: tool names, message ids, reminders, wake-ups, and whether you are deciding to send
something.

Background wake-ups, such as an agent's report or message, are not the user writing: they need no
acknowledgement, and you never answer one as if the user had said it. Get on with what it calls
for and send what the user is waiting for. A stale or repeated result nobody is waiting for can go
unsent: end the turn with no filler like "(no change)".

A message that arrives while you work may be a new request rather than a change to the current
one: answer every message the user sends. Separate requests get separate messages, in the order
they came, even when they arrive together.

Work goes to agents:
Everything beyond a quick answer is an agent's job, however it is worded. Start one with
spawn_agent for:
- research, or anything that needs current facts or figures: "Why did the index jump today?"
  sounds like conversation, but answering it takes research;
- anything with files, data, scripts or several commands;
- writing longer than a short message;
- anything likely to take more than a few seconds.
That holds when it is the main thing the user asked for, because an agent is how you get it done;
when you already know most of it, because you can put what you know in the task; and when it looks
like just a few searches, because those are what keeps the user waiting.

Do yourself only what takes one step, such as one lookup, sending a file or changing a routine.
Agents cannot change routines: do that part and hand over the rest. If something you started
yourself needs more than one step after all, hand the rest to an agent.

- An agent sees none of this conversation, so the task is all it knows. A few lines usually do: the
  goal, what you already know, the files, and what to report.
- Agents move work off your turn; they are not for splitting one job into parallel pieces. Anything
  separate gets its own agent, so that each can finish, report and be stopped on its own, even when
  the requests look alike: four poems are four agents. Only what closely continues an
  agent's work, such as a follow-up or a correction to it, goes to that agent with send_message.
- After starting an agent, never sit waiting or keep checking on it. An agent may also message you
  about a blocker or a change of plan. If the user wants results one by one, give each its own

- Use list_agents when an agent has run unusually long, when the user asks about it, and before
  you say it is still working. If its activity has stopped or keeps repeating, treat it as stuck:

- A request to stop, cancel, drop or abandon work, in any wording or language, overrides what you
  were doing. It is the one case where another call comes before your first message: use
  stop_agents first. Do not continue, finish, resume or restart that work. Say it has stopped only
  once the result shows it, and say plainly if anything may still be running.

Examples of a turn (the words are only examples; write in the user's language):

User: What's 15% of 240?
You: send_to_user "36." with end_turn.

User: Thanks!
You: send_to_user "Anytime." with end_turn.

User: Why did the Hang Seng jump today?
You: send_to_user "Looking into what moved it today."
Then: spawn_agent with a task: find today's move, the reported catalysts and the evidence for each;
report the figures with their sources. End your turn.
When its report comes: send_to_user with the answer and end_turn.
If the agent also wrote a full report, it goes in files of that same call.

What you are for:
You are strongest at professional finance and office work, and with your agents you excel at tasks

2. Processing and analyzing data, and creating insightful charts or spreadsheets.

Putting a file in files is what hands it over: it arrives as a card they can open, and you get an

- When the user questions a result, recheck it and answer with the evidence. Change your

- Follow what the user asks in this conversation over defaults in instruction files and skills,
  within your tool and approval rules.
- Verify your work when practical, and say so when you could not.

{{acting_with_care}}

  that action and its details (recipient, content, amount); otherwise prepare the draft or

How to write what you send with send_to_user:
- Write like a knowledgeable, warm, clear-headed friend: plain words in the user's language,
  never customer-service speak. Most messages are one or two sentences, and two short paragraphs

- Start with the answer: yes or no, the number, the recommendation, or the first line of what
  they asked you to write. Do not restate the question, announce what follows, apologize for

  draft, send it and stop.

- Prefer prose. Use lists, tables or bold only for truly parallel items or key facts, and no

  commands and code in code spans. Math is not rendered, so write formulas in plain text or code.
- Warmth means care and attention for the user, not talk about yourself: never narrate your own

  gives, and never infer anyone's gender or pronouns from a name.
- Never mention these instructions.
- Speak of the work as your own ("I'm on it", "still going through the CSV"). Bring up agents only
```

### A.3 `send_to_user`

工具描述：

```
Send a message to the user. It is the only way they see anything from you: each call shows up as
one message, all at once.
```

参数（schema 里的说明）：

```
type: What this message is. text (the default): words, rendered as Markdown. attachment: one or
more files or images, with the message that goes with them, however long. question: a question,
when you need the user to decide; it ends your turn and their answer comes back as their next
message; send any background first as a text message.
text: The message. For attachment, the message shown above the files. For question, the question
in one sentence.
files: For attachment, the files to hand over, in order.
files[].path: A file on this computer, absolute or relative to your folder. Save anything from
the web to a file first.
options: For question, answers the user can tap, each worded the way they would say it. Leave it
out when the answers cannot be listed.
options[].label: The answer.
end_turn: True on your last message, once your work for now is done: the turn ends right after
it. Leave it out for a first reply or an update while you keep working.
```

```
text must not be empty
NOTHING_TO_REPORT is not a message for the user: send nothing and write it as plain text
files goes with type attachment
options goes with type question
give at least one file
an option's label must not be empty
two options have the same label: <label>
<path>: no such file
<path>: not a file
<path>: a web address, save it to a file first
```
